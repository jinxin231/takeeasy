# 04 AOF 日志：宕机了，Redis 如何避免数据丢失？

> 来源：极客时间《Redis 核心技术与实战》蒋德钧（基础篇 04）
> 整理日期：2026-11-13

---

## 一、内容总结

**为什么需要持久化**：宕机内存数据全丢，从后端 DB 恢复有两个问题——给 DB 巨大压力 + 慢速 DB 读取拖垮应用响应。所以 Redis 必须自己持久化。两大机制：**AOF 日志**（本讲）和 **RDB 快照**（05 讲）。

**AOF 是"写后日志"**（对比数据库的 WAL 写前日志）：
- 流程：**先执行命令写入内存，再记录日志**——与 redo log 记"修改后的数据"不同，AOF 记的是**收到的每一条命令**（文本形式，如 `*3 $3 set $7 testkey $9 testvalue`）
- 为什么写后：记日志前**不做语法检查**（省开销），先执行就保证日志里只有成功执行的命令，恢复时不会出错
- 附带好处：不阻塞当前写操作

**两个潜在风险（都与写回磁盘时机相关）**：
1. 命令执行完还没来得及记日志就宕机 → 数据丢失
2. AOF 写回在主线程执行，磁盘压力大时写盘慢 → **后续操作被阻塞**

**三种写回策略（`appendfsync`）——trade-off 的教科书案例**：

| 策略 | 机制 | 可靠性 | 性能 |
|---|---|---|---|
| Always | 每个命令同步写回磁盘 | 基本不丢 | 每命令一次慢速落盘，差 |
| **Everysec** | 先写内存缓冲区，**每秒**刷盘一次 | 丢 1 秒内数据 | 折中（推荐） |
| No | 写缓冲区，**操作系统**决定何时刷盘 | 落盘时机失控 | 最好 |

**AOF 文件过大的三重危害**：文件系统大小限制；追加效率变低；**恢复时逐条重放，文件越大恢复越慢**。

**AOF 重写机制——"多变一"**：
- 根据**数据库现状**生成新 AOF：读取每个键值对当前最新状态，一个键值对只记一条写入命令（6 次 LPUSH 的历史 → 1 条最终状态的命令）
- 被反复修改成百上千次的键值对，节省空间巨大

**重写会不会阻塞？——"一个拷贝，两处日志"**：
- 由后台子进程 **bgrewriteaof** 完成，不阻塞主线程
- **一个拷贝**：主线程 fork 出子进程（共享内存数据快照），子进程把数据写成操作记入重写日志
- **两处日志**：重写期间主线程的新写操作，**同时**写入 ①正在使用的 AOF 缓冲区（保证宕机可恢复）②AOF 重写缓冲区（保证新文件不缺最新操作）；重写完成后新文件替换旧文件

**每课一问**（评论区 Kaito 置顶答案，含金量极高）：

**Q1：重写过程还有潜在阻塞风险吗？**
- **fork 瞬间阻塞主线程**：fork 采用 COW，不拷贝物理内存，但要拷贝**页表**（虚拟→物理映射）。实例越大页表越大，fork 阻塞越久
- **重写期间父进程写入触发 COW**：父进程修改已有 key 时真正拷贝内存页（默认 4K）、申请新空间——bigkey 大块分配耗时变长可能阻塞
- **Huge Page 必须关闭**：内存大页（2MB）让 COW 的读写放大严重（改 256B 也要拷贝 2MB 页），Redis 机器上建议关掉

**Q2：重写日志为什么不共享 AOF 本身的日志？**
- 父子进程写同一文件有**竞争**，控制竞争影响父进程性能
- 重写失败会**污染**原 AOF 文件，无法用于恢复。独立新文件：失败删掉即可，原文件毫发无损，完成后原子替换

**其他评论精选**：
- 重写触发配置：`auto-aof-rewrite-min-size 64mb` + `auto-aof-rewrite-percentage 100`（超 64MB 且比上次重写后体积增长 100% 时自动触发）；手动 `BGREWRITEAOF`
- 同时开 RDB+AOF 时重启**优先用 AOF 恢复**（命令记录通常更全）

## 二、设计问答

### Q1：AOF 和数据库的 redo log（WAL）有什么区别？

redo log 是**写前日志**（先记日志再改数据），记录修改后的数据页，用于崩溃恢复；AOF 是**写后日志**（先执行再记录），记录的是命令文本。AOF 写后的原因：省去语法检查开销 + 保证日志中命令必然正确。写后的代价：刚执行完未记录就宕机会丢数据（用 appendfsync 策略控制窗口）。

### Q2：三种写回策略怎么选？

Always：金融级不丢数据，性能差；Everysec：丢 1 秒，性能折中，**绝大多数业务的默认选择**；No：性能最好但落盘时机交给 OS，宕机丢多少不可控。这是性能与可靠性取舍（trade-off）的教科书案例——做系统设计时先想清楚"我能丢多少"。

### Q3：AOF 重写的原理？为什么说"多变一"？

重写不读旧日志，而是**遍历当前数据库**，为每个键值对按最新状态生成一条写入命令。历史上一键值对被改 N 次旧日志有 N 条，重写后只剩 1 条——"多变一"。由 bgrewriteaof 子进程执行，"一个拷贝两处日志"保证重写期间新写不丢。

### Q4：fork 为什么还会阻塞主线程？COW 不是很快吗？

fork 的 COW 只免了**物理内存**拷贝，**页表**（虚拟地址→物理地址映射）必须拷贝。实例内存越大页表越大，拷贝页表期间主线程阻塞。此外重写/快照期间父进程每次写已存在的 key 都要真正拷贝内存页（4K 起步，bigkey 更久）+ 申请新内存——所以大实例 + 高写入场景，fork 和 COW 的代价都不可忽略。

### Q5：RDB 和 AOF 同时开启，重启用哪个恢复？

**优先 AOF**——它记录的命令更全（Everysec 最多丢 1 秒，RDB 可能丢几分钟）。RDB 的价值在恢复速度快（直接读文件载入内存，不用逐条重放命令）。

## 三、实践要点

- 生产配置：缓存场景 AOF Everysec 足够；当数据库用且不能丢数据才考虑 Always（同时接受性能损失）
- **Redis 机器必须关闭 Huge Page**（`echo never > /sys/kernel/mm/transparent_hugepage/enabled`）——COW 读写放大的坑
- 控制单实例内存大小（如 ≤ 10GB 级别），**页表大小决定 fork 阻塞时长**，大实例是延迟抖动之源（18 讲展开）
- AOF 文件定期重写（默认 64MB + 100% 增长触发），恢复演练时关注重放耗时
- 主从架构下可把持久化压力放到从库（主库关 AOF/RDB，从库开）——但要清楚从库同步中断的风险（06/32 讲展开）

## 四、深入追问

### Q1："一个拷贝两处日志"里，新的重写日志缓冲区由谁写？（易误解点）

主线程写。重写期间主线程每执行一个写命令，会**同时**写正在使用的 AOF 缓冲区和 AOF 重写缓冲区（所以原文图中主线程和重写缓冲区有连线）；子进程（bgrewriteaof）只负责把拷贝到的内存数据写成新 AOF 文件。最后子进程完成 → 主线程把重写缓冲区内容追加到新文件 → 原子替换旧文件。

### Q2：AOF 恢复时是单线程逐条重放，大文件恢复慢怎么破？

这就是 RDB 的存在意义（05 讲）：RDB 是二进制快照，恢复时直接读入内存，速度远快于 AOF 重放。Redis 4.0 的**混合持久化**（`aof-use-rdb-preamble yes`）：重写的 AOF 文件前半部分是 RDB 格式的全量数据、后半部分是增量命令——恢复时先快载 RDB 再重放少量增量，兼得两者。

### Q3：过期 key 在 AOF 重写时怎么处理？

重写遍历的是**当前有效数据**，已过期的 key 不会写入新 AOF（天然瘦身）。AOF 恢复时若 key 的过期时间已过，恢复逻辑会跳过/删除。所以不用担心 AOF 把过期数据"复活"——但要注意：AOF 记录的是 DEL 命令，主从场景下从库的过期语义有讲究（主库删除后才同步 DEL，从库可能短暂返回过期数据，06/32 讲的坑）。

### Q4：与面经 09 讲"自动故障处理"的呼应？

面经里"Redis 崩了限流保护 DB"的兜底逻辑，前提是理解"崩了之后恢复要多久"——AOF 重放慢正是恢复时间的决定因素。容量规划时要把"故障恢复时长 = 数据加载时间 + 流量预热时间"算进 SLA，这也是混合持久化在云上成为默认配置的原因。
