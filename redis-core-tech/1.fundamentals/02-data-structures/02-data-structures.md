# 02 数据结构：快速的 Redis 有哪些慢操作？

> 来源：极客时间《Redis 核心技术与实战》蒋德钧（基础篇 02）
> 整理日期：2026-11-13

---

## 一、内容总结

**数据类型 vs 底层数据结构**：String/List/Hash/Set/Sorted Set 只是值的"保存形式"；底层数据结构共 6 种——**简单动态字符串（SDS）、双向链表、压缩列表、哈希表、跳表、整数数组**。String 只有 SDS 一种实现；List/Hash/Set/ZSet 四种集合类型各有两种实现（量少用紧凑结构，量多转高效结构）。

**键和值的组织：全局哈希表**
- 所有键值对由一个**全局哈希表**索引：数组（哈希桶）+ entry 存 `*key`/`*value` 指针（集合类型也是指针指向集合对象）
- 查找 = 一次哈希计算，**O(1)**，与数据量无关——这是 Redis "快"的第一根基

**哈希表的两大隐患**（"快"背后的慢操作伏笔）：
1. **哈希冲突**：多 key 落同一桶 → **链式哈希**（冲突链）。链过长则查找退化成遍历
2. **rehash**：数据增多 → 扩容。Redis 备**两个全局哈希表**（表 1 在用，表 2 扩容备用），rehash 三步：表 2 分配 2 倍空间 → 表 1 数据重映射拷贝 → 释放表 1
   - 一次性拷贝会阻塞主线程 → **渐进式 rehash**：每处理一个请求，顺带迁移一个索引位置的所有 entries，把拷贝开销摊到多次请求里
   - 补充（评论作者回复）：还有**定时任务兜底**——没有请求时周期性（约 100ms）主动搬一批，防止 rehash 拖太久

**集合类型的操作效率 = 底层结构 + 操作特点**：

| 底层结构 | 特点 | 复杂度 |
|---|---|---|
| 哈希表 | 点查 | O(1) |
| 跳表 | 多级索引（链表+分层指针），类似二分 | O(logN) |
| 整数数组 / 双向链表 | 顺序读写 | O(N) |
| 压缩列表 | 类数组，表头 zlbytes/zltail/zllen + 表尾 zlend；**头尾 O(1)**，中间 O(N) | O(1)~O(N) |

**跳表原理**：有序链表 + 多级索引（每级抽取部分元素作索引，索引指向下一级）。数据量大时查找 O(logN)。zset 的范围操作（ZRANGEBYSCORE）靠它；点查分数（ZSCORE）靠配套的 dict（O(1)）——**zset = dict + skiplist 双结构**（呼应面经缓存模块讨论）。

**操作复杂度"四句口诀"**：
1. **单元素操作是基础**——HGET/HSET/HDEL、SADD 等由底层结构定复杂度（哈希表则 O(1)）；批量版本（HMSET M 个）复杂度变 O(M)
2. **范围操作非常耗时**——HGETALL、SMEMBERS、LRANGE、ZRANGE 都是 O(N)，避免；**用 SCAN 系列（2.8+）渐进式遍历替代**
3. **统计操作通常高效**——LLEN/SCARD 等 O(1)（结构上专门记录了元素个数）
4. **例外情况只有几个**——压缩列表/双向链表记录了头尾偏移量，所以 List 的 LPOP/RPOP/LPUSH/RPUSH 头尾操作 O(1)

**实践建议**：
- 集合范围操作用 SCAN 系列替代全量遍历
- List 的两种底层结构（双向链表/压缩列表）都是 O(N)，**因地制宜：只做 FIFO 队列（PUSH/POP 快），别当随机读写集合用**
- 掌握原理推断复杂度，不用死记所有命令

## 二、设计问答

### Q1：Redis 的"快"靠什么？有哪些潜在的慢操作？

快：①内存操作；②全局哈希表 O(1) 索引；③集合类型用高效结构（哈希表、跳表）。慢操作潜伏在：哈希冲突链过长、rehash 大规模拷贝（已由渐进式 rehash 缓解）、集合范围操作 O(N)、List 中间元素操作 O(N)。**排查慢操作先看底层结构再看操作类型**。

### Q2：渐进式 rehash 怎么工作的？会不会永远迁不完？

每次处理请求时顺带迁移一个桶位的全部 entries，把一次性拷贝摊到多次请求。若长期没有请求，还有**定时任务**周期性（约 100ms）主动迁移一批，保证 rehash 最终完成。rehash 期间读写会**同时查两个表**（先查表 1 再查表 2），写只写表 2，保证数据不错乱。

### Q3：压缩列表查找 O(N)，为什么还用它？（每课一问）

①**内存利用率**：数组/压缩列表是紧凑连续内存，比链表省内存（无指针开销）——Redis 是内存数据库，省内存是硬指标；②**CPU 高速缓存友好**：连续内存顺序访问命中缓存行，实际速度不慢。所以元素少时用紧凑结构，超过阈值转哈希表/跳表。**时间复杂度不是唯一维度，常数因子（缓存命中、内存紧凑）在小数据量下更重要**。

### Q4：rehash 时 key 的位置为什么会变？哈希值不是固定的吗？

存桶时用的是 `hash(key) mod 桶个数`。rehash 改变了**桶个数**，取模结果变了，所以同一个 key 要迁移到新位置。变的不是哈希值，是映射关系。

### Q5：zset 为什么是 dict + skiplist 两个结构？

各管一段：skiplist 服务**范围操作**（ZRANGEBYSCORE 等，O(logN)）；dict 存 member→score，服务**点查**（ZSCORE，O(1)）。空间换时间的典型设计（与开篇词评论区的作者回复一致）。

## 三、实践要点

- **禁用/替代清单**：生产环境 HGETALL、SMEMBERS、LRANGE 0 -1、KEYS 全量扫描换成 HSCAN/SSCAN/LRANGE 分页/SCAN——一次 O(N) 全量操作在大集合上就是一次主线程卡顿
- **List 只当队列用**：LPUSH+RPOP 或 RPUSH+LPOP，别 LPUSH 后 LINDEX/LRANGE 大区间随机读
- 批量命令注意复杂度：HMSET M 个 = O(M)，大 M 时拆批
- 大 Hash/大 Set 也有 rehash（底层同为哈希表），写放大期留意延迟抖动
- 监控慢操作的入口：`SLOWLOG` + `INFO commandstats`（呼应面经 36 讲专题 2 的观测清单）

## 四、深入追问

### Q1：渐进式 rehash 期间，读写操作怎么保证正确？

读：先查表 1，未命中再查表 2；写/删：直接操作表 2（新数据不再进表 1）；迁移按桶位推进，已迁移的桶位在表 1 中置空。这样任何时刻数据只在一处，不会出现两份不一致。

### Q2：压缩列表的级联更新问题是什么？（进阶坑）

压缩列表每个 entry 记录前一个 entry 的长度（prevlen），长度 < 254 字节用 1 字节记录，≥ 254 用 5 字节。如果在头部插入一个 ≥ 254 字节的元素，后一个 entry 的 prevlen 要从 1 字节扩到 5 字节，entry 变大又可能引发再下一个 entry 的 prevlen 扩展——**连锁反应**，最坏 O(N²)。这是压缩列表后来被 listpack（Redis 7.0 全面替换）取代的核心原因。面试提这个直接封神。

### Q3：与面经 35 讲"大 key 危害"的呼应？

大 key 的删除/全量读（HGETALL、SMEMBERS）正是本讲"范围操作 O(N)"的生产事故版：单线程 + O(N) = 阻塞期间所有请求排队。面经讲了危害与治理（拆分、异步删除 UNLINK），本讲给了复杂度根源。**UNLINK 之所以快，就是把 O(N) 的内存释放挪到后台线程**（16 讲异步机制展开）。

### Q4：整数数组（intset）什么时候触发升级？

Set 全为整数且元素少时用 intset（有序整数数组，二分查找 O(logN)）。插入超出当前编码范围的整数时**升级编码**（int16→int32→int64），升级要重新分配内存并移动全部元素——只升不降。这也是"小数据量优化"路线的又一例：阈值内省内存，超阈值转哈希表。
