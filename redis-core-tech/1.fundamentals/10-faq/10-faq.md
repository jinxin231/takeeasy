## 一、课后思考题答案速查（各讲详细内容见对应笔记）

| 讲 | 问题 | 答案要点 |
|---|---|---|
| 01 | SimpleKV 缺什么？ | 丰富数据结构、内存优化（压缩编码）、分配器选择、过期淘汰、持久化、主从/哨兵、集群、事务、辅助模块（统计/通知/调试） |
| 02 | 整数数组/压缩列表查找无优势，为什么还用？ | ①紧凑连续内存省空间（内存数据库的硬指标）②CPU 缓存友好；元素超阈值再转哈希表/跳表 |
| 03 | 基本 IO 模型还有哪些瓶颈？ | 主线程执行的任何耗时操作都是瓶颈：bigkey、全量返回、慢命令等 |
| 04 | AOF 重写的潜在阻塞风险？ | ①**fork 瞬间**：内核创建+拷贝 PCB、拷贝页表，实例越大越久，阻塞主线程；②**重写期间**：主线程写操作申请新内存（bigkey 大空间分配有查找和锁开销） |
| 04 | 重写日志为何不共享 AOF？ | 主线程和子进程竞争文件系统锁，影响主线程性能；失败会污染原文件 |
| 05 | 2C4G、2GB 数据、8:2 写读比，RDB 风险？ | ①**内存**：COW 为 80% 写操作复制约 1.6GB，接近饱和 → Swap（性能崩）或 OOM（被 kill）；②**CPU**：2 核上主线程、子进程、后台线程互相争抢 → 请求延迟增大 |
| 06 | 主从复制为什么不用 AOF？ | ①RDB 是二进制，写盘和网络传输 IO 效率高于 AOF 文本命令流；②从库加载 RDB 比逐条重放 AOF 快 |
| 07 | 切换期间客户端怎么办？ | 读走从库（可能旧值），写不可用；无感知需客户端**缓存写请求**，切换完成后重发到新主库 |
| 08 | 哨兵越多越好吗？down-after 调大好吗？ | 哨兵多→误判率低但票数要求高、投票耗时、切换变慢、客户端请求堆积超时；down-after 调大→误判少但故障发现慢、不可用窗口拉长。**都要权衡，没有越大越好** |
| 09 | 为什么不直接记 key→实例的表？ | 表随实例增减/数据重分布要修改：单线程改串行慢、多线程改有锁开销；数据量大时表本身的存储开销也大。槽数（16384）远小于 key 数，槽→实例的表修改和存储都轻量 |

## 二、典型问题讲解（本讲核心价值）

### 问题 1：rehash 的触发时机和渐进式执行机制

**触发条件**（装载因子 load factor = entry 总数 / 哈希桶数）：

| 条件 | 动作 |
|---|---|
| 装载因子 ≥ 1 且**允许 rehash** | 触发（避免链式哈希） |
| 装载因子 ≥ 5 | **无条件立即触发**（冲突链已严重影响性能） |
| 装载因子 < 1，或 1~5 之间但**正在 RDB/AOF 重写** | 不触发（rehash 被禁止，避免干扰持久化） |

- ≥1 触发的原因：装载因子 1 意味着一桶一个（不用链式哈希），再有写入就要拉链了
- **RDB/AOF 重写期间禁止 rehash**：避免 rehash 的内存变动与 COW 叠加放大内存开销

**没有新请求时还做 rehash 吗？** 做。**定时任务兜底**：rehash 触发后，即使没有请求，定时任务（约每 100ms）也会执行一次 rehash，**每次执行不超过 1ms**，避免影响其他任务。

### 问题 2：主线程、子进程、后台线程的联系与区别

- **进程 = 资源分配单元**（堆、栈、虚存页表、fd）；**线程 = CPU 调度执行实体**
- 进程启动后没再建额外线程 → 既是主进程也是主线程（Redis 本体就是：接收请求、处理读写都在这一个线程）
- **fork 创建的子进程**（3 个）：bgsave 生成 RDB（兼主从同步传输）、无盘复制传输 RDB、bgrewriteaof
- **pthread_create 创建的后台线程**（4.0+）：异步删除（lazy-free）等任务（16 讲详述）

### 问题 3：写时复制（COW）的底层实现

- fork 后子进程**复制的是主线程的页表**（虚拟页→物理页映射），不是物理内存——页表数据远小于内存数据
- 主线程写某虚页（如虚页 7）→ 新分配物理页（53）写入修改后数据，更新自己页表；**子进程页表里虚页 7 仍指向旧物理页（33）**→ 子进程读到的是原始数据，无误写入 RDB
- 内存分配有查找和锁开销——**bigkey 大空间分配是主线程的阻塞风险点**

### 问题 4：replication buffer vs repl_backlog_buffer（权威版）

| | replication buffer | repl_backlog_buffer |
|---|---|---|
| 用途 | 主库向从库**发送数据**的输出缓冲区 | 保存**写操作命令流**，支持增量复制 |
| 作用域 | **每个从库一个**（主库为每个从库建客户端，各配 buffer） | **全局一个，所有从库共享** |
| 大小控制 | `client_buffer` 配置项 | `repl_backlog_size` |
| 时机 | 全量复制第三阶段 + 命令传播 | 服务器启动后持续记录所有写命令 |

从库重连时各自上报 slave_repl_offset，主库按各自进度从 backlog 独立补发。

## 三、实践要点

- **大实例 + RDB/AOF 期间，避免大规模写入**：rehash 被禁（冲突链变长查询变慢）+ COW 内存放大，双重夹击
- 排查"为什么我的 Redis 突然变慢"的新线索：检查是否正处于 rehash 禁止期 + 写入激增（装载因子冲向 5 的路上）
- 内存规划：实例内存 ≤ 物理内存的 60~70%，给 COW 和 fork 留空间；2C4G 小机器别塞 2GB 数据还高频写
- 监控 replication buffer：从库消费慢时它膨胀会挤爆内存（21 讲"缓冲区惨案"预告）

## 四、深入追问

### Q1：装载因子 ≥1 才扩容，是不是太晚了？（评论区质疑）

Java HashMap 等 0.75 就扩容，Redis 全局哈希表 ≥1 才动——因为 Redis 有**渐进式 rehash + 定时任务**，扩容可以"边服务边进行"，启动晚一点也不会雪崩；且 ≥5 的硬触发兜底了极端情况。设计差异的根源：Java 的扩容是 stop-the-world 的，必须提前；Redis 的扩容是渐进的，可以延后。**触发时机与执行成本是配套的**。

### Q2：为什么 RDB/AOF 期间要禁止 rehash？

rehash 搬移数据会修改大量内存页 → 触发大量 COW 复制 → 快照期间内存膨胀加剧（05 讲的 OOM 风险）；同时 rehash 本身耗 CPU，和 bgsave/bgrewriteaof 子进程抢核。禁止 rehash 是"非常时期非常管制"，代价是冲突链暂时变长——两害相权。

### Q3：基础篇知识地图（面试自我介绍素材）

```
            → 06 主从复制(全量/增量/backlog) → 07 哨兵(主观客观/选主) → 08 哨兵集群(pubsub/Raft)

```
