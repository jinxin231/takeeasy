# 09 切片集群：数据增多了，是该加内存还是加实例？

> 来源：极客时间《Redis 核心技术与实战》蒋德钧（基础篇 09）
> 整理日期：2026-11-13

---

## 一、内容总结

**扩展的两条路**：
- **纵向扩展（scale up）**：加内存。简单直接，但内存越大 → RDB 持久化时 fork 越阻塞主线程（05 讲），且受硬件和成本限制
- **横向扩展（scale out）**：**切片集群**，多实例分担数据——不管多少数据都能应对

**切片集群的两大问题**：①数据切片后如何在多实例间分布？②客户端怎么确定数据在哪个实例？

**Redis Cluster 方案（3.0+ 官方切片实现，无中心化）**：

**① 数据分布：哈希槽（Hash Slot）**
- 全集群固定 **16384 个槽**，类似数据分区
- 映射两步：key → **CRC16**（16 bit）→ **mod 16384** → 槽号（0~16383）
- 槽→实例分配：`cluster create` 自动均分（每实例 16384/N）；或 `cluster meet` 建连 + `cluster addslots` 手动按机器配置分配（内存大的多分）
- **必须 16384 个槽全部分完**，否则集群不工作

**② 客户端定位数据**
- 实例间互传哈希槽信息（扩散），每个实例最终拥有**全量槽映射表**；客户端连上任一实例即可拿到并**缓存到本地**
- 请求时客户端自算槽号 → 查本地缓存 → 直连对应实例（**去中心化，无 proxy**）
- 但槽与实例的映射会**变**（实例增减、负载均衡迁移），客户端无法主动感知 → **重定向机制**

**MOVED 重定向**：
- 槽数据已全部迁走，客户端还按旧缓存访问旧实例 → 旧实例返回 `MOVED 13320 172.16.19.5:6379`
- 客户端**更新本地缓存**，后续该槽请求都发新实例

**ASK 重定向**：
- 槽**正在迁移**（部分 key 已走、部分还在）：客户端请求已迁走的 key → 返回 `ASK 13320 新地址`
- 客户端先给新实例发 `ASKING`（让新实例临时受理），再发操作命令
- **ASK 不更新客户端缓存**——下次请求还是发旧实例（只为这一次放行）
- 对照：MOVED = 搬完了，以后别来；ASK = 正在搬，这次去那边办

**每课一问：为什么要哈希槽这一层，不直接记 key→实例的映射表？**（Kaito 精彩回答）
1. key 数量不可预估，逐 key 映射表**太大**（服务端/客户端都存不起）
2. Cluster 无中心化，**每个节点要存全量路由表**以纠正客户端错误路由——逐 key 表节点间交换成本高、内存浪费
3. 扩缩容/数据均衡时，逐 key 修改映射关系维护成本高
4. 哈希槽把**数据与节点解耦**：key 只关心槽号，槽→实例的表极小（16384 项），交换轻量、分布均匀
5. 迁移以**槽为基本单位**，简化扩缩容和数据均衡的操作难度

**评论精选**：
- 为什么不用 Range-based 分片（现代分布式数据库常用）？范围分片易**数据倾斜**（某 range 记录特别多、访问特别热）；哈希打散分布均匀，负载均衡好
- 每个切片可配从库（生产建议配），`cluster replicate` 命令
- 复杂类型（Hash 等）的 key 同样分片——按**集合本身的 key**算槽，不是 value 内部字段
- 3.0 前的业界方案：客户端分区的 ShardedJedis、代理层的 Codis/Twemproxy（35 讲对比 Codis vs Cluster）

## 二、设计问答

### Q1：切片集群和 Redis Cluster 是什么关系？

切片集群是**通用机制**（数据分片到多实例），Redis Cluster 是官方**实现方案**（3.0+）。其他实现：ShardedJedis（客户端分区）、Codis/Twemproxy（代理层）。面试别把两个词混用——说"我们用的切片集群方案是 Redis Cluster"。

### Q2：16384 个槽是怎么用的？为什么是 16384？

映射：CRC16(key) mod 16384 = 槽号，槽再分配到实例。16384 = 2^14 的考量：槽数太少（如 100）迁移粒度粗、分布易不均；太多则每个节点携带的槽位图（bitmap）变大、Gossip 消息变大。**16384 用 2KB bitmap 就能表示**，节点间心跳消息能塞进合理大小，是空间与粒度的平衡点。

### Q3：MOVED 和 ASK 的区别？

| | MOVED | ASK |
|---|---|---|
| 时机 | 槽已**全部**迁走 | 槽**正在迁移** |
| 含义 | 数据永远在新实例，以后去那 | 这次请求的 key 已在新实例，临时去那办 |
| 客户端动作 | **更新本地缓存**，后续都发新实例 | 先发 `ASKING` 再发命令，**不更新缓存** |
| 类比 | 搬家完成，通知新地址 | 搬家中，东西在新家，这次去新家取 |

### Q4：为什么 Redis Cluster 要在 key 和实例之间加"槽"这一层？

解耦 + 压缩：逐 key 的路由表太大存不下、换不动；槽是固定 16384 项的小表，key 与槽的关系靠**计算**（CRC16 mod）不需存储，槽与实例的关系才需要存储和交换。扩缩容时迁移以槽为单位批量进行，不用逐 key 改映射。**计算机科学的老规律：没有什么是加一层间接层解决不了的**。

### Q5：客户端怎么知道数据在哪个实例？

本地缓存"槽→实例"映射表（首次连实例时获取）→ 请求时算槽直连。表过期了靠 MOVED 纠错更新。所以 Cluster 客户端必须用**集群版 SDK**（JedisCluster/Lettuce cluster），单机 SDK 不懂这套协议。

## 三、实践要点

- 生产每个切片**配从库**（cluster replicate），否则切片挂了该槽数据直接不可用
- 手动分槽按机器配置来（内存大的多分），别一味均分；**16384 槽必须分完**
- 迁移期间客户端 RT 会变高（ASK 两次往返 + ASKING）——**数据迁移避开高峰**
- 多 key 操作（MGET、事务、lua）的 key 必须在**同一槽**——用 **hash tag**（`{user1001}.profile` 花括号内参与槽计算）强制同槽，否则 CROSSSLOT 报错
- 集群版 SDK 才支持 MOVED/ASK 协议；客户端异常日志里大量 MOVED 说明映射表滞后严重（可能刚扩缩容或迁移中）
- 云厂商集群版的 proxy 已把这套协议封装掉（客户端无感）——自建 Cluster 才需要关心这些细节

## 四、深入追问

### Q1：Cluster 的去中心化靠什么维持？Gossip 协议。

实例间通过 Gossip 交换信息（槽映射、节点状态、故障标记）：每个节点周期性地随机挑几个节点互发 PING/PONG，捎带自己知道的集群视图——信息像 gossip 一样在集群里扩散收敛。这带来两个后续问题：①**集群规模受通信开销限制**（38 讲专门讲，节点太多 Gossip 消息爆炸）；②故障检测的最终一致性（误判/传播延迟）。Codis 用中心化的 dashboard 存路由表，就没这个问题——这是 35 讲 Codis vs Cluster 的核心分歧。

### Q2：迁移一个 key 的完整过程？（Cluster 的在线迁移为什么"有损"）

`MIGRATE` 命令：**同步阻塞**地把 key 从源实例搬到目标实例（源和目标都阻塞）。大 key 迁移 = 两个实例同时卡顿——所以生产上 Cluster 的大 key 比普通部署更危险。Codis 改进为**异步迁移**（leak buffer + 逐步搬迁），这是 Kaito 评论里 Codis 的优势点，也是 35 讲的素材。

### Q3：hash tag 的原理和代价？

规则：key 含 `{}` 时只用花括号内的子串算槽。`{u1}.orders`、`{u1}.profile` 同槽 → 多 key 操作可用。代价：用不好会**人为制造数据倾斜**（某个 tag 数据量/访问量巨大，全压一个实例）——37 讲"数据倾斜"的对策清单里就有"检查 hash tag 滥用"。

### Q4：和面经 09 讲"自动扩容"的呼应？

面经讲 K8s 自动扩应用节点；Redis Cluster 的扩容多一步**数据再平衡**（reshard）：新实例加入 → 分配槽 → 迁移数据（MOVED/ASK 期间服务有损）。所以 Redis 扩容不是"拉起新 Pod"就完事，迁移速度、大 key、迁移期间 RT 都要规划——这也是云厂商托管集群的卖点：扩缩容 + rebalance 一键完成，proxy 屏蔽 MOVED/ASK。
