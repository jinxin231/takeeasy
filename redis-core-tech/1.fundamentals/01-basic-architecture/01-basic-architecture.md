# 01 基本架构：一个键值数据库包含什么？

> 来源：极客时间《Redis 核心技术与实战》蒋德钧（基础篇 01）
> 整理日期：2026-11-13

---

## 一、内容总结

**学习方法论**：不一上来就扎进"单线程""缓存"等具体技术点，先建**系统观**——通过解剖一个最简键值数据库（SimpleKV，相当于解剖小白鼠），抓住 Redis 的架构主线。这个学习方式可迁移到任何中间件。

**SimpleKV 构建六步**（前两步是应用视角，后四步是内部构造）：

**① 数据模型——能存什么数据**
- 基本模型 key-value；SimpleKV 的 key 是 String，value 是基本类型
- **选型关键在 value 类型**：Memcached 只支持 String，Redis 支持 String/哈希/列表/集合等——Redis 应用广泛正得益于此
- value 类型的差异隐含**数据结构的性能、空间效率差异**（02 讲展开）
- 判据：数据模型决定"能不能存"（用户信息可以 KV 化），操作接口决定"合不合适"（多用户年龄求均值，KV 做不了聚合计算）

**② 操作接口——能做什么操作**
- 基本集合：**PUT / GET / DELETE / SCAN**（SCAN = 按 key 范围查询，如查用户一段时间访问记录）
- 按需扩展：EXISTS（黑白名单）等；value 类型多了，接口也要跟着多（列表 LPUSH/LPOP 等）

**③ 存储位置——内存还是外存**
- 内存：百 ns 级读写，掉电丢数据；外存：ms 级，不丢但拖垮性能
- 按场景选：**缓存场景允许丢失、要求快 → 内存**（Memcached、Redis 都是内存键值数据库）

**④ 访问模式——怎么被访问**
- 动态链接库（libsimplekv.so，库与调用方同进程同主机，如 RocksDB）vs **网络框架**（Socket Server + 协议解析，如 Redis/Memcached）
- 网络框架引出核心设计问题：**IO 模型**——连接处理、请求解析、数据存取用几个线程/进程？一个线程全包则一步阻塞全阻塞；多线程则有共享资源竞争。这是"两难"，03 讲展开
- 二次开发/自研客户端必须掌握通信协议（加餐四展开）

**⑤ 索引模块——怎么定位键值对**
- 常见索引：哈希表、B+ 树、字典树。Memcached/Redis 用**哈希表**，RocksDB 用**跳表**做内存索引
- 内存 KV 选哈希表的原因：内存的随机访问特性与哈希表 O(1) 完美匹配
- Redis 特别之处：哈希表找到 value 后，还要在 value 的复杂结构（集合/列表）里二次定位——**value 的底层结构本身就是索引结构**（如 zset 的跳表），这是 Redis 高性能的支撑之一

**⑥ 操作模块 + 存储模块**
- GET/SCAN：按位置返回值；PUT：分配内存；DELETE：释放内存——后两者引出**内存分配器**
- glibc malloc 对随机大小内存块分配表现差 → 内存碎片问题；**分配器是键值数据库的关键因素**，Redis 提供多种分配器选择
- 持久化（重启快速恢复）：每条落盘（可靠但慢）vs 周期落盘（快但有丢失风险）——Redis 的答案是 AOF + RDB 两套机制（04/05 讲）

**SimpleKV → Redis 的四个演进**：
1. 动态库 → 网络框架（成为基础网络服务）
2. value 类型丰富化 → 操作接口爆炸（LPUSH/SADD...）
3. 持久化双机制：AOF 日志 + RDB 快照
4. 单机 → 高可靠集群 + 高可扩展集群

## 二、设计问答

### Q1：一个键值数据库包含哪些基本组件？

访问框架（动态库或网络框架）、索引模块（定位 value）、操作模块（各操作的具体逻辑）、存储模块（内存分配 + 持久化）。外加应用视角的数据模型和操作接口。SimpleKV 麻雀虽小五脏俱全，Redis 就是这些组件的精细优化版。

### Q2：为什么内存键值数据库都用哈希表做索引，而不是 B+ 树？

内存的随机访问性能极好且均匀，哈希表 O(1) 的点查询与之完美匹配；B+ 树的优势在磁盘场景（减少 IO 次数、支持范围查询），内存场景用不上它的优势还白白付出 O(logN) 和复杂实现。反过来说，哈希表的软肋是**范围查询**——这正是 Redis 用 KEYS 全扫低效、zset 内部还得靠跳表的原因。

### Q3：Redis 的索引是跳表吗？（常见误解澄清）

不是。从 key 找到 value 靠的是**全局哈希表**；跳表只是 value 为有序集合（zset）时，集合**内部**组织元素的索引（ZRANGEBYSCORE 等范围操作 O(logN)）。两级索引：key → 哈希表 → value 对象 →（zset 内部）跳表 → 元素。

### Q4：动态库访问和网络框架访问的区别？

动态库：数据库与应用程序同进程同主机，直接函数调用（`db.get(key)`），语言相关（C++ 库给 C++ 程序用），如 RocksDB。网络框架：数据库是独立服务，客户端通过 Socket + 协议访问，可跨主机跨语言，如 Redis。注意与 SDK 的区别：SDK 封装的是网络访问 API，动态库里是真的存着数据。

### Q5：SimpleKV 比 Redis 缺了什么？（每课一问 + 评论精选）

按"三高"主线归类：
- **高性能**：丰富的 value 数据结构及内存优化（压缩编码）、内存分配器选择、过期与淘汰机制
- **高可靠**：持久化双机制（AOF/RDB）、主从复制、哨兵
- **高可扩展**：集群、分片
- **辅助**：统计、通知、调试、元数据查询模块；事务（多操作原子性）

## 三、实践要点

- **选型判据记牢**：键值数据库选型核心看 value 类型支持 + 操作接口；拿不准"该不该用 Redis"时，先问"数据模型能 KV 化吗？需要的操作 KV 接口支持吗？"（聚合、关联查询请回关系型）
- **SCAN 是一等公民**：范围查询需求在设计键值模型时就要考虑（key 设计带前缀/时间戳，靠 SCAN 按前缀检索）
- 自研客户端或二次开发前，先吃透 RESP 通信协议（加餐四）
- 内存分配器不是小事：随机大小分配场景 glibc 表现差，生产 Redis 关注 jemalloc（默认）与碎片的监控（`INFO memory` 的 `mem_fragmentation_ratio`）

## 四、深入追问

### Q1：为什么"网络框架"会引出 IO 模型这个两难问题？

单机动态库没有这个问题——函数调用天然串行。网络框架下，连接处理、协议解析、数据存取三件事的关系必须做架构决策：全塞一个线程，任一步骤阻塞（如磁盘 IO）则全系统卡死；拆成多线程，共享数据结构的竞争（锁）又吃掉性能。Redis 的解法是**单线程 + epoll IO 复用**（03 讲）：连接和解析用 IO 多路复用避免阻塞，数据存取因是纯内存操作足够快所以单线程扛得住——两难被"操作足够快"这个前提化解。

### Q2：与《高阶面经》36 讲的呼应？

面经 36 讲从面试视角讲"为什么 Redis 单线程快"（epoll + Reactor），本课程 01 讲从架构视角讲"单线程是 IO 模型设计的取舍结果"。面试时可以先给架构层答案（IO 模型两难 → Redis 前提：内存操作足够快 → 单线程消除竞争），再给机制层答案（epoll 细节）——**先架构后机制**，比直接背 epoll 更有层次。

### Q3：哈希表索引在高并发下有什么问题？（为后续埋伏笔）

Redis 的全局哈希表需要 rehash（扩容时数据迁移），大实例 rehash 若一次性完成会阻塞主线程——所以 Redis 用**渐进式 rehash**（每次操作迁移一小部分）。这是 02/18 讲"慢操作""延迟抖动"的伏笔。面试被问"哈希表 O(1) 就高枕无忧了吗"，答案就是 rehash 这个坑。
