# 06 数据同步：主从库如何实现数据一致？

> 来源：极客时间《Redis 核心技术与实战》蒋德钧（基础篇 06）
> 整理日期：2026-11-13

---

## 一、内容总结

**为什么主从**：读写分离——写走主库、读走主从均可，分摊读压力；避免"同时写多个实例"的数据不一致。**复制是异步的**（作者确认）：主库本地执行完就返回客户端，不等从库同步——所以**从库不是强一致**（从库执行 bigkey 等慢操作时复制进度会落后）。

**主从同步三种模式**：

**① 全量复制（第一次同步）——三个阶段**
1. 建立连接、协商同步：从库 `replicaof 主库IP 6379`，发 `psync`（带 runID 和 offset）告诉主库同步进度
2. 主库 `bgsave` 生成 RDB → 传给从库；从库**清空自身数据**后加载 RDB。期间主库新收到的写操作记入 **replication buffer**（保证不丢）
3. 主库把 replication buffer 的修改操作发给从库执行 → 同步完成

主库的两个耗时操作：生成 RDB（fork 阻塞主线程）+ 传输 RDB（占网络带宽）。

**② 基于长连接的命令传播（常规阶段）**
全量完成后，主从维护长连接，主库后续收到的命令持续传给从库——避免频繁建连开销。

**③ 增量复制（网络断连恢复，2.8+；2.8 前只能全量重传）**
- 断连期间主库把写命令同时写入 replication buffer 和 **`repl_backlog_buffer`（环形缓冲区）**
- 主库记 `master_repl_offset`（写位置，单调递增），**每个从库自己记** `slave_repl_offset`（读位置）
- 重连后从库发 psync 上报自己的 offset，主库只把**两个 offset 之间的命令**补发给从库

**repl_backlog_buffer 的覆盖风险（核心考点）**：
- 环形缓冲区写满后**新写覆盖旧数据**——从库读得慢，没读到的部分被覆盖 → 主从不一致，只能**全量复制**兜底
- 缓冲空间计算公式：`缓冲空间 = 主库写入速度 - 网络传输速度`，**`repl_backlog_size = 缓冲空间 × 2`**（留突发余量）
  - 例：主库每秒写 2000 操作 × 2KB，网络每秒传 1000 → 需缓冲 1000 操作 = 2MB → 最终设 4MB
- 并发再大就调 4 倍，或上**切片集群**分担（09 讲）
- 断连过长的检测：从库每秒发 `replconf ack`，主库超过 `repl_timeout` 没收到就断开；从库重连上报进度，已被覆盖则全量复制

**主-从-从级联模式（分担全量复制压力）**：
- 多个从库都要全量复制 → 主库忙于 fork + 传 RDB
- 手动选一个从库（内存配置高的）级联其他从库：`replicaof 所选从库IP 6379`——主库的 RDB 生成和传输压力被级联分摊

**小结建议**：**单实例数据不要太大（几 GB 级合适）**——减少 RDB 生成、传输、加载开销；调大 `repl_backlog_size` 降低断连后全量复制风险。

**每课一问：主从复制为什么不用 AOF 而用 RDB？**
AOF 若未重写，含同一 key 的反复操作，全量同步效率低；RDB 是紧凑的二进制快照，生成快、传输小、从库加载快（直接载入内存 vs 逐条重放命令）。

**评论精选**：
- **无盘复制**：全量复制支持不落盘、主库直接 socket 传数据给从库——磁盘差网络好的机器适用
- 读写分离的路由要**客户端实现**（如 Redisson）或加 proxy 判断读写
- 4.0 后（psync2）主从切换后从库只需和新主库**增量同步**（4.0 前要全量）

## 二、设计问答

### Q1：主从复制有哪几种模式？分别在什么时机发生？

①全量复制：从库首次接入（或断连太久 backlog 被覆盖）；②长连接命令传播：全量完成后的常规同步；③增量复制：2.8+ 断连重连后，用 repl_backlog_buffer 补发断连期间的命令。一句话：**首次全量、日常传播、断连增量**。

### Q2：全量复制三阶段是什么？主库哪里最疼？

连接协商（psync）→ RDB 生成与传输（从库清空后加载）→ replication buffer 增量补发。主库疼在两点：bgsave 的 fork 阻塞主线程（页表拷贝）+ RDB 传输占带宽。多个从库同时全量时尤其疼——解法：主-从-从级联，把压力分摊给级联从库。

### Q3：repl_backlog_buffer 是什么？覆盖问题怎么解？

主库侧的**环形缓冲区**，记录最近写入的命令流，主记写 offset、各从库自记读 offset。断连恢复时补发 offset 差值。写满后新覆盖旧——从库没读到的被覆盖只能全量复制。解法：`repl_backlog_size = (写入速度 - 传输速度) × 2`（突发再翻倍），并发太大就用切片集群分摊。

### Q4：主从复制是强一致吗？

不是。**异步复制**：主库执行完就返回客户端，不等从库。从库慢（如执行 bigkey）时复制落后，客户端从从库可能读到旧值。强一致要靠 WAIT 命令（阻塞等 N 个从库确认，但性能差、实际很少用）或换 CP 系统。

### Q5：为什么主从全量复制用 RDB 不用 AOF？

AOF 是命令流，未重写时同一 key 的反复修改全在里面，体积大、从库还要逐条重放（慢）；RDB 是某一时刻的二进制快照，体积小、加载快。全量场景要的就是"给从库一份当前状态的镜像"，RDB 天然匹配。

## 三、实践要点

- **单实例几 GB 为宜**：fork 阻塞、RDB 传输、加载耗时全部与实例大小正相关
- 多从库部署用**级联模式**（挑内存高的从库做二级主），主库只同步少量从库
- `repl_backlog_size` 按公式调（默认 1MB 通常**太小**），这是断连后"增量 or 全量"的分水岭
- 读写分离的读要容忍**旧值**（异步复制）；对一致性敏感的读走主库
- 监控：`INFO replication` 的 `master_repl_offset - slave_repl_offset` 差距（复制延迟）、`repl_backlog_histlen`
- 无盘复制（`repl-diskless-sync yes`）：主库磁盘慢但网络好时开启

## 四、深入追问

### Q1：psync 的 runID 是干什么的？

runID 是实例启动时生成的 40 字节随机串（SHA-1）。从库记录自己复制过的主库 runID，重连时上报：runID 匹配说明"咱俩之前同步过"→ 尝试增量；不匹配（主库换人了）→ 全量。4.0 的 psync2 让新主库继承旧主的复制历史（runID2），主从切换后从库也能增量——这就是评论区"4.0 后不用全量"的原理。

### Q2：环形缓冲区里 offset 和实际位置怎么换算？（评论区较真）

`master_repl_offset` 单调递增、可以无限大；`repl_backlog_idx = offset mod repl_backlog_size` 才是环形缓冲区的真实写入位置。选主时哨兵直接比较各从库的 `slave_repl_offset` 大小即可（不需要知道主库的——主库都挂了，见 07 讲）。

### Q3：与面经 01 讲"注册中心崩溃"的呼应？

Redis 主从的"主库挂了怎么办"和微服务注册中心崩溃是同一类问题：①发现（哨兵 PING 心跳 ≈ 注册中心续约）；②决策（多数派客观下线 ≈ AP 的客户端自决）；③切换（选主 ≈ 客户端切流量）。不同的是 Redis 涉及**数据**（复制进度成为选主标准），注册中心只涉及地址——所以 Redis 的选主比服务发现多一轮"谁的数据最新"。

### Q4：replication buffer 和 repl_backlog_buffer 的区别？

- **replication buffer**：**每个从连接一个**，全量复制第三阶段和命令传播阶段往从库发数据的输出缓冲区（21 讲"缓冲区惨案"的主角之一）
- **repl_backlog_buffer**：**全局一个**，所有从库共享的环形命令流，只为增量复制服务
名字像，作用域完全不同——面试分清这两个加分。
