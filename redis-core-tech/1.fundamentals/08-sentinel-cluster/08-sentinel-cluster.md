# 08 哨兵集群：哨兵挂了，主从库还能切换吗？

> 来源：极客时间《Redis 核心技术与实战》蒋德钧（基础篇 08）
> 整理日期：2026-11-13

---

## 一、内容总结

**思路演进**：为解决主从切换引入哨兵 → 为避免单哨兵故障/误判引入哨兵集群 → 哨兵集群自身也需要机制支撑。任何新机制都会带来新问题，这是系统设计的常态。

**哨兵集群的三大支撑机制（都基于 pub/sub）**：

**① 哨兵集群的组成——`__sentinel__:hello` 频道**
- 哨兵配置里**只写主库地址**；各哨兵把自己的 IP:port **发布**到主库的 `__sentinel__:hello` 频道，同时**订阅**该频道 → 互相发现、建立连接 → 集群形成
- 哨兵 = 一个特殊的 Redis 实例，所以天然自带 pub/sub 能力

**② 哨兵与从库的连接——INFO 命令**
- 哨兵向**主库**发 `INFO`，拿到从库列表 → 与每个从库建立连接并监控（选主打分所需的 slave_priority/slave_repl_offset/runID 全部来自 INFO 监控信息——评论区源码验证）

**③ 客户端事件通知——哨兵的 pub/sub**
- 客户端连哨兵后订阅事件频道：`SUBSCRIBE +odown`（客观下线）、`PSUBSCRIBE *`（全部）
- 关键事件 `switch-master <master name> <oldip> <oldport> <newip> <newport>` → 客户端据此改连新主库，还能感知切换进度

**主从切换由谁执行？——Leader 选举（投票仲裁，Raft 风格）**

前置回顾——**客观下线仲裁**：某哨兵自己判主观下线后，向其他哨兵发 `is-master-down-by-addr`，其他哨兵回 Y/N；赞成票（含自己一票）≥ **quorum** → 标记客观下线。

**Leader 选举**：客观下线后，哨兵发起"由我执行切换"的投票。成为 Leader 需**同时满足两个条件**：
1. 赞成票 **> N/2**（半数以上）
2. 赞成票 **≥ quorum**

**选举过程示例**（3 哨兵 quorum=2）：
- S1 先判客观下线 → 自投 1 票 → 向 S2、S3 拉票
- S3 随后也判客观下线 → 自投 1 票 → 拉票
- 规则：**已投过自己的票就拒绝别人；没投过的，投给"第一个来拉票的"，之后的全拒**
- S2 先收到 S3 的请求 → 投给 S3 → S3 拿到 2 票当选 Leader（S1 与 S2 网络拥塞，票来晚了）
- 选不出 Leader（各持 1 票僵持）→ 等一段时间（约 failover_timeout × 2）后**重新选**

**防"同时当选"的细节（评论区）**：哨兵的周期任务（每 100ms）加了**随机时间偏移**，让各哨兵判定下线/发起选举的时间错开，天然降低僵持概率。

**为什么至少 3 个哨兵**：2 个哨兵时 Leader 需 2 票（>2/2），挂 1 个就永远选不出 → 无法切换。

**作者踩坑经验**：**所有哨兵配置必须一致**，尤其 `down-after-milliseconds`——配置不一致导致集群对故障主库形不成共识，迟迟不切换，服务不稳定。

**每课一问**（1 主 4 从、5 哨兵、quorum=2，3 个哨兵挂了，还能客观下线和切换吗？——Kaito 实测）：
- **能判客观下线**：活 2 个哨兵互相确认，2 票 ≥ quorum=2 ✓
- **不能切换**：Leader 需 > 5/2=3 票，只剩 2 个哨兵怎么投都到不了 3 票 ✗
- 细节：选举投票有两种场景——a. A 先判 B 未判：B 没投过自己，会投给 A（A 得 2 票）；b. 同时判：各自投自己、互拒（各 1 票）。两种都凑不够多数
- **哨兵不是越多越好**：通信次数、机器故障面、选举耗时都随之增加
- **down-after-milliseconds 调大**：降误判但拉长不可用窗口，按业务权衡

## 二、设计问答

### Q1：哨兵之间是怎么互相发现的？

不需要互相配置地址。每个哨兵只配主库地址，然后往主库的 `__sentinel__:hello` 频道发布自己的 IP:port 并订阅该频道——其他哨兵从频道里看到它，建立连接。**复用 Redis 自身的 pub/sub 做服务发现**，零外部依赖。

### Q2：客观下线和 Leader 选举有什么区别？（常见混淆）

是两件事、两套阈值：**客观下线**看 `quorum`（多少个哨兵认为主库挂了）；**Leader 选举**要求 `>N/2 且 ≥quorum`（谁来执行切换）。先达成共识"主库死了"，再选"谁来办丧事"。评论区多人混淆——quorum 只管判断，选举多数派才管切换。

### Q3：Leader 选举的规则？为什么可能选不出？

想当选：自投 + 拉票；已投过自己的拒绝别人；未投过的投给第一个来拉票的。需同时满足 `>N/2` 和 `≥quorum`。多个哨兵同时参选各持 1 票 → 僵局 → 等 failover_timeout×2 后重选。缓解僵持：周期任务加随机偏移，让各哨兵行动时间错开。

### Q4：客户端怎么感知主从切换？

连哨兵订阅事件频道：`+odown`（客观下线）、`switch-master`（切换完成，含新旧地址）等。拿到 switch-master 后改连新主。支持哨兵的 SDK（Lettuce/Redisson）内置了这套订阅 + 连接管理——这就是为什么生产上客户端要配哨兵地址而不是写死主库 IP。

### Q5：哨兵挂了一部分，集群还能工作吗？

分两层看：判断客观下线——存活哨兵能凑够 quorum 就行；执行切换——存活哨兵能选出 Leader（>N/2）才行。5 哨兵挂 3（剩 2）：能判客观下线（quorum=2 可达），但永远选不出 Leader（需 3 票）→ **知道主库死了却没人能救**，最坏状态。

## 三、实践要点

- **哨兵 ≥ 3 个**，分散在不同机器/可用区；**所有哨兵配置一致**（尤其 down-after-milliseconds）——作者亲测的坑
- quorum 别乱调：quorum 同时约束客观下线判断和 Leader 选举的下限，3 哨兵配 2、5 哨兵配 2~3 是常见选择
- 客户端订阅 `switch-master` 做连接切换 + 切换期间本地缓存写请求（07 讲的"无感知"方案落地）
- 监控哨兵自身健康：哨兵全挂 = 主从切换功能整个失效（哨兵都挂了无能为力）
- 哨兵数量不是越多越好：3~5 个是甜区，再多选举变慢、故障面变大

## 四、深入追问

### Q1：哨兵 Leader 选举和 Raft 的关系？

核心规则同源：每任期一票（投过自己/投过别人就拒）、先到先得的投票倾向、多数派当选、僵局后随机退避重选（哨兵用"随机时间偏移"错开行动 ≈ Raft 的 randomized election timeout）。可以把哨兵集群理解为一个**用途特化的 Raft 集群**：它选出的"Leader"只管一件事——执行 failover。

### Q2：为什么 Leader 选举要求"≥quorum"这个下限？

防止"小团体政变"：如果 quorum=5 的集群里，2 个哨兵通过网络分区组成了多数（比如总共只有 3 个活着），没有 quorum 下限它们也能选出 Leader 执行切换——但 quorum=5 意味着管理员要求"5 票共识才算数"，小团体不满足条件就切不了。**quorum 是管理员对"多大共识才允许动数据"的显式声明**。

### Q3：INFO 在哨兵体系里扮演什么角色？（评论区源码党）

哨兵周期性地向主库和从库都发 `INFO`（sentinel.c 的 sentinelInfoReplyCallback）：从主库的 INFO 拿从库列表；从各从库的 INFO 拿 `run_id`、`slave_repl_offset`、`slave_priority`——**07 讲选主三轮打分的全部输入都来自这里**。监控信息流和决策信息流在 INFO 上汇合。

### Q4：和面经微服务模块的对照？

哨兵集群 ≈ 注册中心 + 健康检查 + 配置下发的合体：`__sentinel__:hello` 频道是服务发现（对照 Nacos 集群节点互知）、INFO 是健康检查、switch-master 事件推送 ≈ 注册中心变更推送。差异在**数据有状态**：哨兵决策要考虑复制进度（数据新旧），服务发现不用——这再次印证"带状态的系统选举更贵"（见 06/07 讲）。
