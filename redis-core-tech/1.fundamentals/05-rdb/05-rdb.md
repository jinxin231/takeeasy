# 05 内存快照：宕机后，Redis 如何实现快速恢复？

> 来源：极客时间《Redis 核心技术与实战》蒋德钧（基础篇 05）
> 整理日期：2026-11-13

---

## 一、内容总结

**RDB（Redis DataBase）= 内存快照**：把某一时刻的内存数据全量写入磁盘文件。恢复时**直接读文件载入内存**，避免 AOF 逐条重放命令的低效——**恢复快**是 RDB 的核心价值。

**三个关键问题**：

**① 给哪些数据做快照？——全量**
- 两个命令：`save`（主线程执行，阻塞所有请求）和 **`bgsave`**（fork 子进程后台执行，默认方式）
- save 的窘境：快照期间为保完整性只能处理读操作——暂停写不可接受

**② 快照时数据能修改吗？——写时复制（COW）**
- bgsave 子进程由主线程 fork 生成，**共享主线程的内存数据**（页表映射）
- 主线程读数据：父子互不影响
- 主线程**写**某块数据：该数据页被复制一份副本（C'），主线程在副本上改，子进程继续把**原数据**写入 RDB——既保快照完整性又不挡写
- **澄清（作者回复纠错）**：fork 拷贝的是**页表**不是物理内存；子进程读到的是**修改前**的原始数据，主线程把新数据写到**新的物理地址**并更新自己的页表映射

**③ 可以每秒做一次快照吗？——不行**
- 快照间隔 t 越小丢得越少，但频繁全量快照有两大开销：
  1. **磁盘压力**：频繁全量写盘，多个快照竞争磁盘带宽
  2. **fork 开销**：fork 本身阻塞主线程（页表拷贝，实例越大越久），频繁 fork 主线程频繁卡
- **增量快照为什么不做**：要"记住"哪些数据被修改 → 额外元数据开销（1 万个被改的键值对 = 1 万条记录；32 字节的键值对可能配 8 字节元数据）——对内存宝贵的 Redis 得不偿失

**Redis 4.0 混合持久化（鱼和熊掌兼得）**：
- 内存快照按一定频率执行，**两次快照之间用 AOF 记录增量操作**
- 快照不用频繁 → 避免频繁 fork；AOF 只记两次快照间的操作 → 不会过大，也避免重写开销
- 第二次全量快照时清空 AOF（修改已记入快照）

**AOF vs RDB 选择建议（作者三条）**：
1. 数据不能丢 → **混合使用**（推荐）
2. 允许分钟级丢失 → 只用 RDB
3. 只用 AOF → 优先 **everysec**（可靠性性能折中）

**每课一问**（2 核 CPU、4GB 内存、2GB 数据、写读比 8:2，用 RDB 有什么风险？——Kaito 置顶答案）：

- **内存风险**：快照期间 80% 是写 → COW 复制约 **1.6GB** 内存副本，加上原 2GB 接近 4GB 上限。开 Swap → 数据换到磁盘，访问性能"武功被废"；不开 Swap → **OOM**，父子进程被 kill
- **CPU 风险**：只有 2 核，父进程（含后台线程：AOF 刷盘、异步关 fd）已占一半以上，bgsave 子进程抢 CPU → 父进程请求延迟增大，子进程快照也变慢，整体性能下降
- **延伸：CPU 绑定（亲和性）的坑**：子进程继承父进程 CPU 亲和性，若父进程绑了核，父子必抢同一个核——**开了 RDB/AOF 重写的 Redis 不要绑核**（17 讲 CPU 结构展开）
- 补充维度：QPS 高低、**写操作的键值对范围**（集中改一小部分 vs 大范围改，COW 放大程度不同）

## 二、设计问答

### Q1：RDB 和 AOF 的本质区别？

RDB 是**数据快照**（二进制，某一时刻全量内存的镜像），恢复快（直接载入）但间隔期间的数据会丢；AOF 是**操作日志**（命令文本），数据更全（最多丢 1 秒）但恢复要逐条重放、慢。一个记"结果"，一个记"过程"——类似 MySQL 的全量备份 vs binlog 增量（评论区的贯通记忆法：AOF≈binlog 记操作，RDB≈全量备份记状态）。

### Q2：写时复制（COW）到底怎么工作？

fork 时子进程**复制父进程页表**，父子指向相同物理内存（不拷贝数据本身）。主线程写某页 → OS 复制该页（默认 4K）→ 主线程在新页上写、更新自己页表；子进程页表不变，继续读旧页。效果：子进程拿到 fork 时刻的完整快照，父进程写无感知。**代价**：快照期间写入越多，复制页越多，内存膨胀越厉害（最坏接近翻倍）。

### Q3：为什么 bgsave 不阻塞但还是不能频繁做？

bgsave 不阻塞的是"子进程写盘阶段"；**fork 瞬间**（页表拷贝）必阻塞主线程，且与实例内存大小正相关。加上频繁全量写盘的磁盘压力，快照频率只能在"丢数据窗口"和"系统开销"之间取平衡——分钟级是常见选择，秒级不可行。

### Q4：为什么增量快照不划算？

"记住哪些数据被改"需要元数据：每改一个键值对一条记录。键值对越小，元数据占比越高（32B 数据配 8B 元数据 = 25% 额外开销）。Redis 内存宝贵，不值得为快照频率付这个税——**混合持久化用 AOF 记增量，本质是用"命令日志"替代"修改元数据"，更省**。

### Q5：混合持久化恢复时怎么工作？

AOF 文件前半部分是 RDB 格式的全量快照，后半部分是两次快照间的增量命令。恢复：先快速载入 RDB 部分 → 再重放少量增量命令。兼顾 RDB 的恢复速度和 AOF 的低丢失率。配置：`aof-use-rdb-preamble yes`（4.0+ 默认开）。

## 三、实践要点

- **单实例内存别太大**：fork 阻塞 ∝ 页表大小 ∝ 内存；大实例拆分（Cluster 分片）比硬扛强
- **快照期间关注内存水位**：写多的业务，COW 会让内存最多接近翻倍——机器内存预留 ≥ 50% 空闲，`maxmemory` 留余量
- **关闭 Swap**：Redis 数据被换到磁盘 = 性能崩塌；同时监控 OOM 风险
- **不要给 Redis 绑核**（开了 bgsave/AOF 重写的场景）：子进程继承亲和性，父子抢同一个核
- 快照触发：`save 60 10000`（60s 内 1 万次修改触发 bgsave）；生产常把 RDB/AOF 放在从库做，减轻主库压力
- 云上实例：开混合持久化，恢复演练验证 RTO

## 四、深入追问

### Q1：fork 的阻塞能让子进程去做吗？（评论区的较真）

不能。①若子进程没把某块数据写入 RDB，主线程就改了它，**快照完整性被破坏**；②子进程复制数据时若加锁防主线程改，主线程写请求照样被锁阻塞——绕一圈回到原点。COW 的意义正是**免锁**：靠"写时复制页"把"改"和"读快照"物理隔离，谁都不等谁（除了被复制的那一页）。

### Q2：主线程 vs 主进程的称呼之争（评论区置顶）

Redis 启动后是一个进程，主体工作（接收请求、读写数据）在这个进程中完成——叫"主进程"可以；这个进程是**单线程的进程**，所以也叫"主线程"，突显单线程模式。多线程程序才不能这样混用。bgsave 是 fork 出的**子进程**（不是线程）。

### Q3：COW 期间 bigkey 为什么是放大器？

COW 以**内存页（4K）**为粒度复制。改一个 bigkey（比如几 MB 的 Hash）会涉及大量内存页 → 复制量大、分配新内存耗时 → 主线程在申请内存时阻塞变长。若开了 Huge Page（2MB 页），改 256B 也要拷 2MB——放大 512 倍。所以大 key 治理（面经 35）和关闭 Huge Page 是同一战役的两翼。

### Q4：与面经 34 讲"缓存一致性"的呼应？

面经里"缓存宕机重启后是冷数据，要限流保护 DB"的场景，恢复速度直接决定限流时长。RDB 快速载入 + 混合持久化把"冷启动"压缩到分钟级；再往上就是面经 35 的"集群互备 + 渐进切流"——**持久化决定了单机恢复的底，集群容错决定了系统恢复的顶**。
