# 03 高性能 IO 模型：为什么单线程 Redis 能那么快？

> 来源：极客时间《Redis 核心技术与实战》蒋德钧（基础篇 03）
> 整理日期：2026-11-13

---

## 一、内容总结

**先厘清"单线程"**：指**网络 IO + 键值对读写**由一个线程完成（对外服务的主流程）。持久化、异步删除、集群同步由额外线程执行——严格说 Redis 不是单线程，只是"单线程"叫起来酷。（更精确的说法：单线程的进程，见 10 讲答疑）

**为什么用单线程？——多线程的开销**
- 多线程期望：线程数↑吞吐率↑；现实：再增加线程吞吐率增长迟缓甚至下降
- 瓶颈：**共享资源的并发访问控制**。例：线程 A 对 List LPUSH（长度+1）与线程 B LPOP（长度-1），必须串行化否则长度错乱；粗粒度互斥锁让"并行变串行"，线程多了全在等锁
- 同步原语还降低代码易调试性、可维护性 → Redis 干脆单线程，**把并发控制问题连根拔掉**

**单线程为什么快？——三个设计选择的合力**
1. 大部分操作在内存完成
2. 高效数据结构（哈希表、跳表）
3. **IO 多路复用**——单线程也能并发处理海量客户端连接

**基本 IO 模型与阻塞点**（以 GET 为例的处理链）：
`bind/listen → accept → recv → parse → get → send`
潜在阻塞点两个：
- `accept()`：没有连接请求到达时一直等
- `recv()`：已连接但数据没到达时一直等
单线程一旦被这两个点卡住，所有客户端都饿死。

**非阻塞模式**：socket 支持非阻塞设置（监听套接字 accept 非阻塞、已连接套接字 recv 非阻塞）——但"不阻塞地返回"之后，还得有机制继续监听并在事件到达时**通知** Redis。这个角色由内核的 IO 多路复用扮演。

**IO 多路复用（select/epoll）**：
- 一个线程处理多个 IO 流：内核同时监听多个监听套接字 + 已连接套接字，有请求到达就交给 Redis 线程
- **基于事件的回调机制**：FD 上的事件（Accept/Read）被放入**事件队列**，Redis 单线程循环处理队列、调用对应回调函数（accept/get）——无需轮询，不浪费 CPU，响应及时
- 类比**医院分诊台**：内核 = 分诊台（登记、测温），Redis 单线程 = 医生（只看病）——一个医生效率也很高
- 跨平台：Linux select/epoll、FreeBSD kqueue、Solaris evport，按运行系统选实现

**每课一问：基本 IO 模型里还有哪些潜在瓶颈？**（评论区精华）
- **任一事件耗时，后面全排队**（单线程宿命）：bigkey 读写/删除、高复杂度命令（SORT/SUNION/ZUNIONSTORE、O(N) 且 N 大）、大量 key 集中过期、淘汰策略触发、AOF always 刷盘、fork 生成 RDB 瞬间
- **单线程读写客户端 IO 是同步 IO**：并发量极大时无法用多核分担 read/write 系统调用——这正是 6.0 引入 IO 多线程的原因（39 讲）
- 对策：业务规避慢操作；4.0 lazy-free 异步删 bigkey；6.0 IO 多线程

## 二、设计问答

### Q1：Redis 为什么用单线程？为什么不用 Netty 那样的主从 Reactor？

核心原因是**避免多线程的并发控制问题**（共享数据结构加锁，并行变串行）+ 实现简单、易调试维护。Redis 的前提是"内存操作足够快"，单线程不会成为数据存取的瓶颈，所以不需要业务线程池。6.0 之后网络读写/解析拆给了 IO 线程（因为网络硬件变快，IO 成了新瓶颈），但**命令执行仍是主线程**——可以看做主从 Reactor 的变体，只是刻意把"业务处理"留在单线程保无锁语义（呼应面经 36 讲追问 Q6）。

### Q2：单线程为什么能达到数十万 QPS？

①内存操作微秒级；②哈希表/跳表高效结构；③IO 多路复用：内核监听海量 FD，事件入队，单线程循环消费——没有 accept/recv 阻塞，没有轮询浪费，单线程的时间全部花在有效工作上。**单线程的敌人从来不是"单"，而是"堵"**。

### Q3：select/epoll 的回调机制怎么理解？

内核监测到 FD 事件（连接到达→Accept 事件，数据到达→Read 事件）→ 放入事件队列 → Redis 单线程从队列取事件、调用注册的回调函数处理。Redis 不需要主动轮询"有没有请求"，事件驱动把 CPU 从空转中解放出来。类比：分诊台（内核）预处理，医生（Redis）只看已分诊的病人。

### Q4：单线程模型下哪些操作会拖垮整个服务？（生产高危清单）

bigkey 操作、高复杂度命令（SORT/SUNION/ZUNIONSTORE、O(N) 大 N）、大量 key 集中过期、淘汰策略在主线程执行、AOF always 刷盘、fork（RDB/主从全量同步）瞬间阻塞。对策：业务规避 + lazy-free 异步删除 + 6.0 IO 多线程分流网络读写。

### Q5：fork 不是创建子进程吗，为什么会阻塞主线程？

bgsave/bgrewriteaof 用 `fork()` 创建子进程做快照——fork 瞬间要复制页表等元数据，实例越大（内存越多）页表复制越久，**fork 本身是主线程调用的**，所以阻塞主线程。子进程之后的写盘才是不阻塞的。"fork 这一下"是面试高频坑（18 讲延迟抖动展开）。

## 三、实践要点

- **单线程 = 所有慢操作都被放大**：命令上线前想一遍复杂度（见 02 讲口诀），大集合禁止全量操作
- 客户端超时设置别太短：单线程排队时 RT 会毛刺，过短超时 → 重试风暴 → 雪上加霜（呼应面经 07 超时控制）
- 规避"集中过期"：批量写入的 key 加随机 TTL（呼应面经 35 雪崩）
- 6.0+ 且网卡/连接是瓶颈时，开 `io-threads`（默认关闭）；但**能用 Cluster 扩容就别开**（面经 36 讲专题 4 决策框架）

## 四、深入追问

### Q1：epoll 的"事件队列"在 Redis 源码里对应什么？

Redis 的事件循环（aeEventLoop）每轮调 `aeApiPoll`（封装 epoll_wait）取就绪事件，然后逐个派发给文件事件处理器（acceptTcpHandler / readQueryFromClient / sendReplyToClient）。时间事件（serverCron，如过期清理、rehash 兜底）和文件事件共用这一个循环——所以 serverCron 里也不能有重活。

### Q2：与面经 36 讲的侧重点差异？

面经 36 讲从面试角度给了 epoll 三调用、中断机制、LT/ET、6.0 多线程细节（偏"怎么答"）；本讲从架构演进角度给了"为什么单线程"的决策链（多线程开销 → 并发控制 → 单线程 + 多路复用）。面试组合打法：**先讲决策链（为什么单线程）→ 再讲机制（多路复用怎么支撑）→ 最后给边界（什么时候单线程不够用 → 6.0 多线程）**。

### Q3：单线程模型对客户端有什么隐含要求？

单线程服务的 RT 分布天然有长尾（任一慢操作影响后续所有请求），所以客户端要：①连接池复用（避免频繁建连开销）；②超时 + 有限重试，重试带退避；③避免在 pipeline 里塞巨型批量命令（一个大命令堵一船人）。这也是 21 讲"缓冲区惨案"的伏笔——服务端给每个客户端维护输出缓冲区，大响应 + 慢客户端会把内存顶爆。
