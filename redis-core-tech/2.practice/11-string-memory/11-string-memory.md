# 11 "万金油"的 String，为什么不好用了？

> 来源：极客时间《Redis 核心技术与实战》蒋德钧（实践篇 11）
> 整理日期：2026-11-13

---

## 一、内容总结

**案例**：保存图片 ID（10 位数）→ 图片存储对象 ID（10 位数）的映射，8 字节 Long 就能表示的数，用 String 存却占 **64 字节**——数据本身小，**元数据开销喧宾夺主**。

**String 的内存开销拆解（64 字节从哪来）**：

**① SDS（简单动态字符串）**——含字符时的存储结构：
- `buf`：字节数组存实际数据（结尾自动加 `\0`，+1 字节）
- `len`（4 字节，已用长度）+ `alloc`（4 字节，实际分配长度）

**② RedisObject**——所有数据类型的统一元数据壳：
- 8 字节元数据（最后访问时间、引用计数等）+ 8 字节指针指向实际数据

**③ 三种编码方式（省内存的布局设计）**：

| 编码 | 场景 | 布局 |
|---|---|---|
| **int** | 64 位整数 | 指针位置**直接存整数**，省掉指针和 SDS |
| **embstr** | 字符串 ≤ 44 字节 | RedisObject + SDS **连续内存**，一次分配，避免碎片 |
| **raw** | 字符串 > 44 字节 | SDS 独立分配，指针指向 |

**④ dictEntry（全局哈希表项）**：3 个 8 字节指针（key、value、next）= 24 字节，但 **jemalloc 按 2 的幂就近分配**（24 → 32 字节）——申请 N 字节，分配 ≥N 的最小 2 次幂，减少分配次数

**案例算账**：两个 int 编码 ID 各 16 字节（8 元数据 + 8 整数值）= 32 字节 + dictEntry 32 字节 = **64 字节**。

**省内存方案：压缩列表（ziplist）**：
- 连续内存的 entry 序列，无指针开销。entry 结构：`prev_len`（前 entry 长度，<254 字节用 **1 字节**，否则 **5 字节**）+ `len`（4 字节）+ `encoding`（1 字节）+ `content`
- 表头 zlbytes/zltail/zllen，表尾 zlend（默认 255，所以 prev_len 的 1 字节模式上限是 254 不是 255）
- 例：8 字节 ID 的 entry = 1+4+1+8 = 14 字节，实际分配 16 字节

**集合类型省内存的本质**：String 一键值对一个 dictEntry（32 字节）；Hash 集合**一个 key 只有一个 dictEntry**，却能装下大量元素——dictEntry 开销被摊薄。

**二级编码法（单值键值对怎么塞进集合类型）**：
- 把单值 ID **拆两段**：前 7 位做 Hash 的 **key**，后 3 位做 Hash 集合内的 **field**，存储对象 ID 做 value
- 例：图片 ID `1101000060` → `HSET 1101000 060 3302000080`
- 实测：一条记录只增 16 字节（vs String 64 字节），**省到 1/4**；评论实测 100 万条：String 70MB → Hash ziplist **9MB**

**为什么"后 3 位"是有讲究的——ziplist 阈值**：
- `hash-max-ziplist-entries`（默认 512）：元素个数上限
- `hash-max-ziplist-value`（默认 64 字节）：单元素长度上限
- 超任一阈值 → 转哈希表，**且不可回退**（哈希表省内存不如 ziplist）
- 后 3 位 = 每集合 ≤ 1000 个元素 → 把 `hash-max-ziplist-entries` 设为 1000，**保证永远用 ziplist**

**每课一问（Kaito 答案：还能用什么类型？）**：
- **Sorted Set（勉强）**：ziplist 存（`zset-max-ziplist-entries` 设 1000），`ZADD 1101000 3302000080 060` + `ZSCORE` 查询。缺点：ziplist 按 score 排序，插入要定位（Hash 直接尾部追加）→ 插入性能差些
- **ziplist 的通病**：查询要遍历整个列表，元素不宜过多（阈值别设太大）；**级联更新**——修改一个元素超过一定大小，后续元素的 prev_len 连锁扩展重排（02 讲的坑）
- **重要权衡**：Hash/ZSet 只能**整个 key 设过期**（不能按元素过期）→ 等于把 Redis 当数据库用，必须保可靠性（备份/主从）；String 可按 key 过期 + maxmemory 淘汰，可当缓存用（DB 里再存一份映射兜底）。**选型看场景，没有银弹**

**工具**：redis-memory-calculator（输入键值对长度和类型，算实际内存开销）。

## 二、设计问答

### Q1：String 为什么"万金油不好用了"？

数据本身小时（如两个 Long ID），元数据（SDS 的 len/alloc、RedisObject 16 字节、dictEntry 32 字节）远超数据本身——64 字节里数据只占 16。**String 的开销是按 key 计的**，key 越多浪费越大。海量小键值对场景要换集合类型摊薄 dictEntry。

### Q2：int/embstr/raw 三种编码怎么理解？

String 按内容自适应编码：纯整数用 int（指针位直接存值）；短字符串（≤44B）embstr（一次连续分配）；长字符串 raw（SDS 独立分配）。判断依据可以用 `OBJECT ENCODING key` 查看。44 字节的来历：RedisObject 16B + SDS 头 3B + buf ≤ 44B + `\0` = 64B——正好卡在 jemalloc 一次分配 64 字节的档位。

### Q3：压缩列表为什么省内存？代价是什么？

省：连续内存无指针（链表每个节点两个指针 16 字节没了），entry 元数据最小 6 字节。代价：①查询 O(N) 遍历；②插入/修改可能**级联更新**（prev_len 连锁扩展）；③只能按整个 key 设过期。**时间换空间的典型**——所以阈值（512/64B）守住了才划算，别把阈值调太大。

### Q4：二级编码怎么设计？有什么坑？

设计：ID 拆"高位段做 Hash key + 低位段做 field"，低位段基数 ≈ `hash-max-ziplist-entries` 设定值（如 1000），保证集合永不转哈希表。坑：①高位段要分得**均匀**（ID 连续递增时低位变化快，选低位做 field 才对）；②拆分后**不能按记录设过期**；③查询要拼两段，业务代码有改造成本；④field 冲突不用担心——不同高位段落在不同 Hash 集合里。

### Q5：什么时候该用这个优化，什么时候是过度设计？

信号：**key 数量巨大（百万级+）× 单键值对小（几十字节内）× 内存成本敏感**。反例：key 几万、内存充足——64 字节 vs 16 字节的差距无感，二级编码带来的复杂度（查询拼接、过期失效、运维理解成本）不划算。**先算总账：key 数 × 48 字节差值 = 能省多少内存**，值这个钱再动手。

## 三、实践要点

- 查编码：`OBJECT ENCODING key`；查内存：`MEMORY USAGE key`（对比 String vs Hash 方案的实际开销）
- 阈值配置三兄弟：`hash-max-ziplist-entries/value`、`zset-max-ziplist-entries/value`、`list-max-ziplist-size`——想让小集合留在 ziplist，阈值和业务数据规模对齐
- **jemalloc 档位意识**：24B→32B、44B→64B，设计 value 长度时卡档位下沿（如 value 控制在 44 字节内保持 embstr）
- 大 Hash 集合（已转哈希表）不会转回 ziplist——上线前压测验证，别等转完再后悔
- Kaito 的选型矩阵：要按记录过期/淘汰 → String（当缓存）；能接受整 key 生命周期 → Hash/ZSet（当数据库，做好主从+备份）

## 四、深入追问

### Q1：ziplist 的级联更新具体怎么发生？

头部插入一个 ≥254 字节的 entry → 后一个 entry 的 prev_len 从 1 字节扩到 5 字节 → 该 entry 总长变大了 4 字节……如果它原来 250~253 字节，变大后超过 254 → 再下一个 entry 的 prev_len 也要扩 → **连锁反应**传遍全表，每次插入最坏 O(N²)。这是 ziplist 被 **listpack**（Redis 5.0 引入、7.0 全面替换）取代的核心原因——listpack 的 entry 记录的是**自己**的长度，反向遍历靠总长回推，彻底斩断级联。

### Q2：RedisObject 的 8 字节元数据里都有什么？

type（4bit）+ encoding（4bit）+ lru（24bit，LRU 时钟/LFU 计数——面经 32 讲淘汰策略的数据基础）+ refcount（引用计数，共享对象用）。所以"淘汰策略看 lru 字段""共享整数的 refcount"这些进阶话题都挂在这 8 字节上。

### Q3：和面经 32 讲"大 key 治理"的对照？

面经讲的是"单 key 太大"的治理（拆分、异步删），本讲是"**key 太多太小**"的治理（合并、二级编码）——两个方向的本质相同：**让元数据/数据的比例合理化**。大 key 是数据侧失控，小 key 海量化是元数据侧失控。面试把这两个案例一起讲，体现对 Redis 内存模型的完整理解。

### Q4：SDS 比 C 字符串强在哪？（基础但常考）

O(1) 取长度（len 字段）；杜绝缓冲区溢出（API 先检查 alloc 再扩容）；二进制安全（靠 len 判断结束，不怕内容含 `\0`）；空间预分配 + 惰性释放（减少 realloc 次数）。3.2 后按长度分 sdshdr5/8/16/32/64 五种头，小字符串头开销仅 1 字节——"根据字节长度划分得很细致"（评论区）。
