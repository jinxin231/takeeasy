# 37：云原生——MQ 的分层存储架构都有哪些实现方案？

> 整理日期：2026-11-06

## 一、内容总结

**先分清两个概念**（易混）：**存算分离**解决集群**弹性**问题（计算存储分两层）；**分层存储**解决**冷数据低成本**问题（本地存算一体不变，把老数据段上传远端，需要时再拉回来）。两者可组合（分离架构的存储层再做分层）。

**定义**：冷热分离——写入仍走本地分段，Broker 内置模块按策略把**老数据段上传到远程分布式文件系统**；消费时本地有就读本地，没有就从远端拉。一句话：**不动本地架构，把冷数据搬去便宜的地方**。

**成本账**（为什么诱人）：5TB 日常数据，分层后本地留 1TB + 远端 4TB。远端成本 ≈ 本地 1/3：`1×1 + 4×(1/3) = 2.3` vs 原来 5——**省一半**。

**但不是银弹**（代价两条铁律）：①远程存储性能**必然低于本地盘**；②引入第三方存储 → 它的稳定性**必然传导**到 MQ。技术优化能缓解不能根治。结论：**大流量、可靠性要求不极致的场景**用来降成本；性能/可靠性敏感场景别开。**可选项 + 用户可控开关**。

**技术实现四要点**：

**① 远程文件系统选型**：云厂商**对象存储**（S3/COS，稳定和成本最优，落地主流）；自建选 **HDFS**。

**② 生产性能**：写本地 + 异步上传 → **写入性能基本不受影响**；受影响的是异步线程占用的 CPU/内存/网卡/硬盘（见隔离性）。若实时写远端则性能必降（靠编码技巧弥补）。

**③ 消费性能（核心难点：数据在远端怎么读）**：
| 方案 | 机制 | 优点 | 缺点 |
|---|---|---|---|
| **一：下载到本地再读（近期主流）** | 异步线程按**预读算法**提前下载后续分段；消费只读本地 | 命中热读时**性能与非分层一致**；顺序消费让预读好设计（提前下一段） | 下载占硬盘空间/IOPS/带宽；**冷启动卡顿**（初始化/重置位点时数据不在本地，只能等下载——无法根治但可优化） |
| 二：远程流式直读 | 本地判断，在远端就 SDK 流式读，内存转 FetchRecord 返回 | 不占本地盘 IO 和空间 | 远程读性能必然低；占带宽；技术上难对齐方案一 |

**④ 隔离性与回滚**：
- 隔离（防上传下载挤垮主流程）：进程内无法强隔离，组合手段——**线程绑核**（CPU）、堆外内存/Direct IO（内存精控）、**限制同时上传下载的文件数和速度**（网卡）、**分盘**（写用 A 盘下载用 B 盘，IO 隔离但增运维复杂度）。落地版：线程数 + 速度限制 + 预读缓存优化为主，绑核/内存精控为辅
- **回滚（稳定性兜底）**：远端服务不可用时——①**暂停上传**（新段留本地，生产正常）；②**老数据消费报错，只允许消费新数据**。**回滚救不了老数据消费**，这是必须向用户明示的边界

**两家实现对比**：

| | Kafka（KIP-405，开发中） | RocketMQ（多级存储，早期） |
|---|---|---|
| 上传 | **异步**：段写满后异步上传分区数据段 | **准实时**：Dispatch 机制——TieredDispatcher 注册为 CommitLog 的 Dispatcher，消息引用写内存 Buffer 即返回，按 Queue 重建 CommitLog/ConsumeQueue 后持续上传 |
| 存储模型 | 直接上传分区段（Kafka 本来就是分区文件） | **要把 Broker 级共享 CommitLog 按 Topic/Queue 维度重构**（共享文件存储结构使然，见 05/11 讲） |
| 读取 | 官方未明确（理论同方案一/二） | 实时读 + **预读缓存**（仿 TCP 拥塞控制：**加法增、乘法减**控制预读量） |
| 组件 | RemoteLogManager（内部）+ RemoteLogMetadataManager（强一致远程段元数据，默认内部 Topic 实现）+ RemoteStorageManager（可插拔） | TieredMessageStore 实现读取接口，含故障恢复/上传进度/分层元数据 |

**为什么 RocketMQ 用准实时**（思考题）：它的存储是 **Broker 级共享 CommitLog**——按段异步上传没法直接对应到 Topic/Queue（一个段含所有 Topic 的数据），必须在写入时就按 Queue 维度重构出独立日志，所以顺势做成准实时分发上传。Kafka 本来就是分区独立文件，段写满异步上传即可。**存储结构决定分层方案**。

## 二、设计问答（Q&A）

### Q1：分层存储和存算分离的区别？

目标不同：分离为**弹性**（计算无状态），分层为**成本**（冷数据迁廉价存储）。架构不同：分离是计算/存储两层都常驻，分层是本地为主 + 冷数据异步归档。可组合：分离架构的存储层再做分层（BK 热层 → S3 冷层）。

### Q2：分层存储什么时候值得开？

成本账 + 容忍度：本地盘成本是远端 3 倍，数据保留越长越划算（7 天保留分层收益有限，30 天+收益显著）。容忍：①冷启动卡顿（重置位点/新消费组）；②远端故障时老数据消费中断。大流量、可靠性要求不极致的场景开；性能/可靠性敏感不开。**必须有开关和回滚预案**。

### Q3：两种消费读取方案怎么选？

近期选**方案一（下载本地读）**：顺序消费让预读天然好设计，命中热读性能对齐非分层；代价是硬盘/带宽占用和冷启动。方案二（远程流式直读）省本地 IO 但性能天花板低，等技术成熟再考虑。原则：**冷热分层的前提是"冷数据访问少"**——访问多的数据别分层。

### Q4：预读算法为什么"加法增、乘法减"？（RocketMQ 仿 TCP）

读远程数据延迟高且不稳定——预读量要像 TCP 拥塞窗口一样自适应：命中顺利就**加性增大**（多预读），超时/失败就**乘性减小**（退避防压垮）。这和 AIMD 控制网络流量同思想（联动 1.microservices 05 笔记限流算法）。

### Q5：回滚方案的硬伤是什么？怎么补？

硬伤：**远端故障时老数据消费中断**（新数据无碍）。补救：①消费端降级——老数据查询走离线通道（数据导出到 Hive/ES 的备份链路）；②双副本——关键业务冷数据不只存对象存储一份；③SLA 明示：分层数据消费可用性依赖远端 SLA。**分层存储的 SLA = min(本地 SLA, 远端 SLA)**。

### Q6：为什么存储结构决定分层方案？（思考题展开）

Kafka 每分区独立文件：段 = 分区的天然切割单元，段写满 → 异步上传，零改造。RocketMQ 共享 CommitLog：一段混所有 Topic——按段上传等于把所有 Topic 全量复制到远端（浪费且无意义），只能写入时按 Queue 重构成独立日志再传 → 准实时是必然。**分层方案的形态是被底层存储模型锁死的**——选存储结构时就要想好后路。

## 三、实践要点

1. 开启前测算：数据保留期 ≥ 30 天且冷访问 <5% 才值得；回滚预案（暂停上传 + 老数据降级）必须演练
2. 隔离基线：上传下载线程数限制 + 带宽限速 + 分盘（写/下载分离）
3. 消费端提示：重置位点到分层区间时给用户明确预期（冷启动延迟）
4. 监控：预读命中率、远端读 RT、上传进度 lag、远端存储可用性

## 四、深入追问

### Q1：分层存储下，分区的 retention 语义怎么变了？

本地 retention 变"热层窗口"，远端变"冷层窗口"——总保留 = 热 + 冷。清理变成两段：本地段滚动删（照常），远端段到期删（对象存储生命周期规则或自研清理）。消费透明：客户端不感知（ Broker 内部按位点路由本地/远端读）。**管理复杂度翻倍**：两套生命周期要对齐。

### Q2：分层存储对"重置消费位点重放历史"的影响？

重放冷区间 = 批量下载——消费速率被远端读性能限速（对象存储 GET 延迟 100ms 级，远低于本地盘），重放 TB 级历史要按天计。优化：批量并发下载 + 临时提高热层窗口（把要重放的区间先拉回本地）。**要重放历史数据的业务，分层窗口要覆盖重放范围**。

### Q3：RocketMQ 预读缓存"加法增乘法减"的具体收益？

直读远端时延迟波动大（对象存储 P99 远高于 P50）。固定预读量：小了冷启动多，大了浪费且故障时冲击远端。AIMD 让预读量随远端健康状况自适应——健康时多吃带宽提速，抖动时收敛保护。**把网络控制思想用于存储预取，是跨域迁移的漂亮案例**。

### Q4：对象存储的"请求成本"在分层存储里怎么算？

对象存储不止容量便宜，**请求按次计费**（GET/PUT per 1k 次）。高频小段上传下载会让请求费反超容量节省。优化：上传按段聚合（段级上传而非消息级）、下载预读聚合（一次拉整段）。**分层存储的成本模型 = 容量节省 − 请求费用 − 本地冗余成本**，要全算。
