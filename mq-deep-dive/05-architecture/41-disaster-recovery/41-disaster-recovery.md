# 41：容灾——如何实现跨地域、跨可用区的容灾和同步？

> 来源：极客时间《深入拆解消息队列47讲》许文强
> 整理日期：2026-11-06

## 一、内容总结

**容灾**：异常时服务自动切换并正常运行。**RTO**（容忍服务停止时间，越低越好）与 **RPO**（容忍数据丢失量，越低越好）——理想都为 0。两类：**集群内容灾**（主从切换）/ **集群间容灾**（主备集群切换）。

**集群内容灾三步**：①Broker 部署多可用区（运维活）；②**控制副本分布在不同可用区**（创建 Topic 时感知节点所属 AZ；**副本数建议 = AZ 数的倍数**，流量均衡）；③内核主从切换（15 讲机制）。
- RTO：**不可能为 0**（异常感知 → Controller 切 Leader → 客户端感知 → 写新 Leader，**最少秒级**）
- RPO：取决于一致性协议——**强一致 = 0**；最终一致 > 0；弱一致 > 最终一致（丢得更多）
- 集群内容灾**解决不了整个地域故障** → 需要集群间容灾

**集群间（主备）容灾**：
- 除地域故障，还解决**集群内部问题**（元数据丢失、Topic 负载异常致整集群不可用）
- 核心：**消息数据 + 元数据双向复制**（两条链路，可用连接器/事件驱动/Serverless Function 实现，思路一致 Runtime 不同）
- 复制组件部署三思路：**独立运行（推荐：不影响主备集群本体）** / 主集群复制 / 备集群复制

**客户端连接与主备切换**：
| 方案 | 切换方式 | RTO | 风险 |
|---|---|---|---|
| 直连 Broker | 改配置重启 | **分钟级** | 人工成本高 |
| DNS 域名 | 改 DNS 解析 | 受 DNS 缓存（默认 **10 分钟**）+ **长连接不断开**影响——**须确认解析更新后重启客户端** | 客户端可能滞留老集群 |
| **网关/虚拟 IP（推荐）** | 改网关后映射的 RS | **可秒级** | 注意：老集群**未消费数据短时不可消费**——消费端要支持**双集群消费或回溯消费** |

**双向同步两难题**：
1. **元数据以谁为准**：不是"当前主集群"（配置变更时主可能已换）——正确是"**变更时的主集群**"（难精准识别）；**实用方案：元数据只在主集群变更，备永远只同步**（复制方向不变，简单可靠）
2. **消息回环**：消息头加 **source 字段**标记来源集群——同步时：无 source → 同步；source = 目标集群 → 不投递；写入目标时设置 source = 源集群。四步判断防回环

**主备切换的 RTO/RPO**：RTO 必 > 0（网关方案理论秒级，直连分钟级）；**RPO 大多可为 0**（双向同步，未同步完的数据还在老集群不丢）。

**Kafka MirrorMaker（V2）**：独立部署、集群模式运行，**底层基于 Kafka Connector**（封装多个 Connector：数据、元数据、心跳、Checkpoint）。三类复制：消息数据、Topic/分区/配置元数据、**消费进度**（V2 新增，V1 无）。
- **消费位点同步的坑**：源/目标分区 **Offset 不一致**（过期清理导致目标 Offset 更大）→ 直接同步 ConsumeOffset 会错乱 → **要维护"源 Offset ↔ 目标 Offset"映射**（存内部 Topic），切换后按映射找准确位点。例：源 A4 offset=4 ↔ 目标 offset=14

**思考题 1（为什么集群内容灾不跨地域）**：跨地域网络延迟（数十 ms）+ 不稳定 → 主从同步复制延迟大、强一致写延迟不可接受、分区故障频繁触发切换。集群内容灾适合同城多 AZ（低延迟），地域级容灾交给主备集群（异步复制容忍延迟）。

**上节闭环补充**（作者对连接器的冷静判断）：MQ 连接器的意义是**生态闭环 + 轻量**（与自家 MQ 深度绑定），但 Flink CDC/DataX/SeaTunnel 等更专业——连接器需求不强是同质化竞争的结果。

## 二、设计问答（Q&A）

### Q1：RTO 和 RPO 分别由什么决定？

RTO = 故障检测时间 + 切换执行时间 + 客户端感知时间——集群内主从切换秒级起；跨集群切网关秒级、改 DNS/重启分钟级。RPO = 复制一致性——集群内强一致 0、最终/弱一致 > 0；跨集群异步复制时未同步部分留在老集群不丢（双向同步下 RPO ≈ 0）。

### Q2：集群内容灾为什么副本数建议 AZ 数倍数？

副本按 AZ 均匀分布时，任一 AZ 故障后剩余 AZ 的副本承接流量均衡。非倍数会导致某 AZ 副本多、故障后该 AZ 剩余节点压力翻倍。**均衡是规划出来的，不是切换时调出来的**。

### Q3：主备集群为什么要双向同步而不是单向？

主备会**切换**：备升主后要能接管写入，此时老主恢复后要能追平新数据——复制方向必须双向可逆。单向同步在切换后就断裂（老主成备却收不到新主的数据）。双向同步的关键配套：消息 source 标记防回环。

### Q4：消费位点同步为什么是硬骨头？

位点 = (group, topic, partition) → offset，但**同一条消息在主备分区的 offset 不一样**（各自过期清理节奏不同 + 复制起点不同）。同步位点必须先建**主备 offset 映射**（MirrorMaker 存内部 Topic），切换后按映射换算。没有映射直接搬 offset = 消费错乱（重复或跳过）。

### Q5：元数据同步"以变更时的主集群为准"为什么难落地？工程上怎么妥协？

难在：配置变更和主备切换可能同时发生，"变更那一刻谁是主"是个**有竞态的历史判断**——可能双方都认为自己是主（脑裂期），各自的变更冲突无法合并。工程妥协：**元数据变更锁定在一个权威源**（主集群），备只读同步——把并发写冲突从设计上消除（单写者原则）。

### Q6：思考题 2——Pulsar Geo Replication 和 MirrorMaker 异同？

同：异步复制 + Topic 级配置 + 主备消费位点映射。异：①Pulsar **Broker 内建**（namespace 级 geo-replication 配置即可，不用独立组件），MirrorMaker 是独立应用（Connect 集群）；②Pulsar 有 **replicated-subscription**（订阅级复制）和主动/被动模式；③Pulsar 的复制在 broker 写路径上（性能优但耦合），MirrorMaker 走消费-生产（解耦但多一跳）。Pulsar 模式侵入小运维轻，MirrorMaker 模式独立性好。

## 三、实践要点

1. 容灾配置基线：副本数 ≥3 且为 AZ 倍数 + 跨 AZ 分布 + 强一致（核心业务）
2. 主备切换客户端方案：**网关/VIP**，别用改配置重启；DNS 方案要处理缓存和长连接
3. 切换演练必测：消费位点映射正确性、未消费数据的回溯消费、元数据单写者纪律
4. RPO=0 的前提是双向同步 + 强一致写主集群；弱业务可放宽

## 四、深入追问

### Q1：跨集群容灾的元数据为什么不能双写？

双写 = 两个权威源：网络分区时两集群各自接受变更 → 元数据冲突无法合并（Topic 配置 A 还是 B？）。**元数据只能单写者**——主集群写、备集群同步。切换时权威转移（新主成为新权威），旧的变更历史靠复制连续性保证。这是"配置即状态"系统的通用纪律（同 16 讲 Controller 单写）。

### Q2：主备切换后，位点映射表本身怎么保证不丢？

映射表存**内部 Topic**（自带副本和持久化）——和 `__consumer_offsets` 一个思路（元数据即日志，27 讲）。MirrorMaker 的 Checkpoint Connector 负责定期持久化映射。备集群提升为主后，映射表也随 Topic 复制存在，切换后可继续用。**自救设施本身也要高可用**。

### Q3：为什么"老集群未消费数据短时不可消费"？怎么解？

切到备集群后，客户端从新位点消费备集群数据；老集群里**尚未复制到备集群的尾部消息**暂时无人消费。解法：①切换前尽量等复制追平（lag 监控，RTO 与 RPO 的权衡点）；②消费端支持**双集群并行消费**（同时订主备，去重靠幂等）；③支持回溯消费（事后回老集群补）。实践中 lag 接近 0 才切换是标准纪律。

### Q4：容灾和"多活"的区别？

容灾（主备）：一主一备，备不承载生产流量，切换有 RTO。多活（同城双活/异地多活）：**多集群同时服务**，按单元/地域分流，无切换概念——要求数据模型和业务设计支持（单元化、就近写入、跨地域同步防冲突）。容灾是多活的前置能力；多活是更高阶的架构选择，成本和复杂度都高一个量级。
