# 38：Serverless——如何基于 Serverless 架构实现流式数据处理？

> 来源：极客时间《深入拆解消息队列47讲》许文强
> 整理日期：2026-11-06

---

## 一、内容总结

**问题背景**：MQ 上下游数据流（数据源 → 总线 → 目标）要多种方案并存（Spark/Flink 计算、CDC/DataX 集成、Logstash 清洗、MQ 自带容灾组件）——**每种方案场景不同，学习运维成本高**。Serverless Function 提供了"一个平台承接多种数据流"的可能。

**数据流四场景**：

| 方向 | 需求 | 代表方案 | 短板 |
|---|---|---|---|
| 计算 | 流式计算/聚合/转储 | Spark/Flink | 学习运维成本高，简单 ETL 场景 ROI 低 |
| 集成 | 数据源→目标同步 | Flink CDC/SeaTunnel/DataX | 复杂计算要引 Spark/Flink；底层还是重引擎 |
| 清洗 | 简单格式化分发 | Logstash/MQ Connector | 功能单一 |
| 容灾 | 集群间数据同步 | Kafka/RocketMQ Connector、Pulsar IO、RabbitMQ Federation/Shovel | 各自为政 |

**Serverless 本质**：不是"没有服务器"，是**客户不关心服务器**（部署、调度、扩缩容、故障平台全包）。
**Serverless Function**：跑在平台上的函数段——用熟悉的语言写函数提交即运行。生命周期六步：编写代码段 → 定义事件（什么触发）→ 触发事件 → 部署（打成小镜像进 K8s）→ 输出结果 → **销毁资源**。与 Spark 对比：语法零学习（原生语言）、免打包发版、免运维。

**数据处理流程**：流入/流出层的多组件 → 换成 **Serverless Function 平台**。清洗场景：函数消费数据 → 处理 → 写下游。**小流量时 Cron/单进程跑，大流量时提交到平台跑——代码零改动**。

**底层原理**：
- **事件触发三形式**：事件触发（数据源主动触发，实时性最强）、定时触发、流式拉取——互补关系
- **运行平台 = K8s + 容器**：函数封装进镜像 → 调度 Pod 运行 → 自动扩缩容
- **成本逻辑：下沉 + 规模效应**——业务波峰波谷交错，多业务共用平台实现资源复用。所以**建议用公有云 Serverless 产品**（规模效应，自建 Knative 无成本优势）

**优劣势**：优势（免运维、弹性、按量付费）；劣势（**技术处于快速完善期、稳定性待打磨、冷启动**——容器缩到 0 时事件触发要重新拉起）。适用：图片处理、**小流量流式处理、事件型流处理**；暂不能全面替代重引擎。

**两个实战案例**：
1. **日志清洗（ETL）**：合作方日志打包传 HDFS，数据量大、波峰波谷明显、成本敏感。老架构 HDFS+Logstash+Spark 按峰值备机（低峰浪费）。新方案：事件触发函数解压 + Python 函数清洗——**平台按流量曲线调度，省近 40% 成本**
2. **事件流处理**：中台审核（图片/文本审核、打标、死链监测）要**实时**（违规内容窗口期曝光风险）。消息接 RabbitMQ → **事件推模式触发函数**——Push 的反压问题（高峰下游处理不过来）恰好被 Serverless 的**近乎无限弹性 + 按量付费**化解

**长期改进方向**：函数持久化运行态（流处理需要常驻）、更多事件源、**丰富的扩缩容因子**（Kafka 堆积数、仓库图片数等业务指标，不只 CPU）、高阶算子封装（开箱即用）。

## 二、设计问答（Q&A）

### Q1：Serverless Function 相比 Spark/Flink 解决什么问题？

解决**简单数据流的成本问题**：Spark 功能强但学习运维重，简单 ETL/清洗场景 ROI 低。Function 用原生语言写几十行代码提交即跑，免打包免运维，按量付费。定位：**轻量数据流的性价比方案**，不是替代 Spark 的复杂计算。

### Q2：事件触发、定时触发、流式拉取怎么选？

**事件触发**（实时性最强）：违规审核、实时告警——数据源主动推，延迟秒级；**定时触发**：批式任务（日志打包处理）；**流式拉取**：持续数据流（Kafka 消费）。选择按"数据到达形态"：有明确事件源用事件，批量文件用定时，持续流用拉取。

### Q3：Serverless 平台省钱的原理？

**下沉 + 规模效应**：单业务有波峰波谷（峰值备机低峰浪费），多业务错峰共用平台资源池 → 利用率拉平提升。所以公有云 Serverless 天然比自建便宜（它们的资源池大、客户多）——**自建 Serverless 拿不到规模效应的红利**。

### Q4：事件流案例中 Serverless 为什么能解 Push 反压？

传统 Push 模型：下游处理有瓶颈 → 数据反压 → 服务端推不动。Serverless 函数**弹性近乎无限**（平台储备）：高峰自动扩容出更多函数实例消费，瓶颈被容量吸收，按量付费只付实际用的。反压问题从"调优问题"变成"钱的问题"，而峰值时段短，钱很少。

### Q5：Serverless 做流式处理的硬伤？

①**冷启动**：实例缩到 0 时触发要重新拉起（秒级延迟），实时敏感场景要预留最小实例数（用预留实例换冷启动）；②**函数是短生命周期**——流处理要常驻消费，需要"持久化运行态"（业界在补）；③**扩缩容因子单一**（多按 CPU），MQ 场景要按**消息堆积**扩缩容才准；④稳定性在完善期。

## 三、实践要点

1. 适用边界：小流量流处理、事件型任务（图片/审核）、波峰波谷明显的批处理——优先 Serverless；复杂计算/有状态流处理留 Spark/Flink
2. 成本验证：对比"峰值备机成本" vs "Serverless 按量成本"（案例省 40%）
3. 实时场景：预留最小实例防冷启动；扩缩容因子配业务指标（Kafka lag）而非仅 CPU
4. 函数设计：无状态、幂等（重试必然重复）、单职责

## 四、深入追问

### Q1：Serverless Function 和 MQ 消费组是什么关系？

可以互相替代轻量场景：Function 事件触发 ≈ 消费者（平台自动扩缩 ≈ 消费组弹性）。差异：消费组是**常驻**长连接消费（低延迟、位点精细管理）；Function 是**按事件拉起**（弹性无敌、有冷启动、位点管理粗放）。融合形态：MQ 触发器（Kafka trigger）——平台按 lag 扩缩函数实例，是消费组的 Serverless 化。

### Q2：为什么"扩缩容因子"是流式 Serverless 的关键？

流式负载的正确信号是**积压量**（Kafka lag、队列深度），不是 CPU——CPU 低可能是在等下游，lag 高才是真忙。按 CPU 扩缩会误判。平台要支持自定义指标（lag、队列深度、仓库文件数）作为扩缩容因子，才能让弹性用在刀刃上。

### Q3：Serverless 的"持久化运行态"为什么难？

Function 设计哲学是**无状态短任务**（用完即毁）。流式处理要常驻：①消费位点要持续提交（状态）；②常驻意味着弹性语义变化（不能像短任务随意回收）；③常驻实例的调度成本接近普通容器，失去 Serverless 的成本优势。解法方向：函数内做 checkpoint（位点/状态外置到 MQ/存储），回收可恢复——**状态外置让长任务也变可弹性**。

### Q4：自建 Serverless（Knative）为什么不划算？

Serverless 的成本优势 = 规模效应（多租户错峰复用）。单企业自建：自己的业务峰谷有限，资源池利用率提升有限；还要养平台团队（K8s + Knative + 镜像仓库 + 调度）。**结论：Serverless 是云厂商的游戏**，用户买服务就好——除非你是超大企业有自有数据中心闲置资源。
