# 36：云原生——业界 MQ 的计算存储分离是如何实现的？

> 来源：极客时间《深入拆解消息队列47讲》许文强
> 整理日期：2026-11-06

---

## 一、内容总结

**定义**：计算层（协议解析、事务、延时、压缩等功能逻辑，吃 CPU）与存储层（存储结构、消息格式、数据分段等持久化）是否在同一台机器。
- **存算一体**（Kafka/RocketMQ/RabbitMQ 现状）：同一 Broker 内计算+存储，交互就是本地文件读写（FileChannel）。**有状态服务**——架构简单、开发成本低，但**无法快速弹性扩缩容**（扩缩要搬数据）
- **存算分离**：计算层集群 + 独立存储层集群，经网络协议交互。计算层**无状态** → 弹性好；代价：架构复杂、研发运维成本高、**多一跳网络性能下降**

**可选项还是必选项？（作者的判断：可选项）**——用户画像说话：
| 用户类型 | 核心诉求 | 对存算分离的需求 |
|---|---|---|
| 中长尾企业（≈80~90% 的三类用户） | 稳定、能用、免运维 | 无感 |
| 大型企业核心业务 | 稳定性、恢复速度第一；弹性成本第二梯队 | 弱 |
| **云服务提供商** | 弹性+成本 = **核心竞争力** | **刚需（必走之路）** |

有趣现象：大会文章里喊存算分离最凶的都是云厂商——他们有这个需求。符合二八原则。**理想形态：可插拔存储结构**（存算一体/分离可选）。

**存储层引擎三选一**（存算分离的核心是选存储引擎）：

| 引擎 | 优点 | 致命短板 | 适用 |
|---|---|---|---|
| 对象存储（S3/COS） | 可靠 + **成本极低** | 读写不灵活、流式性能低 | 冷数据/分层存储（37 讲），实时热数据难 |
| **分布式存储服务**（HDFS/BookKeeper/阿里盘古/腾讯 CFS） | 分布式可靠 + **读写性能高** + 多语言流式 API | 集群自身稳定性要保障 | **MQ 存储层主流**（Pulsar-BK） |
| 云盘 | 远端多副本、接口像本地盘 | **绑定单节点**——分区迁移/Leader 切换要卸载再挂载，**服务停顿，几乎无解** | 不适合高频切换场景 |

**分区存储模型**：分离架构基本选**每分区独立"文件"**——网络读取下，共享文件要维护**二级索引 + 随机读**（性能降），独立文件顺序读写。**模型设计依赖存储引擎选型**（Pulsar 用 Ledger 就是跟着 BookKeeper 的概念走）。

**计算层无状态写入**：存储层有多副本 → **计算层分区不再要副本（副本下沉）**，计算层 Topic 永远单分区。写入两模式：元数据寻址（Pulsar，分区绑 Broker）/ **服务端转发**（RocketMQ 5.0 Proxy 无状态随机写再转发——分离架构下转发变常用）。计算层调存储层 SDK 的编码功力（线程/批量/安全，见 18 讲）。

**两条产品路径对比**：

| | RocketMQ 5.0 | Pulsar |
|---|---|---|
| 本质 | **Proxy 模式，非真存算分离**（Proxy 只转发，计算存储仍在 Broker）——演化第一步，历史包袱重 | **原生存算分离**（设计之初就选 BookKeeper） |
| 存储层 | 原 Broker 集群（自己的分布式存储） | Apache BookKeeper |
| 下一步 | 计算逻辑上移 Proxy，Broker 纯存储化 | — |
| 分区模型 | 大概率沿用现有（改动太大） | 分区 = 多个 Ledger，Ledger = 多个 Entry，Ledger 多副本分布 Bookie |
| 弹性 | Proxy 无状态写入已就绪 | Broker 绑分区但**迁服务权不迁数据** + **自动负载均衡**（Controller 检测负载自动迁 Topic）+ **Bundle** 批量迁移 |

**Pulsar 选 BookKeeper 三原因**：①BK 就是为高性能分布式**流日志**（Append 模型）存储而生，与消息数据特点天然吻合；②流式读写高性能 + 分布式可靠；③Pulsar 核心开发者多来自 BK 团队。

**计算层弹性三关键**：①**快速迁移**——不搬数据（存算分离天然满足）；②**自动迁移**——内核自动调度（Pulsar Controller 按负载均衡策略迁 Topic）；③**高效迁移**——**Bundle**（Namespace 与 Topic 之间的逻辑分组，批量迁移避免 Namespace 太粗、Topic 太碎）。

**思考题答案（Bundle 的价值）**：迁移的**粒度控制**——Topic 级迁移元数据变更太频繁（万级 Topic），Namespace 级太粗；Bundle 把一组 Topic 聚成一个调度单元，负载均衡批量高效。

## 二、设计问答（Q&A）

### Q1：存算分离的核心优势和代价？

优势：**弹性**（计算层无状态，扩缩容不搬数据）→ 资源利用率高 → 成本低。代价：架构复杂度（多一套存储集群）、多一跳网络 IO（性能略降）、研发运维学习成本。**80~90% 的用户用不到这个优势**——所以是可选项；云厂商把它当核心竞争力，所以是必走之路。

### Q2：为什么加了 Proxy 的 RocketMQ 5.0 不算存算分离？

判定标准：**计算逻辑和数据持久化在哪**。RocketMQ 5.0 的 Proxy 只是转发层（gRPC 接入），事务、消费、存储全在 Broker——数据路径多了一跳代理，本质没变。真分离 = Broker 无状态化 + 存储独立成层（Pulsar 的 Broker + BookKeeper）。**别被架构图的"分层"骗了，看数据在哪落盘**。

### Q3：存储引擎为什么主流选分布式存储服务而不是对象存储？

MQ 热路径是**高频小批量追加写 + 低延迟顺序读**。对象存储按对象读写（PUT/GET 整对象），流式小写性能差、请求成本高——适合冷数据归档（分层存储，37 讲）不适合热日志。云盘绑单节点，Leader 切换要卸载挂载（服务停顿无解）。分布式存储服务（BK/HDFS/盘古）提供流式 API + 多副本 + 高性能，正好。

### Q4：存算分离下副本概念去哪了？

**副本下沉**：计算层分区单副本无 Leader/Follower，可靠性由存储层（Ledger 多副本）承担。计算层故障 = 换台 Broker 接管服务权（元数据变更）；存储层故障 = 存储集群自己补副本。**两层故障独立处理**——这是分离架构容灾的结构性红利。

### Q5：为什么分离架构倾向每分区独立文件？

存算一体时共享文件（CommitLog）靠 page cache 和本地预读掩盖随机读；分离架构**读要走网络**，共享文件需要二级索引定位 + 随机读——网络随机 IO 的代价被放大。独立文件顺序读写，把网络 IO 也变成流式的。

## 三、实践要点

1. 选型决策树：自建/中小规模 → 存算一体（Kafka/RocketMQ 够用）；云上弹性刚需 → Pulsar 或 RocketMQ 5.0+ Proxy 过渡
2. 评估存算分离先算三笔账：扩容耗时、峰谷利用率提升、研发运维增量成本
3. 存储层压测重点：写确认延迟、连续读、随机回放、跨 AZ 网络抖动、故障恢复时间
4. Pulsar 弹性验证：kill 一台 Broker，观察 Bundle 迁移耗时与业务影响

## 四、深入追问

### Q1：存算分离和分层存储（37 讲）的组合关系？

两层远程化：存算分离把**热存储**抽出（弹性），分层存储把**冷数据**再迁到对象存储（成本）。组合后：计算层 → BK/热层 → S3/冷层。收益叠加（弹性 + 成本），故障域也叠加（两个远程依赖），读延迟分层：内存 < BK < S3。

### Q2：计算层"无状态"是真无状态吗？

不是绝对无状态。Broker 仍有**软状态**：分区归属（Bundle 分配）、写缓冲、读缓存、订阅游标。只是这些状态**可快速重建**（元数据 + 存储层拉取），不像存算一体的数据必须跟随节点。准确说法：**无硬状态（无不可迁移状态）**。

### Q3：RocketMQ 演进到真存算分离的最大障碍？

历史包袱：①CommitLog 存储模型与 Broker 深度耦合（计算逻辑直接操作文件/MMap）；②Remoting 客户端与 Broker 的丰富交互（事务、位点、重试）要全部上移 Proxy；③NameServer 路由模型要改造。**每一步都要兼容存量**——这就是"演化"比"原生"难的原因（对照 Pulsar 一张白纸）。

### Q4：Bundle 和 Redis Cluster 的 slot 是不是一个东西？

思想完全同构：**逻辑分片与物理节点的间接映射层**。slot（16384）让 Redis 数据迁移以槽为单位；Bundle 让 Pulsar 服务权迁移以组为单位。共同收益：调度粒度从"单实体"（key/Topic）聚合为"批量单元"（slot/Bundle），元数据变更量和迁移成本可控。再往外看：分库分表的逻辑表-物理表、ES 的 shard 分配——**间接层是分布式系统调度的通用解**（呼应 3.mq 24 笔记的槽分配）。
