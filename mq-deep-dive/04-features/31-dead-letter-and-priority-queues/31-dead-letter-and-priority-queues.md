# 31：死信队列和优先级队列——如何实现？

> 来源：极客时间《深入拆解消息队列47讲》许文强
> 整理日期：2026-11-06

## 一、内容总结

**死信队列本质：是功能不是队列**。三种形态：**生产端**（写入失败 → 转存他处，避免写入阻塞）、**Broker 端**（数据过期未消费 → 转存防丢）、**消费端**（处理一直失败 → 投递他处，避免消费阻塞）。最常用：生产失败 + 消费失败。意义：**把业务自定义的复杂重复工作收进 MQ 内部**，降低业务成本。

**死信目标存储**：默认同集群另一 Topic；业务自实现可选其他引擎/跨集群（集群异常时保数据流稳定）；**内核 SDK 一般只支持同集群 Topic**（集成其他引擎让 SDK 臃肿，长期维护成本高）。

**三场景实现**：
- **生产死信**（客户端 SDK）：重试耗尽 → 判断启用死信 → 写死信队列，业务正常返回。伪代码即 try/catch + deadLetterProducer.send
- **消费死信**：处理失败重试 → 达最大次数 → 投死信队列 + **正常提交位点**消费下一条
- **Broker 死信**：过期/删除逻辑上加死信判断，投递目标队列（实现同延时消息，见 29 讲）
- 要点：**生产和消费死信都在客户端完成，服务端基本无参与**

**业界支持**：仅 RocketMQ（消费死信：重试耗尽自动投内部特殊 Topic）和 RabbitMQ（**DLX 死信交换机**：消息被拒绝/过期/队列满 → 重发 DLX，绑定 DLX 的队列即死信队列）。投递目标都是本集群资源。

**优先级队列**：发消息带优先级，**消费端一定先拿高优先级消息**（不管发送顺序）。场景：头部/腰部/尾部客户通知。

**实现两路径**：
- **业务层模拟**：每优先级一个分区/Topic，消费端优先读高优先级——缺点：优先级级别不灵活、冗余多 Topic、客户端逻辑复杂
- **内核实现**（合理）：①协议加 priority 字段；②内核保序。内核三思路：**优先级排序索引**（数据正常写分区，另维护按优先级排序的索引，消费先查索引定位——常用）；全量重排序（资源消耗大）；分优先级分文件（改存储模型，改动大）
- **索引方案两问题**：①数据结构——只有排序没有搜索需求 → **排序链表**；排序算法选**归并**（大数据量稳定；MQ 优先级固定阶梯）②持久化——**建议不持久化**：源数据在分区，索引丢失就读分区重建（Leader 切换时新主重建）。内存评估：节点存分区号+位点+优先级（12B），100 万条 ≈ 11MB，100 队列/节点 ≈ 1.1G
- **RabbitMQ 实现**：`x-max-priority` 建队列定最大优先级；消息带 priority；内核用**优先级堆 + 子队列**（每优先级一子队列，消费从高到低检查）。注意大量使用优先级队列会降性能

## 二、设计问答（Q&A）

### Q1：死信队列的本质和价值？

本质是**功能不是队列**：处理失败的数据自动转存，主流程不阻塞。价值在于把"失败兜底"从业务代码下沉到 MQ SDK——业务自定义也能做，但每业务重复造且易错。三形态：生产失败转存、过期转存（Broker）、消费失败转存。

### Q2：消费死信为什么要"投死信 + 正常提交位点"？

不提交位点：毒消息卡死分区，后续消息全堵（见 3.mq 25 笔记毒消息）。投死信 = 把失败消息**移出主通道**存档待查，位点正常前进。死信 = 隔离病房，不是垃圾桶——要配监控和人工修复通道。

### Q3：死信目标为什么不推荐第三方引擎？

内核 SDK 集成 MySQL/ES 写入逻辑 → SDK 臃肿、耦合其他引擎的可用性、维护成本高。同集群 Topic 复用 MQ 自身存储分发，最内聚。真要跨引擎：用"消费死信 Topic → 转发服务 → ES/MySQL"的间接层，而不是 SDK 直写。

### Q4：优先级队列为什么内核实现优于业务模拟？

业务模拟（分区/Topic 当优先级）：级别变动要重建拓扑、客户端要维护"级别→通道"映射、扩缩容复杂。内核实现（优先级索引）：协议加字段 + 内存排序索引，业务零感知。MQ 优先级通常固定几级——**归并排序**稳定且大数据量性能好，索引不持久化（重建便宜）。

### Q5：优先级队列为什么只有 RabbitMQ 支持？

需求频率低 + 与"顺序写日志"存储模型冲突（优先级要打乱写入序）。RabbitMQ 的实现也克制（子队列 + 堆，官方自己都警告大量用会降性能）。**FIFO 是 MQ 的性能之本，优先级是奢侈品**——多数场景用多 Topic 分流（快/慢通道）就够了。

### Q6：上节闭环——为什么 MQ 事务不用 3PC/TCC？

3PC 多的一步（询问资源）在 MQ 无意义：生产/位点提交只需保证操作成功，没有"资源预留"概念。TCC 要业务实现 Try/Confirm/Cancel 三态接口——中间件不能把这种改造成本推给通用业务。所以选 **2PC + 回查**（悬挂由 Broker 回查解决）。

## 三、实践要点

1. 死信上线三件套：死信 Topic 命名规范（`%DLQ%group`）+ 死信监控告警 + 重放工具
2. 消费失败处理链：本地重试 → 重试队列（阶梯延迟）→ 死信——别一步到位
3. 优先级需求先评估能否用"多 Topic 快慢通道"替代内建优先级队列

## 四、深入追问

### Q1：死信消息什么时候应该重放（requeue）？

重放条件：故障根因已修复（依赖恢复/数据修复）+ 重放速率受控（防二次冲击，限速 + 批量）+ 防循环（记录重放次数，超限人工）。RocketMQ 运维侧的"死信重投"和 RabbitMQ 的 shovel 插件是现成工具。**重放是运维动作不是自动机制**——自动重放死信等于把炸弹搬回客厅。

### Q2：优先级索引和延时消息的时间轮能否复用？

思想同构（都是"额外索引/调度结构改变投递顺序"），但结构不同：优先级是**静态属性排序**（优先级堆/排序链表），延时是**时间维度轮转**（时间轮）。有趣的合并场景：优先级 + 延时双重调度（先按时间到期，同级别按优先级出队）——自研调度器时可选多级结构。

### Q3：RabbitMQ 优先级队列为什么性能差？

每优先级一个子队列：写入要判断入哪个子队列，消费要按序检查各子队列——**队列管理开销 × 优先级数**。x-max-priority 越大越慢。且优先级打破 FIFO 的批量顺序读写优化（段内连续读变成跳读）。官方建议 x-max-priority 别超 10。

### Q4：生产死信在客户端做，集群切换时死信数据怎么办？

客户端死信写在**集群 A 的死信 Topic**——集群 A 恢复前这部分数据不可用。增强：①死信 Topic 写在**独立高可用集群**（死信通道比主通道更耐死）；②SDK 双写本地磁盘兜底（最极端情况）；③恢复后对账补投。核心认知：**死信通道是你最后的退路，它的可靠性要高于主通道**。
