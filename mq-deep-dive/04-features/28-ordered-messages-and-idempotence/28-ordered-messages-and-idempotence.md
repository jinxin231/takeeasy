# 28：顺序消息和幂等——如何实现顺序消息和数据幂等？

> 来源：极客时间《深入拆解消息队列47讲》许文强
> 整理日期：2026-11-06

---

## 一、内容总结

**顺序消息定义**：时间顺序性——生产端发出顺序 = 消费端接收顺序（**以 Broker 接收顺序为准**）。

**为什么难**：MQ 底层是**顺序写文件**（无 B 树——复杂结构影响读写性能，且 MQ 不需要复杂检索），理想模型是"按序发→按序存→按序消费"。现实三破坏：
1. **多生产者**：发送时间和网络延迟不同 → 落盘顺序不可保
2. **单生产者异步发送**：多线程 + 失败重试 → 到达顺序 ≠ 发送顺序
3. **多分区**：分区分配策略把消息打散 → 消费顺序不可控

**实现三要素**：**单一生产者 + 同步发送 + 单一分区**。前两者保生产端有序（前一条成功才发下一条），后者保消费端有序。

**水平扩容与顺序的矛盾 → 局部有序**：真实业务很少要全局有序——binlog 订阅只要表/行级有序。解法：**给需有序的数据同一标识**（Kafka/Pulsar 的 Key、RocketMQ 的 MessageGroup、RabbitMQ 的 RouteKey），同标识进同分区。缺点：标识数据量不均 → **写入倾斜**（服务端难解，客户端打散又失序）。彻底解法（消费时重排序）复杂且性能低，MQ 很少用。

**幂等的定义与分类**：接口幂等 = 调多少次结果都一样。MQ 幂等分**生产幂等**（同消息只保存一份）、消费幂等（位点机制天生幂等——不提交就一直返回同一条；消费端谈的更多是 Exactly Once，事务讲）、管控幂等。

**生产幂等的核心问题**：**Broker 怎么识别两条消息是同一条？** 关键澄清：消息唯一性以 **Producer 的 send 调用**为准（send 两次 = 两条消息，即使内容相同；send 一次被底层重传 = 同一条）。

**方案一：消息唯一 ID**：
- 客户端生成 MsgID（**Snowflake**——64 位 = 符号位+时间戳+数据中心 ID+机器 ID+计数器；MQ 场景可把后两段换成**集群 ID + TopicID**）；UUID 太长且可能重复、集中式 ID 引入 SDK 复杂度
- Broker 存已收 MsgID 判重。技巧：①**Topic 维度**分集合保存（查询加载快）；②只保留**生命周期内**的 ID（消息过期，ID 集合也过期——复用 TTL）；③**布隆过滤器**提判重性能
- 前提：同 MsgID 必须落同分区（按 Key Hash）

**方案二：生产者 ID + 自增序号**：
- (ProducerID, seqnum) 二元组唯一标识。ProducerID 可 Snowflake/UUID
- 朴素版要存全量 seqnum 集合（与方案一复杂度相同）。**技巧：只保留最新 seqnum**——收到 current+1 才写入；跳号（来 8 等 5）两策略：缓存等待（可能永远等不到 → 内存风险）或**返回可重试错误**让客户端重发

**Kafka 幂等的真实实现**：
- PID **从 Broker 申请**（Broker 经 ZK 生成自增 ID——避免客户端直连 ZK 的复杂度）
- **四元组（PID, Topic, Partition, seqnum）**——seqnum 是**分区维度独立**的；Batch 语义下每批一个 seqnum
- Broker **只缓存最近 5 个 batch**（hardcode）：判重循环比对，重复拒绝
- **不是完全幂等**：缓存被挤掉后旧消息重发会判为不重复写入。取舍：主打高性能，不能为幂等拖垮写入——**缓存少量换大多数情况幂等**
- 为什么分区维度 seqnum：全局维度下大分区快速刷掉小分区的缓存，幂等失效；内存账 T = P(分区数) × M(生产者数) × N(缓存条数)，P/M 不可控 → N 只能小（5）

**对比 MySQL 排序（思考题闭环）**：MySQL 用 B+ 树索引保序（写入时维护有序结构）+ 查询时 filesort——**写入时保序 vs 查询时排序**的路线之争：MQ 选写入时保序（存储简单快），DB 两者皆有。

## 二、设计问答（Q&A）

### Q1：顺序消息的三个必要条件？

单一生产者（多生产者时序无法协调）、同步发送（异步重传会乱到达顺序）、单一分区（多分区消费顺序不可控）。工程化落地 = 局部有序：同标识（Key/MessageGroup/RouteKey）进同分区，保住水平扩容。

### Q2：局部有序的数据倾斜怎么办？

服务端难解（倾斜是业务分布造成的）。选择：①接受倾斜 + 监控（多数实践）；②客户端打散（放弃顺序）；③复杂结构消费端重排序（性能差，少用）。**顺序与均匀是同一标识上的矛盾**——没有免费午餐。

### Q3：生产幂等的本质难题？

Broker 无法区分"客户端主动 send 两次"和"send 一次被重传"——所以唯一性必须以 send 为准，客户端给标识。两方案：消息唯一 ID（MsgID 去重，Broker 存 ID 集合 + BF）vs PID+seqnum（只存最新序号，跳号拒绝/缓存）。Kafka 用后者。

### Q4：Kafka 幂等为什么只缓存 5 个 batch？代价是什么？

内存账：T = 分区数 × 生产者数 × N，分区和生产者都不可控 → N 必须小（hardcode 5）。代价：**不完全幂等**——缓存挤出后旧消息重发会被当新消息。定位匹配：Kafka 是高性能流管道，幂等是"大多数情况兜住重试重复"，不是金融级去重。真要完全幂等：业务层唯一索引/BF（见 3.mq 27 笔记）。

### Q5：为什么 Kafka 的 seqnum 是分区维度？

全局 seqnum 下，流量大的分区会快速把共享缓存刷掉，小流量分区的幂等记录被挤出 → 完全失幂等。分区维度各自独立缓存，互不影响。**缓存的隔离粒度要跟数据倾斜的粒度一致**。

### Q6：Snowflake 怎么用在消息 ID 上？

64 位 = 符号位 + 时间戳 + 数据中心 ID + 机器 ID + 计数器。唯一性靠"数据中心 + 机器"段唯一。MQ 场景替换为**集群 ID + TopicID**——Topic 维度唯一即可（业务只要 Topic 内有序去重）。优势：趋势递增（可当时间排序用）、无中心依赖、本地生成快。

## 三、实践要点

1. 顺序需求先问"全局还是局部"——90% 是局部（订单/用户/表维度），用 Key 分区方案
2. Kafka 幂等开启：`enable.idempotence=true`（自动 acks=all、max.in.flight≤5、重试>0）——理解其边界（非完全幂等）
3. 完全幂等需求 → 业务层去重（唯一索引/BF/Redis），别指望 MQ 内建
4. 生产幂等调试入口：重复消息先看 PID/seqnum 缓存命中率

## 四、深入追问

### Q1：为什么"查询时重排序"不适合 MQ？

MQ 是流式吐出（消费者持续拉），重排序要**等齐一个窗口的数据**再排——引入不确定延迟（慢分区拖累整体）；且排序要缓冲 + 比较，内存和 CPU 成本高。DB 场景查询是"一问一答"有边界，排序可控；MQ 消费是无边界流。**流式系统保序的成本在写入端最低**（写入时就排好），这是 MQ 选写入保序的深层原因。

### Q2：Kafka 幂等 + 事务的关系？

幂等是基础：事务消息（跨分区原子写）构建在幂等之上——PID+seqnum 提供单分区去重，事务协调器 + `__transaction_state` 提供跨分区原子。幂等管"不重"，事务管"都成或都不成"。**没有幂等，事务的重试会引入重复**。

### Q3：跳号时"返回可重试错误"会不会死循环？

场景：seqnum 5 永远丢失，6 来了被拒 → 客户端重发 6 → 还是被拒 → 循环。解法：①重试上限后放弃（这条链路的后续消息也会因缺 5 被拒 → 要**重置会话**：客户端重启申请新 PID）；②Broker 侧超时跳过（等 N 秒 5 没来就接受 6，容忍缺口）；③Kafka 实际策略：Producer 超时/重启 → 新 PID 重来。**序号链断了就换链，别修链**。

### Q4：消费端 Exactly Once 为什么难？（预告 30 讲事务）

消费 = 读消息 + 处理业务 + 提交位点三步，业务和位点是两个系统——跨系统原子就是分布式事务。Kafka Streams 的 exactly-once 是把"处理结果 + 位点"写进同一事务（都是 Kafka Topic 才成立）。业务写 DB 的场景只能靠幂等（去重表）。**EOS 只在"输入输出都是 Kafka"时成立**。
