## 一、内容总结

功能篇开篇：往集群里加功能。本讲四块：静态/动态配置、集群与节点元数据、Topic 与分区支持、消费分组进度管理。（假设集群基于 ZK。）

**① 静态/动态配置**：
- 静态配置：YAML/JSON/Properties，启动加载——变更要重启，重操作场景不行
- 动态配置两方案：
  | 方案 | 机制 | 优劣 |
  |---|---|---|
  | 第三方组件（ZK） | /config 持久节点 + Watch 监听变更。两种监听：**逐节点监听**（立即生效）/ **通知节点**（/config/notification，先改再生效，更灵活） | 合理但引入依赖；Kafka/Pulsar 用（架构里本就有 ZK） |
  | 本地文件热加载 | 监听文件变更即生效 | 无依赖、简单；集群要逐台改，要发布系统/内置变更接口辅助。RocketMQ 用（NameServer 无存储和 Watch） |

**② 集群和节点元数据**：
- 集群元数据最少两字段：**ClusterId + ClusterName**。ZK `/cluster` 持久节点；首台 Broker 启动触发初始化（生成 ID 写入）
- 节点元数据最少三字段：**BrokerID + IP + Port**。**要用 BrokerID 而非 IP+Port 标识节点**——容器/云环境 IP 会复用，可能误识别集群
- 存储：每 Broker 一个 ZK 临时节点（/brokers/brokerID），优于全塞一个节点（分开管理、互不影响、防单节点数据过大）

**③ Topic 和分区**：
- **必须有**：性能——单分区有瓶颈无水平扩容；Topic = 组织分区的逻辑层。RabbitMQ 无 Topic 但 Exchange+Route 起同样作用
- Topic 元数据三要素：**TopicID、TopicName、Replica**（分区号 + Leader + 副本分布）。存储：/topics/topicX 持久节点；集群启动选各分区 Leader，节点变动触发切换并更新
- 选主/建 Topic/分区分布计算见 15 讲

**④ 消费进度管理**：
- 特性：**低查询（初始化拉一次）+ 高更新（每次消费都提交）**
- 存储格式：**（消费分组 + Topic + 分区号）三元组 + offset**。JSON vs 行/二进制格式——差异在空间占用和搜索效率；数据量不大，**建议 JSON**（可读性优先）
- **保存机制四方案**：
  | 方案 | 优劣 | 使用者 |
  |---|---|---|
  | 存 ZK | 最简单（分布式一致性自带） | 分组/消费者多时占空间 + **频繁更新压垮 ZK** | Kafka 早期 |
  | 存本地文件 | 性能好、容量够；**单机故障丢进度**，要跨节点同步一致性（=副本问题） | RocketMQ |
  | **存内部 Topic** | 特殊 Topic 只存位点；位点"只保留最新值"→ **Topic 压缩（compaction）**按 Key（group-topic-partition）只留最后一条；+缓存/索引/二分提速 | **Kafka 现行（__consumer_offsets）** |
  | 存其他引擎 | MySQL/Redis——本质同 ZK，性能和稳定性不足；为位点单独引入组件增加复杂度 | Pulsar（存 BookKeeper——存算分离天然自带引擎，零新增成本） |

**上节课闭环（Pulsar 弱 ZK 的决策思考）**：引入别的引擎只缓解不根治（ZK 的问题其他引擎也会有），且架构复杂度不降；真正答案是去第三方（Kafka KRaft）。Pulsar 走可插拔是因为**去 ZK 工作量太大，不适合其快速发展阶段**——可插拔改动小、能引入 etcd/RocksDB/内存覆盖集群化/单机/测试多场景。

## 二、设计问答（Q&A）

### Q1：Topic 和分区为什么必须存在？

分区是存储和并行的最小单位（单分区有性能瓶颈）；Topic 是组织多分区的逻辑层（让扩容对用户透明）。没有 Topic：用户直接面对分区，扩容要改代码；没有分区：单通道无并发。RabbitMQ 无 Topic，但 Exchange+Route 承担同样的"逻辑分组"职能。

### Q2：节点标识为什么用 BrokerID 不用 IP+Port？

容器/云环境 IP 会被复用——节点销毁后新节点可能分到同 IP，客户端把两个集群/节点搞混，出现串集群的诡异故障。**身份标识必须是不变的逻辑 ID，不是可变的网络地址**。

### Q3：消费进度四种保存方案怎么选？

跟架构走：有 ZK/协调服务且量小 → 存 ZK；高吞吐分组多 → **内部 Topic + 压缩**（Kafka 路线，自举）；架构极简 → 本地文件（RocketMQ，接受单机故障风险）；存算分离 → 复用存储层（Pulsar-BK）。客户端自管进度才存第三方引擎（MySQL/Redis）。

### Q4：Kafka 位点为什么从 ZK 迁到内部 Topic？

ZK 写入走 Leader + 共识，offset 提交是高频写（每消费都提交）——ZK 被打爆。内部 Topic：offset 提交 = 写消息，享受 Kafka 自身的批量/顺序写/副本/压缩。Topic 压缩（compaction）按 group-topic-partition 为 key 只留最新值——**日志压缩把"更新"语义映射成"追加 + 保留最新"**，完美契合 append-only 存储。

### Q5：动态配置"通知节点"为什么比逐节点监听更灵活？

逐节点监听：写入即生效——改错配置立刻全集群生效，没有缓冲。通知节点：**先改配置不生效，确认无误后写通知节点统一生效**——多了一道"确认闸门"，支持灰度和回滚编排（先改不生效 → 观察 → 再生效）。生产配置的变更是高危操作，灵活方案给运维留了操作空间。

## 三、实践要点

1. 元数据设计从最小集起步：ClusterId+Name / BrokerID+IP+Port / TopicID+Name+Replica——功能扩展再加字段
2. 位点管理选型默认跟生态：Kafka 用内置 Topic 别改 ZK；自研 MQ 优先内部 Topic 方案
3. 配置变更纪律：先改再生效（通知节点模式），防误改即时扩散

## 四、深入追问

### Q1：思考题——元数据存 MySQL 的增删改查流程？

写路径：管理操作 → SQL 事务写 MySQL（强一致好做）→ **通知问题**是短板（MySQL 无 Watch）→ Broker 定时轮询版本号/更新时间戳（或加一张变更通知表 + 轮询），延迟秒级。读路径：Broker 启动全量加载 + 定时增量同步。结论：能跑但**通知靠轮询，变更生效慢**；且 MySQL 单点/主从延迟引入新问题。所以没人用 MySQL 做元数据——**Watch/通知能力是协调服务与数据库的本质区别**。

### Q2：Topic 压缩（compaction）能保证"只留最新"吗？

不能实时保证——压缩是**后台异步**的（cleaner 线程），压缩前旧值仍在日志里。所以 compaction Topic 的正确读法是**读到底（log end）再取每 key 最新**（Kafka 消费者内部处理）。另外压缩按 segment 内做，跨段旧值要等段合并。语义是"最终只留最新"，不是"实时只留最新"。

### Q3：为什么 RocketMQ 选本地文件存位点而 Kafka 不敢？

架构基因：RocketMQ 位点文件在 **Broker**（服务端存——消费进度跟 Broker 走，Broker 主从同步带走位点文件）；Kafka 位点跟着**协调者/分区**走，需要一个全局一致的视图——本地文件做不到跨 Broker 一致。**位点放哪，取决于"谁来回答'我消费到哪了'"**。

### Q4：元数据节点"一节点存全部 vs 每实体一节点"怎么权衡？

集中存：一次读全（快），但写要整节点更新（大实体写放大、并发冲突、超 ZK 单节点 1MB 限制）。分开存：写小、可并发、可分别监听；读取要多次（可本地缓存弥补）。结论：**按"实体"分节点（每 Broker/Topic/Group 一个子节点）**——元数据模型就是树形目录，让变更的粒度最小化。
