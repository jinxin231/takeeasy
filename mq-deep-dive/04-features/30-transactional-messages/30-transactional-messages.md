# 30：事务消息——如何实现一个完整的事务消息模块？

> 来源：极客时间《深入拆解消息队列47讲》许文强
> 整理日期：2026-11-06

## 一、内容总结

**事务概念**：一批操作的集合，要么全成功要么全失败。ACID 中**原子性是事务的独特标识**（一致性/隔离性/持久性其他场景也有）。**注意：不同引擎的事务语义不一样**，别把 MySQL 事务想当然套到 MQ。

**MQ 事务的操作集合**：核心操作是生产/消费/管控，值得事务化的组合：生产事务、消费事务、生产+消费、**消费+处理+生产**（流场景）。

**四家事务形态**（同一个"事务消息"，语义全不同）：

| MQ | 事务范围 | 机制 |
|---|---|---|
| RabbitMQ | **生产事务** | **Channel 维度**：通道设事务模式，消息缓存，commit 才投递 Exchange，rollback 则不投递 |
| RocketMQ | **生产 + 本地事务** | 半消息：先发事务消息（Commitlog 持久化但**不可见**）→ 本地事务完成二次确认（可见）→ **Broker 主动回查**客户端本地事务状态。仅 Transaction 类型 Topic 可用 |
| Kafka | **生产事务（跨 Topic/分区原子写）** | **事务 ID 维度**（多生产者可同 ID）；消息先存不可见，提交后可见；状态存 `__transaction_state` 内置 Topic |
| Pulsar | **消费+处理+生产**（流场景原子性） | 思路同 Kafka（事务 ID + 内部 Topic 记录状态），提交后生产可见 + 消费位点提交——**Kafka 事务升级版** |

三个共性：**都是两阶段（准备/确认）；生产消息先不可见、提交后可见**。

**分布式事务理论**：
- **2PC**：请求阶段（参与者执行不提交，报结果）+ 提交阶段（协调者全员成功则提交，否则回滚）。缺陷：同步阻塞、单点故障、数据不一致
- **3PC**：拆准备为 CanCommit（预估不执行）+ PreCommit（执行不提交）+ DoCommit；引入超时（参与者超时会**自动提交**——协调者发回滚但参与者没收到时不一致）
- **TCC**：应用层 Try（检查+预留资源）/Confirm（用预留资源执行）/Cancel
- **MQ 事务 = 2PC 的实现**

**MQ 事务三技术要点**：

**① 事务状态存储**：状态要持久化和查询。推荐**内部 Topic**（Kafka `__transaction_state`、Pulsar 同）——复用分布式存储能力零新增；RocketMQ 存 Commitlog；RabbitMQ 无集中存储（靠 Channel 上下文）

**② 事务协调者设计**（优雅方案）：选谁当协调者 → 存状态 → 通知各 Broker 提交/回滚。Kafka/Pulsar 的做法：**内部 Topic + 事务 ID 哈希定分区 → 分区 Leader 所在 Broker 即协调者**——协调者的选举和故障转移复用分区 Leader 机制，不用单独实现。客户端与该 Broker 交互写状态；提交时协调者内部接口通知各 Broker。

**③ 不可见→可见机制**（两思路）：
- **另存再转**（RabbitMQ）：消息先存别处，提交时写入真 Topic——同延时消息的转储思路
- **原地标记（主流）**：消息按原流程写入目标 Topic，带事务 ID 标记不可见。难点：顺序存储**消息内容不可改** → 引入**独立数据结构存事务状态**，消费时判断
- 消费遇未提交事务消息怎么办：**卡住等**（简单、保序、可能消费卡顿——事务过期再跳过）vs **跳过继续**（快、乱序、要维护未确认消息列表，复杂）——按"是否要顺序 + 消费速度"选

## 二、设计问答（Q&A）

### Q1：MQ 事务和 MySQL 事务的区别？

MySQL 事务：单机一批 SQL 的 ACID。MQ 事务：**分布式事务**，操作集合因产品而异（RabbitMQ/Kafka 只管生产批写入原子；RocketMQ 管生产+本地事务协同；Pulsar 管流式消费-处理-生产）。用之前先搞清该引擎的事务覆盖什么操作——**名称相同，语义不同**。

### Q2：RocketMQ 的回查机制解决什么？

两阶段里"客户端本地事务完成后没发二次确认"（宕机/网络断）——Broker 的半消息一直不可见会卡住。Broker 主动**回查**客户端"你本地事务到底成没成"，按结果提交或回滚。**回查 = 2PC 协调者对参与者的超时兜底**（防止参与者状态悬挂）。细节见 3.mq 26 笔记的自建方案。

### Q3：事务协调者为什么用"事务 ID 哈希 → 分区 Leader"当？

复用分区机制：协调者要存储（内置 Topic 分区就是存储）、要故障转移（分区 Leader 切换就是协调者切换）、要分散负载（事务 ID 哈希天然分散到多分区）。**不另造轮子，一切复用分区原语**——这是 Kafka/Pulsar 设计的优雅之处。

### Q4：为什么 MQ 事务不用 3PC/TCC？（思考题）

3PC 的超时自动提交在 MQ 场景反而引入不一致（网络分区时参与者自作主张）；TCC 把 Try/Confirm/Cancel 推向业务方——MQ 作为中间件要为**通用业务**服务，没法要求业务实现三态接口（改造成本太高）。2PC 的问题（阻塞、悬挂）由**回查机制**弥补——MQ 的选择是"2PC + 回查"，在通用性和可靠性间最优。

### Q5：未提交事务消息"卡住等"和"跳过"怎么选？

卡住等：保序、实现零成本、可能卡顿（事务悬挂时）——顺序消息场景必选。跳过：消费快、乱序、要维护未确认列表持续检查——高吞吐无序场景。Kafka 用 `isolation.level=read_committed` 时消费者**跳过**未提交/已中止消息（read_uncommitted 则全见）——它的答案是不卡。

## 三、实践要点

1. 选型速记：要"发消息+写库"一致 → RocketMQ 事务消息；要多分区原子写 → Kafka 事务；流处理 EOS → Pulsar/Kafka Streams
2. 用 Kafka 事务必知：`isolation.level=read_committed` 消费端才不看未提交消息
3. 事务消息有性能代价（状态存储 + 协调 + 回查），非必要不用

## 四、深入追问

### Q1：2PC 的"同步阻塞"在 MQ 事务里怎么体现和缓解？

体现：事务未决期间消息不可见（占用存储且挡消费）、协调者持有状态。缓解：①**事务超时**（超时自动回滚，RocketMQ 回查 + Kafka transaction.timeout.ms）；②未决消息跳过机制（不阻塞正常消费）；③协调者分片（事务 ID 哈希到多分区，协调压力分散）。

### Q2：Kafka 事务的 zombie fencing 是什么问题？

同一 transaction.id 的新生产者上线（旧的可能还活着——GC 停顿后苏醒）→ 两个生产者用同一 ID 写，状态错乱。解法：**epoch 机制**——新生产者注册时 epoch+1，旧 epoch 的写被 Broker 拒绝（fencing）。和分布式锁的 fencing token 同一思想（见 4.cache 37 笔记）。

### Q3：RocketMQ 半消息为什么存 Commitlog 而不是单独存储？

写入路径零分叉：半消息 = 普通写 Commitlog（顺序写高性能）+ 属性标记不可见；消费时过滤。单独存储（如 RabbitMQ Channel 缓存）则写路径分叉、持久化语义要重做。**复用主存储 + 状态标记 > 另建存储**——和"可见性用标记"方案同源。

### Q4：消费+处理+生产事务（EOS）的边界在哪？

Pulsar/Kafka 流事务的原子范围 = **消费位点 + 产出消息**，都在 MQ 内才成立。处理过程中的**外部副作用**（写 DB、调 HTTP）不在事务内——外部系统不支持 MQ 事务协议。所以"端到端 EOS"的宣传要打折：只在"输入输出皆 MQ"的纯流链路成立，涉及外部系统仍要幂等。
