# 29：延时消息——如何实现高性能的定时/延时消息？

> 来源：极客时间《深入拆解消息队列47讲》许文强
> 整理日期：2026-11-06

## 一、内容总结

**场景与定义**：订单 30 分钟未支付自动取消。直观方案（DB + 定时扫描）的问题：业务要维护定时任务和扩缩容、数据量大性能差、精度低。**理想：延时逻辑下沉到底层引擎（MQ）**，业务零感知。定义：发设置了到期时间的消息，到期才可被消费。表现：Broker 先持久化 + **标记不可见** → 到期变可见。

**技术拆解四部分**：数据存储（基础篇）、**如何让消息可见**、**定时机制**、主动推送（基础篇）。重点讲中间两个。

**如何让消息可见**——临时存储三选（独立数据结构/独立 Topic/本地引擎 RocksDB/Mnesia），到期转可见两思路：
| 思路 | 机制 | 优劣 |
|---|---|---|
| **定时检测写入（主流）** | 独立线程检测到期 → 写入真实 Topic | 主流程改造小；量大时**到期不够精准** |
| 消费时判断 | 消费时查第三方存储有无到期消息 | 省定时线程；消费 QPS 高，每次检测有性能问题 |

**定时机制** = 定时器（推进时间：while+sleep / Timer / DelayQueue / Go Timer）+ **延时消息定位处理**（每刻度高效取到期消息，关注添加/获取时间复杂度）。真实需求六条：任意精度（毫秒级）、任意时长（月/年）、数量大（百万级）、添加获取复杂度低、可靠不丢、内存占用可控。

**方案一：轮询检测**（独立存储 + while+sleep 定时器 + 独立线程检测）：
- 数据结构复杂度对比：链表（插 O(1)/取 O(n)）、排序链表和堆（插 O(nlogn)/取 O(1)）、红黑树（插取都 O(logn)）
- **分治缓解**：按时间维度拆多个存储（1h/6h/12h/1天/>1天），降每个结构长度
- 优点：实现简单成本低；缺点：精度粗。够用——**业界多数 MQ 用它**

**方案二：时间轮**（多级时间轮 + 刻度挂延时消息索引链表）：
- 四效果：**插入获取都 O(1)**、任意精度、任意时长、每刻度任意多元素
- 核心思想：时间分多维度（年/月/日/时/分/秒）多级轮子；上一级最小刻度 = 下一级刻度总和；添加找刻度挂链表尾，到期取整条链表
- **工程难点**：内存控制、**持久化与多节点同步**、低成本实现——参考 Kafka 的延时机制（多级时间轮 + DelayQueue 推进，性能空间俱佳）
- 理论更优但实现成本高——这是多数 MQ 选轮询检测的原因

**四家实现**：
| MQ | 方案 | 细节 |
|---|---|---|
| **RocketMQ** | 轮询检测 | `SCHEDULE_TOPIC_XXXX` 内置 Topic，**18 队列对应 18 固定级别**（1s~2h）；原 Topic/Queue 存消息属性里；18 个定时任务每 100ms 检查对应队列，到期投递真 Topic |
| **RabbitMQ** | 轮询检测两路 | 死信队列（队列 TTL + 死信 Exchange 转发）；延迟插件（Mnesia 暂存 + 定时投递） |
| **Pulsar** | 轮询检测取巧 | **Delayed Message Tracker**（堆外内存优先级队列，按延迟时间堆排序，最短在头部）；**消费时触发检测**（消费线程当检测线程）；Broker 宕机/Leader 切换重建 delayed index |
| **Kafka** | **时间轮**（但不支持延时消息） | 延时机制用于延时回包/延时确认；多级时间轮 + DelayQueue |

## 二、设计问答（Q&A）

### Q1：延时消息的技术拆解？

四部分：数据存储（先持久化）、可见性控制（临时存储 + 定时检测写入/消费时判断）、定时机制（定时器 + 定位处理）、到期投递。重点在定时机制的数据结构——轮询检测（简单、精度粗）vs 时间轮（O(1)、任意精度时长，但工程难）。

### Q2：RocketMQ 为什么是 18 个固定级别而不是任意时间？

轮询检测方案的精度-复杂度折中：固定级别 → 每级别一个队列 + 一个定时任务，顺序扫描极简；任意时间要排序/索引，复杂度上升（且 18 级别覆盖 90% 业务）。**用功能受限换实现极简**——业务可适配固定级别，不值得为任意延迟上时间轮。

### Q3：时间轮为什么难落地？

算法好懂，工程难：①内存控制（百万级消息的索引驻留内存要精打细算，所以只能存索引不存消息体）；②**持久化与多节点同步**（时间轮状态宕机丢失要重建，多节点不共享状态）；③实现成本（Kafka 的 HierarchicalWheelTimer + DelayQueue 组合是参考答案）。

### Q4：Pulsar 的"消费时检测"为什么没性能问题？

Delayed Message Tracker 是**堆外内存的优先级队列**（堆排序，取头部 O(1)）——检测只是看一眼队首时间戳，代价极小。且 Tracker 随 Topic 维度在 Broker 内存/堆外维护，重建机制兜底故障。取巧点：**借消费动作当定时器**，省了独立线程。

### Q5：思考题——延时消息的存储结构按 Topic 独享还是共享？

参考 05 讲存储结构之争：延时消息**量级远小于主消息流**，且到期要批量取——**Broker 级共享存储**（一个延时存储引擎 + 按时间索引）更合理：①独立引擎独立生命周期（清理/备份简单）；②到期扫描不用遍历每 Topic；③RocketMQ 实践即是（SCHEDULE_TOPIC 单 Topic 18 队列共享）。按 Topic 独享只在隔离性要求极高时考虑。

## 三、实践要点

1. 选型默认：RocketMQ 固定级别够用就别追任意时间；Kafka 环境用外置方案（见 3.mq 23 笔记）
2. 延时精度口径写进 SLA：轮询检测方案明确"到期时间 ± 检测间隔"
3. 自建延时服务最小集：独立存储（按时间索引）+ 定时器线程 + 到期投递 + 持久化

## 四、深入追问

### Q1：多级时间轮的"降级"是怎么工作的？

消息先挂在高层轮（年/月），时间推进到边界时把消息**降级（重新插入）到低层轮**——像钟表：分针走完一圈，时针进一格。所以长延时消息大部分时间在粗粒度轮上，快到期才进秒轮。**内存效率的来源**：任何时刻只有近未来的消息在精细刻度上。

### Q2：时间轮的持久化怎么做？

两条路：①**不持久化轮子本身**，持久化消息（存引擎/Topic），重启后扫描重建时间轮（Pulsar 重建 delayed index 思路）；②时间轮状态快照 + WAL。主流是前者——轮子是索引不是数据，重建成本低。关键：重启期间到期的消息要在重建后立即补投。

### Q3：延时消息集群化，多 Broker 谁负责检测？

RocketMQ：SCHEDULE_TOPIC 的队列像普通分区一样分布到 Broker，**各自检测自己 Leader 的队列**（分区天然分治）。共享存储方案（RocksDB）：要**抢锁/选主**防多 Broker 重复投递（或按时间分片）。分布式延时的核心问题：**到期的"那一瞬间"只能有一个节点投递**，否则重复。

### Q4：为什么延时消息难做精准？

轮询检测间隔（100ms 级）天然有误差；到期瞬间消息洪峰时投递要排队；时间轮也有 tick 精度。物理上"精准到毫秒且零抖动"意味着定时器随时可中断主流程——代价不可接受。所以业界口径都是"**到期时间不早于设定值**"，业务要容忍秒级抖动。
