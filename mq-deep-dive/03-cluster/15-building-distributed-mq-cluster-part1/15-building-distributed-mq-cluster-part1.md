## 一、内容总结

**有状态 vs 无状态服务**（集群设计的分水岭）：是否本地持久化数据。无状态（HTTP Web）：Nginx 后面挂一批节点，任意转发，节点互不知晓。有状态（MQ）：**消息绑分区、分区绑节点**，发错节点就是失败——所以 MQ 收发要么客户端寻址要么服务端转发，集群必须按有状态服务设计。

**有状态集群四大件**：元数据存储、节点发现、节点探活、主节点选举。

**① 元数据存储**（Topic/分区/配置/节点/权限——丢了元数据，消息数据也没意义）：
| 方案 | 代表 | 优劣 |
|---|---|---|
| 第三方引擎 | ZK（Kafka/Pulsar）、etcd、Mnesia（RabbitMQ）、数据库 | 拿来即用、前期稳定；额外部署成本、受限于组件瓶颈、可能不一致 |
| 集群内自实现 | Kafka KRaft | 架构轻量、自我把控；开发成本高、短期稳定性弱——**长期更合理（作者倾向）** |

**② 节点发现**（所有节点知道彼此存在）：
| 方案 | 机制 | 优劣 | 使用者 |
|---|---|---|---|
| 配置文件 | 静态配置所有节点 IP | 简单；扩容要改配置重启 | ZK、Kafka KRaft |
| 类广播 | 广播/DNS 解析自动发现 | 自动扩容；开发成本高 | RabbitMQ、ES |
| **集中式组件** | 节点向中心组件注册/注销 | 动态感知、扩容方便、实现简单 | **主流**（Kafka-ZK 版、RocketMQ、Pulsar） |

**③ 节点探活**：探活角色 = 主节点或第三方组件。**主动上报 vs 定时探测**——差别在发起方；中心组件探测在节点多时有瓶颈，**业界主流是主动上报**。策略：ping-pong，如 3s 一次、连续 3 次失败剔除，超时时间设短。Kafka 借 ZK **临时节点 + Hook**：TCP 断 → 临时节点删 → 触发上下线操作（底层仍是 ping-pong 心跳）。

**④ 主节点选举**：
- **相互选举**：节点互投（Raft 类）——ZK、ES、Kafka KRaft
- **第三方争抢注册**：谁先在 ZK/etcd 某位置写入谁当主——实现简单
- MQ 里的主节点叫 **Controller**，负责集群管理（Topic 增删改、节点上下线、Leader 切换），由某台 Broker 担任

**集群架构抽象**：Metadata Service（存元数据）+ Controller（读管元数据、指挥 Broker）+ Broker 集群。Broker 上报元数据可经 Controller（路径 1）或直连 Metadata Service（路径 2），无明显优劣。

**运行机制三个动作**：
1. **集群启动**：节点注册 → 触发选举出 Controller → 定期心跳 → 上下线同步元数据
2. **创建 Topic**：客户端发指令（分区数 + 副本数）→ Controller 按集群现状计算分区/副本分布并选 Leader → 存元数据 → 通知各 Broker 创建
3. **Leader 切换**：Controller 监听节点存活 → 判定挂掉 → RPC 通知存活 Broker 把 Follower 提为 Leader → 更新元数据。**客户端无通知机制**——靠错误码/定期更新元数据感知切换（呼应 07 讲寻址保鲜）
4. 删除 Topic / 扩容分区：Controller 收指令 → 通知节点删/建分区副本 → 更新元数据

## 二、设计问答（Q&A）

### Q1：MQ 集群为什么不能像 Web 服务那样挂 Nginx 就行？

MQ 是**有状态**服务：消息绑定分区、分区绑定节点，请求必须到对的节点。Nginx 式"任意转发"成立的前提是节点无差别（无状态）。MQ 只能在前面加**转发层**（RabbitMQ 方案，有性能损耗）或让**客户端寻址**——都是有状态带来的路由刚性。

### Q2：元数据存储选型怎么决策？

前期/求快 → 第三方（ZK/etcd）；产品成熟/长期主义 → 集群内自实现（KRaft 路线）。判断依据：第三方的不一致隐患和运维成本会**随集群规模线性放大**，自研的开发成本是**一次性**的——规模越大越该自研。

### Q3：节点发现三种方案的核心差异？

配置文件：零成本但扩容要改配置重启。类广播/DNS：自动发现但实现复杂。集中式注册：**动态感知 + 实现简单**，是主流——节点发现的本质是"谁来当权威名录"，集中式组件把这个职责显式化了。

### Q4：探活为什么推荐主动上报而不是中心探测？

中心探测：N 个节点 × 探测频率，中心组件的连接和 CPU 随 N 线性增长，大集群下自身成瓶颈。主动上报：压力分散到各节点，中心只收心跳——**把扇出压力反转成扇入**，扇入可用批量/聚合消化。

### Q5：Controller 的职责边界是什么？

只管**集群控制面**：Topic/分区/副本的增删、Leader 切换、节点上下线、配置变更。不碰数据面（消息读写由分区 Leader 直接服务）。控制面与数据面分离——Controller 挂了不影响已有分区读写，只影响变更操作。

### Q6：思考题——分区缩容怎么做？注意什么？

步骤：①新写入停止路由到待下线分区（元数据标记）；②等存量数据被消费/迁移完（或迁移到新分区）；③Controller 通知节点删除分区副本；④删元数据。注意：**Kafka 原生不支持缩分区**（offset 连续性、Key Hash 映射都会被破坏——见 3.mq 24 笔记的失序问题）；要缩容通常建新 Topic 迁移。缩容的本质矛盾：**分区数进了路由函数，就不能随便变**。

## 三、实践要点

1. 集群问题排查地图：元数据不一致（查 ZK/NameServer）、节点下线不切换（查 Controller）、客户端路由错乱（查元数据更新机制）
2. Controller 是控制面单点——关注其负载（大集群 Leader 切换风暴时 Controller 是热点）
3. 扩容操作标准流程：新节点注册 → 心跳 → Controller 感知 → 分区迁移/新建

## 四、深入追问

### Q1：争抢注册选举和 Raft 选举各有什么坑？

争抢注册（ZK 写节点）：**时钟与 session 边界**——旧 Leader 假死后醒来还认为自己是主（脑裂），要 fencing（epoch/令牌）辅助。Raft 选举：任期号内建 fencing、多数派安全，但实现复杂、成员变更（扩缩容）要小心 joint consensus。工程结论：简单集群争抢注册够用，严肃存储用 Raft。

### Q2：为什么 Leader 切换后不主动通知客户端？

服务端推送切换通知要维护所有客户端连接状态（Broker 背负担）且客户端可能不在线/收不到——**推送不可靠**。客户端拉模型（错误码触发 + 定期刷新）天然可靠：发错节点必有错误码回来。这是"控制面变更用拉不用推"的通用原则（与注册中心 Nacos 推送 + 客户端兜底拉取同思路）。

### Q3：Kafka 的 Controller 挂了会怎样？

控制面停摆：不能创建 Topic、不能 Leader 切换；**数据面读写不受影响**（分区 Leader 照常服务）。Controller 自身靠 ZK/KRaft 选举快速 failover（新 Broker 抢注/当选）。所以大故障时（某 broker 宕机）最怕的是 Controller 同时在恢复——Leader 切换延迟叠加，这也是大集群要监控 Controller 选举耗时的原因。

### Q4：类广播/DNS 发现为什么开发成本高？

广播要处理网络分区下的双集群互见、广播风暴抑制；DNS 发现依赖 DNS 记录更新的及时性（TTL 缓存）和 SRV 记录支持，Kubernetes 时代靠 Headless Service + 就绪探针才顺手。而且"发现"只是开始——发现的节点对不对（配置漂移）、全不全（部分注册失败）都要额外的对账逻辑。集中式注册把这些复杂度收进一个组件。
