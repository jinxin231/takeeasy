## 一、内容总结

**核心命题**：**元数据存储服务是集群架构设计的核心**，其他模块围绕它展开。

**元数据存储两条路线细化**：

**① 第三方引擎**：能可靠存储的都可选（内存/文件/单机 DB/KV → 分布式协调服务 ZK/etcd）。单机方案有单机风险，主流用 ZK/etcd。Pulsar 还支持**插件化元数据存储**（简化单机/测试/现网不同部署）。
- 架构形态：独立元数据集群 + Broker 集群；**Controller 无状态**（只算不存），由某 Broker 兼任，挂了借元数据服务快速切换
- 一图多用：元数据服务换成 ZK = Kafka/Pulsar；换成 NameServer = RocketMQ
- 缺点：最少 6 节点（3 元数据 + 3 Broker），部署运维重

**② 集群内自实现元数据存储**（三思路）：
| 思路 | 机制 | 代表 |
|---|---|---|
| Broker 内建小型元数据集群 | 元数据量小不需扩容，**适合配置文件发现节点** | **Kafka KRaft** |
| 内嵌分布式存储引擎 | 直接调引擎接口（Mnesia 分布式，几乎零工作量） | RabbitMQ Mnesia |
| 内嵌单机引擎 + 自建同步 | RocksDB 各存一份 + 节点间同步机制 | 单机场景；强一致难，工作量居中 |

**ZooKeeper 集群构建**（案例一）：
- **配置文件静态发现**（server.0/1/2 IP 列表）→ 启动两两通信投票，**多数派**选出 Leader（间隔随机投票保证快速收敛）
- Leader 主动 ping Follower 探活，**可用节点 < 半数则选不出 Leader 集群异常**
- Leader 管写（写请求转发 Leader，半数 Follower 成功才算成功），Follower 管读
- ZK 是数据存储服务，**没有 Controller 和元数据存储的概念分层**——典型固定配置集群

**Kafka 集群构建两种实现**（案例二，重点）：

**ZK 版**：
- 节点发现：Broker 启动在 `/brokers/ids` 创建**临时节点**（存 IP/ID），宕机 TCP 断 → 临时节点删
- **Controller 选举**：`/controller` 节点争抢注册——不存在就自己写上，所有 Broker 监听该节点，没了就抢
- Controller 监听 ZK 多目录（`/brokers/ids` 增删等 Hook）感知变化 → 元数据经 TCP 通知各 Broker 保持全量一致
- 建 Topic 两路径：调 Broker（算分布 → 写 ZK → Controller Hook 到 → 通知建分区）或**直接写 ZK**（生成计划）

**KRaft 版**（3.0+）：
- 元数据模块内建，**Raft 协议**实现；配置 `controller.quorum.voters` 指定可当选节点，互投出 Leader
- Controller **自带元数据存储**（= ZK 版 Controller + ZK Leader 合体）；无 ZK 监听链路，**链路短、稳定性高**
- 建 Topic 只有一条路：Admin SDK → Broker（非 Controller 则转发）→ Controller 算分布 → 通知创建 → 存元数据
- 解决 ZK 版痼疾：**分区数上限低、缓存不一致**

## 二、设计问答（Q&A）

### Q1：为什么说元数据服务是集群架构的核心？

集群的一切操作（建 Topic、扩缩容、Leader 切换、权限变更）都是"**读元数据 → 算 → 写元数据 → 通知执行**"。元数据服务的可靠性、性能、一致性直接决定集群上限。选型的第二层效应：它决定部署形态（要不要多一套集群）、故障域、分区规模天花板。

### Q2：Controller 为什么可以无状态？

Controller 只负责**计算**（分区分布、选 Leader），状态全在元数据服务里。无状态的好处：挂了由元数据服务辅助秒级切换到别的 Broker，不用搬数据。设计原则：**控制面无状态化，状态集中存储**——这样控制面才有弹性。

### Q3：Kafka 的 Controller 选举为什么用"抢注"而不是 Raft 投票？

简单够用：Controller 不是数据一致性的关键路径（元数据真本在 ZK），抢注实现极简、故障转移快。而 ZK 自身选 Leader 必须 Raft 式投票（Zab）——因为它要保**数据**一致性。**选举方案的复杂度应该与被选举者的状态重要性匹配**。

### Q4：KRaft 解决了 ZK 版哪些痼疾？怎么做到的？

①**分区数上限低**：ZK 写入走 Leader + 半数确认，分区状态变更洪峰（大面积 Leader 切换）会压垮 ZK；KRaft 元数据 = 内部 Raft 日志，批量顺序写，百万分区可行。②**缓存不一致**：ZK 版 Controller 经 ZK Hook 通知 Broker，链路长环节多，各 Broker 元数据视图有窗口差异；KRaft 链路短（Controller 直连）。③部署简化：少一套集群。

### Q5：思考题——Kafka 修改配置/权限的流程？

ZK 版：Admin 调 Broker → Broker 写 ZK 对应 znode（如 /config/topics/xxx）→ Controller Hook 到变更 → 通知各 Broker 生效。KRaft 版：Admin → Controller → 元数据日志追加（Raft 复制）→ Controller 通知各 Broker。共性：**配置即元数据，变更走"写元数据 + 通知生效"两段式**。

## 三、实践要点

1. Kafka 集群规划先定元数据路线：老集群 ZK 版要监控 ZK 写入压力；新建直接 KRaft
2. ZK 集群纪律：奇数节点（3/5）、`minimum` 语义、别把业务数据塞 ZK
3. Controller 监控：选举耗时、切换频率、元数据传播延迟

## 四、深入追问

### Q1：为什么"配置文件发现"适合 KRaft 却不适合 Broker 集群？

元数据集群**节点少且固定**（3~5 个 voter，不需扩容）——配置文件的一次性成本可接受，换来无外部依赖。Broker 集群要**频繁弹性扩缩容**——静态配置每次都要改配置重启，不可接受。发现机制的选择 = 节点变动频率的函数。

### Q2：多播发现（ES/RabbitMQ）比单播配置好在哪？风险？

多播：新节点广播自己/监听广播自动入伙，**扩容零配置**。风险：①跨网段/VLAN 多播常被禁（云上基本不可用）；②多播风暴和安全（陌生节点入伙）；③网络分区时双方各自认为自己是全集——脑裂温床。所以 ES 后来也加了单播 seed 发现。云上集群基本回到"单播列表/集中注册"。

### Q3：ZK 版 Kafka 的"缓存不一致"具体指什么？

Controller 是元数据的权威计算者，但元数据先写 ZK 再经 Hook 异步通知 Broker——窗口期内：ZK 已变、部分 Broker 还没收到通知、客户端从不同 Broker 拿到的元数据不一致（分区路由错乱、写错 Leader）。KRaft 把元数据复制做成 Raft 日志（有序、可回放），Broker 按日志位点对齐——**不一致从"时间窗口"变成"日志落后量"，可度量可追赶**。

### Q4：如果让你设计新一代 MQ 的集群元数据方案，你怎么选？

推荐形态：**内嵌 Raft 元数据模块（KRaft 式）+ 元数据分片**（元数据量大时按 namespace 分片到多个 Raft group）+ 读路径本地缓存 + Watch 推送。理由：①无外部依赖部署最简；②Raft 日志天然带位点，客户端可对账；③分片解决超大规模单 Raft 组的写入上限。避免重蹈：外部 ZK（两套系统）、无共识轻元数据（NameServer 式，靠上报修复，强一致场景不够）。
