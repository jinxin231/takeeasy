# 19：安全——身份认证、资源鉴权和加密传输都是怎么实现的？

> 来源：极客时间《深入拆解消息队列47讲》许文强
> 整理日期：2026-11-06

---

## 一、内容总结

**MQ 系统安全六部分**：网络隔离、传输安全、集群认证、资源授权、自我保护、数据加密。本讲讲前四个。

**① 网络隔离**：最完美保护是完全隔离的网络（别人根本访问不到）。VPC/内网即独立网络。但现实是要和外部交互（开通公网/拉专线），隔离失效 → 需要认证鉴权。**注意：几乎所有 MQ 默认不开认证鉴权**（Kafka/RocketMQ/Pulsar/RabbitMQ 默认可直连）。

**② 传输安全（SSL/TLS）**：SSL 与 TLS 是同一物（SSL 3.0 后改名 TLS，产品文档写哪个取决于开发年代）。MQ 主链路 = **TCP + SSL/TLS**；HTTPS = HTTP + SSL。实现两步：服务端制证书 + SSL 库起 Server（Netty 集成 SSL）；客户端 SDK 带公钥证书。缺点：**耗资源、性能下降**——私有网络里意义不大，公网必开。

**③ 集群认证（连接建立的身份门槛）**：
- 概念一堆（SASL/OAuth/SCRAM/PLAIN/Kerberos/mTLS/JWT），本质 = **认证框架 + 具体认证实现**（接口 `AuthenticationProvider.authenticate()`，实现类即认证方式）
- 各家实现：Kafka 用 **SASL 框架**（机制完善但复杂）；RabbitMQ/Pulsar **自定义可插拔框架**（配置指定插件）——作者认为自定义够用、编码成本低
- 主流认证机制：**用户名+密码**（Kafka PLAIN/SCRAM、RabbitMQ PLAIN、RocketMQ AK/SK——PLAIN 静态文件要重启，SCRAM 存 ZK 可动态变更）；**Kerberos**（独立配置中心，大数据组件常见）；**OAuth/Token/JWT/mTLS**（场景各异的变体）

**④ 资源授权**：
- **数据类 vs 资源类操作要隔离**（研发用数据、运维管资源）：
  | 方案 | 机制 | 优劣 | 使用者 |
  |---|---|---|---|
  | **两条链路** | 数据走 TCP，资源管控走 HTTP | 内核鉴权成本低、运维配置简单（作者推荐） | Pulsar、RabbitMQ |
  | 单链路 | 全部走一条 TCP，按接口/资源鉴权 | 无需双 Server；鉴权维度多、编码配置成本高 | Kafka、RocketMQ |
- **ACL 三维度**：资源（Topic/Queue、消费分组、集群、Exchange）；操作（读/写/创建/删除/修改/配置）；接口。鉴权主体：**用户 + IP**（可叠加"某用户只能从某 IP 访问"）。Kafka 粒度最细（因为它单链路，必须精细）；RabbitMQ 维度少（架构简单 + 管控走 HTTP）
- 实现很轻：取连接的用户/IP → 调鉴权函数比对内存授权数据。**可插拔**（Kafka `authorizer.class.name` 自定义鉴权类）
- **超级用户**：写死在配置、不可改删——防止权限被误改后系统无法恢复，运维应急用。Kafka 有，**RabbitMQ 没有**（运营中密码被改要特殊处理，不方便不安全）

## 二、设计问答（Q&A）

### Q1：MQ 安全体系怎么分层？

四层：网络隔离（VPC/内网，最彻底）→ 传输加密（SSL/TLS，公网必开内网可省）→ 认证（你是谁，连接门槛）→ 鉴权（你能干什么，ACL 资源×操作×用户/IP）。外加自我保护（限流）和数据加密（落盘加密）补全六块。

### Q2：为什么 MQ 默认不开认证？

历史与场景：MQ 诞生于内网可信环境，默认配置追开箱即用。安全风险留给部署方（网络隔离兜底）。**上生产前第一件事就是评估要不要开认证**——默认裸奔是事故温床。

### Q3：SASL 框架和自定义认证框架怎么选？

SASL：机制完善、标准化（企业级需求、对接 Kerberos/LDAP 现成），但编码规范约束多、复杂。自定义框架：接口 + 实现类，几十行代码搞定，灵活。**MQ 场景的认证需求有限，自定义框架性价比高**（RabbitMQ/Pulsar 的选择）；大数据生态要对接 Kerberos 就上 SASL（Kafka 的选择）。

### Q4：为什么 Kafka 的 ACL 做得比 RabbitMQ 细？

架构决定：Kafka **单链路**（数据和管控同走 TCP），必须精细到接口级才能区分运维和研发操作；RabbitMQ **双链路**（管控在 HTTP），链路本身就完成了粗隔离，数据链路只需管 Exchange/Queue 的读写。启示：**链路分离降低鉴权复杂度**。

### Q5：超级用户机制为什么必要？

权限系统的自举问题：所有权限都可分配 → 就能被全收回/误删 → 系统锁死。写死的超级用户是"最后一道门钥匙"。RabbitMQ 没有这个设计，运营中反复踩坑（密码被改无法恢复）——**设计权限系统时先留好不可删除的逃生通道**。

## 三、实践要点

1. 生产上线安全清单：认证开启 + ACL 最小授权 + 超级用户保护 + 公网强制 TLS + 内网靠 VPC
2. 认证方式默认选用户名密码（SCRAM/AK-SK），企业合规要 Kerberos/OAuth 再上
3. 权限审计：定期核对 ACL（谁有生产权限、谁有集群配置权限），离职/转岗及时回收

## 四、深入追问

### Q1：TLS 的性能损耗在哪？怎么缓解？

损耗：握手（非对称加密，数次往返）+ 传输（对称加解密的 CPU）。缓解：①**会话复用/会话票证**（省完整握手）；②TLS 1.3（握手 1-RTT 甚至 0-RTT）；③硬件加速（AES-NI）；④长连接摊薄握手（MQ 天然长连接，所以 TLS 在 MQ 里的成本比 HTTP 短连接低得多）。**内网不开 TLS、公网必开**是主流平衡点。

### Q2：Kafka 的 SCRAM 比 PLAIN 好在哪？

PLAIN：密码静态文件存储（服务端明文/弱哈希），加用户要重启。SCRAM：挑战-应答机制（**密码不上线**，服务端存的是加盐迭代哈希），凭证存 ZK 可动态增删，防窃听重放。安全 + 运维双赢——新部署一律 SCRAM。

### Q3：ACL 鉴权在高并发下会不会成为性能瓶颈？

鉴权是内存比对（用户→权限规则哈希查找），单次微秒级，瓶颈风险低。真正的注意点：①规则变更的**内存刷新一致性**（多 Broker 各自加载 ACL，变更传播延迟要可控）；②鉴权函数别做远程调用（调外部 IAM 就引入网络依赖和延迟——要本地缓存规则）；③审计日志异步写，别挡主链路。

### Q4：多租户集群的鉴权怎么做？

租户（Tenant）/命名空间（Namespace）作为 ACL 的**前缀维度**：资源 = 租户.命名空间.Topic，权限按前缀授权。再加**资源配额**（限流）防租户间挤占——认证鉴权只管"能不能"，配额管"用多少"，合起来才是完整的多租户隔离（Pulsar 的模型）。
