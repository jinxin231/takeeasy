## 一、内容总结

**集群构建**：
- **节点发现**插件化支持 4 类 7 种：固定配置（同 ZK）/ 类广播（DNS，同 ES 多播）/ 第三方组件（AWS EC2、K8s、Consul、etcd——同 Kafka 用 ZK、RocketMQ 用 NameServer）/ **手动管理**（rabbitmqctl 人工加减节点——特殊，别家很少用）
- **元数据**：Erlang 内置分布式 DB **Mnesia**——进程启动即自带分布式元数据能力，"天生自带 KRaft"

**数据可靠性**：Queue 维度副本。建 Queue 默认**单副本**；多副本两阶段：
| | 镜像队列（3.8.0 前） | **仲裁队列 Quorum Queue（3.8.0+）** |
|---|---|---|
| 机制 | 策略配置副本（All/Exactly/Nodes），GM 模块组播同步（原子性） | **Raft 共识**，主从 + 多数原则 |
| 一致性 | 强一致（同步复制，性能杀手） | 多数派写入即成功 |
| 故障恢复 | 节点重启动**清空重同步**；同步时**阻塞队列不可用** | 增量同步、不阻塞主副本 |
| 规模 | — | ≥3 节点；3~4 节点容忍 1 坏、5 节点容忍 2 坏；>5 性能大降（写入要 >3 节点确认） |

镜像队列三缺陷：强一致同步拖性能、节点重启清空重同步、同步阻塞队列——所以被 Quorum Queue 替代（与 ZK Zab、Pulsar 同宗：多数原则）。

**安全控制**：
- **TLS**：Broker 配置 or 代理/LB 配置（HAProxy）——两法无明显优劣；注意 **TLS 与非 TLS 是不同端口**
- **认证**：用户名密码 + X.509 证书；插件化支持 LDAP/HTTP/IP 来源；基于 SASL 框架实现 PLAIN/AMQPPLAIN/**EXTERNAL**（插件入口）。**亮点：链式认证**（如 IP+LDAP+密码三重全过才算过）——别家一般只支持单种
- **鉴权**：管理页面四角色（management/policymaker/monitoring/administrator）；数据流按 Vhost/Exchange 鉴权，权限分 Configure/Write/Read

**可观测性**：
- 指标四维立体：集群（Exchange/Queue/Channel 数、生产消费者数）/ 应用（Socket/Channel 打开率）/ 队列（消息总数、未确认数）/ 节点（硬件 + OS + **Erlang VM** 线程/GC）
- 暴露：官方推荐 **Prometheus + Grafana**；HTTP API 供内部系统集成；命令行 rabbitmq-diagnostics/rabbitmq-top 现场排查；Zabbix/DataDog/CloudWatch 天然集成
- **内核自带健康检查/拨测**（rabbitmq-diagnostics 或 HTTP API 模拟"建 Exchange/Queue + 生产 + 消费"全流程）——**指标是二级信息，拨测才直接表达集群死活**（指标异常集群可能正常，反之亦然）
- 日志：多类型多级别、分类分文件、按时间/大小滚动
- 消息轨迹：内核无原生支持，用 **Firehose 插件**扩展（见 22 讲方案）

## 二、设计问答（Q&A）

### Q1：镜像队列为什么被仲裁队列替代？

镜像队列三宗罪：①强一致同步复制 → 集群性能低；②节点挂掉重启后**数据清空重新全同步**；③同步期间**阻塞队列不可用**（数据量大时长不可用）。仲裁队列用 Raft：增量同步、不阻塞、多数派写入即成功——性能与可用性双赢。

### Q2：仲裁队列的节点数怎么选？（思考题变形）

Raft 多数派：3 节点容忍 1 坏、5 节点容忍 2 坏；**>5 节点性能大降**（写入要等 >3 节点确认，确认链路变长）。甜点值 = 3 或 5。仲裁队列按 Queue 建集群，一个 RabbitMQ 集群里可以有多套独立的 Quorum 组。

### Q3：RabbitMQ 为什么支持那么多种节点发现？（思考题）

历史长 + 部署环境杂（物理机/私有云/公有云/K8s）——每种环境的"权威名录"不同（配置文件/DNS/EC2 API/Consul），插件化发现是对**部署环境多样性**的适应。手动管理则源自它早期的 Erlang 集群传统（ERL 分布式节点互联要显式 join）。其他 MQ 起步晚、目标环境单一（IDC/云），一种集中式注册就够了。

### Q4：健康检查（拨测）和监控指标的关系？

指标是**二级信息**：只能间接推断（连接数高不一定有事）。拨测是**一级证据**：模拟真实客户端走全流程（建资源→生产→消费→删除），直接回答"集群现在能不能干活"。拨测也可能误报（拨测路径资源问题），所以两者结合：拨测定死活，指标定原因。

### Q5：RabbitMQ 的 TLS 为什么要单独端口？

历史实现选择（明文/密文监听分离），代价是端口管理复杂、客户端要选对端口。现代实现（Kafka/Pulsar）可以同端口协商。启示：**安全特性的引入时机影响协议形态**——后补的安全往往是"外挂式"的。

## 三、实践要点

1. 新建队列副本策略：**一律 Quorum Queue**（3 副本），镜像队列只存在于遗留系统
2. 监控标配：Prometheus + Grafana + **定时拨测**（拨测失败优先告警）
3. 节点扩容后记得检查 Quorum 组的分布均衡
4. 上节课闭环：轨迹成本压缩路线——简化查询条件（只按 ID）→ 引擎选择面变大（MongoDB/HBase）→ 内容极简三字段 → 本地盘 + grep 零成本

## 四、深入追问

### Q1：Quorum Queue 的 Raft 和 Kafka ISR 的核心差异？

Quorum Queue：**队列内每个队列一个独立 Raft 组**，多数派确认才返回成功（写延迟含共识）；ISR：异步复制 + ISR 集合 + acks 客户端选级别。Quorum 更稳（强一致默认）、吞吐更低；ISR 更快（批量异步）、极端场景有丢失窗口（见 3.mq 26 笔记）。**Raft 派 vs ISR 派 = 可靠性优先 vs 吞吐优先的两种 MQ 哲学**。

### Q2：RabbitMQ 的 GM 模块组播同步为什么被诟病？

GM（guaranteed multicast）保证"发到所有镜像或都不发"的原子组播——要求所有镜像在线且响应，任一镜像慢/挂都阻塞整个队列的写。同步重、故障敏感、恢复要全量重同步。Raft 只需多数派在线——**可用性门槛从"全员健康"降到"过半健康"**。

### Q3：链式认证有什么真实场景？

高安全行业：如"来自办公网 IP + LDAP 域账号 + 服务密码"三重验证访问生产 MQ。本质是**认证因子叠加**（知识因子 + 位置因子）。实现上注意：链式认证的任一环节失败都应该给同样模糊的错误（防枚举攻击探测哪一重失败）。

### Q4：RabbitMQ 集群为什么规模做不大？

三个天花板叠加：①Mnesia 全量元数据每节点一份，节点多同步慢、一致性窗口大；②Queue 是存储单元且位置固定，扩节点不扩 Queue 能力（除非 Quorum 组重分布）；③Erlang VM 的集群全连接（full mesh）在几十节点后心跳开销陡增。经验值：**RabbitMQ 集群别超几十节点**，超大拆多套集群——这也是它"中小流量业务消息"定位的物理边界。
