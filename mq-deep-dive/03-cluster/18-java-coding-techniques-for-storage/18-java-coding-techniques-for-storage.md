# 18：性能——Java 开发分布式存储系统都有哪些常用的编码技巧？

> 来源：极客时间《深入拆解消息队列47讲》许文强
> 整理日期：2026-11-06

---

## 一、内容总结

零散但实战的 Java 存储系统编码技巧集。**大架构差别不大时，性能差异就来自这些细节**。

**① PageCache 调优与 Direct IO**：
- PageCache 三失效场景：FileChannel 走 Direct IO 时不经页缓存；内存不足频繁换页命中率低；大量随机读不命中
- 解法：**自定义 Cache + Direct IO**（绕过 OS，自管加载/命中/换页/刷盘策略，等同 C++ 自管内存）。Java 可用 JNA 库（jaydio）。RocketMQ 的刷盘策略、ES 的缓存都是这思路

**② FileChannel vs mmap**：
- FileChannel + ByteBuffer（堆内存）：写路径 = 应用内存 → PageCache → 磁盘；`force()` 手动刷盘
- mmap（`FileChannel.map` → MappedByteBuffer）：文件映射进内存，像读写内存一样读写文件，**省用户态↔内核态拷贝**
- mmap 缺点：要预知映射大小、**单次 Map 限 ~1.5G**、刷盘时机难控、回收复杂（要手动释放）
- 选型：**优先 FileChannel**（够用、省心）；数据量小 + 内存充足 + 文件固定（如 MQ 分段文件）用 mmap。RocketMQ 主写路径用 mmap

**③ 预分配/预初始化/池化**：分段文件**预写空数据**（真写时直接覆盖，快很多）；实例化成本高的对象预初始化；反复 new 的东西**池化**（Netty Recycler、RingBuffer 预分配）

**④ 堆内 vs 堆外内存五原则**：
1. 大块内存用堆外（堆内受限）
2. 堆外适合**生命周期中长**的对象
3. 堆内刷盘要多拷一份到堆外——IO 路径用堆外更优
4. 堆外创建成本高 → **必须复用**
5. **池化 + 堆外**组合（ThreadLocal<ByteBuffer>）。写存储系统优先考虑堆外

**⑤ 同步刷盘提速（批量同步刷盘）**——重要方案：
```
业务线程 T1~T6 写数据 → 内存汇总 → IO 线程收集 → 批量 force 刷盘 → 唤醒各业务线程返回成功
```
与 PageCache 方案的本质区别：**写入线程能感知刷盘结果**（失败可重试/报错）；PageCache 写成功≠落盘。服务端 Process 线程池配合同步刷盘时就用它。MQ 更常用的可靠性替代：**多副本各写 PageCache 即返回**（多台同时挂概率低），避免同步刷盘

**⑥ 硬件/系统技巧**：AEP（傲腾持久内存，比 SSD 快 1~n 数量级，金融级 MQ 用；成本高、用法特殊未普及）；**线程绑核**（IO 线程独占核，Java 用 Java-Thread-Affinity）；**SSD 4KB 对齐**（读写不跨物理扇区；MQ 消息大小不固定，强制对齐会浪费空间——场景合适才用）

**⑦ 减少线程切换**：短持锁、锁分离/分段、CAS 代替 synchronized、Condition 系替换 wait/notify（可区分唤醒）、线程池合理线程数。协程切换成本最低（JDK 19+ 虚拟线程）

**⑧ 其他**：Unsafe（直接操作内存/CAS/内存屏障，JDK9 起受限）；集合长度固定用数组替 Map（降 HashMap 开销）；JVM 调优（降 GC 次数、避 Full GC/STW）。

## 二、设计问答（Q&A）

### Q1：FileChannel 和 mmap 怎么选？

FileChannel 优先——简单可靠够用。mmap 用在：文件大小固定可预知（MQ 分段文件）、内存充足、随机读写频繁的场景。注意 mmap 三坑：映射要定大小（单次 ~1.5G 上限）、刷盘时机难控、回收复杂。RocketMQ 写用 mmap，但多数系统 FileChannel 足够。

### Q2：同步刷盘慢，怎么不减可靠性还提速？

①批量同步刷盘：IO 线程聚合多业务线程的数据一次性 force——刷盘次数从 N 降到 1，业务线程 await 拿真实结果；②换思路：多副本各写 PageCache 即返回，用分布式冗余替代单机强刷；③硬件：NVMe/AEP。实践顺序：先多副本，再批量刷盘，最后砸硬件。

### Q3：堆外内存的代价是什么？

创建成本高（要复用/池化）、无 GC 管理要手动释放（泄漏无告警）、不受堆监控工具覆盖。适合：大块、长生命周期、IO 路径的 buffer（Netty 的 DirectByteBuffer 全家桶）。原则：**堆外是给"IO 数据通路"用的，不是给业务对象用的**。

### Q4：为什么减少线程切换是性能优化？

每次切换要保存/恢复上下文（寄存器、栈），还要面对缓存失效（L1/L2 被别的线程污染）——微秒级 × 高频 = 可观开销。手段：减锁持有时间、锁细化、CAS、合理线程数、绑核。终极：协程/虚拟线程（JDK19+），切换成本接近函数调用。

### Q5：4KB 对齐为什么 MQ 里不常用？

消息大小不固定，强制 4KB 对齐要填充空数据——量大时填充浪费的磁盘空间可观。4KB 对齐适合**定长记录**系统（DB 页、固定 size 的索引文件）。工程原则：对齐收益 vs 填充浪费，要算清楚。

## 三、实践要点

1. 写存储组件的检查清单：FileChannel+force / mmap 选型、堆外+池化、预分配分段文件、批量刷盘
2. 排查 IO 性能先看三件事：PageCache 命中率、是否走了 Direct IO、GC 日志
3. 极限场景才动：Direct IO、Unsafe、绑核、AEP——每样都带维护成本

## 四、深入追问

### Q1：批量同步刷盘和 PageCache 异步刷盘的成功语义差别？

PageCache：write 返回 = 数据进缓存，**落盘与否不可知**（宕机丢失无感知）。批量同步刷盘：IO 线程 force 成功才唤醒业务线程返回——**响应 = 真落盘**，失败能重试。前者性能极限、后者可靠性真实。RocketMQ 的 SYNC_FLUSH 就是批量聚合刷盘模型。

### Q2：mmap 的 1.5G 限制哪来的？怎么绕？

`FileChannel.map()` 的 size 参数是 long，但内部实现受平台映射窗口和 Integer 范围的数组索引限制，实践上单次映射约 1.5~2G。绕法：**分段多次 map**（MQ 分段文件天然契合——一个段文件一次 map）。这也是 MQ 段文件默认 1G 的一个隐藏动机。

### Q3：Netty 的零拷贝用了本文哪些技巧？

CompositeByteBuf（逻辑合并避免拷贝）+ DirectByteBuffer（堆外）+ Recycler（池化）+ `FileRegion`（sendfile/transferTo）。所以 Netty 零拷贝是**一组技巧的组合拳**，不是单个 API——这正是"魔鬼在细节"的例证。

### Q4：线程绑核什么时候真的有用？

只在**重 IO + 高负载 + 追求尾延迟**（P99.9）场景：IO 线程独占核消除调度抖动。普通业务绑核收益可忽略，还降低了调度灵活性（别的线程不能用这些核）。金融行情、存储引擎的 IO 线程是典型受益者。
