# 22：可观测性——如何设计实现消息轨迹功能？

> 来源：极客时间《深入拆解消息队列47讲》许文强
> 整理日期：2026-11-06

---

## 一、内容总结

**消息轨迹 = MQ 领域的 Traces**：还原单条消息的全生命周期（业务消息丢失会导致流程异常，轨迹是排查刚需）。

**"丢消息"的五种真实形态**（不只是服务端弄丢）：
1. **生产失败**（服务端异常或消息超长/格式不合规）
2. **延时消息错过有效时间**（延时队列未及时出队，被业务抛弃）
3. **服务端存储后丢失**（一致性设定、异步刷盘、重启、消息截断）
4. **消费位点错误**（该消费 100 却从 101 开始——消费视角就是丢）
5. **进死信队列**（无人订阅死信 = 生命周期终结）
→ 结论：生命周期长，任何一环出错业务都感知为"丢"。轨迹的使命是**定位到环节**。

**消息唯一标识**：
- RocketMQ 有明确消息 ID；RabbitMQ 的 ID 是 Header 可选项（不传就没有）；**Kafka 用 Topic+Partition+Offset**（严格说不能唯一标识——重发同数据算两条）
- **ID 必须在客户端生成**（服务端生成会把重发的同一条数据当两条）
- 生成方案：UUID（简单但千亿级有碰撞概率）、集中式（MySQL/Redis/ZK 自增——增加 SDK 复杂度）、**SnowFlake（作者推荐，工业验证稳定）**、自定义算法

**轨迹设计三要素：记录、存储、查询**：
- **记录**：关键点埋点（发出/收到响应/服务端接收/进出延时队列/被消费/处理成败/进死信）。两原则：**不影响主流程性能**（10ms 主流程不能花 5ms 记轨迹，最好无感知）、**旁路可丢**（轨迹可偶尔丢失，不能影响主流程稳定）
- **存储**：轨迹是**写多读少**模型（写入性能必须好）；轨迹比消息**数倍放大**（RabbitMQ 例 9 倍）→ **存储成本占比最大** → 内容要极简（最简两个字段：消息 ID + 时间）；要支持多维查询但**够用即可**（索引多 = 存储贵）
- **查询**：按消息 ID 或 时间+ID 精准查询为主

**记录上报方案**：
- 客户端：SDK 内置轨迹上报（TCP/HTTP 接口或内置主题）——不用本地文件（客户端部署不可控，采集难统一）
- 服务端四形态：本地文件（ELK 体系成熟但链路长、要 Agent）/ **内置 Topic**（复用 MQ 缓冲，远程消费者集群采集——**作者推荐**，私有化闭环）/ 第三方服务直写（链路短但稳定性依赖第三方）/ 单机存储引擎（RocksDB 各节点 + 逐节点查询，零成本但查询麻烦、单机挂则丢）

**存储引擎选择**：ES 最普遍（功能强，但**存储放大严重、磁盘贵**）；大规模下成本优先 → ClickHouse/HBase/MySQL（小量）——**大规模运营的平衡点是功能/性能/稳定性/成本四角，可以牺牲部分换成本**。

**RabbitMQ 实操方案**：ES 引擎 + 自研 SDK 上报客户端轨迹到 amq.rabbitmq.trace + 内核 Trace 开关（服务端轨迹自带）+ 消费者消费 Trace Queue 写 ES + 查询平台走 ES REST。优化：改本地文件 + Filebeat 采集（消费快不积压）。

**大集群极限案例（PB 级轨迹）**：**本地文件按时间分段 + 保留 10 天 + 节点起 HTTP Server + grep 检索**——Linux 原生 grep + Broker 磁盘冗余 = **几乎零成本**。思路：成本极限时，功能降级到"能查到"即可。

## 二、设计问答（Q&A）

### Q1：用户说"消息丢了"，怎么排查？

先定义"丢"的五种形态（生产失败/延时不及时/服务端丢/位点错/进死信），再按轨迹逐段定位：查生产端轨迹（发没发成功）→ 服务端轨迹（收没收到、存没存住）→ 消费端轨迹（拉没拉到、ACK 没、进没进死信）。没有轨迹就只能翻日志猜——轨迹的价值是把"丢没丢、哪丢的"变成查询题。

### Q2：消息 ID 为什么必须在客户端生成？

客户端会重发同一条数据（超时重试）。服务端生成 ID：重发的同一数据得到两个 ID，业务无法去重；客户端生成：同一数据的 ID 恒定，天然幂等标识。生成方案选 SnowFlake（成熟、趋势递增、无中心依赖）。

### Q3：轨迹记录怎么做到不影响主流程？

①异步化（轨迹写内存队列，后台线程批量上报）；②采样/降级开关（高压时降低轨迹上报率）；③旁路容忍丢失（上报失败不重试不阻塞）；④内容极简（ID+时间戳起步）。原则：**轨迹是审计设施，不能成为主链路的依赖**。

### Q4：存储引擎为什么是 ES 最普遍，大规模又不合适？

ES 检索能力强、访问方便，中小规模成本无感；但**存储放大严重**（索引 + 正排 + 倒排副本），PB 级轨迹成本爆炸。大规模选 ClickHouse/HBase（列存压缩率高、写入强），功能退一点（模糊查询弱）换成本数量级下降。选型公式：**轨迹量 × 留存天数 × 放大系数 vs 预算**。

### Q5：思考题——数据量大但成本严控的轨迹方案？

作者现网答案：本地文件分段 + 时间清理 + grep via HTTP Server。升级版可加：①写本地前**先过滤**（只记关键业务/异常消息的完整轨迹，正常消息只记 ID+时间）；②单机 RocksDB（比文件好查，零外部依赖）；③轨迹分级：热轨迹（3 天）本地、冷轨迹归档对象存储。核心思想：**把"查询便利"降级为"能查到"，换取接近零的存储成本**。

## 三、实践要点

1. 轨迹上线最小集：消息 ID（客户端 SnowFlake）+ 生产/服务端/消费三端时间点 + 结果状态
2. 存储选型默认 ES，量上来后评估 ClickHouse；始终算存储放大账
3. RabbitMQ 内核 Trace（amq.rabbitmq.trace）开箱即用，别重复造服务端轨迹

## 四、深入追问

### Q1：消息轨迹和分布式链路追踪（SkyWalking/OTel Trace）什么关系？

轨迹 = **MQ 消息生命周期视角**（一条消息在 MQ 内外的旅程：延时队列、死信等 MQ 特有状态）；Trace = **调用链视角**（一次请求跨服务的 span 树）。交集：消息 ID 可以当 Trace 的一根"虚拟 span 链接"。实践上二者互补：业务故障先用 Trace 定位到服务，再用轨迹定位消息在 MQ 内的命运。理想形态是打通——MQ SDK 埋点把消息 ID 写入 trace context。

### Q2：轨迹数据为什么写多读少还要"支持多维查询"？

写多读少（每次生产消费都写，查询只在出问题时）→ 写入性能是引擎第一指标。多维查询是因为**定位手段不确定**：有 ID 按 ID，没 ID 按时间+Queue+路由条件组合缩小范围。但"多维"要克制——每个索引维度都是存储和写入成本，按真实排查场景（ID/时间/Queue/Exchange）设计索引，不做通用查询引擎。

### Q3：Kafka 没有消息 ID，怎么做轨迹？

用 Topic+Partition+Offset 做主键 + 客户端补充业务 ID（header 里塞）。局限：重发同消息产生两个 offset 记录，要靠业务 ID 聚合。Kafka 系做法：①拦截器（ProducerInterceptor/ConsumerInterceptor）埋点上报；②轨迹 Topic 汇总；③查询层按业务 ID 聚合多条物理记录。比 RocketMQ 的内建 ID 麻烦，但可用。

### Q4：内置 Topic 存轨迹，会不会影响业务集群？

会——轨迹流量与业务流量共享集群资源。缓解：①轨迹 Topic 分区/副本精简（可丢）；②独立小集群存轨迹（业务集群只当管道转发）；③限流隔离轨迹消费者；④轨迹 Topic 的 retention 调短。**核心：轨迹是旁路，绝不能让它影响主业务的 SLA**。
