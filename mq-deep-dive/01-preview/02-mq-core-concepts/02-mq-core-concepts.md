# 02：消息队列在架构和功能层面都包含哪些概念？

> 来源：极客时间《深入拆解消息队列47讲》许文强
> 整理日期：2026-11-06

---

## 一、内容总结

**MQ 的定位**：系统架构中的**总线和管道**——解耦上下游、数据缓冲。与数据库的区别：DB 有计算/聚合/查询逻辑，MQ 核心操作永远只有**生产和消费**（不支持修改/删除单条消息）。两大经典场景：下单流程（一份数据多下游处理）、日志采集（数据大，先缓存防下游崩溃）。基本特性：**高性能、高吞吐、低延时**。

**架构层概念速查**：

| 概念 | 定义 | 注意点 |
|---|---|---|
| Broker | 一个进程；通常一个物理节点一个进程，也可多个 | "Broker≈节点"在大多情况下成立 |
| Topic | 组织分区的逻辑概念（含多个分区） | **RabbitMQ 例外**：Topic 是一种路由模式（topic exchange） |
| Partition/Queue/MessageQueue | **数据存储的最小单位**，三者同义 | 可直接写分区，或写 Topic 再分发 |
| Producer/Consumer | 发送方/接收方 | — |
| ConsumerGroup/Subscription | 组织消费者与分区关系的逻辑概念 + **保存消费进度** | 分组与订阅基本同义 |
| Offset/Cursor | 消费分区的进度位点 | — |
| ACK/OffsetCommit | 提交消费进度 | 消费成功后提交，防重复消费 |
| Leader/Follower | 分区维度的主从副本 | 一般一主多从 |
| Segment | 分区底层存储的数据分段文件 | Kafka Segment、Pulsar Ledger 同物 |
| StartOffset/EndOffset | 分区最早有效消息位点 / 最新写入位置；随过期清理和持续写入**动态变化** | 起始位点后移 = 旧数据已清理 |
| ACL | 资源权限控制（Topic/分区的读写权限） | — |

**功能层概念速查**：

| 功能 | 一句话 |
|---|---|
| 顺序消息 | 消费顺序 = 生产写入顺序 |
| 延时/定时消息 | 延迟=Broker 收到后 N 时间可消费；定时=指定时刻可消费。**内核上同一个东西** |
| 事务消息 | 一批消息要么都成功要么都失败（各 MQ 实现不一） |
| 消息重试 | 生产端重试（发送失败）+ 消费端重试（处理失败） |
| 消息回溯 | 消费成功不删除，可重复消费 |
| 广播消费 | 一条消息能被多个消费者消费到（非主动推送） |
| 死信队列 | 处理失败的消息存起来、不阻塞后续——**是功能不是实体**，SDK 集成了而已，业务也可自实现 |
| 优先级队列 | 消息维度设权重，权重大的先消费（打破 FIFO） |
| 消息过滤 | 按标签过滤消费（消费端生效），如 RocketMQ Tag |
| TTL | 消息超时间/超大小自动删除（MQ 是缓冲，必须清理） |
| 消息轨迹 | 消息全生命周期追溯（发送/保存/消费各环节时间与成败） |
| 消息查询 | 按消息 ID/位点查消息 ≈ DB 固定条件 select |
| 消息压缩 | 省网卡/硬盘；**客户端压缩更合理** |
| 多租户 | 逻辑隔离（Namespace/Tenant），同集群可建同名主题 |
| 消息持久化 | 是否落盘；纯内存 MQ 重启即丢 |
| 消息流控 | Topic/分区/消费组/集群维度的限流 |

**评论区高价值补充**（作者认可）：
- **batch 语义是消息/流的分水岭**：流（Kafka/Pulsar）必须支持 batch（不批量吞吐上不去），但 batch 要本地聚合等待、增加发送耗时——**业务消息追求及时性，RocketMQ/RabbitMQ 没有 batch 语义**
- Kafka 起源于日志处理，延迟优先级低，对高级消息功能兴趣不大；RocketMQ 号称金融级可靠性和低延迟
- RocketMQ 消费并发度 = 读队列数 × 并发线程数（比分区数维度更灵活）

**选型建议（作者版）**：业务消息优先 **RocketMQ**（性能高、社区活跃、集群稳定、功能全，RabbitMQ 架构老、单机瓶颈、高 QPS 弱、有分区风险）；流场景优先 **Kafka**（性能吞吐优越、稳定；Pulsar 理念先进但现网运营尚不成熟）。实际常同时运营多款（RocketMQ/RabbitMQ + Kafka）。

## 二、设计问答（Q&A）

### Q1：MQ 与 DB 的本质区别是什么？

DB 的基本操作是增删改查，有计算聚合查询逻辑；MQ 只有**读和写**（生产/消费），不支持修改删除单条数据。定位上 DB 是"数据的家"，MQ 是"数据的管道"——缓冲、解耦、削峰。所以 MQ 有 TTL（缓冲完要清理），DB 没有。

### Q2：广播消费是不是 Broker 主动推送？

不是。广播是**语义效果**而非推送动作：一条消息能被多个消费者消费到（如每个消费组都拿到全量）就叫广播。实现上仍是拉模型，只是消费进度按组独立维护。

### Q3：延时消息和定时消息有区别吗？

客户端视角有细微差别（延时=相对 Broker 接收时间的偏移；定时=指定绝对时刻），**内核实现是同一个概念**——都是"到点才可见"。所以各 MQ 的实现只做一个。

### Q4：为什么流消息要 batch，业务消息不要？

流场景追吞吐：batch 聚合摊薄 IO/网络开销，吞吐倍增，代价是聚合等待增加发送耗时（流场景对延迟不敏感）。业务消息追及时性：一条消息就是一个业务动作（订单创建），等几百毫秒攒批不可接受。所以 RocketMQ/RabbitMQ 没有 batch 语义，Kafka/Pulsar 有——**功能有无背后是场景定位差异**。

### Q5：多租户是什么？RabbitMQ 的 virtual host 算吗？

多租户 = 同一物理集群的逻辑隔离（Namespace/Tenant），不同租户可建同名 Topic 互不可见。RabbitMQ 的 vhost 确实提供了类似的隔离能力（评论区也指出了）——但 vhost 缺少资源配额、计费等完整租户语义，算"半个多租户"。

## 四、深入追问

### Q1：为什么 MQ 不支持修改和删除单条消息？

设计取舍：MQ 是**追加式日志**（WAL）——存储模型为吞吐优化（顺序写、段不可变）。支持单条修改/删除要引入随机写和索引维护，吞吐崩溃。"改"的语义用"发一条新的修正消息"（或 compact 主题）替代——Kafka 的 log compaction 就是折中：按 key 保留最新值，后台压缩，不影响写路径。

### Q2：消息轨迹功能为什么难做？（22 讲伏笔）

轨迹要记录消息全生命周期（发送/保存/消费），等于在 MQ 内部再建一套"关于消息的消息"系统——数据量与业务消息同量级、还要可查询。难点：①轨迹数据本身怎么存（再开一个内部 Topic 是通行做法）；②异步上报不影响主链路性能；③查询索引设计。实现质量是衡量 MQ 厂商工程能力的标尺。

### Q3：RabbitMQ 的 Topic 和 Kafka 的 Topic 为什么不是一回事？

RabbitMQ 的 Topic 是 **exchange 的路由模式**（topic exchange 按 routing key 模式匹配分发）——它是路由逻辑；Kafka 的 Topic 是**存储和消费的逻辑分组**（下挂分区）。同名不同物：RabbitMQ 里存数据的是 queue，Kafka 里存数据的是 partition。混用这两个概念是面试常见翻车点。
