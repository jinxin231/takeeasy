# 01：业界的主流消息队列是如何发展起来的？

> 来源：极客时间《深入拆解消息队列47讲》许文强
> 整理日期：2026-11-06

---

## 一、内容总结

**反常识开篇**：90% 以上的用户数据量不大、场景不复杂，只用生产/消费基本功能——**很多时候不需要标准 MQ 产品**。简单场景（如只传用户 ID 和审核结果）用 Redis List Push/Pop 甚至 MySQL 表都行。

**什么时候必须上标准 MQ**：大消息 + 大流量 + 复杂场景。作者的选型实证：游戏论坛评论/点赞下发，高峰几千万回帖、内容含图片表情（大消息）——Redis 会打爆内存（大 value 有性能和稳定性问题），MySQL insert 扛不住瞬时高频写入，Kafka 的高吞吐/大消息/高并发/持久化正好匹配。

**MQ 的定义（广义）**：**具有缓冲作用、具备类发布订阅能力的存储引擎**都可称为消息队列。最基本功能是生产和消费；之上扩展死信、顺序、延时等高阶能力 + 高吞吐/低延时/高可靠特性 = 标准 MQ。

**四款主流 MQ 横向对比**（核心表格）：

| 产品 | 出身 | 定位 | 优点 | 缺点 |
|---|---|---|---|---|
| RabbitMQ（2007） | Erlang，AMQP 实现 | 业务消息总线 | **功能最全**（延时/死信/优先级/事务）、低流量稳定 | 分布式设计年代早，**大流量高并发下有瓶颈和稳定性风险**（集群不可用、网络分区难解决） |
| Kafka（2011，LinkedIn→Apache） | 大数据流场景 | 高吞吐流式管道 | 吞吐/性能天花板 | **功能简单**（仅生产消费，后加幂等事务） |
| RocketMQ（2013 阿里，2017 Apache 毕业） | 移动互联网复杂业务 | **RabbitMQ 的高可用分布式升级版** | 功能丰富（Tag、轨迹、查询），大流量稳定，性能介于 RabbitMQ 与 Kafka 之间 | — |
| Pulsar（2017 Yahoo，2018 Apache 顶级） | 流计算 | **Kafka 升级版**，云原生 | 架构优秀：存算分离、弹性、多租户；功能追赶 RabbitMQ/RocketMQ | 发展时间短、架构复杂，**当前稳定性不如 Kafka** |

**商业 MQ 的江湖**：IBM MQ 在金融证券近乎一统天下，2020 年仍有近 10 亿美金年营收（国内云厂商 MQ 收入加起来不够零头）；微软 MSMQ（1997）、AWS SQS（2004）。国内自研：阿里 RocketMQ、腾讯 CMQ/TubeMQ、京东 JMQ、字节 BMQ。

**两条发展脉络**（本文主旨）：
- **需求线**：消息 → 流 → **消息和流融合**
- **架构线**：单机 → 分布式 → **云原生/Serverless**（存算分离、分层存储、多租户、弹性计算）

**消息与流融合的商业逻辑（"都是钱的原因"）**：流领域 Kafka 一家独大、消息领域国外 RabbitMQ 国内 RocketMQ——厂商要扩份额就得功能更全、成本更低；用户侧用多款 MQ 意味着研发运维双重成本，**一款 MQ 满足所有场景**有巨大商业价值。四家动作：RabbitMQ 不走这条路；Kafka 忙于自身架构优化（去 ZK）；RocketMQ 向流扩展；**Pulsar 天生就是消息+流融合架构**。注意：融合是厂商趋势，不是用户的必然选择——实践中 Kafka 当业务总线、RocketMQ 传日志都很常见。

**云原生/Serverless 的技术映射**：降成本 → 弹性是基本要求 → **存算分离**（计算弹性）、**分层存储**（低存储成本）、**多租户**（资源复用）。

## 二、设计问答（Q&A）

### Q1：到底什么时候需要引入标准消息队列？

判断标准不是"有没有异步需求"，而是**数据量和场景复杂度**：只传简单结构、量小 → Redis List/MySQL 表够用；大消息、大流量、要堆积/回溯/高级功能（死信/延时/事务）→ 标准 MQ。作者原话：是否需要，取决于数据和业务场景的需求。

### Q2：为什么简单场景不该用 Redis List 或 MySQL 当 MQ？

两个反例恰好说明标准 MQ 的存在价值：①Redis 数据全在内存，消费不及时打爆内存，大 value 有性能稳定性问题；②MySQL insert 有性能瓶颈，瞬时高频写入扛不住。Kafka 类标准 MQ 的高吞吐、持久化、长久堆积就是为这些场景设计的。

### Q3：四款主流 MQ 怎么选？（一句话选型法）

- 要功能丰富、业务复杂（延时/死信/Tag/轨迹）、量不是超大 → **RocketMQ**
- 大数据管道、日志、流式、极致吞吐、求稳 → **Kafka**
- 老系统 AMQP 生态、中小流量、功能全 → **RabbitMQ**
- 云原生新建、要多租户/存算分离/弹性、能扛稳定性风险 → **Pulsar**

### Q4：为什么 RabbitMQ 大流量下不稳，RocketMQ 就好？

RabbitMQ 设计于分布式理念不成熟年代，集群架构有先天缺陷（镜像队列同步重、网络分区难处理）；RocketMQ 是移动互联网时代按分布式架构重新设计的——NameServer 无状态 + 主从 + 分区化存储，天然为高并发大流量而生。选型要看**架构诞生的时代背景**。

### Q5："消息和流融合"对用户有什么实际意义？

运维侧只维护一款 MQ、研发侧只学一套 API——成本降低。但要警惕：融合产品的"全能"往往意味着两边都不极致（Pulsar 功能全但稳定性在追赶）；**按当前团队能力选，不为厂商路线图买单**。

## 三、选型与实践要点

1. 引入 MQ 前先回答：数据量多大？消息多大？要不要堆积/高级功能？——简单场景 Redis/MySQL 顶上更省
2. 四款 MQ 的记忆锚点：**RabbitMQ=功能老大哥、Kafka=吞吐流之王、RocketMQ=分布式业务消息、Pulsar=云原生新贵**
3. 技术选型不要只看功能列表，看**架构基因**（诞生年代决定分布式设计水平）和**社区稳定性**
4. 演进方向的实用价值：谈成本优化/弹性扩容时，存算分离、分层存储、多租户是答题关键词

## 四、深入追问

### Q1：AMQP 是什么？为什么没统一业界？

AMQP 是消息队列**协议规范**（2003 年金融机构发起），目标是统一 SDK、降低切换成本——RabbitMQ 是它的 Erlang 实现。没统一的原因：Kafka 等新生代为性能自定义私有协议（二进制精简协议），AMQP 协议本身重、语义复杂。教训：**协议标准化输给了性能与迭代速度**。

### Q2：IBM MQ 凭什么在金融一统天下？

金融场景要的不是吞吐而是**极致可靠与合规**：事务完整性、审计、几十年的稳定性口碑、商业支持 SLA。开源 MQ 的"尽力而为"语义在银行核心系统里不可接受。这提醒选型：**不同行业对 MQ 的第一诉求完全不同**（互联网要吞吐、金融要可靠）。

### Q3：Pulsar 解决 Kafka 的哪些痛点？

①扩缩容慢、分区迁移要 rebalance——Pulsar 存算分离，broker 无状态秒级扩容；②超多分区支持（Kafka 分区多了性能衰退，见 3.mq 29 笔记）；③多租户内建。代价：架构复杂度（BookKeeper + ZooKeeper/ETCD 两套依赖）、社区成熟度、稳定性仍需时间。
