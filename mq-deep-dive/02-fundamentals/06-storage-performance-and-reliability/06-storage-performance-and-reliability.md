# 06：存储——如何提升存储模块的性能和可靠性？

> 来源：极客时间《深入拆解消息队列47讲》许文强
> 整理日期：2026-11-06

## 一、内容总结

**四条基础理论**（一切优化的公理）：①内存读写 > 硬盘读写；②批量 > 单条；③顺序 > 随机；④**数据复制次数越多效率越低**。核心命题就两个：**写得快、读得快**。

**写入优化三板斧**：

**1. 缓存写 + 批量写（PageCache）**：写内存（PageCache）→ 批量刷盘。OS 刷盘策略：按脏数据比例（`dirty_background_ratio`/`dirty_background_bytes`，字节数优先）或按时间周期（`dirty_expire_seconds` + `dirty_writeback_centisecs`）自动刷；应用可手动 `fsync()`（Java：`FileChannel.write()` + `force(true)`）。Kafka/RocketMQ/Pulsar 都先写 PageCache。MQ 一般开放三配置：是否同步刷盘、时间周期、空间比例。**异步刷性能最高，同步刷可靠性最高**。

**2. 顺序写 vs 随机写——关键洞察：顺序/随机是硬盘视角，不是文件视角**：
- 单文件顺序写 = 硬盘连续区域写 → 真顺序
- **多文件各自顺序写 = 硬盘同时操作多个存储区域 → 对硬盘是随机写！**
- 对应两种存储结构（见 05 讲）：每分区一文件 vs 全部分区共享一个文件（**写入性能上共享文件方案更优**——永远只有一个写入流）

**3. 写入可靠性三手段**：

| 手段 | 机制 | 取舍 |
|---|---|---|
| 同步刷盘 | 每条写后 force() | 可靠性最高、性能大降（放弃内存优势） |
| WAL 预写日志 | 先写日志后写数据，崩溃用日志恢复 | 日志量小、可顺序写、可预测 → **WAL 盘与数据盘分离**（高性能小盘放 WAL，大盘放数据）+ 并行读写优化，性能损失可控；缺点是运维成本高（要单独配盘） |
| **多副本备份** | 多节点同时写内存，不全部重启就不丢 | 分布式维度可靠性；全部同时重启仍可能丢 |

业界选型：**方案一都支持；Kafka/RabbitMQ/RocketMQ 用多副本，Pulsar 用 WAL**（BookKeeper）。

**读取优化四手段**：
1. **冷读 vs 热读**：热读 = 数据还在缓存（内存读，最快）；冷读 = 已换页换出要读盘。代码无法控制冷热，只能**加大内存提高热读概率**
2. **顺序读/批量读/预读**：消费时批量读 + **预读**（提前读下一批）。预读两层：硬盘层预读（连续地址空间，取决于存储结构——每分区一文件的方案读取连续，预读最好；共享文件方案按索引跳读≈随机）vs 应用层预读（程序主动调度，繁琐且慢）。**读取上每分区一文件更优**——与写入的结论相反，设计要权衡
3. **零拷贝**：减少复制次数 + 上下文切换 + DMA 代劳。正常"读盘发网卡"= 硬盘→ReadBuffer→应用→SocketBuffer→网卡，**4 次拷贝 4 次态切换**；零拷贝后 硬盘→ReadBuffer→网卡，**2 次拷贝 2 次态切换**。"零"指的是内核态↔用户态拷贝次数为零。两种实现：**mmap+write**（内存映射，省一次拷贝）和 **sendfile**（内核内直接 fd 到 fd）。Java 实现：mmap = `FileChannel.map()`；sendfile = `transferTo()/transferFrom()`；DMA 代码不可控靠 OS。**几乎所有 MQ 消费都用 sendfile，至少提速一倍**
4. 硬件/系统层：①提升配置（大内存提高热读率；硬盘看 IOPS/吞吐/延时三指标：机械盘 < SSD < NVMe SSD < 云盘各规格）；②**多盘多目录读写**（不同数据段调度到不同盘，叠加吞吐；缺陷是多盘间不能共享 IO/容量，倾斜时有瓶颈）；③**RAID/LVM 磁盘阵列**（串联多盘 IO 与容量，解决多目录的倾斜问题）

## 二、设计问答（Q&A）

### Q1：写入性能优化的核心思路？

缓存写 + 批量写 + 顺序写。先写 PageCache 再批量刷盘（次数降几个数量级）；顺序写的关键是**存储目录结构设计**——注意"多文件各自顺序写对硬盘仍是随机写"这个反直觉点，全分区共享单文件在写入上最优。

### Q2：page cache 刷盘有哪些策略？

OS 自动刷：按脏页比例/字节数阈值（dirty_background_ratio/bytes）、按时间周期（dirty_expire + writeback）。应用手动刷：fsync/force。MQ 的对应配置：同步刷盘开关 + 时间周期 + 空间比例。

### Q3：同步刷盘、WAL、多副本怎么选？

单机维度：同步刷盘最稳但性能损失大；WAL 折中（小数据量日志走高性能盘）。分布式维度：多副本（多台同时缓存成功才返回）。业界：Kafka/RabbitMQ/RocketMQ 选多副本，Pulsar 选 WAL（BookKeeper 日志盘分离）。关键业务可叠加（多副本 + 同步刷盘）。

### Q4：读性能怎么优化？

热读（加大内存）+ 批量读 + 预读（硬盘层顺序预读最优，要求存储结构连续）+ 零拷贝（sendfile，消费提速至少一倍）。

### Q5：为什么写入最优结构和读取最优结构矛盾？

写：全分区共享单文件永远顺序（多文件对硬盘=随机写）。读：每分区一文件数据连续，预读友好；共享文件要按索引跳读≈随机读。**Kafka 选前者（每分区一文件），Pulsar/BookKeeper 选后者（共享 ledger）**——各自按读写侧重做的权衡，这也是 Kafka 分区过多写性能下降的原因（见 3.mq 29 笔记）。

### Q6：零拷贝的"零"指什么？Java 里怎么用？

零 = 内核态与用户态之间的拷贝次数为 0。普通 read+write 要内核↔用户来回拷；mmap（`FileChannel.map`）省一次拷贝；sendfile（`transferTo/transferFrom`）全程内核内完成，配 DMA 拷贝次数 4→2、态切换 4→2。

## 三、实践要点

1. MQ 部署盘阵选择：WAL/journal 盘与数据盘分离（Pulsar BookKeeper 的标准部署）
2. 容量规划看热读率：内存 ≥ 热数据工作集；`iostat` + cache 命中率验证
3. 多盘部署优先 RAID/LVM 再考虑多目录（倾斜问题）
4. 思考题答案要点：应用层可以自管批量（内存聚合 + 定时/定量 flush），优点是策略可控（比如按业务优先级刷），缺点是把丢数据风险、GC 压力、崩溃恢复全部揽到应用层——**PageCache 是免费的、久经考验的中间层，除非有特殊调度需求，不要重复造轮子**

## 四、深入追问

### Q1：PageCache 方案和 Direct IO 方案各适合什么？

PageCache：读多写多、有热数据局部性（MQ 追尾读、DB）——缓存收益大。Direct IO（绕开 page cache）：写一次读一次的大文件流（备份、全量导出）——缓存纯浪费还污染热数据。Kafka 追尾读模型是 PageCache 的完美场景（刚写入的数据还在缓存里就被消费）。

### Q2：WAL 为什么"量小且可预测"？

MQ 的 WAL（如 BookKeeper journal）只记**写入意图**而非全量数据副本，日志量 ≈ 元信息量级；且写入速率上限可由配置（缓存大小、flush 策略）推算——所以可以配小容量高性能盘（NVMe）专盘专用。与之对比，数据盘要大容量低成本（SATA SSD/机械盘）——**分层存储思想在单机上的雏形**。

### Q3：多副本"只要不是全部同时重启就不丢"的数学依据是什么？

假设单机年故障率 p，n 副本同时故障率 ≈ p^n（独立故障假设下）。三副本 + 跨机架/跨 AZ 部署把"同时"概率压到天文数字——这就是多副本替代单机强刷盘的底气：**用故障独立性换可靠性，比追求单机绝对可靠便宜得多**（与 Kafka 官方"靠副本而非刷盘"同哲学）。

### Q4：mmap 和 sendfile 怎么选？

mmap：文件映射进进程地址空间，适合**随机读写**（Redis/RocketMQ 的索引文件、需要修改的场景）；省一次内核→用户拷贝但可读写。sendfile：纯**转发**场景（读文件发网卡，内容不动）——MQ 消费响应、静态文件服务器。Kafka 消费链路用 sendfile（FileChannel.transferTo），RocketMQ 读用 mmap（MappedByteBuffer）+ 写用堆外内存。**看是否需要在用户态碰数据**。
