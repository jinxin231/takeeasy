# 05：存储——消息数据和元数据的存储是如何设计的？

> 来源：极客时间《深入拆解消息队列47讲》许文强
> 整理日期：2026-11-06

---

## 一、内容总结

存储模块 = MQ 高吞吐/低延时/高可靠的**最核心模块**。分**元数据存储**和**消息数据存储**两块。MQ 的数据是临时缓冲，过期自动删除是必备能力。

**元数据存储**（Topic/Group/User/ACL/Config——量小、读写少、要求强一致高可靠、要通知所有 Broker）：

| 思路 | 代表 | 优点 | 缺点 |
|---|---|---|---|
| **第三方组件**（业界主流） | Kafka ZK 版、Pulsar（ZK）、RocketMQ（NameServer+Broker） | 复用一致性存储/读写/Hook 机制，**开发成本低**；集群构建也可复用 | 部署运维复杂；第三方稳定性引入风险；**元数据不一致无法根治** |
| 集群内部自实现 | Kafka 去 ZK（KRaft）、RabbitMQ Mnesia、RedPanda | 部署运维简单、无不一致隐患 | 前期开发成本巨大 |

选型结论：**项目前期选第三方**（开发成本优先）；架构成熟或投入充足再自研（使用/机器/运维成本长期更低，根治隐患）。

**消息数据存储四部分**：

**① 存储结构设计**——Topic 只是逻辑组织，**分区才是存储最小单位**。两种思路：

| | 每分区一文件（Kafka） | 全分区共享一文件 + 索引（RocketMQ/RabbitMQ/Pulsar-BookKeeper） |
|---|---|---|
| 写 | 单文件顺序写；**分区多了硬盘层面退化为随机写**，FD 占用多 | 永远单流顺序写，**写入性能一直很高** |
| 读 | 数据连续，顺序读+预读最优 | 同分区数据不连续，随机读（SSD 可缓解） |
| 管理 | 分区多管理复杂 | 管理简单 |

选择核心：**对读和写的性能要求**。目录组织有"topic/分区二级"和"topic-分区一级"两种，无实质优劣。FD 上限可配几十万，不用太担心。

**② 数据分段**：单文件过大会导致加载/写入/检索/清理低效 → 按大小分段（默认约 1G，可配）。分段后的消息定位两种思路：
- **偏移量定位**：段文件名携带起始偏移量，二分查找定位文件——适合每分区一文件（数据同属一分区，二分最快）
- **索引定位**：独立索引文件记录消息的文件+位置——适合共享文件（数据属于多个分区，二分低效，**哈希查找最快**；RabbitMQ/RocketMQ 用此）

**③ 存储格式**：文件内是**二进制**（性能/空间；cat 是乱码，要用工具如 `kafka.tools.DumpLogSegments`）。内容格式 = **通用信息**（时间戳、CRC、Header、Value、偏移量、长度）+ **业务信息**（事务、幂等、系统标记、来源/目标节点）。Kafka V2 还有 Batch 相关字段（base/last offset）。设计原则：**完整且不冗余**——冗余费磁盘和网络，缺字段有些功能做不了。

**④ 数据清理机制**（三种方案）：

| 方案 | 机制 | 优点 | 缺点 | 使用者 |
|---|---|---|---|---|
| ACK 删除 | 消费成功回调 ACK → 标记删除 | 不重复消费 | **无法消息重放**；前一条卡住要配死信队列 | RabbitMQ |
| 时间/大小过期 | 提交位点标记进度，异步线程按策略清理 | **可重放** | 客户端用不好会大量重复消费 | Kafka、RocketMQ |
| **结合** | Group 维度 ACK（消息不删、本组不重消费、新组可再订阅） | 兼顾重放与组内不重复 | 实现最复杂 | Pulsar（作者认为最合理） |

**删除实现讲究：延时删除、以段为单位清理**——段内数据全可删才整段删；单条删除先**标记删除**（内存/Backlog 文件记录），消费时感知标记跳过，避免反复"读文件-删记录-写文件"的随机 IO。

## 二、设计问答（Q&A）

### Q1：元数据为什么用第三方组件而不是自己存？

元数据量小但要求强一致 + 高可靠 + 要通知所有 Broker——自己实现等于重写一遍 ZK。复用 ZK/etcd 的一致性存储和 Watch 机制，开发成本最低。代价：部署运维复杂度、第三方稳定性风险、元数据不一致隐患（无法根治）。所以架构成熟后都转向自研（KRaft、Mnesia）——**先求活下来，再求活得好**。

### Q2：每分区一文件 vs 共享文件怎么选？

看读写侧重：写多读少选共享文件（顺序写永远成立）；读性能敏感选每分区一文件（顺序读+预读）。Kafka 吞吐优先选前者（分区过多写性能衰退是已知代价），RocketMQ/Pulsar 选后者 + SSD 缓解随机读。

### Q3：分段后怎么定位一条消息？

两种：偏移量定位（段文件名带起始 offset，二分查找——Kafka，适合数据同属一个分区）；索引定位（独立索引文件哈希查找——RocketMQ/RabbitMQ，适合多分区共享文件）。**定位方式是被存储结构决定的**。

### Q4：消息存储格式为什么要带 CRC、时间戳、长度这些"非业务"字段？

CRC：数据损坏检测（磁盘位衰减、传输错误）；时间戳：过期清理/按时间消费/轨迹；长度：快速跳过本条读取下一条（变长记录的游标）。这些是"格式完整性"的一部分——缺了某些功能（按时间查、损坏检测）就做不了。

### Q5：三种过期删除方案怎么选？

要能重放 → 不能选 ACK 删除；要高吞吐 + 可重放 → 时间/大小过期；要兼顾多业务订阅 + 组内不重复 → Group 维度 ACK（Pulsar 式，作者认为最合理）。RabbitMQ 的 ACK 删除源自其"消息即任务"的业务消息定位。

### Q6：为什么删除要"以段为单位 + 标记删除"？

文件内既有可删又有不可删数据，即时删除要反复"读-找-删-写"随机 IO。标记删除（先记 Backlog/内存标记，消费时跳过）+ 段整体清理（段内全可删才删文件）把随机写变成整段删除——和 LSM 的压缩、ES 的段合并（标记删 + 段切换）是同一思想（联动 mq-deep-dive 01、5.nosql 01 笔记）。

1. Kafka 排查存储文件：`kafka-run-class.sh kafka.tools.DumpLogSegments --files xxx.log --print-data-log` 看格式化内容
2. 设计新存储系统先回答：存什么（元数据/数据）→ 按什么组织（Topic/分区）→ 单文件还是共享文件 → 怎么分段 → 怎么定位 → 怎么清理（本讲思考题的思考路径）
3. 评估 MQ 可靠性方案时问一句：过期删除是哪种？决定能否做消息回放/审计

## 四、深入追问

### Q1：Kafka 去 ZK（KRaft）为什么是大势所趋？

ZK 方案的三宗罪：①额外一套集群要部署运维（机器+人力成本）；②元数据不一致窗口（ZK 与 Broker 状态对不上的幽灵问题）；③分区数量受 ZK 写入瓶颈限制（ZK 不是为高并发元数据写设计的）。KRaft 把元数据变成**内部 Topic + Raft 共识**——元数据即日志，和消息数据用同一套存储复制机制，架构收敛。这印证了文章观点：第三方组件是"前期求快"，自研是"长期求解"。

### Q2：RocketMQ 的 commitlog + index 结构下，消费队列（ConsumeQueue）起什么作用？

ConsumeQueue 是每个分区的**定长索引文件**（offset/size/tagcode 20 字节一条），消费时按分区读 ConsumeQueue（定长所以二分/顺序都快）→ 拿 commitlog 物理偏移 → 回 commitlog 读消息本体。等于把"共享文件的随机读"拆成"索引文件顺序读 + 数据文件精准读"——**索引层把随机度吃掉大半**。这是共享文件方案能用起来的关键工程补丁。

### Q3：ACK 删除方案下，"卡住的消息"除了死信还有别的解法吗？

有：①**重试队列**（RocketMQ：失败后先投重试 Topic，阶梯延迟重试 N 次再进死信——死信是最后归宿不是第一选择）；②nack + requeue（RabbitMQ：重新入队，但要防死循环）；③消费端暂停 + 人工介入。核心矛盾：严格顺序与单条失败不可兼得——**死信/重试队列本质是"保进度"对"保单条"的让位**。

### Q4：为什么说"MQ 数据不需要存一年"？存储定位的差异在哪？

MQ 是缓冲管道，数据的价值随时间快速衰减（业务消息消费完即失效，日志流转完即归档）；需要长期留存的数据应归档到廉价存储（对象存储/HDFS）——这正是分层存储的动机（见 37 讲预告）。**MQ 的 TTL 机制承认了一个事实：它不是数据库**。
