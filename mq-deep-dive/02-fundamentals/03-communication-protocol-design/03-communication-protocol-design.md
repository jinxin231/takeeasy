# 03：通信协议——如何设计一个好的通信协议？

> 来源：极客时间《深入拆解消息队列47讲》许文强
> 整理日期：2026-11-06

---

## 一、内容总结

**基础 MQ 的五模块**：通信协议、网络模块、存储模块、生产者、消费者。MQ 本质是 CS 模型，通信协议是客户端与 Broker 交互的地基。

**协议的四个要求**（MQ 高吞吐/低延时/高可靠映射到协议层）：①可靠性高不丢数据；②性能高延时低；③内容精简带宽利用率高；④可扩展方便功能增减。

**公有协议 vs 私有协议**：
- 公有：AMQP、MQTT、OpenMessaging（还有 JMS/HTTP/STOMP）——为互通性而生，但标准制定慢、**灵活性不足跟不上需求变化**
- 私有：Kafka/RocketMQ/Pulsar 各自自定义——**功能支持、迭代速度、灵活性**完胜。所以主流 MQ 核心链路都用私有协议

**私有协议设计三步**：①网络通信协议选型；②应用通信协议设计；③编解码实现。

**① 网络通信协议选型**：
- **TCP 是绝对主流**（可靠 + 长连接）。UDP 虽快但不可靠，没人用
- HTTP（七层）三次握手/四次关闭 + 协议结构不精简 → 核心链路不用；但客户端库丰富、接入成本极低 → **轻量 MQ（AWS SQS、腾讯 CMQ）主链路用 HTTP**，牺牲性能换多场景接入门槛——"某些对耗时不敏感的业务，降低接入成本收益很高"

**② 应用通信协议设计**：
- 结构 = **协议头 + 协议体**；请求和返回**分开设计**（请求变化频繁，返回只需标识对应请求——协议版本分开定义，升级更灵活）
- 协议头放**请求维度的通用信息**（Kafka V2 请求头：api_key 请求类型、api_version 协议版本、correlation_id 请求 ID、client_id 客户端 ID）；返回头只需 correlation_id + 处理结果
- 协议体放**业务维度的具体内容**，设计三原则：**极简**（字段、类型都压缩，省带宽和省编解码开销）、**向后兼容**、**协议版本管理**
- **数据类型要自定义**（如 INT16/INT32）——原因：①多语言通信，各语言基础类型定义不同会解析错乱；②尽量精简长度（1 byte 能表达就别用 4 byte）

**③ 编解码（序列化/反序列化）**：
- 必要性：网络传输是二进制流，发送端编码、接收端按约定解码
- 核心难题是 **TCP 粘包/拆包**（TCP 是流协议无边界）。解法：消息定长 / 分隔符（FTP）/ **消息头带消息总长**（主流）/ 复杂应用层协议
- 两条路径：自定义实现（RabbitMQ、RocketMQ 4.x、Kafka——历史原因）vs **成熟框架 Protobuf**（Pulsar、RocketMQ 5.0）

**RocketMQ 双协议实证**（业界唯一双支持）：5.0 前 Remoting 自定义编解码（要自己设计头体结构、各语言分别实现）；5.0 起 gRPC（基于 Protobuf）——只定义消息体即可，结构简单、工具生成多语言代码。**新项目/新架构选 Protobuf**。

**经验谈**：协议内容设计考验功底——放多浪费带宽，放少频繁改协议。技巧：参考业界主流协议的元素和踩坑史。**核心是保证向前/向后兼容**，不可能一次设计完美。

## 二、设计问答（Q&A）

### Q1：为什么 MQ 不用 HTTP 做主链路协议？

HTTP 每次通信要走完整 HTTP 语义（握手、header 冗长），结构不精简、延时高，不适合高吞吐低延时。但轻量 MQ（SQS/CMQ）反用 HTTP——接入门槛极低、客户端库现成，对耗时不敏感的业务是正确取舍。**协议选型 = 需求匹配，不是性能攀比**。

### Q2：为什么主流 MQ 都选私有协议而不是 AMQP/MQTT？

公有标准协议制定周期长，跟不上功能迭代（事务消息、延迟消息等新功能等不起标准）；私有协议可以按自身需求精简直通。代价：每款 MQ 一套 SDK，用户切换成本高——这正是 AMQP 当年想解决而没解决的问题。

### Q3：协议头和协议体的划分原则？

**请求维度的通用信息放协议头**（版本、请求 ID、客户端 ID、请求类型），**本次请求的业务内容放协议体**。请求头和返回头分开做版本管理——返回头只需 correlation_id，变化少。

### Q4：为什么不能直接用 int/string 当协议字段类型？

①多语言解析不一致（各语言对基础类型的定义/字节序不同）；②长度浪费——自定义类型（INT8/16/32）按需占位。参考 Kafka 协议类型或 Protobuf 类型系统设计。

### Q5：TCP 粘包/拆包怎么处理？

TCP 是流协议无消息边界。主流方案：**消息头携带消息总长度**，接收方先读头、按长度读体。其余方案：定长消息（浪费）、分隔符（要转义）、完整应用层协议（HTTP/WebSocket）。Netty 的 LengthFieldBasedFrameDecoder 就是这个原理的现成实现。

### Q6：自定义编解码 vs Protobuf 怎么选？

新项目一律 Protobuf（或 gRPC 全家桶）：多语言代码生成、编解码性能高、向后兼容内建、社区成熟。自定义只在两种情况下合理：历史包袱（RocketMQ Remoting）、极端性能裁剪。RocketMQ 5.0 的演进就是官方答案。

## 三、选型与实践要点

1. 设计私有协议先抄作业：Kafka 协议（字段精简史）、gRPC/Protobuf（结构定义）
2. 兼容性纪律：协议版本独立演进、新字段向后兼容、废弃字段先标记后删除
3. 轻量接入需求强烈的场景，HTTP/REST 网关可作为私有协议的补充接入层（不替代主链路）

## 四、深入追问

### Q1：为什么业界存在多种"标准"消息协议？（思考题）

因为每个标准都想终结分裂但都成了新的分裂（XKCD 927 定律）：AMQP 太重（金融基因）、MQTT 太轻（物联网基因）、OpenMessaging 来得太晚。深层原因：**协议绑定了场景假设**——吞吐、延迟、可靠性的权重各场景不同，单一协议无法同时最优。所以"标准"存活在各自场景里，统一反而没了。

### Q2：Kafka 协议的 correlation_id 解决了什么问题？

TCP 长连接上**多请求并发在途**（流水线化），响应顺序不保证与请求一致——correlation_id 让客户端把响应关联回请求。没有它要么串行（性能差）要么歧义。这是所有长连接私有协议的标配设计（HTTP/2 的 stream id 同理）。

### Q3：Protobuf 为什么比 JSON/XML 适合当编解码？

二进制编码（varint 压缩）体积为 JSON 的 1/3~1/10；编解码是内存操作无需文本解析，快一个数量级；schema 内建字段编号 → 天然向后兼容（加字段不炸老客户端）。代价：不可读（要工具解码）、调试不如文本直观——MQ 主链路性能优先，可读性让位。
