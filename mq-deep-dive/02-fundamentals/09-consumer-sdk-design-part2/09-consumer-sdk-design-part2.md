## 一、内容总结

**消费分组（Consumer Group）**：组织**消费者、分区、消费进度**三方关系的逻辑概念。为什么需要它：不重复消费就要记录进度，进度需要一个标识——这个标识就是消费分组。三大功能：①管理消费者↔分区对应关系；②保存消费进度；③实现消息可重复消费（多组各自消费）。分组数据是集群元数据的一部分，存 Broker 的元数据服务。分组与 Topic 强相关：一组可订阅多 Topic，一 Topic 可被多组订阅。

**Rebalance（消费重平衡）**：消费者/分区变动（消费者挂、新增消费者、分区数变）时重新分配消费关系。**协调者（Coordinator）**：拥有分组+消费者+分区三方信息、执行重平衡并记录进度的模块。分配可在协调者内完成再同步给消费者，或由某个消费者计算后同步——技术优劣差别不大。
- Kafka 的协调者定位：消费组名 hash % `__consumer_offsets` 分区数 → 该分区 Leader 所在 Broker 即协调者。

**消费分区分配策略三原则**：①负载尽量均衡（最常用）；②重平衡时**尽量少变动**（加速收敛、保持处理连续性）；③支持业务特性（机房就近等）。
- **轮询**：所有分区打乱逐个分，每人分区数相差 ≤1；缺陷：多 Topic 订阅时同 Topic 多分区可能集中到一个消费者 → 倾斜 → 变种（同 Topic 分区尽量打散到不同消费者）
- **粘性（Sticky）**：变动时只重分受影响的，其余不动——**一致性哈希是常用实现**（节点变动只需少量再分配）
- 特色：RocketMQ 机房就近/指定机房（跨 AZ 场景）；Kafka RoundRobinAssignor 改进版
- 自定义：实现 PartitionAssignor 接口（Kafka）

**消费确认（ACK）两种形态**：
| 形态 | 机制 | 优劣 | 使用者 |
|---|---|---|---|
| 确认后删除 | ACK 回调即删数据（单条/批量 ACK） | 不重复消费；**不能回溯**，用得少 | RabbitMQ 类 |
| **保存消费进度**（主流） | 提交位点，删除交给过期策略 | 可回溯多次消费 | Kafka/RocketMQ/Pulsar |

**进度保存**：
- **服务端保存（默认）**：调服务端"提交消费进度"接口，服务端用内置 Topic/文件持久化（Kafka `__consumer_offsets`）；客户端封装好、简单不灵活
  - **自动提交**：按时间批次或拉到即提，用户无感知——**可能丢数据**（拉到未处理就提交）
  - **手动提交**：业务处理完再提——**作者建议手动**，避免丢失
- **客户端自定义保存**：自己存缓存/文件/服务——灵活但有额外工作量；业务需要（如回滚位点）时用

**消费失败处理三段**：
| 失败点 | 处理 |
|---|---|
| 拉取失败 | 可重试错误重试，不可重试向上抛（同客户端错误处理） |
| **本地业务处理失败** | 偶发：业务重试 + 手动提交。一直失败（毒消息）：**死信队列**接住，保证进度不阻塞 |
| 提交位点失败 | **一直重试**；持续失败向上抛——否则重拉同批数据造成重复消费 |

**消费端设计三步**：①能消费、能确认（基本）→ ②快速稳定消费（性能稳定）→ ③回溯/删除/广播（功能）。

## 二、设计问答（Q&A）

### Q1：为什么需要消费分组这个概念？

不重复消费必须记录进度，进度需要归属标识——分组就是这个标识。它顺带解决：①消费者↔分区分配关系的载体（rebalance）；②多业务方独立消费同一 Topic（各自进度 = 广播消费的基础）；③回溯消费（重置组位点即可重放）。**空分组无意义**——分组因订阅 Topic 而存在。

### Q2：协调者是干什么的？Kafka 怎么选协调者？

协调者掌握分组+消费者+分区三方信息，执行 rebalance 并记录消费进度。Kafka：组名 hash % `__consumer_offsets` 分区数 → 分区 Leader 所在 Broker 任协调者——**元数据 Topic 的分区 Leader 天然分散，协调者负载天然均衡**。

### Q3：轮询和粘性分配怎么选？

轮询追求**均匀**（每人分区数差 ≤1），粘性追求**少变动**（rebalance 只动受影响的）。高频率变动/大组大分区场景选粘性（rebalance 耗时和切换成本敏感）；追求理论均衡选轮询及其打散变种。Kafka 的 CooperativeStickyAssignor 进一步做到**增量协作式 rebalance**（不全停）。

### Q4：自动提交和手动提交怎么选？

**手动提交**。自动提交在"拉到未处理"时提前记位点 → 宕机丢消息；手动提交把位点控制权还给业务（处理成功才提交），代价是要处理重复消费（幂等）。这呼应可靠性铁律：**不丢和不重不能兼得，位点后置 + 幂等是唯一正解**（见 3.mq 26/27 笔记）。

### Q5：消费一直失败的数据怎么处理？

毒消息处理链：业务重试（限次限时）→ 仍失败投**死信队列**保存 → 消费继续前进。**不能让单条消息卡住整个分区**——毒消息隔离 + 死信告警 + 人工/自动修复通道（联动 3.mq 25 笔记）。

### Q6：思考题——倾斜分区堆积怎么解？（上节闭环）

三情况：①数据可丢 → 重置位点到最新（历史丢弃，但消费跟不上还会再积）；②不可丢不保序 → 切**共享消费**，多消费者打一个分区 + 横向扩人根治；③不可丢且保序 → 只能**治生产端**（写入倾斜的根源治理）。

## 三、实践要点

1. 生产配置清单：`enable.auto.commit=false` + 处理成功手动提交 + 幂等消费——可靠消费三件套
2. rebalance 频繁排查：消费者 hang（max.poll.interval.ms）、网络抖动、分区数变动——粘性分配缓解
3. 位点保存选型：默认服务端保存；要做"消费到某状态才推进位点"或跨系统事务时，客户端自定义保存

## 四、深入追问

### Q1：Kafka 的 __consumer_offsets 为什么用内置 Topic 而不是 ZK/外部存储？

早期 Kafka 用 ZK 存 offset——ZK 写入性能差（每节点都要走 Leader），高频提交直接把 ZK 打垮。改内置 Topic 后：offset 提交 = 写消息，享受 Kafka 自身的批量/顺序写/副本机制，**用 MQ 自己的强项解决自己的元数据**——自举（bootstrap）设计。这也是 KRaft 去 ZK 的同源思路（见 05 笔记 Q1）。

### Q2：粘性分配为什么要用一致性哈希而不是"最小改动贪心"？

一致性哈希把"消费者-分区"映射变成环上的确定性函数——变动时只需迁移环上相邻区段，**算法无状态、收敛快、实现简单**。贪心最小改动要维护"当前分配状态"并在每次 rebalance 做 diff——状态一致性本身成为新问题（各消费者视图不一致时贪心结果发散）。工程上：**无状态算法 > 有状态算法**。

### Q3：手动提交失败一直重试，会不会卡死消费？

会——所以重试要有上限和退避，耗尽后向上抛错让业务决策（暂停消费/告警）。更精细的做法：**位点提交与拉取解耦**——提交失败期间继续拉取和处理（位点缓存待提交），但要控内存水位，防"处理了一堆但位点没推进"宕机后大面积重复消费。

### Q4：广播消费的三种实现怎么选？

- 内核投递（Pulsar Share）：体验最好但要内核支持
- **多消费组**（Kafka/RocketMQ 主用）：零开发，每组独立位点——代价是每组都全量拉一遍，**读流量 × 组数**（组多了 broker 读压力大）
- 指定分区 + 本地记位点：最灵活但位点管理自担，故障恢复复杂
选型：组少（≤3）用多分组；组多考虑共享订阅或换 Pulsar。
