## 一、内容总结

消费端功能五块：消费模型、分区消费模式、消费分组（订阅）、消费确认、消费失败处理。本讲覆盖前两块。

**消费模型：Pull / Push / Pop**

**① Pull 拉模型（业界主流）**：客户端轮询拉取。优点：客户端按自身速率拉取，不对双方造成额外压力。缺点：**空轮询**浪费资源、及时性不足。
- 空轮询治理（客户端等待策略不好定，所以服务端协助）：
  - 方案 A：服务端 **hold 住请求**（没数据等一段时间，有数据一起返回）——吞吐好；但 hold 太久客户端超时、消费延时高
  - 方案 B：服务端有数据时通知客户端——但 CS 半双工，服务端不能主动触达客户端
  - **最佳实践**：客户端拉取时带三个参数——**最多多少、最少多少、没凑够最少时最多等多久**。有则立即返回；不足则 hold 到超时返回当前结果。空轮询 TPS 可预估（总时间/等待时长）；要降低消费延时就调小"最小数据量 + 最大等待时长"，理想延时可压到两次 Pull 的间隔。业务消息场景可直接把等待设为 0（请求-返回模式）

**② Push 推模型**（为消费及时性而生）三种实现：

| 实现 | 机制 | 优劣 | 使用者 |
|---|---|---|---|
| Broker 内置 Push | Broker 主动推给客户端 | 无需重复开发，Broker 感知堆积推送及时；**维护海量长连接 + 处理客户端异常（卡住/接收慢）反压 Broker 性能稳定性** | RabbitMQ、金融证券 MQ（要全链路毫秒级） |
| 独立 Push 组件 | 第三方组件先 Pull 再 Push | 隔离 Broker 风险；本质还是先 Pull，延时仍在，开发运维成本高 | 回调/事件触发场景，流消费少用 |
| **客户端伪 Push** | SDK 底层 Pull → 内存队列 → **回调用户函数** | 用户体验是 Push；底层仍是 Pull 的轮询和延时（可靠编码技巧缓解） | **主流 MQ 的常用方案** |

**③ Pop 模型**（为解决 Push/Pull 的客户端重、rebalance 暂停且慢、消费倾斜而生）：客户端**不感知分区**，像 HTTP 一样调 `Pop` 接口拿数据、消费后 `ACK`。**分区分配、进度管理移到服务端**，服务端还能感知堆积、按堆积分配数据。本质上是 Pull 的变种，但实现思路和适用场景不同。

**分区消费模式四种**：

| 模式 | 语义 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **独占消费**（默认） | 一个分区同一时间只被一个消费者消费；消费者 > 分区数则有人空置，反之一人多分区 | **分区有序**；关系变动时重新分配 | 数据倾斜或消费者 hang → 分区堆积 | Kafka/RocketMQ/Pulsar 默认 |
| **共享消费** | 一个分区可被多个消费者同时消费，一条数据只投一人 | 单分区性能最高；单消费者出问题不堆积 | **不保序** | 日志等无序场景（Pulsar Share 模型） |
| **广播消费** | 一条数据所有消费者都收到 | 全员收 | 实现三路：内核投递（Pulsar Share）、**多消费组**（各管各进度，Kafka/RocketMQ 主用）、指定分区消费（本地记位点） | 配置下发、缓存刷新 |
| **灾备消费** | 独占 + 灾备消费者待命，主挂灾备接 | 顺序 + 容灾 | 解决不了倾斜；多养一个消费者成本高 | 少 |

## 二、设计问答（Q&A）

### Q1：Pull 和 Push 的本质差异是什么？

不是"谁主动"的形式差异，而是**速率控制权**在谁手里：Pull 由消费者按自身能力取（天然背压），Push 由服务端按数据到达推（消费者慢了就堆积/反压）。所以高吞吐、消费者能力参差不齐的场景必须 Pull；只有"消费者少且快、投递及时性极致"（金融行情）才用真 Push。客户端伪 Push 是体验与安全的折中。

### Q2：Pull 的空轮询怎么治？（三参数模型）

客户端拉取携带：最多拉多少（maxBytes）、最少拉多少（minBytes）、不足时最多等多久（maxWaitMs）。服务端：够 minBytes 立即返回；不够则 hold 到超时返回当前结果。效果：空轮询 TPS 封顶可预估、消费延时可压到两次 Pull 间隔。Kafka 的 `fetch.min.bytes`/`fetch.max.wait.ms` 就是这个模型。

### Q3：为什么 Broker 内置真 Push 在主流 MQ 中用得少？

Broker 要维护与所有消费者的长连接，处理客户端卡住/接收慢/处理慢等异常——推送、异常处理、连接维护都消耗 Broker 资源，形成**对 Broker 的反压**，性能和稳定性受损。Broker 的职责边界应该是存储与分发，不该背消费者的健康状态。

### Q4：Pop 模型解决了什么问题？

Pull/Push 下客户端要感知分区分配、参与 rebalance（暂停消费、可能耗时很长）、消费倾斜。Pop 把分区分配和进度管理收归服务端，客户端只剩 `Pop`/`ACK` 两个调用（HTTP 式）。适合**轻量化接入**（云函数、多语言瘦客户端、Serverless——与 Pulsar/RocketMQ 5.0 Proxy 的云原生方向一致）。

### Q5：思考题——分区数据倾斜导致部分分区堆积，选什么消费模式？

**共享消费**：倾斜分区的数据可同时被多个消费者消费，天然打散热点（独占模式下热点分区只能一个消费者死扛）。代价是放弃该分区的顺序语义——若业务要保序，则不能用，只能治本（槽分配/一致性哈希重分布，见 3.mq 24 笔记）或扩容 + 异步消费。

## 三、实践要点

1. 排查消费延时先看 Pull 三参数（minBytes/maxWaitMs）——默认参数在高吞吐场景可能引入不必要等待
2. 消费模式选择决策树：要顺序 → 独占（倾斜治本）；不要顺序要吞吐 → 共享；全员接收 → 广播（多消费组）
3. rebalance 频繁/耗时长（大组大分区）的场景评估 Pop/Share 类模型或静态成员（static membership）

## 四、深入追问

### Q1：hold 住请求会不会把服务端连接/线程耗尽？

hold 的是"未完成的响应"，不是线程——基于 NIO 的异步 IO 里 hold 不占用工作线程（请求对象挂到等待队列，事件驱动）。但要控制：①hold 时长上限（防超时风暴）；②hold 请求数上限（防内存堆积）；③连接级心跳继续走（防假死）。Kafka 的 purgatory（炼狱）就是这套延迟操作的实现——DelayedOperation 挂时间轮，条件满足或超时触发。

### Q2：客户端伪 Push 的"编码技巧"指什么？

①后台拉取线程 + 有界内存队列（防 OOM，队列满则暂停拉取——背压）；②拉取参数自适应（堆积时调大批次，空闲时调小等待）；③回调分发用独立线程池，避免用户回调卡住拉取线程；④rebalance 时暂停拉取并排空队列防乱序。本质：**把 Pull 的轮询细节全部藏在 SDK 里**。

### Q3：独占消费下消费者 hang 住导致分区堆积，框架层面能做什么？

①`max.poll.interval.ms` 判死踢出（rebalance 把分区给别人）——但判死时间长，堆积已发生；②**灾备消费**（本文方案）；③共享消费无此问题（天然多消费者）；④监控 lag + 告警人工介入。治本是业务侧：消费逻辑做超时保护，别让单条毒消息卡死线程（呼应 3.mq 25 笔记毒消息处理）。

### Q4：Pop 模型下服务端怎么做分区分配和进度管理？

服务端维护"虚拟订阅队列"：Pop 请求到来时按堆积情况/轮询策略选一个分区的下一批数据返回，记录"已 Pop 未 ACK"的 in-flight 集合；ACK 则推进位点，超时未 ACK 重新入可 Pop 池。难点：①in-flight 状态管理（类似 RabbitMQ 的 unacked）；②多客户端并发 Pop 同一分区时的互斥分发。这正是 Pulsar 的 Shared 订阅在 Broker 端的实现思路。
