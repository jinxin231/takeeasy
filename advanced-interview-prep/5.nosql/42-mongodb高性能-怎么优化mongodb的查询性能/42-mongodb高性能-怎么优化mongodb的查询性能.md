## 一、文章总结

**查询过程（mongos 的角色）**：分片集合的查询由 **mongos** 路由到目标分片并**合并结果集**（类比：分库分表中间件/代理计算目标表）。mongos 是查询的潜在瓶颈。

**ESR 规则（索引设计黄金法则）**：索引列按 **E（Equality 等值）→ S（Sort 排序）→ R（Range 范围）** 的顺序排列。可重复（EESR、ESSR、ERR 都行），**相对顺序不能乱**（A 等值 B 排序 C 范围就必须建 ABC，BAC 违背）。

**六大优化方案**：

| 方案 | 机制 | 案例/要点 |
|---|---|---|
| **1. 覆盖索引** | 查询字段全在索引里（projection 指定），不加载整个文档 | 新接口只返回必需字段，性能 +30%；更新同理——只传/只更新修改字段，别整文档覆盖 |
| **2. 优化排序** | 能用索引排序就直接按索引序读，否则**内存排序**（叠加 `skip(100000).limit(100)` 深分页更致命——要加载全部再排序） | ①改查询或**新建索引**让排序走索引；②借鉴分库分表**禁跳页**：带上一页排序字段极值（`create_time <= $last_min`），极值取 max/min 取决于排序方向 |
| **3. 增加 mongos** | mongos 合并结果集是 CPU/内存/带宽瓶颈（深分页时要在 mongos 上全局排序） | 加实例 + **独立部署**独享资源；进阶：**隔离**——核心业务独立 mongos / 独立集群 |
| **4. 拆分大文档** | 大文档加载成本高。拆法二选一（可叠加）：按**访问频率**拆（高频小字段一文档、低频大字段一文档）；按**字段大小**拆（巨大字段独立成文档） | 案例：一拆三——高频小字段 / 低频大字段 / 其余。缺点：需要完整文档时查三次再合并。**最好一开始就约束文档大小** |
| **5. 嵌入文档**（反向下策的反面） | A、B 关联紧密且总是一起查 → B 嵌入 A，两次查询变一次 | **懒惰渐进式整合**：查 A 发现没嵌入 B 就查 B 嵌入后更新 A，更新条件带"A 不包含 B"（**乐观锁**）；变种：**冗余字段**（如昵称头像冗余，容忍不一致） |
| **6. 操作系统优化** | 索引要全内存（钞能力加内存）；调小 `vm.swappiness` 防交换 | 与 Kafka/ES/MySQL 的 OS 层优化一脉相承 |

**思考题 1 补答（网络/磁盘 IO）**：网络——调大 TCP 读写缓冲区（同 Kafka）；磁盘——WiredTiger 本来就重度依赖 page cache 与顺序写 journal，XFS/禁 atime 同样适用，但收益不如内存和索引直接（效果中等，优先级排后）。

**面试准备清单**：慢查询案例（原因/解法）、索引优化经历、参数调整史、平均 RT 与 99/999 线。策略：**MySQL + ES + MongoDB 三者优化合并讲**，横向对比立"方法论人设"。

## 二、Q&A（问题 + 标准答案）

### Q1：MongoDB 的查询是怎么执行的？

分片集群：mongos 接收查询 → 按片键路由到目标分片（无片键条件则广播全分片）→ 各分片执行 → mongos **合并结果集**（排序/分页在 mongos 上做）。所以 mongos 是潜在瓶颈——优化手段：加 mongos 实例、独立部署、核心业务隔离。

### Q2：MongoDB 索引设计遵循什么规则？

**ESR 规则**：等值列在前、排序列居中、范围列最后（E→S→R）。列可重复（EESR/ESSR/ERR），相对顺序不可乱。原理：等值定位索引区间后，排序列在区间内的索引序直接可用（避免内存排序），范围列放最后做过滤。

### Q3：怎么优化一个"排序 + 深分页"的慢查询？

两步：①建索引让排序走索引（ESR 中 S 列对齐排序字段），消除内存排序；②深分页改**极值翻页**（禁跳页）：每页带上一页排序字段的极值条件（如 `create_time < $上一页最小值`），查询量与偏移量脱钩。这和 MySQL/分库分表/ES Search After 是同一套思想。

### Q4：覆盖索引在 MongoDB 里怎么用？

`projection` 只返回索引字段，MongoDB 直接从索引取数，不加载文档本体。案例：旧接口返回整个文档 → 新增只返回必要字段的接口，调用方迁移后性能 +30%。更新侧同理：只更新修改字段，别整文档覆盖写。

### Q5：大文档为什么慢？拆还是嵌？

大文档：加载整个文档的 IO/内存成本高 → **按访问频率或字段大小拆分**（高频小字段一文档、低频大字段一文档），多数查询只碰小文档。反过来，强关联且总是一起查的 A、B 可以**嵌入合并**（两次查询变一次）——**拆与嵌方向相反，判断依据是"数据是否总被一起访问"**。冗余字段（昵称头像）是嵌入的轻量版，代价是一致性。

### Q6：嵌入文档的渐进式迁移怎么做？（乐观锁细节）

懒惰整合：读 A 时发现未嵌入 B → 查 B 嵌入后更新 A，更新条件为"A 仍不包含 B"（乐观锁，防并发重复整合）。前提：B 只通过 A 操作（无独立更新 B 的路径），否则要处理并发一致性。

### Q7：mongos 会成为瓶颈吗？怎么治理？

会：无片键查询广播全分片后 mongos 要合并排序（深分页时尤甚），CPU/内存/带宽都可能打满。治理：①加 mongos 实例（**独立部署**独享资源）；②**隔离**——核心业务独立 mongos 甚至独立集群；③治本：查询带片键、避免深分页、排序走索引，减少 mongos 合并负担。

## 四、面试官连环追问清单（含参考答案）

### Q1：ESR 和 MySQL 的最左前缀原则是什么关系？

同族思想的不同表达：最左前缀是"**索引列从左到右依次生效，中断即止**"；ESR 在此之上细化了**每类列的位置**——等值（能精确定位区间）→ 排序（区间内索引序直接可用）→ 范围（会破坏后续列的有序性，只能过滤）。违反 ESR 的索引在 MySQL 里同样失效：范围列后面的列用不上（`A=?, B>?, ORDER BY C` 中 C 无法走索引排序）。一句话：**ESR 是最左前缀在"等值/排序/范围"三类谓词下的具体化**。

### Q2：什么时候该嵌入，什么时候该引用？（文档建模题）

看三个维度：①**一起读吗**——总是一起查就嵌入（一次查询），否则引用；②**基数**——一对多且"多"侧无界增长（订单的物流轨迹）不能嵌（撞 16MB 文档上限），有界小数组可嵌；③**更新模式**——嵌入文档原子更新（单文档事务天然支持），跨文档引用要保持一致需多文档事务（4.0+ 有但贵）。口诀：**"一起创建、一起读取、一起更新"就嵌入，否则引用**。

### Q3：MongoDB 的 16MB 文档限制怎么影响设计？

嵌入策略的天花板：无界增长的数组（评论列表、操作日志）会撞顶。应对：①**bucket 模式**（按时间/数量分桶，每桶一文档，如每小时一个文档存事件流）；②引用拆分 + 应用层聚合；③超大二进制走 GridFS。设计期就要预估数组增长率——这是"先约束文档大小"比"事后拆分"更优的原因。

### Q4：为什么"内存要装下全部索引"？装不下会怎样？

索引在内存：查找是纯内存二分，微秒级；索引超内存：每次索引查找都可能触发磁盘 IO（page fault），RT 从微秒变毫秒，高并发下 IO 打满雪崩。监控 `wiredTiger.cache` 命中率与 `index size`（`db.collection.stats()`）。扩容优先加内存；其次**索引瘦身**（删冗余索引、用部分索引 partial index、稀疏索引）——WiredTiger 默认缓存是内存的 50% 减 1GB，也要考虑工作集（数据热部分）。

### Q5：MongoDB 需要像 Redis 那样防缓存雪崩吗？（WiredTiger 缓存追问）

WiredTiger 内部缓存（默认 50% 内存）存放的是数据页和索引——重启后缓存全冷，**启动初期慢查询飙升**（MongoDB 版"冷启动"）。应对：①滚动重启（副本集逐台重启，流量不切）；②预热脚本（启动后扫一遍热索引/热数据，或低权重接入流量慢热——与缓存预热、熔断逐步放量同一思想）；③监控 `cache bytes read into cache` 速率判断预热完成度。

### Q6：思考题 2——你印象最深的 MongoDB 优化方案？（开放题备料）

可讲的储备：①**部分索引（partial index）**：只为满足条件的文档建索引（如只对 status='active' 的 1% 数据建索引），索引体积降两个数量级；②**TTL 索引**：过期数据自动删除（验证码、会话），免去定时清理任务；③**读写分离 + tag**：报表查询路由到只读从节点，与在线写入隔离；④`explain("executionStats")` 分析执行计划，重点看 `totalDocsExamined/totalKeysExamined` 比例——扫描文档数远大于返回数就是索引问题。任选其一讲透，比泛泛罗列强。
