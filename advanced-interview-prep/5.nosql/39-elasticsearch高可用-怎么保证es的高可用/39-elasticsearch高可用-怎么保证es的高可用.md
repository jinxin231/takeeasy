## 一、文章总结

**中间件面试的统一框架**：高可用/高性能 ×（中间件自身怎么做的 / 你实践中怎么做的）。本讲 = ES 高可用的"自身机制 + 四个实践方案"。

**节点角色**（原则：**有钱专款专用，没钱兼任**；兼任可能引发性能问题，追求高可用就单一角色）：

| 角色 | 职责 |
|---|---|
| 候选主节点 Master-eligible | 可被选举为主节点；主节点管集群元数据（创建索引等）。另有仅投票节点（只投票不当选） |
| 协调节点 Coordinating | 接收查询 → 分发数据节点 → **合并结果集**（大多数节点兼任） |
| 数据节点 Data | 存数据、执行查询。细分 Hot/Warm/Cold（按数据热度） |

**写入流程与近实时**：
```
文档 → ES Buffer →(refresh，默认 1s)→ Page Cache（生成 Segment，**此时才可被搜索**）→(flush)→ 磁盘 + Commit Point
```
- **近实时（NRT）的原因**：文档只有 refresh 到 Page Cache 生成段后才能搜到，默认 1s 延迟
- **段合并**：写多了段就多（每个段耗 CPU/内存/文件句柄）→ 合并。老段不动 → 新段写入（标记删除的文档不写入）→ **Commit Point 切换**（记录哪些段可用）→ 老段的查询结束后删老段——与数据迁移、LSM-tree 同思想
- **Translog**（类比 MySQL redo log）：写 Buffer 的同时写 Translog，崩溃后用它恢复。Translog 只追加（顺序写，快），**默认 5s 刷一次盘** → 最坏丢 5s 数据

**索引与分片**：ES 的"索引" = 倒排索引 + 文档（语义不同于 RDBMS）。类比分库分表：**索引 = 逻辑表，分片 = 分库分表，每分片主从结构**；分片尽量分散在不同节点（同 Kafka 分区分散 broker）。主分片崩溃 → **主节点**从从分片中选一个提升（类似 Redis Sentinel 选主）。

**四个高可用实践方案**：

| 方案 | 机制 | 要点 |
|---|---|---|
| **限流保护节点** | ①插件：按内存/CPU 使用率超阈值一段时间触发限流（呼应微服务限流）；②网关/代理（如极限网关，市面产品少，担心性能损耗可只当了解）；③**客户端限流**（最好落地：慢查询多的业务阈值压低） | 限流是治标，常触发就该扩容 |
| **消息队列削峰** | 写路径改"写 DB → Canal 监听 binlog → Kafka → 消费写 ES"（替代双写）；ES 闲则快消费、忙则慢消费，天然削峰 | 叠加**降级**：核心/非核心两类消费者，ES 差时停非核心；大促可停全部同步只保查询 |
| **保护协调节点** | 协调节点合并结果集，大请求（命中 10 分片 × 每片几万条）容易 CPU 100%/OOM。①钞能力：纯协调节点专属部署；②**隔离**：客户端判定大请求 → 路由到纯协调节点，普通请求走兼任节点（大请求打崩也只影响大请求）；③大厂可二次开发：资源不足时协调节点直接拒大请求 | 升华：所有节点单一角色，可用性和性能双升 |
| **双集群** | 钞能力：付费 CCR 跨集群复制。穷办法：**MQ 双写**（两个消费者分别写 A、B 集群）+ 查询优先 A、A 故障切 B（切换：客户端封装自动切换——监控 RT/超时率；或 DNS 切换） | 判断集群故障的思路同微服务节点健康检测 |

**面试准备清单**：公司 ES 用在哪、读写流量/数据量、索引分片数怎么定的、有没有高可用措施和网关、出过什么故障。

## 二、Q&A（问题 + 标准答案）

### Q1：Elasticsearch 是怎么做到高可用的？（基本盘）

核心是**分片 + 主从结构**：每个分片有主从副本，主分片崩溃时主节点从从分片中选新主。分片尽量分散在不同节点（单节点崩溃影响最小化）。再补 Translog：写入先落 Buffer 和 Translog（顺序写、5s 刷盘），崩溃后用 Translog 恢复，数据丢失窗口收敛到秒级。

### Q2：为什么 ES 是近实时的？refresh 和 flush 的区别？

文档写入后先待在 ES Buffer，**refresh（默认 1s）** 刷到 Page Cache 生成 Segment 后才能被搜到——所以有约 1s 的可见延迟，叫近实时。flush 是把数据真正落盘并记录 Commit Point（同时触发 Translog 清理）。一句话：**refresh 管"能搜到"，flush 管"丢不了"**。

### Q3：ES 写入过程是什么样的？

文档 → ES Buffer + Translog →（refresh，1s）Page Cache 生成 Segment（可搜索）→ 段持续增多 → 段合并（老段不动、写新段、Commit Point 切换、老查询结束删老段）→（flush）落盘。Translog 5s 刷盘，最坏丢 5s。

### Q4：写入流量太大 ES 扛不住怎么办？（MQ 削峰方案）

双写改异步：业务只写 DB，Canal 监听 binlog 发到 Kafka，消费者写 ES——消费速率随 ES 状态自然伸缩（削峰）。再叠降级：消费者分核心/非核心两类，ES 写入超时增多时停掉非核心消费者；大促可全停同步只保查询。前提：业务对实时性要求不高。

### Q5：协调节点为什么容易崩？怎么保护？

协调节点要**分发请求 + 合并所有分片的结果集**——一个命中 10 分片、每片返回几万条的查询，合并时内存/CPU 瞬间打满（CPU 100%/OOM）。保护：①纯协调节点专属部署；②**隔离**：大请求路由到纯协调节点组，普通请求走兼任节点——大请求崩了只影响大请求；③大厂二次开发：协调节点资源不足时直接拒绝大请求。

### Q6：不用付费 CCR 怎么做双集群？

MQ 双写：写入发消息，两个消费者分别写 A、B 集群；查询优先 A，客户端封装监控 A 的 RT/超时率，异常自动切 B（也可用 DNS 切换——解析从 A 的 IP 换成 B 的 IP）。集群健康判断复用微服务节点检测思路（心跳 + 超时率）。

### Q7：思考题 1——主分片由主节点选，主节点自己怎么选出来的？

主节点由**候选主节点（master-eligible）集群投票选举**产生（Zen Discovery / 7.x 后的新选举层，基于 Raft-like 共识）：多数派（quorum）同意才当选，防止脑裂——所以生产上候选主节点要奇数个（3 或 5），且 `discovery.zen.minimum_master_nodes`（老版本）/ `cluster.initial_master_nodes` 配置正确。仅投票节点参与投票但不当选，用于小集群凑票数。

## 四、面试官连环追问清单（含参考答案）

### Q1：Translog 也可能丢 5 秒数据，能接受吗？怎么调？

默认 `index.translog.durability=async` + `sync_interval=5s`——异步刷盘，最坏丢 5s。要更强持久性：改 `request`（每个请求都 sync 刷盘）——可靠但写入吞吐大降。选型同 MySQL `innodb_flush_log_at_trx_commit` 的 0/1/2：**用吞吐换丢失窗口**。多数业务 5s 可接受（配合业务层重发/对账），金融级改 request 或接受并补偿。

### Q2：段合并会不会影响查询？（和 LSM 的共性追问）

设计上不影响：老段继续服务查询，新段写好 + Commit Point 原子切换后新查询走新段，老段等老查询结束才删。但**资源层面有影响**：合并消耗 IO 和 CPU（读写放大），高峰期合并可能拖慢集群——所以合并策略（tiered 策略、并发度 `max_merge_at_once`、限流 `indices.store.throttle`）是 ES 运维调优的常见项。这套"不可变段 + 后台合并"和 LSM-tree（RocksDB/HBase）完全同构。

### Q3：分片数量怎么确定？分片多了有什么问题？

经验值：单分片 **10GB~50GB**（日志类可到 50GB+）；总分片数考虑节点内存（**每 GB 堆内存约 20 个分片以内**）。分片过多的代价：①每分片是独立 Lucene 索引，占用堆内存/文件句柄；②查询要扇出到更多分片、协调节点合并负担加重（呼应 Q5）；③集群元数据膨胀，主节点压力大。分片过少：单分片过大，迁移/恢复慢，无法水平扩展。创建时定好，后期改要 reindex——**分片数是一次性决策，慎重**。

### Q4：MQ 削峰写入方案的数据一致性怎么保证？（串联缓存模块）

链路：DB（源）→ binlog → Kafka → ES（副本）。窗口：binlog→ES 的延迟（正常秒级，积压时更长）——期间搜索到旧数据。保证措施：①Canal/消费者位点监控告警（延迟超阈值人工介入）；②消费幂等（同文档重复写 ES 无妨，文档 ID 唯一天然幂等）；③强一致场景的关键查询可直查 DB 兜底。和缓存 Refresh Ahead 是同一套思想（见缓存 03 笔记）。

### Q5：为什么大请求隔离在协调节点层做，而不是限流？

限流是"拒绝"，隔离是"分流"——大请求是合法业务（复杂报表、导出），拒绝它等于功能缺失；隔离让它在专属资源池里跑，崩了也只影响同类。这是微服务**舱壁隔离（bulkhead）**在 ES 场景的落地：故障域按请求特征切分。两者可以叠加：专属池内再限流防总量失控。

### Q6：ES 集群脑裂是怎么回事？怎么防？

网络分区导致候选主节点分裂成两派，各自选主 → 两个"主节点"同时写，数据冲突。防御：①多数派选举（候选主节点奇数，quorum = n/2+1）；②老版本 `minimum_master_nodes` 设对、7.x+ 用 `cluster.initial_master_nodes` 正确引导；③跨机架/可用区部署降低分区概率。脑裂的代价和 ZK 场景的教训一致（见微服务 01 笔记）——**所有主从选举系统都要回答这个问题**。
