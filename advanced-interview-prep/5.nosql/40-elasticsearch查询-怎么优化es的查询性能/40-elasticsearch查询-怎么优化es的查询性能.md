# 面经总结 40：Elasticsearch 查询——怎么优化 Elasticsearch 的查询性能？

> 来源：极客时间《后端工程师的高阶面经》邓明（NoSQL 模块 40 讲）
> 整理日期：2026-11-06

---

## 一、文章总结

**索引机制（理解 ES 的关键）——倒排索引**：
- 正排：文档 → 关键字；**倒排：关键字 → 文档**。没有倒排索引查"包含 Elasticsearch 的文档"要全量遍历
- 写入时：分词器把字段切成 Term，统计频率构建 **posting list**（关键词 → 文档 ID、频率、位置；位置含"第几个词"和"起始偏移量"两种）
- **Term Dictionary**（关键词表格）：目标是整个装进内存。实现不是普通排序数组，而是 **FST（Finite State Transducers）**——连公共前缀、后缀一起压缩的前缀树
- 查找两步：①FST 定位 **Block**（Block 内关键词多再切 **Floor Block**，按首字母加速）；②Block/Floor Block 内**遍历**找关键词 → 拿到 posting list → 按文档 ID 取文档

**六大优化方案**：

| 方案 | 要点 | 量化效果/细节 |
|---|---|---|
| **优化分页查询** | 深分页问题：命中 N 个分片，查询量 = N × (X+Y)（FROM X SIZE Y ≈ OFFSET+LIMIT）。解法：**Search After**（推荐，每次带上次的 search_after 值，等价于分库分表的 `WHERE id > $max_id` 禁跳页）；Scroll/Scroll Scan（导出场景，游标式） | 查询量与偏移量脱钩，只与页大小和分片数有关 |
| **调大刷新间隔** | `index.refresh_interval` 1s → 30s | 性能提升约 20%；代价是近实时窗口变长 |
| **批量提交** | ①化单为批：实时同步改异步定时批量（每秒一次，业务 RT 降 50%）；②Kafka 消费批量写 ES（一次拉 100 条批量提交，解决积压）；③日志场景调大批次 + **降级**（ES 异常先丢 INFO 日志，再丢 WARN） | 批量为什么快：省系统调用和协议开销（见 MQ 08 笔记） |
| **优化不必要字段** | 只同步要查询的字段，主体数据留 DB；查询先拿主键再回库（类比**分库分表中间表**思想）；动态 mapping 是大坑（无意间索引一堆新字段） | 受影响需回库的查询 <10% 可接受；后续 reindex 重建优雅索引 |
| **冷热分离** | 热数据在高性能节点（SSD），冷数据迁移到廉价节点（机械盘）；用**索引生命周期管理（ILM）**自动化（如日志 3 天热 → 冷），Kibana 可傻瓜配置 | 降本增效经典；思考题 2：机械盘顺序读写不差 + 冷数据访问少，性价比高（联动 Kafka 顺序写） |
| **常规优化** | ①GC：老 CMS 停顿 100ms+ → 换 **G1**（停顿 <15ms），超大堆可调研 ZGC；②swap：OS 层禁用或 `vm.swappiness` 调小，或 `bootstrap.memory_lock=true` 锁内存；③文件描述符调大（65536+），大集群共用曾耗尽 FD 拖垮多个核心业务——**隔离**的教训 | JVM 优化是 Java 面试的天然话题引子 |

**通用优化方法论**（贯穿 MySQL/Redis/Kafka/ES 的总结）：
1. **优化查询本身**（改写 SQL、优化索引）
2. **优化中间件本身**（调参数；大厂可二次开发；JVM 系的调 JVM）
3. **优化操作系统**（内存、网络 IO、磁盘 IO 相关参数）

**面试准备清单**：节点数与内存分配、JVM/GC 配置与停顿时间、与默认值不同的配置及原因、读写流量容量。

## 二、Q&A（问题 + 标准答案）

### Q1：ES 的倒排索引是什么原理？

写入时分词器把字段切成 Term，构建 posting list（关键词 → 文档 ID、频率、位置）。查询时从关键词直接定位文档列表，避免全量扫描。关键词由 **Term Dictionary** 组织——用 FST（压缩公共前后缀的前缀树）实现以装进内存：FST 定位 Block，Block 内遍历找词，拿到 posting list 取文档。

### Q2：ES 深分页为什么慢？怎么优化？

`FROM X SIZE Y` 命中 N 个分片时，协调节点要汇集 N×(X+Y) 条数据再排序丢弃前 X 条——页越深越慢（与分库分表 OFFSET 同病）。优化：**Search After**——每次查询带上次的 search_after 值（等价 `WHERE id > max_id`），查询量与偏移量无关，只与页大小和分片数有关；代价是不支持随机跳页。导出场景用 Scroll/Scroll Scan 游标。

### Q3：调大 refresh_interval 为什么能提性能？代价？

refresh 把 Buffer 数据刷到 Page Cache 生成段——每次 refresh 都产生新段（段要耗资源、后续还要合并）。默认 1s 太频繁，调大到 30s 后 refresh 次数锐减、段数量下降，写入性能提升约 20%。代价：**近实时延迟变长**（新文档最长 30s 才能搜到）——实时性要求低的业务（日志、报表）放心调。

### Q4：批量提交怎么落地？有什么配套技巧？

三种形态：①实时同步改**异步定时批量**（每秒扫变更批量提交，业务 RT 降 50%）；②Kafka 消费者**批量消费批量写**（一次拉 100 条攒批提交，解决积压）；③日志管道调大批次 + **降级**（ES 异常先丢 INFO、再丢 WARN）——把调批次和降级组合用，体现综合治理能力。

### Q5：怎么优化索引字段？

只同步**要被查询的字段**，其余留 DB。查询变成"ES 查条件拿主键 → 回库取完整数据"（与分库分表中间表解决无分片键查询同思想）。评估回库比例（<10% 可接受）。警惕**动态 mapping** 自动索引一堆无用新字段——生产建议关 dynamic 或显式 mapping。

### Q6：冷热分离怎么做？为什么冷数据用机械盘？

ILM 生命周期管理：数据先写热节点（SSD 高性能），到龄自动迁移冷节点（廉价机械盘）——如日志 3 天热→冷，Kibana 可配置，全程自动。机械盘合理性（思考题 2）：①冷数据**访问少**，慢点无感；②ES 读段文件**顺序读**为主，机械盘顺序读写不差（呼应 Kafka"顺序写不慢"）；③同预算下容量大数倍——冷热分离本质是**按访问频率匹配存储性价比**。

### Q7：ES 的 JVM 和 OS 层怎么优化？

①GC：大堆别用老 CMS（停顿 100ms+），换 **G1**（停顿 <15ms），特大堆调研 ZGC；②swap：禁用 / `vm.swappiness` 调小 / `bootstrap.memory_lock=true` 锁内存（与 Kafka 同法）；③文件描述符调大到 65536+——大集群 FD 耗尽曾拖垮多个核心业务，引出业务**隔离**（不同业务分拆集群）。

## 四、面试官连环追问清单（含参考答案）

### Q1：FST 为什么比哈希表/B+ 树更适合 Term Dictionary？

Term Dictionary 的需求：**字典序前缀查找 + 全内存**。哈希表不支持前缀查询（match/前缀/模糊查询是 ES 核心场景）；B+ 树支持范围但节点指针开销大，千万级 Term 装不进内存。FST 把公共前后缀压缩成状态机边——**共享前缀的 Term 只存一份**，内存占用比 Trie 还小一个量级，且查找是 O(len(term))。代价：构建复杂、不可增量修改（所以随段不可变，合并时重建）——这又是 LSM 不可变思想的体现。

### Q2：Search After 有什么坑？

①**必须稳定排序**（通常 `_doc` 或带唯一字段，否则翻页错乱）；②排序字段值**重复**时要有 tiebreaker（如文档 ID，否则同值数据丢/重——呼应 MQ 07"同时发送"边界）；③不能跳页、不能回翻，UI 要改成"加载更多"；④PIT（Point In Time）过期后 search_after 失效要处理。本质都是"游标翻页"的通用坑（与分库分表、feed 流翻页一致）。

### Q3：为什么 ES 堆内存官方建议不超过 32GB 的一半？

两层原因：①**另一半留给 page cache**——ES 重度依赖 OS 页缓存做段文件读写（Lucene 走 mmap），堆给多了 page cache 不足，查询反而慢；②**32GB 是 JVM 压缩指针（Compressed Oops）的临界点**——超过后对象指针从 4 字节变 8 字节，堆的有效容量不增反降。所以大内存机器的正确姿势是**多实例**，不是大堆。

### Q4：批量写入的最佳批次大小怎么定？

没有银弹，**压测爬升法**：从 100~500 条/批起步，逐步翻倍观察吞吐和 RT，找到吞吐拐点（通常 5~15MB/批）。注意三件事：①批次越大内存占用越高（bulk 请求在协调节点排队）；②失败处理——bulk 是部分成功语义，要逐条检查失败项重试；③背压——ES 返回 429（rejected execution）说明线程池/队列满，该降速而不是加压（呼应 ES 的自我保护）。

### Q5：ES 的 429 是怎么回事？（延伸自我保护机制）

ES 的写入/搜索队列满时返回 429（rejected_execution_exception）——**这是 ES 内置的自我保护**（线程池 + 有界队列的背压机制），不是错误而是信号。正确处理：客户端指数退避重试；长期 429 说明容量不足，该扩容或降载（调大批次反而加重——429 时要降批次）。面试提这个，说明你真在生产环境写过 ES。

### Q6：冷热分离迁移过程会影响查询吗？

ILM 的迁移是**分片级 reallocate**：目标节点复制分片数据，完成后切换。期间该分片仍可查询（读不受影响），写入若路由到迁移中的分片会有轻微影响。注意：①迁移占网络带宽和 IO，要限速（`cluster.routing.allocation` 相关参数）防迁移风暴压垮集群；②冷节点查询慢会拖长整体 RT（尾延迟），冷数据查询要走独立协调节点或降级容忍——和 01 讲"协调节点隔离"是一脉相承的思路。
