## 一、文章总结

**为什么用 MongoDB（选型话术）**：①**灵活的文档模型**——数据模型经常变动、难以预料输入（vs MySQL 适合稳定模型）；②**横向扩展容易**——分片自动均衡，vs 关系型分库分表的运维复杂度。中小公司 MySQL 也能应付，非必须。

**分片机制**：
- 分片集合（collection）= 逻辑表，分片 = 物理表（类比分库分表）
- 分片由若干 **chunk（块）** 组成，默认 128MB；**拆分条件二选一**：数据量超 128MB（**数据太多**）或文档数超均值 1.3 倍（**文档太多**）
- **自动负载均衡（rebalance）**：按分片间 chunk 数量差阈值触发，本质是**挪 chunk**
- **块迁移七步**：平衡器发 moveChunk → 源分片继续负责读写 → 目标分片建索引 → 同步数据 → 追平迁移期间的变更 → 更新元数据 → 源分片游标关闭后删旧块。与其他中间件的数据迁移大同小异

**配置服务器（config server）**：存元数据（分片信息、权限、分布式锁），mongos 查询依赖它。**特点：主节点崩溃仍可读**（区别于多数中间件主崩即全不可用）——元数据读多写少，这个特性直接拉高集群可用性。它是集群关键组件，轻微抖动影响全局。

**复制机制（Replica Set）**：Primary/Secondary，同步靠 **oplog**（类比 MySQL binlog）。oplog 两个缺陷：
1. **幂等转换导致体积膨胀**——所有操作转成幂等形式（理解成 set 整个文档），改一小部分也生成整条文档的 oplog
2. **有容量期限**——oplog 写满被删，来不及同步的从节点只能**全量重新同步**

**写入语义 Write Concern（类比 Kafka acks）**：`w` + `j` + `wtimeout` 三参数：
| 参数 | 取值 | 含义 |
|---|---|---|
| w | majority（默认） | 同步给多数节点——可用性强、写入性能差 |
| w | N（数字） | 1=写主即可；N>1=主+N-1 从；**0=不等任何节点**（性能最好，可能"成功但丢失"） |
| w | 标签策略 | 写入带指定标签的节点（用得少，用了是面试亮点） |
| j | true/false | 是否写到磁盘（journal） |
| wtimeout | 毫秒 | 仅 w>1 生效；**超时返回错误但数据可能已写入**（经典陷阱） |

**三个高可用措施**（层层递进）：
1. **启用主从**（最基本）：一主两从推荐配置起步，主崩从选主。历史话术：单节点时每年宕机一两次 → 改主从后消失
2. **引入仲裁节点（Arbiter）**：只投票不存数据（类比 ES 仅投票节点），轻量低成本，从节点崩溃时仍保多数派
3. **配置服务器上主从**（一主两从）：主崩仍可读（元数据读多写少）
4. **多数据中心主从**：两数据中心部署（如 1 主 1 从 + 2 从跨中心）；**调整优先级**让主节点优先从同机房选出（同中心数据较新）
5. **引入分片**：性能和可用性双升，比关系型分库分表简单；已有数据改分片是**危险操作**（低峰期 + 运维协助，没实操过慎讲）
6. **调整写入语义**：真实 Bug 案例——数据偶发丢失，排查发现 `w=1`（只写主），改回 `majority` + `j=true` 后消失（与 Kafka acks=0 丢消息同款教训）

**横向总结（面试升华）**：主流中间件高可用 = **分片（对等结构）+ 主从结构**——MongoDB、Redis、ES、Kafka 一脉相承；关系型分库分表也是"对等 + 主从"模式。

## 二、Q&A（问题 + 标准答案）

### Q1：为什么选 MongoDB 而不是 MySQL？

两个决策理由：①文档模型灵活——数据模型频繁变动、字段不可预知时 MySQL 的固定 schema 很痛苦；②横向扩展简单——分片内建自动均衡，MySQL 分库分表要自建路由、扩容迁移靠人工。数据模型稳定、团队无 MongoDB 经验时，MySQL 完全够用。

### Q2：MongoDB 的分片和分库分表有什么区别？

概念同构（集合=逻辑表、分片=物理表），但 MongoDB **自动化**：chunk 超阈值自动拆分、分片间数据不均自动 rebalance 迁移，全程无人工。分库分表要你自己预估数据、设计路由、手动扩容迁移。代价是 MongoDB 的 rebalance 迁移会消耗 IO/带宽，高峰要限速。

### Q3：oplog 是什么？有什么坑？

主从同步日志（类比 binlog），从节点重放 oplog 追数据。两个坑：①**幂等转换**——所有操作转成幂等形式，小更新也产生整条文档的 oplog，体积可能远超预期（磁盘规划要注意）；②**容量有限**——写满覆盖，从节点掉队太久只能全量重同步（大实例的全量同步又是 IO 风暴——和 Redis 全量同步、MySQL 从库重建是同族问题）。

### Q4：Write Concern 怎么选？wtimeout 有什么陷阱？

- 强可靠：`w=majority` + `j=true`（默认推荐，关键数据）
- 高性能低风险数据：`w=1`
- 特殊拓扑：标签策略（如"必须写到一个异地节点"）
- **wtimeout 陷阱**：超时返回错误≠写入失败——数据可能已在部分节点写入成功。客户端**不能把超时错误当失败处理**（重试要幂等），这与 Kafka 生产者超时重试是同一个坑。

### Q5：配置服务器为什么关键？它自己怎么高可用？

存集群元数据（分片映射、权限、分布式锁），mongos 路由全靠它——它抖一下全集群受影响。高可用：主从部署（一主两从）。独特优势：**主节点崩溃仍可读**（多数中间件主崩即全停），而元数据读多写少，集群可用性因此显著提升。

### Q6：怎么设计 MongoDB 的多数据中心部署？

两数据中心简化版：1 主 1 从在中心 A、2 从在中心 B（或一主三从分摊）。**选举优先级调同机房**——同中心从节点数据较新，主崩时优先就地选主，避免跨中心数据滞后。中心级故障时另一中心接管。这是主流多活架构的简化形态（对应 ES 双集群、Redis 互备的思路）。

### Q7：已有数据的集合改分片要注意什么？

高危操作：①选**业务低峰期** + 运维协助；②**片键选择是终身的**——改不了，按查询模式选（高频查询条件、基数大、避免单调递增导致写热点）；③改造期间 chunk 拆分和初始均衡会产生大量 IO，监控集群负载；④先在测试环境全流程演练。（没实操过面试慎讲细节，见文章警告。）

### 项目经历栏·案例：MongoDB 可用性提升

**版本 A（简洁版，一行）**
- 提升 MongoDB 可用性：单节点改一主两从复制集并引入仲裁节点，配置服务器启用主从（主崩仍可读），排查根治"w=1 写入语义导致的数据丢失"（改回 majority + j=true），核心业务再未发生数据丢失与集群不可用

**版本 B（详细版，供面试口述）**
> 我接手时 MongoDB 是单节点，每年总有一两次宕机不可用。第一步改成一主两从复制集，成本很低但主崩能自动选主；随后引入仲裁节点（只投票不存数据，轻量服务器），保证任何单点故障都有多数派。后来发现配置服务器是更大的单点——它存分片元数据，一挂全集群瘫痪，于是也上了主从，利用它"主崩仍可读"的特性（元数据读多写少）把影响降到最低。最有价值的一次排查是数据偶发丢失：我联想到 Kafka acks 的教训去查写入语义，果然发现有人把 Write Concern 的 w 设成了 1——主节点写完就崩溃时从节点没有这条数据。改回 majority 并把 j 设为 true 之后，再没丢过。整个过程我最大的体会是：主流中间件的高可用都是"分片 + 主从"的一脉相承，排查思路也是相通的。

## 四、面试官连环追问清单（含参考答案）

### Q1：思考题 1——还有哪些中间件是"主节点崩溃仍可读"？

- **MongoDB 配置服务器**（本文）：元数据读多写少，主崩可读
- **ZooKeeper**：Follower/Observer 直接服务读请求（写转发 Leader）——ZK 的设计哲学就是"读全集群、写 Leader"
- **etcd**：串行读（serializable read）可以走任意节点，线性读走 Leader
- **Eureka（AP）**：任何节点都可读可写（对等结构，没有主）——它是把问题消解了
- 对比反例：MySQL 主库、Redis（3.2 前从库读过期数据是 Bug）、Kafka（只允许读写主分区）。设计共性：**读路径去中心化程度越高，主节点故障的影响面越小**

### Q2：思考题 2——MySQL 数据迁移到 MongoDB 的话术怎么讲？

四段式：①**动机**：这部分数据模型变动频繁（如商品扩展属性、用户自定义字段），MySQL 里用 JSON 列或频繁 DDL 很痛苦，文档模型天然匹配；②**迁移**：双写过渡（新写双写 → 历史数据批量搬迁 → 校验对账 → 读切换 → 停写旧库），或 Canal 监听 binlog 实时同步，全程可回滚；③**验证**：抽样比对 + 影子流量双读对比；④**收益**：schema 变更零成本，分片能力为后续增长留好空间。要点：强调"适合才迁"，不是为迁而迁。

### Q3：仲裁节点为什么不存数据？它会不会成为脑裂隐患？

Arbiter 只投票不存数据——价值是用最低成本凑**多数派**（2 数据节点 + 1 arbiter = 3 票，挂一个数据节点仍有 2 票）。脑裂问题恰恰靠它**缓解**而非引入：没有它时 2 个数据节点分区后各 1 票都选不出主（集群不可用）；有了它，与 arbiter 连通的一侧凑够 2 票继续服务。注意：arbiter 与数据节点的部署要考虑机房分布（别把 arbiter 和其中一个数据节点放同机房，否则机房故障照样双失）。

### Q4：w=majority 和 Kafka acks=all + min.insync.replicas=2 等价吗？

思想等价（多数派确认），实现不同：Kafka 的 ISR 是**动态集合**（掉队的从分区被踢出，写确认只等 ISR 内成员），MongoDB 的 majority 是**静态多数**（复制集总成员数 /2+1，不管成员是否掉队）。后果差异：Kafka 在 ISR 收缩时仍可用（牺牲可靠窗口），MongoDB 在多数节点失联时**写直接失败**（更保守）。答题时指出这个细微差别，体现对两种模型的真理解。

### Q5：片键选不好有什么后果？（高频追问）

三大后果：①**单调递增片键**（如时间戳、ObjectId）→ 新数据全写最后一个 chunk → 单分片写热点，均衡器疲于迁移（与 Kafka 分区热点、ES 热点分片同族）；②**基数太低**（如性别）→ chunk 无法有效拆分，分片形同虚设；③**与查询模式错配**→ 查询广播到所有分片（scatter-gather），比不分片还慢。好片键：**高基数、写分布均匀、匹配高频查询**。选了就是一辈子（改片键要重建集合），所以测试环境先验证。

### Q6：MongoDB 的全量重同步（initial sync）怎么降低影响？

触发场景：从节点 oplog 窗口掉队（或新加节点）。影响：全量拷贝打满源节点 IO 和网络，可能拖垮主。缓解：①**调大 oplog**（让窗口覆盖最长预期停机时间，如 24h 写入量）；②从**就近的从节点**同步（`initialSyncSource`），避开主节点；③低峰期操作 + 限速；④大实例考虑文件系统快照拷贝（比逻辑同步快一个量级）。和 MySQL 从库重建、Redis 全量同步的治理思路完全同构。
