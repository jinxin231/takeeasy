> 整理日期：2026-11-06

## 一、文章总结

**核心结论先行**：六大模式 + 删除缓存/延迟双删两个"编外模式"，**除 Write Back（用 Redis 且不丢数据时）外，都不能真正解决一致性问题**——面试官故意问"怎么用缓存模式解决一致性"就是在挖坑。

**模式总览**：

| 模式 | 核心机制 | 一致性问题 |
|---|---|---|
| Cache Aside | 业务控制读写，一般**先写 DB**（以 DB 为准，缓存失败有过期时间兜底自愈） | 先写 DB 或先写缓存都解决不了 |
| Read Through | 缓存未命中时**缓存代替业务**去 DB 加载并回写；写同 Cache Aside | 只管读不管写，同 Cache Aside |
| Write Through | 只写缓存，**缓存代替业务更新 DB**；读同 Cache Aside；一般也先写 DB | 同样没解决 |
| Write Back | 只写缓存，**key 过期时才刷回 DB**；关缓存要全量刷 | 硬伤是**缓存宕机丢数据**；不考虑丢失时一致性反而最好 |
| Refresh Ahead | **CDC 监听 binlog** 异步刷新缓存（Canal → Redis） | 不一致窗口 = DB 写入到 binlog 刷新之间；回写用 SETNX 解决 |
| Singleflight | 同 key 未命中时**只有一个线程加载**，其他等待 | 与一致性无关，解决的是 DB 并发量 |
| 删除缓存（编外） | 更新 DB 后删除缓存 | 不一致源自"读线程未命中回写"与"写线程"冲突 |
| 延迟双删（编外） | 删缓存 + 定时器延时**再删一次** | 理论上仍有窗口（回写与第二次删除之间），实践中很小 |

**Write Back 的一致性亮点**（最绕但最出彩，要一步步引导）：
1. 写只写缓存 → 业务方读写都只经缓存，**对业务视角天然一致**
2. 唯一风险：读未命中从 DB 加载 a=3，还没回写时写请求把缓存改成 a=4 → 读请求用老数据回写覆盖新数据
3. 解法：回写用 **SETNX**（缓存无数据才写），失败则重读缓存
4. 话术分寸：激进版"解决了一致性"印象深刻但有被否风险；保守版"极大缓解了一致性"稳妥

**两个异步变种**（Read/Write Through 通用）：
- 变种一：同步加载、**异步回写缓存**——收益小，只在缓存操作慢时用（大对象、序列化贵）
- 变种二：**完全异步加载**——未命中直接返回错误/默认值，缓存后台加载回写。适合 RT 极苛刻场景，代价是当次拿不到数据
- Write Through 异步写 DB 有**丢数据风险**（返回成功后缓存崩了，DB 没写上）——基本不用，要用就用 Write Back

**删除缓存 vs 延迟双删**：
- 删除缓存的一致性问题**不是两个写线程并发**，而是"一读一写"：读线程未命中回写时与写线程冲突
- 延迟双删用第二次删除清掉这个窗口；代价是**两次删除命中率下降更严重**（写频繁场景缓存被反复删，回源压 DB）
- 被迫选边时的标准答案：**延迟双删**——"并发不高、写请求少，一致性要求高，命中率降一点可接受"

**落地亮点：装饰器模式实现缓存模式**（建议实践后再用）：
```go
type ReadThroughCache struct {
    c  Cache                       // 被装饰的基础缓存（Redis/本地内存）
    fn func(key string) any        // 回源函数
}
func (r *ReadThroughCache) Get(key string) any {
    if val := r.c.Get(key); val != nil { return val }
    val := r.fn(key); r.c.Set(key, val)   // 未命中 → 回源 + 回写
    return val
}
```
抽象统一 Cache 接口（Redis + 本地内存实现）+ 装饰器实现各模式，无侵入、可组合——项目平淡时可做成"统一缓存组件"当特色项目。Beego 缓存模块有类似实现。

**面试准备清单**：公司用了哪些模式、遇到过的一致性问题及解法；业务怎么更新缓存和 DB 的；结合后面穿透/击穿/雪崩一起理解。

## 二、Q&A（问题 + 标准答案）

### Q1：你了解哪些缓存模式？

Cache Aside、Read Through、Write Through、Write Back、Refresh Ahead、Singleflight；外加删除缓存和延迟双删（严格说不算模式，但面试常提）。一句话点题：**除了 Write Back 特定条件下，都不能真正解决一致性问题**。

### Q2：Cache Aside 为什么先写数据库？

大多数业务**以数据库为准**：DB 写成功即认为操作成功。即便随后写缓存失败，缓存有过期时间，过期后重新加载数据自然恢复一致——先写 DB 把失败场景的自愈路径留好了。

### Q3：Cache Aside 有什么不一致场景？

经典时序（记法：线程 2 后开始却先结束）：
- **先写 DB 版**：线程 1 写 DB（a=3）→ 线程 2 写 DB（a=4）、写缓存（a=4）→ 线程 1 写缓存（a=3）→ 缓存是旧值 a=3
- **先写缓存版**：镜像时序，同样脏
结论：不管先写哪个，两个写操作之间没有原子性，都可能留下不一致。

### Q4：Read Through 和 Write Through 的异步变种怎么用？

- RT 变种一：同步回源、异步回写缓存（缓存写入贵时用，如大对象序列化）
- RT 变种二：完全异步加载——未命中直接返回默认/错误，缓存后台加载（RT 极苛刻场景，牺牲当次结果）
- WT 变种：同步写 DB、异步刷缓存（缓存写贵时用）；异步写 DB 有丢数据风险，基本不用

### Q5：Write Back 为什么"一致性最好"但现实中用得少？

一致性好（Redis 场景）：写只写缓存 → 业务视角永远一致；读回写用 SETNX 挡住"老数据覆盖新数据"。用得少是因为**致命伤是丢数据**——缓存宕机，还没刷回 DB 的数据全丢。除非缓存高可用做得极好，否则关键数据不敢用。本地缓存场景它连一致性好都谈不上（多节点各存一份）。

### Q6：删除缓存和延迟双删是什么关系？延迟双删就完全一致了吗？

删除缓存：更新 DB 后删缓存。问题在"读线程未命中 → 读 DB 旧值 → 准备回写"的途中，写线程改完 DB 删了缓存，读线程随后把旧值回写——脏数据。延迟双删：写完删一次，**延时后再删一次**，清掉这个窗口里被回写的脏数据。理论上仍有不一致窗口（回写发生在第二次删除之后），但时间差拉开后概率极低，实践中可接受。

### Q7：Singleflight 解决什么问题？落到 DB 的查询数和什么有关？（思考题 2）

解决**同 key 并发回源**：100 个线程同时访问未命中的 key1，只有 1 个真去 DB，其余等待共享结果。落到 DB 的查询数取决于：**并发请求按 key 的分布**——同 key 并发越高收益越大（热点 key 场景，防击穿），key 分散或并发低则几乎无效。相关因素：key 数量、单 key 热度、加载耗时（加载期间到达的请求才会被合并）。

### Q8：如果让你选一个模式，你选哪个？

没有完美答案，被迫选边答**延迟双删**：一致性问题不严重（只剩理论窗口），代价是命中率降——而我的业务并发不高、写请求少，命中率损失可接受。关键是把**取舍逻辑**讲清楚，而不是背答案。

## 四、面试官连环追问清单（含参考答案）

### Q1：为什么都说"更新缓存"不如"删除缓存"？

更新（写新值进缓存）有两个写线程并发时的时序问题（谁先谁后不确定，缓存可能留下旧值），且更新是"赌这个数据马上会被读"——赌错了白白浪费缓存空间还可能覆盖热点。删除则是懒加载思路：**只留读取路径回源**，写路径只管删，时序问题少一个维度，下次读自然拿到最新值。代价是删除后命中率下降。

### Q2：延迟双删的延时怎么定？第二次删除失败了怎么办？

- 延时：要覆盖"读线程从 DB 读完旧值到回写缓存"的最坏耗时——业务读路径耗时 + 主从延迟（若读从库）+ 余量，常见 500ms~1s
- 第二次失败：引入**重试机制**（失败入 MQ 重试）或干脆走 **Canal 监听 binlog 做第二次删除**（把重试/删除逻辑从业务代码剥离，可靠性更高）——这也是延迟双删进化到 Refresh Ahead 的路径

### Q3：Cache Aside + 删除缓存组合，还有不一致，为什么不直接上分布式锁？

可以但没必要：分布式锁能彻底串行化读写，但引入锁的复杂度、死锁风险和性能损耗，换来的只是把"小概率、短窗口、多数业务可容忍"的不一致降到零。**架构是取舍**：多数业务接受最终一致（缓存本身就有过期时间兜底），只有金融级强一致场景才值得上锁——而且那种场景往往直接用 DB 不用缓存了。

### Q4：Refresh Ahead（Canal 监听 binlog）有什么坑？

- **不一致窗口**：DB 提交 → binlog → Canal → 刷缓存，全链路秒级甚至更长延迟，期间读到旧值
- **中间件链路长**：Canal 挂了/积压，缓存就持续旧——要监控 Canal 延迟
- **表结构变更**：缓存对象与表结构耦合，加字段要同步改刷新逻辑
- 优点同样明显：业务代码零感知（对比删除缓存/延迟双删侵入业务），删除失败问题天然消失（有 binlog 就有重放）

### Q5：SETNX 回写防覆盖，那写请求在回写之后又来改缓存怎么办？

时序：读线程 SETNX 成功（写入旧值 a=3）→ 写线程更新缓存（a=4）→ 后续读都拿 a=4，没问题。真正的危险是写线程**先于** SETNX 完成：此时 SETNX 失败，读线程重读缓存拿新值，也没问题。SETNX 把"回写"变成了只有缓存为空才生效的操作，两种时序都被兜住——这就是 Write Back/Refresh Ahead 场景下它能解决回写覆盖的原因。

### Q6：本地缓存场景下这些模式有什么变化？

本地缓存多节点各存一份，问题全面升级：①Write Back 的一致性优势没了（每个节点都是独立副本）；②删除缓存/延迟双删要**广播到所有节点**（消息总线/配置中心/定时失效），删除失败和广播延迟都会放大不一致窗口；③所以本地缓存通常只配"短过期时间 + 容忍秒级不一致"，一致性诉求高的数据不放本地缓存。

### Q7：Singleflight 在 Go 和 Java 里分别怎么用？

- Go：`golang.org/x/sync/singleflight`，`Do(key, fn)` 同 key 并发只执行一次 fn，共享结果和 error
- Java 没有官方实现，常见做法：`ConcurrentHashMap<String, CompletableFuture<V>>` + `computeIfAbsent`——Future 占位，后到的线程 join 同一个 Future；或 Caffeine/Guava LoadingCache 内置了类似语义
- Redis 分布式场景：用分布式锁（SET NX PX）占位 + 双重检查，本质上就是分布式版的 Singleflight，防缓存击穿

## 五、专题深挖（讨论补充）

### 专题 1：为什么叫 Cache Aside？不一致时序的记忆法

**命名**：Aside = "在旁边"。Cache Aside 里缓存躺在读写路径**旁边**——业务代码自己操作缓存和 DB（先查缓存、未命中查 DB、自己回写），缓存不参与决策。对比 Read/Write **Through**（"穿过"）：缓存在读写路径**正中间**，请求必须穿过缓存层，由缓存代理去访问 DB。一个"绕开走"，一个"穿过去"。

**不一致时序的记忆法**（原文技巧）：线程 1 先开始、后结束；线程 2 **后开始、先结束**——

```
线程1: 写DB(a=3) ────────────── 写缓存(a=3)   ← 慢，横跨线程2全程
线程2:          写DB(a=4)+写缓存(a=4)          ← 快，先结束
```

线程 2 把缓存写成 a=4 之后，线程 1 才慢悠悠覆盖上 a=3 → 脏数据。**先动手的反而最后收尾**，这个"后发先至"的交错就是不一致的本质，先写 DB 还是先写缓存都逃不掉（镜像时序）。

### 专题 2：为什么 SETNX 能解决回写覆盖问题？

问题场景：读线程未命中 → 从 DB 读到旧值 a=3 → **还没回写**，写线程把缓存改成 a=4 → 读线程用普通 SET 把 a=3 盖上去，新数据被旧数据覆盖。

SETNX（不存在才设置）把回写变成"**只有缓存为空才生效**"：

- 时序 A：写线程先完成（a=4 已在缓存）→ 读线程 SETNX **失败**，旧值写不进去 → 重读缓存拿 a=4 ✓
- 时序 B：读线程 SETNX 先成功（写入 a=3）→ 写线程随后更新为 a=4 → 新值覆盖旧值，最终是新的 ✓

关键洞察：**回写操作的合法性只在"缓存为空"这一刻成立**，SETNX 恰好把这个条件变成原子检查；普通 SET 是无条件覆盖，所以漏。Write Back / Refresh Ahead 的回写路径同理（见连环追问 Q5）。

### 专题 3：模式太多记不住缺点？三问判定框架

任何缓存模式套进三个问题，十秒出结论：

| 问什么 | 判断逻辑 |
|---|---|
| ① **写路径经过谁？** | 业务直接写 DB（Aside/双删）→ 两个写操作没原子性，必有一致性窗口；缓存代理写 DB（Through/Back）→ 窗口转移到缓存层内部 |
| ② **并发交错的窗口在哪？** | 一致性问题的唯一来源就是"两个操作交错"。找出哪两步之间能被插入、插入后什么后果——这就是该模式的缺点 |
| ③ **挂了会怎样？** | Write Back：缓存宕机丢数据；Refresh Ahead：Canal 挂了一直旧；延迟双删：第二删失败留脏数据——**每种模式的死穴都在失败场景，不在正常流程** |

速查口诀：**Aside 交错、Through 没区别、Back 怕宕机、Ahead 有延迟、Singleflight 不管一致性、双删降命中**。

"能不能解决一致性"一句话判死：**除 Write Back（Redis 不丢数据前提下）外都不能——一致性的本质是原子性，缓存+DB 是两个系统，没有分布式事务就没有原子性**。面试被问"怎么用缓存模式解决一致性"就是坑，正确姿势是承认解决不了，然后讲怎么把窗口压到业务可接受。

### 专题 4：装饰器模式实现缓存模式（展开）

**为什么装饰器和缓存模式是天作之合**：六个模式的差异点全部在"读写前后挂什么钩子"——Cache Aside 不挂钩子（基准行为）、Read Through 在 Get 未命中挂"回源+回写"、Write Through 在 Set 挂"同步写 DB"、Write Back 挂"只写缓存+过期回调刷 DB"、Singleflight 在 Get 挂"同 key 合并回源"。**接口不变，变的只是行为增强**——正是装饰器模式的定义场景。用继承会类爆炸（每种组合一个类），用 if-else 写在一个实现里违反开闭原则；装饰器让每个模式一个类，运行时自由组合。

**Java 版实现**：

```java
// 统一缓存接口——抽象是地基
public interface Cache {
    Object get(String key);
    void set(String key, Object value, Duration ttl);
    void delete(String key);
}

// 两个基础实现：被装饰的对象
class RedisCache implements Cache { /* Jedis/Lettuce 操作 */ }
class LocalCache implements Cache { /* Caffeine 封装 */ }

// 装饰器 1：Read Through
class ReadThroughCache implements Cache {
    private final Cache delegate;                    // 被装饰的缓存
    private final Function<String, Object> loader;   // 回源函数

    public Object get(String key) {
        Object val = delegate.get(key);
        if (val != null) return val;
        val = loader.apply(key);                     // 未命中 → 回源
        if (val != null) delegate.set(key, val, Duration.ofMinutes(10));
        return val;
    }
    // set/delete 直接透传 delegate
}

// 装饰器 2：Singleflight
class SingleflightCache implements Cache {
    private final Cache delegate;
    private final Map<String, CompletableFuture<Object>> inflight = new ConcurrentHashMap<>();

    public Object get(String key) {
        Object val = delegate.get(key);
        if (val != null) return val;
        // 同 key 并发只有一个线程真正回源，其余 join 等待共享结果
        return inflight.computeIfAbsent(key, k ->
            CompletableFuture.supplyAsync(() -> delegate.get(k))
                .whenComplete((v, e) -> inflight.remove(k))
        ).join();
    }
}
```

业务方使用——**要什么能力套什么壳，像穿衣服**：

```java
Cache cache = new SingleflightCache(              // 最外层：防击穿
                new ReadThroughCache(             // 中间层：未命中回源
                    new RedisCache(jedis),        // 最内层：真实存储
                    key -> userMapper.selectById(key)));
```

换本地缓存只换最内层，去掉 Singleflight 只拆最外层，其余一行不动。

**工程收益（话术素材）**：
1. **开闭原则**：新增模式（如 Write Back）= 新增一个装饰器类，存量零改动
2. **可组合**：模式正交，叠加顺序即能力叠加顺序；组合数 2^n，类数 n
3. **无侵入**：业务只依赖 Cache 接口，一致性/并发细节全部透明
4. **可测试**：每个装饰器可单测（mock delegate），组合行为分层验证
5. **统一治理入口**：监控埋点（命中率/RT）、SETNX 回写、降级开关都可在装饰器层统一加，一处实现全局生效

**和替代方案对比（防追问）**：
- **vs AOP（Spring Cache 注解）**：AOP 也无侵入，但逻辑藏在切面里难调试，组合顺序和复杂状态（如 Singleflight 的 inflight 表）用注解表达别扭；装饰器是显式对象组合，栈轨迹清晰
- **vs 继承**：组合爆炸
- **vs 直接用 Spring Cache**：只给了 Cache Aside 抽象（@Cacheable），Read Through 的 loader 语义有，但 Singleflight、Write Back、定制淘汰管不了——自研组件的价值就在这里

**面试收尾话术**：
> "缓存模式的理论大家都背得出，我把它们落成了一套装饰器组件：统一 Cache 接口 + 每模式一个装饰器类，业务方按能力组合接入，一致性和并发细节全部封装在装饰器层。Beego 的 cache 模块也是类似思路。"

### 专题 5：Double Check 模式的精髓（击穿防护与 DCL 同构）

**要解决什么**：热点 key 过期瞬间（缓存击穿），1000 个并发请求同时未命中。裸奔版 1000 个全部回源打爆 DB；加锁天真版虽然串行了回源，但**串行 ≠ 只执行一次**——1000 个线程挨个拿锁，每个都老实查一遍 DB，DB 从"被并发打爆"变成"被排队打爆"。

**完整形态**：

```java
Data data = cache.get(key);        // 第一次检查（无锁，快路径）
if (data == null) {
    lock();
    try {
        data = cache.get(key);     // 第二次检查（持锁）
        if (data == null) {        // 还是没有 → 才真正回源
            data = db.query(key);
            cache.set(key, data);
        }
    } finally {
        unlock();
    }
}
```

第二次检查时，只有第一个拿到锁的线程发现缓存真空、回源；后面 999 个拿到锁时缓存已被回写，第二次检查命中直接返回——**DB 只被查 1 次**。

**精髓：两次检查各管一件事，缺一不可**

| | 第一次检查（无锁） | 第二次检查（持锁） |
|---|---|---|
| 管什么 | **性能** | **正确性** |
| 挡掉谁 | 99.9% 正常流量（缓存有数据时根本不碰锁） | 等锁期间已被别的线程回写好的线程 |
| 少了它会怎样 | 每次读都抢锁，锁本身成为瓶颈 | 锁只是串行了 1000 次回源，DB 照样被打爆 |

一句话精髓：

> **用一次几乎免费的无锁检查，换取"昂贵操作（回源）在锁内只发生一次"；第二次检查是承认"等锁的这段时间世界已经变了"，进锁后必须重新验证条件再决定动不动手。**——"条件在等锁期间可能已失效"是所有并发编程的通用教训。

**与单例 DCL 完全同构（连坑都同构）**：单例双重检查锁是同一个模式；单例版需要 `volatile` 防指令重排（别的线程读到半初始化对象），缓存版没有这个问题——Redis 操作本身原子，不存在"半初始化的缓存值"。但**本地缓存** double check 可见性问题回来了（线程 A 回写本地 map，线程 B 的 CPU 缓存可能看不到），所以本地缓存必须用 ConcurrentHashMap 兜底。

**与 Singleflight 的关系（33 篇内部联系）**：同解一个问题（击穿时合并回源），路径不同——

| | Double Check | Singleflight |
|---|---|---|
| 思路 | 锁 + 二次确认 | 同 key 并发调用共享同一个进行中的 Future |
| 后到者 | 排队等锁，拿到后检查发现已有值 | 直接 join 第一个调用，连再检查都不用 |
| 分布式版 | SET NX PX 分布式锁 + 双检 | 跨实例协调复杂，一般就用分布式锁双检实现 |

所以 Q7 说"分布式锁占位 + 双重检查 = 分布式版 Singleflight"——double check 是更通用的锤子，singleflight 是它的优化形态。

**为什么收录进一致性篇（作者深意）**：double check 表面管可用性（防击穿），但击穿时 1000 个线程重复回源、每个都执行"读 DB → 回写缓存"，**回写次数越多，撞上"写请求穿插在回写之间"的脏数据窗口概率越大**（Q6 延迟双删要治的窗口）。double check 把回源收敛到 1 次，顺带把一致性攻击面也缩小了——**高可用手段和一致性手段在这里交汇**。
