# 面经总结 33：缓存模式——缓存模式能不能解决缓存一致性问题？

> 来源：极客时间《后端工程师的高阶面经》邓明（缓存模块 33 讲）
> 整理日期：2026-11-06

---

## 一、文章总结

**核心结论先行**：六大模式 + 删除缓存/延迟双删两个"编外模式"，**除 Write Back（用 Redis 且不丢数据时）外，都不能真正解决一致性问题**——面试官故意问"怎么用缓存模式解决一致性"就是在挖坑。

**模式总览**：

| 模式 | 核心机制 | 一致性问题 |
|---|---|---|
| Cache Aside | 业务控制读写，一般**先写 DB**（以 DB 为准，缓存失败有过期时间兜底自愈） | 先写 DB 或先写缓存都解决不了 |
| Read Through | 缓存未命中时**缓存代替业务**去 DB 加载并回写；写同 Cache Aside | 只管读不管写，同 Cache Aside |
| Write Through | 只写缓存，**缓存代替业务更新 DB**；读同 Cache Aside；一般也先写 DB | 同样没解决 |
| Write Back | 只写缓存，**key 过期时才刷回 DB**；关缓存要全量刷 | 硬伤是**缓存宕机丢数据**；不考虑丢失时一致性反而最好 |
| Refresh Ahead | **CDC 监听 binlog** 异步刷新缓存（Canal → Redis） | 不一致窗口 = DB 写入到 binlog 刷新之间；回写用 SETNX 解决 |
| Singleflight | 同 key 未命中时**只有一个线程加载**，其他等待 | 与一致性无关，解决的是 DB 并发量 |
| 删除缓存（编外） | 更新 DB 后删除缓存 | 不一致源自"读线程未命中回写"与"写线程"冲突 |
| 延迟双删（编外） | 删缓存 + 定时器延时**再删一次** | 理论上仍有窗口（回写与第二次删除之间），实践中很小 |

**Write Back 的一致性亮点**（最绕但最出彩，要一步步引导）：
1. 写只写缓存 → 业务方读写都只经缓存，**对业务视角天然一致**
2. 唯一风险：读未命中从 DB 加载 a=3，还没回写时写请求把缓存改成 a=4 → 读请求用老数据回写覆盖新数据
3. 解法：回写用 **SETNX**（缓存无数据才写），失败则重读缓存
4. 话术分寸：激进版"解决了一致性"印象深刻但有被否风险；保守版"极大缓解了一致性"稳妥

**两个异步变种**（Read/Write Through 通用）：
- 变种一：同步加载、**异步回写缓存**——收益小，只在缓存操作慢时用（大对象、序列化贵）
- 变种二：**完全异步加载**——未命中直接返回错误/默认值，缓存后台加载回写。适合 RT 极苛刻场景，代价是当次拿不到数据
- Write Through 异步写 DB 有**丢数据风险**（返回成功后缓存崩了，DB 没写上）——基本不用，要用就用 Write Back

**删除缓存 vs 延迟双删**：
- 删除缓存的一致性问题**不是两个写线程并发**，而是"一读一写"：读线程未命中回写时与写线程冲突
- 延迟双删用第二次删除清掉这个窗口；代价是**两次删除命中率下降更严重**（写频繁场景缓存被反复删，回源压 DB）
- 被迫选边时的标准答案：**延迟双删**——"并发不高、写请求少，一致性要求高，命中率降一点可接受"

**落地亮点：装饰器模式实现缓存模式**（建议实践后再用）：
```go
type ReadThroughCache struct {
    c  Cache                       // 被装饰的基础缓存（Redis/本地内存）
    fn func(key string) any        // 回源函数
}
func (r *ReadThroughCache) Get(key string) any {
    if val := r.c.Get(key); val != nil { return val }
    val := r.fn(key); r.c.Set(key, val)   // 未命中 → 回源 + 回写
    return val
}
```
抽象统一 Cache 接口（Redis + 本地内存实现）+ 装饰器实现各模式，无侵入、可组合——项目平淡时可做成"统一缓存组件"当特色项目。Beego 缓存模块有类似实现。

**面试准备清单**：公司用了哪些模式、遇到过的一致性问题及解法；业务怎么更新缓存和 DB 的；结合后面穿透/击穿/雪崩一起理解。

## 二、Q&A（问题 + 标准答案）

### Q1：你了解哪些缓存模式？

Cache Aside、Read Through、Write Through、Write Back、Refresh Ahead、Singleflight；外加删除缓存和延迟双删（严格说不算模式，但面试常提）。一句话点题：**除了 Write Back 特定条件下，都不能真正解决一致性问题**。

### Q2：Cache Aside 为什么先写数据库？

大多数业务**以数据库为准**：DB 写成功即认为操作成功。即便随后写缓存失败，缓存有过期时间，过期后重新加载数据自然恢复一致——先写 DB 把失败场景的自愈路径留好了。

### Q3：Cache Aside 有什么不一致场景？

经典时序（记法：线程 2 后开始却先结束）：
- **先写 DB 版**：线程 1 写 DB（a=3）→ 线程 2 写 DB（a=4）、写缓存（a=4）→ 线程 1 写缓存（a=3）→ 缓存是旧值 a=3
- **先写缓存版**：镜像时序，同样脏
结论：不管先写哪个，两个写操作之间没有原子性，都可能留下不一致。

### Q4：Read Through 和 Write Through 的异步变种怎么用？

- RT 变种一：同步回源、异步回写缓存（缓存写入贵时用，如大对象序列化）
- RT 变种二：完全异步加载——未命中直接返回默认/错误，缓存后台加载（RT 极苛刻场景，牺牲当次结果）
- WT 变种：同步写 DB、异步刷缓存（缓存写贵时用）；异步写 DB 有丢数据风险，基本不用

### Q5：Write Back 为什么"一致性最好"但现实中用得少？

一致性好（Redis 场景）：写只写缓存 → 业务视角永远一致；读回写用 SETNX 挡住"老数据覆盖新数据"。用得少是因为**致命伤是丢数据**——缓存宕机，还没刷回 DB 的数据全丢。除非缓存高可用做得极好，否则关键数据不敢用。本地缓存场景它连一致性好都谈不上（多节点各存一份）。

### Q6：删除缓存和延迟双删是什么关系？延迟双删就完全一致了吗？

删除缓存：更新 DB 后删缓存。问题在"读线程未命中 → 读 DB 旧值 → 准备回写"的途中，写线程改完 DB 删了缓存，读线程随后把旧值回写——脏数据。延迟双删：写完删一次，**延时后再删一次**，清掉这个窗口里被回写的脏数据。理论上仍有不一致窗口（回写发生在第二次删除之后），但时间差拉开后概率极低，实践中可接受。

### Q7：Singleflight 解决什么问题？落到 DB 的查询数和什么有关？（思考题 2）

解决**同 key 并发回源**：100 个线程同时访问未命中的 key1，只有 1 个真去 DB，其余等待共享结果。落到 DB 的查询数取决于：**并发请求按 key 的分布**——同 key 并发越高收益越大（热点 key 场景，防击穿），key 分散或并发低则几乎无效。相关因素：key 数量、单 key 热度、加载耗时（加载期间到达的请求才会被合并）。

### Q8：如果让你选一个模式，你选哪个？

没有完美答案，被迫选边答**延迟双删**：一致性问题不严重（只剩理论窗口），代价是命中率降——而我的业务并发不高、写请求少，命中率损失可接受。关键是把**取舍逻辑**讲清楚，而不是背答案。

## 四、面试官连环追问清单（含参考答案）

### Q1：为什么都说"更新缓存"不如"删除缓存"？

更新（写新值进缓存）有两个写线程并发时的时序问题（谁先谁后不确定，缓存可能留下旧值），且更新是"赌这个数据马上会被读"——赌错了白白浪费缓存空间还可能覆盖热点。删除则是懒加载思路：**只留读取路径回源**，写路径只管删，时序问题少一个维度，下次读自然拿到最新值。代价是删除后命中率下降。

### Q2：延迟双删的延时怎么定？第二次删除失败了怎么办？

- 延时：要覆盖"读线程从 DB 读完旧值到回写缓存"的最坏耗时——业务读路径耗时 + 主从延迟（若读从库）+ 余量，常见 500ms~1s
- 第二次失败：引入**重试机制**（失败入 MQ 重试）或干脆走 **Canal 监听 binlog 做第二次删除**（把重试/删除逻辑从业务代码剥离，可靠性更高）——这也是延迟双删进化到 Refresh Ahead 的路径

### Q3：Cache Aside + 删除缓存组合，还有不一致，为什么不直接上分布式锁？

可以但没必要：分布式锁能彻底串行化读写，但引入锁的复杂度、死锁风险和性能损耗，换来的只是把"小概率、短窗口、多数业务可容忍"的不一致降到零。**架构是取舍**：多数业务接受最终一致（缓存本身就有过期时间兜底），只有金融级强一致场景才值得上锁——而且那种场景往往直接用 DB 不用缓存了。

### Q4：Refresh Ahead（Canal 监听 binlog）有什么坑？

- **不一致窗口**：DB 提交 → binlog → Canal → 刷缓存，全链路秒级甚至更长延迟，期间读到旧值
- **中间件链路长**：Canal 挂了/积压，缓存就持续旧——要监控 Canal 延迟
- **表结构变更**：缓存对象与表结构耦合，加字段要同步改刷新逻辑
- 优点同样明显：业务代码零感知（对比删除缓存/延迟双删侵入业务），删除失败问题天然消失（有 binlog 就有重放）

### Q5：SETNX 回写防覆盖，那写请求在回写之后又来改缓存怎么办？

时序：读线程 SETNX 成功（写入旧值 a=3）→ 写线程更新缓存（a=4）→ 后续读都拿 a=4，没问题。真正的危险是写线程**先于** SETNX 完成：此时 SETNX 失败，读线程重读缓存拿新值，也没问题。SETNX 把"回写"变成了只有缓存为空才生效的操作，两种时序都被兜住——这就是 Write Back/Refresh Ahead 场景下它能解决回写覆盖的原因。

### Q6：本地缓存场景下这些模式有什么变化？

本地缓存多节点各存一份，问题全面升级：①Write Back 的一致性优势没了（每个节点都是独立副本）；②删除缓存/延迟双删要**广播到所有节点**（消息总线/配置中心/定时失效），删除失败和广播延迟都会放大不一致窗口；③所以本地缓存通常只配"短过期时间 + 容忍秒级不一致"，一致性诉求高的数据不放本地缓存。

### Q7：Singleflight 在 Go 和 Java 里分别怎么用？

- Go：`golang.org/x/sync/singleflight`，`Do(key, fn)` 同 key 并发只执行一次 fn，共享结果和 error
- Java 没有官方实现，常见做法：`ConcurrentHashMap<String, CompletableFuture<V>>` + `computeIfAbsent`——Future 占位，后到的线程 join 同一个 Future；或 Caffeine/Guava LoadingCache 内置了类似语义
- Redis 分布式场景：用分布式锁（SET NX PX）占位 + 双重检查，本质上就是分布式版的 Singleflight，防缓存击穿
