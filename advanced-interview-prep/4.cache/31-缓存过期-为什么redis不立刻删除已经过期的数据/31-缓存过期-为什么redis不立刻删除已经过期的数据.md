# 面经总结 31：缓存过期——为什么 Redis 不立刻删除已经过期的数据？

> 来源：极客时间《后端工程师的高阶面经》邓明（缓存模块 31 讲）
> 整理日期：2026-11-06

## 一、文章总结

**核心指标——缓存命中率**：命中次数 ÷ 查询总次数。目标一般 90%+，但受业务模式影响（大量小请求天然不命中时，实时计算也可接受，别盲目追指标）。

**过期机制四种思路**（通用模型，不限于 Redis）：

| 思路 | 做法 | 为什么缓存场景不用/用 |
|---|---|---|
| 定时删除 | 每个对象一个计时器，到期即删 | ❌ key 太多计时器开销扛不住；改过期时间还要重置 |
| 延迟队列 | 对象按过期时间入队，取出即过期 | ❌ 队列本身开销大；改过期时间要调序；引入线程要并发控制 |
| 懒惰删除 | 用的时候检查，过期顺手删 | ✅ 但单用不够：过期 key 可能永远不再被访问 |
| 定期删除 | 每隔一段时间抽查一批删除 | ✅ Redis 采用，需精细控制开销 |

**Redis = 懒惰删除 + 定期删除结合。**

**为什么不立刻删除**（关键词：性能）：不是做不到，是**代价太高不值得**。浪费一点内存换响应时间，划算。

**定期删除怎么控制开销**（细节可略，记住结论）：
- 每个循环遍历 DB：该 DB 没有设过期时间的 key → 跳过
- 从设了过期时间的 key 里**随机抽一批（默认 25 个）**，逐个检查删除
- **每查 16 个 key 检测一次执行时间**，超阈值就中断（下次从当前 DB 的下一个继续）
- 这批 key 过期比例过低 → 提前中断换下一个 DB；比例过高 → 再抽一批
- **为什么随机抽样而不是顺序遍历**：顺序遍历若每次到中间就没时间，后半段的 key 永远轮不到——随机保证每个 key 都有概率被抽到
- 总结套路：**控制时间 or 控制个数**（本地缓存同理：每个迭代检测时间 / 固定遍历 N 个 / 混合）

**频率控制**：`hz` 参数（默认 10 = 每 100ms 执行一次后台任务，**不要超过 100**，越高 CPU 越贵）；`dynamic-hz` 开启后以 hz 为基数动态计算实际频率。hz 控制的是所有后台任务，不是单独的过期清理。

**从库处理过期 key**（著名 Bug）：
- **3.2 之前**：从库能读到已过期 key 的值
- **3.2 之后**：从库查询过期 key 返回 NULL，但**从库不删**——等主库的 DEL 命令同步（主从删除权在主库）

**持久化处理过期 key**：
- **RDB：主库不读不写**——生成时忽略过期 key，加载时也忽略；**从库原封不动全加载**（随后靠主库同步 DEL 清理）
- **AOF**：定期/懒惰删除都追加 DEL 命令；**重写时忽略过期 key**（重写是直接写内存数据快照）

**过期时间怎么确定**（亮点方法论）：
- 三角关系：**命中率 ↑ → 需要容量 ↑、过期时间 ↑**；资源不足只能缩短过期时间，代价是命中率下降
- 正统做法：模拟线上流量测试，不断延长过期时间直到命中率达标；或从业务出发（30 分钟内大概率复用 → 设 30 分钟）
- 命中率从用户体验反推：要求平均 RT 300ms，命中 100ms、未命中 1000ms → `100p + 1000(1-p) = 300`，p ≈ 0.78（面试说出等式即可，不用真算）

**三个特色案例**：
1. **按重试时间定**：幂等方案的 Redis 防穿透缓存，重试 10 分钟内完毕 → 过期 10 分钟；长流程缓存中间结果同理
2. **按数据热度定**：越热越长——每小时算的榜单缓存 1 小时；大 V 新作品缓存数小时，老作品短缓存
3. **预加载 + 超短过期**：用户看列表页后大概率点详情 → 返回列表时异步预加载前几条详情进缓存，过期设 1 分钟（用内存换响应时间；局限是只适合强关联业务，但面试极出彩）

**补充（文章未提，面试加分）**：
- 本地缓存 Caffeine 的过期：惰性 + 定时（scheduler）+ 写后过期/访问后过期可分别配置；其淘汰用 Window TinyLFU（32 讲伏笔）
- 与故障排查的联动：**大 key 集中过期 → 主动过期循环 + malloc_trim 阻塞主线程**（见故障排查 02 笔记）——过期时间加随机数防集中过期

## 二、Q&A（问题 + 标准答案）

### Q1：Redis 是怎么处理过期 key 的？是立刻删除吗？

不是。懒惰删除 + 定期删除结合：查询时检测到过期就顺手删（懒惰）；后台周期性随机抽查设了过期时间的 key 批量清理（定期），并用"控制执行时间/控制个数"的方式限制开销。

### Q2：为什么不立刻删除过期的 key？

立刻删除的两条路都太贵：①定时器——key 数量级太大计时器开销扛不住，修改过期时间还要重置；②延迟队列——队列本身开销大，改过期时间要调序，还要引入线程做并发控制，拉低整体性能。结论：**理论上做得到，代价不值得**；浪费少量内存对响应时间几乎无影响。

### Q3：定期删除会不会把 Redis 跑挂？怎么控制开销？

不会遍历全部 key。每循环遍历 DB：无过期 key 的 DB 跳过；抽一批（25 个）检查；每 16 个 key 检测执行时间，超时中断、下次续上；过期比例太低提前切下一个 DB。核心是**用时间换吞吐**：在正常请求和清理之间取得平衡。

### Q4：定期删除的频率怎么调？

`hz`（后台任务频率，默认 10，不要超过 100）+ `dynamic-hz`（以 hz 为基数动态计算）。hz 管所有后台任务，不只过期清理。

### Q5：读从库会读到过期 key 吗？

3.2 之前会（著名 Bug）；3.2 之后从库对过期 key 返回 NULL，但**不会自己删**——从库等主库的 DEL 命令，保证主从一致（删除决策权在主库）。

### Q6：RDB 和 AOF 怎么处理过期 key？

- RDB：**主库不读不写**（生成和加载都忽略过期 key）；从库原封不动全加载，之后靠主库同步删除
- AOF：正常追加 DEL 命令；**重写时忽略过期 key**

### Q7：缓存过期时间怎么确定？

先讲三角关系：命中率、容量、过期时间三者联动——要高命中率就要更长过期时间和更多内存。方法：模拟线上流量逐步延长直到命中率达标；或从业务复用周期出发（如 30 分钟内大概率再用 → 30 分钟）。资源不足时只能缩短过期时间，接受命中率下降。命中率的锚点是用户体验：`命中RT × p + 未命中RT × (1-p) = 目标RT` 反解 p。

### Q8：你调过缓存过期时间吗？（调大调小各备一例）

- 调大：某缓存 10min → 20min，命中率 80% → 90%，代价是占用更多内存
- 调小：全公司统一半小时 → 按业务排查后某业务降到 10min，命中率基本不变，Redis 总开销降 30%

### Q9：有没有根据业务特征定过期时间的案例？（三个）

① 按重试时间：幂等缓存 10 分钟（重试窗口）；② 按热度：榜单 1 小时、大 V 新作数小时、老内容短；③ 预加载 + 超短过期：列表→详情强关联场景，异步预加载，过期 1 分钟，内存换响应时间。

## 四、面试官连环追问清单（含参考答案）

### Q1：定时器方案到底为什么不行？key 不多呢？

key 少当然行——JDK DelayQueue、Netty HashedWheelTimer 都是现成方案。但缓存场景 key 是百万/亿级：每个 key 一个 TimerTask 的对象头 + 调度开销就是天文数字；且过期时间可变，每次 SETEX/PSETEX 都要重置定时器。Netty 时间轮能缓解调度开销，但对象本身的开销仍在——所以 Redis 这种通用缓存不会选它。

### Q2：随机抽样为什么比顺序遍历好？

顺序遍历的致命伤：每次循环时间有限，若总在中间被掐断，DB 后半段的 key 永远轮不到，积压过期 key 越来越多。随机抽样保证每个 key 都有非零概率被抽到，长期看清理是"均匀"的。（Redis 的实际抽样算法改过几版，面试不考源码细节，记住这个设计理由即可。）

### Q3：从库不删过期 key，会不会主从不一致？

不会。删除决策权在主库：主库删了之后 DEL 命令随复制流同步到从库，从库执行删除。3.2 之后从库读过期 key 返回 NULL（只是"读层面假装没有"，数据还在），等主库 DEL 到达后物理删除。设计动机：主从复制是异步的，如果允许从库自主删 key，时钟不一致和复制延迟会引入更多不一致窗口。

### Q4：AOF 重写为什么能"忽略"过期 key？

AOF 重写不是"读旧 AOF 再压缩"，而是**直接遍历内存把当前数据转成写命令**（等价于做了一次 RDB 式快照再用命令表达）。过期 key 在重写那一刻已不在有效数据集里（或重写前的定期/懒惰删除已清理），自然不写进新 AOF。所以重写后的 AOF 天然瘦身。

### Q5：本地缓存（Guava/Caffeine）的过期是怎么做的？

- Guava：惰性删除为主（读写时顺带维护），配合 expireAfterWrite/expireAfterAccess
- Caffeine：惰性 + 可配 scheduler 定期清理；淘汰用 Window TinyLFU（频率素描 Count-Min Sketch + 分段 LRU），命中率比 LRU 高——下一讲淘汰策略的伏笔
- 共同点：都要控制清理开销（控制时间/控制个数），思想与 Redis 一脉相承

### Q6：同一个业务的不同请求，过期时间会不一样吗？（思考题 2）

会，叫动态过期时间：按请求特征（VIP/普通）、数据热度（榜单小时级 vs 老内容分钟级）、计算成本（越贵的计算结果缓存越久）、重要性分级设置。工程实现：写缓存时按上下文算 TTL 而不是全局常量——我们文章里的热点数据案例就是雏形。

### Q7：大量 key 同时过期会发生什么？（联动故障排查笔记）

集中过期风暴：主动过期循环一轮删不完（`expired_time_cap_reached_count` 飙高），且若是大 key，释放内存触发 glibc malloc_trim 阻塞主线程 → 周期性 timeout（见故障排查 02 笔记案例二）。解法：过期时间加随机抖动——这也是防缓存雪崩的同一招。
