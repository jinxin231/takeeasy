> 整理日期：2026-11-06

## 一、文章总结

**三个概念精确区分**（最易混淆的是穿透和击穿）：

| 概念 | 数据在缓存 | 数据在 DB | 典型场景 |
|---|---|---|---|
| **穿透** | ❌ | ❌ | 攻击者伪造大量不存在的 key，每次请求都落空且无法回写，DB 被反复打 |
| **击穿** | ❌ | ✅ | **热点 key** 恰好未命中（过期/失效），几百并发同时回源 |
| **雪崩** | 大量 key **同一时刻**过期 | ✅ | 批量预热/批量计算的数据设了相同过期时间，到点集体失效 |

一句话记忆：**穿透是压根没数据，击穿是缓存里没数据，雪崩是大家一起没数据。**

**解决方案对照**：

| 问题 | 首选方案 | 备选/兜底 |
|---|---|---|
| 穿透 | **回写特殊值**（DB 也查不到 → 缓存写入"不存在"标记，下次直接返回） | **布隆过滤器**（见下） |
| 击穿 | **Singleflight**（同 key 并发回源只放一个线程，其余等待） | 热点 key 永不过期 + 后台刷新 |
| 雪崩 | **过期时间加随机偏移量** | 分批加载 |
| 通用兜底 | **限流**（服务层 + DB 层） | 集群互备（亮点方案） |

**回写特殊值的缺点**（引出布隆过滤器）：攻击者每次换不同的 key 就失效；大量"不存在标记"浪费内存，还可能把有用数据**挤淘汰**。

**布隆过滤器要点**：
- 流程：请求先问 BF → 说没有就直接返回；说有才查缓存/DB 并回写
- **假阳性**：BF 说"有"可能是误判（万分之一概率），攻击百万并发也只漏过去 100 个查询——毛毛雨，可接受
- 两种顺序：先问 BF（保护好，提前挡非法请求）vs 先查缓存再问 BF（对正常请求友好，命中就不惊动 BF）；BF 也在 Redis 上实现时两者差别不大

**雪崩偏移量怎么定**（追问点）：**与过期时间成正比**——15 分钟 → 偏移 0~180s；4 小时 → 0~10 分钟；10 秒 → 只能 0~3s。除了随机，也可等差递增（第 N 条加 N 秒）。

**限流的隐含假设（深度点）**：服务层限流假设"全不命中 DB 也撑得住"——但**多数人压测定阈值时把缓存命中算进去了**，所以还要补 **DB 层面的限流**（数据库代理层，或 ORM 层），这是保护 DB 的最后防线。

**亮点方案：集群互为备份（渐进式容错）**——应对 Redis 集群整体崩溃/网络不通：
1. 准备两个 Redis 集群（可以两家云厂商各买一个，**不做数据同步**），业务 1 主用集群 1，业务 2 主用集群 2，互为备份
2. 业务与主集群保持心跳；连不上 → 触发容错：
   - **非核心业务：直接熔断**（舍小保大）
   - **核心业务：按预设比例切到集群 2 + 回查 DB**，其余熔断
3. 没问题就**逐步放大比例**；主集群恢复心跳后**渐进切回**（刚恢复的集群是冷的，先用小流量重建数据）
- **初始流量 = DB 能撑住的量**（初期全不命中全回源）；放量原则**保守**（把备集群弄崩损失更大）
- 经济适用版：**小规模集群甚至单机 Redis 做全业务备份**——只要求撑住核心流量一段时间，"再差也比没有强"

**面试准备清单**：你们 Redis 怎么部署（Cluster/Sentinel）？崩过吗？连不上怎么容错？遇到过穿透/击穿/雪崩吗？有没有保护 DB 的措施？

## 二、Q&A（问题 + 标准答案）

### Q1：穿透、击穿、雪崩的区别？

穿透：缓存和 DB 都没有（数据不存在），每次请求落空且无法回写——典型是攻击伪造不存在的 key。击穿：缓存没有但 DB 有，**热点 key** 未命中导致高并发回源——非热点无所谓，就是普通未命中。雪崩：大量 key 同一时刻过期，集体回源——根因是批量加载 + 相同过期时间。

### Q2：缓存穿透怎么解决？

两个思路：①**回写特殊值**——DB 也没有就缓存"不存在"标记，下次直接返回；缺点是换 key 攻击无效、浪费内存、可能挤掉有用数据。②**布隆过滤器**——请求先问 BF，没有直接返回；假阳性率极低（万分之一），攻击并发百万也只漏 100 个。BF 可放缓存前也可放缓存后，前者保护好，后者对正常请求友好。

### Q3：缓存击穿怎么解决？

**Singleflight**：同 key 未命中时只有一个线程回源，其余等待共享结果——几百并发落到 DB 只剩一个查询。分布式场景用分布式锁占位 + double-check（见 34 笔记）。热点数据也可"永不过期 + 后台异步刷新"。

### Q4：缓存雪崩怎么解决？偏移量怎么定？

根因是批量加载 + 相同 TTL，所以在过期时间上加**随机偏移量**打散。偏移量**与过期时间成正比**：15min → 0~180s；4h → 0~10min；10s → 0~3s。太短（0~10s）打不散，太长影响数据新鲜度。也可用等差递增（第 N 条 +N 秒）。

### Q5：服务层已经限流了，为什么还要 DB 层限流？

服务层限流的隐含假设是"最坏情况（全不命中）DB 也撑得住"——但压测定阈值时大多把缓存命中率考虑进去了，假设不成立。穿透/击穿/雪崩/Redis 崩溃时请求全压到 DB，所以 **DB 层限流是必不可少的最后防线**：数据库代理支持就在代理上做，否则在 ORM/DAO 层做。

### Q6：Redis 集群整个崩了怎么办？（亮点方案）

集群互为备份：两个集群（可两家云）互为主备、不做数据同步。心跳发现主集群不可用 → 非核心业务熔断舍小保大 → 核心业务按初始比例（= DB 承受力）切备集群 + 回源 → 验证无恙逐步放量 → 主集群恢复后渐进切回（先小流量重建冷数据）。成本敏感可用小规模集群甚至单机做备份。

### Q7：思考题 1——Redis 崩溃后启用本地缓存容灾，怎么讲？

可以，而且成本为零（本地内存现成）：Redis 不可用时降级读本地缓存（短 TTL 的热点数据），代价是各节点数据不一致 + 容量有限只能保核心热点。话术要点：本地缓存做"托底副本"，平时影子写入（写 Redis 时同步写本地，TTL 短），故障时切换读取源，恢复后切回——强调这是**有损降级**（容忍秒级不一致），目标是保住核心流量可用性而不是数据一致性。

### Q8：除了文章方案还有什么思路？（思考题 2）

- 穿透：参数校验前置（格式非法直接拒）、网关层封禁攻击 IP、接口签名防伪造
- 击穿：热点探测（JD hotkey 框架）+ 本地缓存热点数据、提前续期（访问时异步延长 TTL）
- 雪崩：多级缓存（本地缓存兜底一层）、分批错峰预热、永不过期 + 版本号刷新
- 通用：多级缓存体系本身就是对三者最好的结构性防御

## 四、面试官连环追问清单（含参考答案）

### Q1：布隆过滤器说"存在"就真存在吗？假阳性怎么来的？

BF 说"不存在"一定不存在，说"存在"可能不存在（假阳性）。原理：k 个哈希函数把元素映射到 bit 数组的 k 个位置置 1，查询时 k 个位置全 1 才认为存在——别的元素恰好把这些位置都置 1 了就误判。假阳性率由 bit 数组大小 m、哈希个数 k、元素数 n 决定：`p ≈ (1 - e^(-kn/m))^k`，k 取 `(m/n)ln2` 时最优。工程上按预期 n 和可接受 p 反推 m。**不能删除元素**（可能误清其他元素的位）——要删除用布谷鸟过滤器或计数型 BF。

### Q2：布隆过滤器的数据怎么维护？新数据入库后怎么办？

- 初始化：全量灌入（启动任务或离线构建）
- 增量：DB 写成功后同步 add 到 BF（注意顺序：先写 DB 成功再更新 BF，失败重试；反了会把不存在的 key 加进去，放过穿透请求）
- 删除：BF 不支持删——接受"已删数据在 BF 里仍存在"（后果只是多查一次缓存/DB，无正确性问题）；或定期重建 BF

### Q3：热点 key 永不过期 + 后台刷新，有什么坑？

①数据一致性窗口变长（后台刷新有延迟）；②刷新任务本身要 HA（挂了热点就永远是旧值）；③逻辑过期时间存在 value 里，删除/更新要主动维护；④对"热点的定义"要准——冷数据永不过期是内存浪费。适合：访问量极大、可容忍秒级~分钟级不一致的头部数据（榜单、大 V 主页）。

### Q4：Singleflight 等待的线程要超时吗？回源失败怎么办？

- **必须超时**：等待不能无限期（回源慢会拖死等待线程池），超时后降级（返回默认值/错误，或各自重试回源——注意防二次并发风暴，可加退避）
- 回源失败：所有等待者共享这个失败结果（Go singleflight 会共享 error）；要配重试策略，且失败的 key 短期熔断（防止失败结果反复触发全量回源）
- 分布式版本：SET NX PX 抢锁回源，没抢到的轮询等待 + 超时降级

### Q5：互备方案里，备集群平时闲着不浪费吗？

不闲着——这就是"互为备份"的精髓：业务 1 主用集群 1，业务 2 主用集群 2，**两个集群平时都承担生产流量**，只在对方故障时接管对方的核心流量（非核心直接熔断，不给备集群加压）。容量设计按"单集群故障时剩余集群能扛住双方核心流量之和 + 余量"规划。比"主备冷备"利用率高得多，比"数据同步的双活"复杂度低得多。

### Q6：怎么判定 Redis 集群"崩溃了"还是"网络抖动"？

和注册中心崩溃检测同思想（见微服务 01 笔记）：心跳失败**立刻**判定不可用并切换（宁可错杀，保护 DB），但**持续探测**；恢复心跳后**渐进**切回（刚恢复的集群是冷的，立刻全量切回 = 人为制造雪崩）。阈值：连续 N 次心跳失败触发切换，恢复后按 10%→30%→100% 梯度回切。

## 五、专题深挖（生产实例确认）

### 专题 1：我们的 Redis 部署形态——生产 INFO 实证

生产实例实测输出（2026-11）：

```
INFO server:    redis_version:5.0.14, uptime_in_days:217, hz:20, proxy_run_id:95d4...
CLUSTER INFO:   cluster_state:ok, cluster_slots_assigned:16384, cluster_known_nodes:1, cluster_size:1
INFO replication: role:master, connected_slaves:1, master_replid2 存在
```

**判定：云厂商集群版 Redis（Cluster 架构，proxy 接入）**。证据链：

1. `CLUSTER INFO` 有输出且 `cluster_state:ok`、16384 slot 全部分配 → Cluster 模式实锤（单机/Sentinel 模式此命令直接报错）
2. `proxy_run_id` 字段 → 连接经过了**云厂商代理层**（开源 Redis 的 INFO 没有此字段）。架构：`应用 → proxy（cluster 协议路由）→ 分片1(主+从)、分片2(主+从)...`
3. `cluster_known_nodes:1 / cluster_size:1` **不代表只有一个分片**——proxy 模式下每个后端分片只能看到自己；真实分片数要去云控制台看实例规格
4. `role:master + connected_slaves:1` → 当前分片一主一从，主挂自动切换
5. `master_replid2 + second_repl_offset` 存在 → **这套实例历史上发生过主从切换**（replid2 是老主的复制 ID，故障转移后才留下）——"公司 Redis 崩过吗"的真实素材：发生过主从切换，业务无感知扛过来了
6. `hz:20`（默认 10）→ 云厂商调优过，后台任务（过期清理等）更勤快

**确认部署形态的三条途径**：`INFO server` 看 `redis_mode`；`CLUSTER INFO` 能否执行；代码客户端类型（JedisCluster / sentinel 配置 / 单地址 + proxy）。

**面试话术**：
> "我们的 Redis 是云厂商集群版，proxy 接入的 Redis Cluster，每个分片一主一从。从复制历史看发生过主从切换，业务无感知。分片扩容和故障切换交给云平台，我们的精力放在缓存设计本身——穿透击穿雪崩防护和大 key 治理。"

### 专题 2：proxy 是谁提供的？业界格局

- **开源 Redis 官方没有 proxy**——官方选"聪明客户端"路线（客户端算 slot、处理 MOVED/ASK 跳转）；官方出过的 `redis-cluster-proxy` 是实验性质，已归档，没人上生产
- **云厂商的 proxy 是自研闭源的**（阿里云、AWS 同理）——不是 Envoy 等开源方案：proxy 承载了云的差异化能力（热 key/大 key 统计、审计、读写分离路由、Tair 扩展数据结构），不可能用通用方案
- **开源 proxy 格局**：Twemproxy（Twitter，静态分片，淘汰）→ Codis（豌豆荚，Go，slot+在线迁移，曾遍地开花，官方 Cluster 成熟后停更）→ Predixy（C++，兼容 Cluster 协议）→ Camellia（网易，Java）/ Overlord（B 站，Go）；Envoy Redis filter 只服务已有服务网格体系的公司
- **proxy 存在的四个动机**：①分片路由对客户端透明；②连接收敛（几万应用连接 → proxy 对后端几十条）；③治理唯一入口（限流/熔断/热 key 统计做在数据必经之路上）；④屏蔽后端变化（切换/迁移/换实现业务无感）。代价：多一跳延迟，proxy 自身要无状态多副本
- **大厂实践**：头部自研 proxy + 管控平台（路由表配置中心下发，proxy 上做观测治理）；中小厂用云托管或裸 Cluster——**proxy 的价值不在路由，在于它是唯一能做全局治理的位置**
