## 一、文章总结

**锁的本质**：Redis 分布式锁 = **一个普通的键值对**。排他性来自 `SETNX`——设置成功即持锁，别人在你删除前无法设置同样的 key。加锁 = SETNX，释放锁 = DEL。支持排他操作的中间件都能做锁（ZooKeeper、Nacos、MySQL `SELECT FOR UPDATE`）。

**加锁的全链路细节**：

| 环节     | 要点                                                                                                                            |
| ------ | ----------------------------------------------------------------------------------------------------------------------------- |
| 等待时间   | 按**锁持有时间**设置（99% 的锁 1s 内释放 → 等待 1s）                                                                                           |
| 等待机制   | ①**轮询**（睡 100ms 重试，直到成功或超时）；②**监听删除事件**（订阅 key，删了立刻重试——实时性好但实现复杂，且"发现锁被持有 + 订阅"必须做成原子整体，否则有并发漏洞）                              |
| 加锁超时重试 | 超时不知道锁上加没有 → **value 用 UUID 标识身份**：重试时查 key 是否存在 + 值是否是自己的 UUID（是自己的 → 重置过期时间；是别人的 → 加锁失败）。最多重试一两次，一直超时也无妨（没加上别人能拿，加上了过期自然释放） |

**锁过期时间**：
- 为什么需要：持有者宕机 → 锁永远没人释放（关键词：**没人释放**）
- 设多长：按业务（99% 业务 1s 完成 → 设 2s）；**保险起见宁长勿短**（正常路径都会主动释放，过期时间只是兜底，设 10s~1min 也没事）

**续约机制**：
- 不管过期时间设多长，都可能有业务跑不完 → 快过期时重置过期时间（1min 的锁，50s 时续回 1min）
- 续约窗口要留足重试时间（预留 10s，第一次续约失败还能重试）
- **续约一直失败怎么办**（关键取舍）：
  - **保守策略**：中断业务——续约失败意味着马上有别人拿到锁，继续执行会破坏排他性
  - **激进策略**：继续执行——接受偶发的数据不一致

**中断业务**（老大难问题）：分布式锁只能**发信号**，不能替你中断。实现：大循环每轮开头检测中断信号；无循环则在每个关键步骤后检测。微服务超时控制面临同样的无解困境——框架做不到自动中断。

**释放锁**：先**确认锁是自己的**（比对 value 中的 UUID）再删——防 Redis 崩溃恢复后锁已被别人持有、或有人手动操作过 Redis。校验 + 删除要用 **lua 脚本**原子执行（补充点，防"检查后删除前"的窗口）。

**Redlock**（知道概念即可，业界很少真用）：
- 要解决的问题：主从异步复制——主节点崩溃时锁还没同步到从节点，从升主后锁丢失，别人能拿到同一把锁
- 思想：**多数原则**——向多个**独立** Redis 节点同时加锁（5 个节点至少 3 个成功才算成功）
- 细节：锁有效期要**减去加锁耗时**（10s 的锁加锁花了 1s 就只剩 9s）；加锁失败要在**所有节点**上释放
- 成本高、性能差，大多数公司不用——面试官随口一问，答出"多数派 + 独立节点"即可

**性能优化两方向**：
1. **优化 Redis 本身**：给分布式锁用**单独的 Redis 集群**，避免别的业务影响加解锁性能
2. **减少竞争**：**Singleflight**——同一实例内同一把锁只选一个线程去竞争（2 实例 × 10 线程 = 20 竞争者 → 优化后只剩 2 个）；激进版：实例释放锁前看本地有没有线程等这把锁，**直接转交**，省一次加解锁
- 竞争越激烈效果越好，低并发无感

**去分布式锁**（最高境界）：
1. **数据库乐观锁替代**：加锁只为"算完更新 DB"的场景 → 去掉锁直接并发算，最后乐观锁（version）更新 DB 兜住并发
2. **一致性哈希**：同业务请求固定落一个节点 → 本地锁 / Singleflight 就够，不需要分布式锁
- 收尾金句：**分布式锁不管怎么优化都有性能损耗，能不用就不用**

## 二、Q&A（问题 + 标准答案）

### Q1：Redis 分布式锁的基本实现？

锁 = 一个普通键值对。加锁：`SET key uuid NX PX 30000`（原子地"不存在才设置 + 带过期时间"，value 用 UUID 标识持有者）。释放：lua 脚本"比对 value 是否是自己的 UUID，是则删除"。等待：轮询或监听删除事件。

### Q2：为什么需要过期时间？设多长？

持有者宕机则锁**没人释放**，系统死锁。过期时间是兜底：按业务 P99 持锁时间设（99% 业务 1s 完成 → 2s），宁长勿短——正常路径主动释放，过期只兜崩溃场景，设长无害。

### Q3：业务没跑完锁就过期了怎么办？

**续约**：快过期时重置过期时间（50s 续回 60s），预留窗口够重试。续约一直失败看业务取舍：排他性严格 → **中断业务**（锁马上会被别人拿走）；可容忍偶发不一致 → 继续执行。Redisson 的看门狗（watchdog）就是这个机制（补充）。

### Q4：怎么中断业务？

分布式锁只能发信号不能替你中断。大循环每轮开头检测中断标志；无循环则在关键步骤间检测。这和微服务超时控制是同一个无解问题——框架无法强制中断业务线程，只能靠代码主动配合。

### Q5：释放锁为什么要先检查 UUID？（误删问题）

场景：线程 1 持锁 → Redis 崩溃恢复 → 线程 2 加了同一把锁 → 线程 1 执行完直接 DEL，把**线程 2 的锁**删了。所以释放前必须比对 value，且"比对 + 删除"用 lua 原子执行。同理**加锁重试**也靠 UUID 判断"上次到底加上没有"（key 存在且值是我的 → 已持锁，重置过期即可）。

### Q6：主从切换丢锁怎么办？Redlock 是什么？

主从异步复制：主崩时锁未同步到从，从升主后锁丢失 → 两人同时持锁。Redlock：**多数原则**——向多个独立节点同时加锁，多数成功才算成功；有效期扣掉加锁耗时；失败则全节点释放。成本高性能差，业界用得少；真要可靠锁，可考虑 ZK/etcd（CP 语义）。

### Q7：分布式锁怎么做性能优化？

①独立 Redis 集群隔离噪音；②**Singleflight 减竞争**：实例内同一把锁只派一个线程去抢（20 竞争者 → 2）；③激进版：**本地转交**——释放前看本地有无等待者，直接移交锁，省一次加解锁。竞争越激烈收益越大。

### Q8：怎么去掉分布式锁？

①**数据库乐观锁**：锁只是为保护"计算 + 更新 DB"的最终一致性 → 并发直接算，乐观锁控制最终写入；②**一致性哈希**：同业务请求固定落一个节点 → 本地锁即可。原则：**能不用分布式锁就不用**。

## 四、面试官连环追问清单（含参考答案）

### Q1：释放锁的重试要考虑什么？（思考题 1）

释放失败重试的风险和加锁相反：**重试 DEL 可能删掉别人的锁**（自己锁已过期被别人拿走）。所以释放重试前必须先 GET 校验 UUID 还是不是自己；不是 → 停止重试（锁已易主，无需再删）。另外释放重试次数要有限——锁本身有过期时间兜底，释放不了最差等过期，无限重试反而引入风险。

### Q2：SET NX 和 PX 为什么要一条命令？分开设会怎样？

`SETNX` + `EXPIRE` 两条命令非原子：第一条成功后客户端崩溃/网络断，key 永远没过期时间 → 死锁。所以必须 `SET key val NX PX ms` 单命令（或 lua）保证"加锁 + 设过期"原子完成。这是面试里最基础的防坑点。

### Q3：锁的等待用轮询，间隔怎么定？惊群问题怎么处理？

间隔按锁持有时间量级定（持锁 1s → 100ms 轮询）；加**随机抖动**防惊群——大量等待者同时醒来同时抢锁，互相踩踏。更好的做法是监听删除事件（文章方案二），但"发现锁被持有 + 订阅"必须原子，否则订阅前锁已释放就永远等不到通知。

### Q4：Redlock 为什么争议大？Martin Kleppmann 怎么批的？（深度补充）

争议核心：Redlock 的正确性依赖**时钟假设**（各节点时钟不能跳变）和**无长时间进程停顿**（GC 暂停/网络延迟超过锁有效期，客户端醒来后锁已过期，两人同时持锁）。Kleppmann 指出：①时钟跳变会让多节点同时认为锁有效；②无法防止 GC pause 破坏互斥；③真要正确需要 **fencing token**（单调递增令牌，存储端拒绝旧令牌的写）。Antirez（Redis 作者）的反驳侧重工程实用。结论话术：**Redlock 不是银弹，强一致需求选 ZK/etcd + fencing token**。

### Q5：ZooKeeper 做锁和 Redis 做锁怎么选？

- ZK：**临时顺序节点**——会话断开自动删除（天然解决"没人释放"）、序号排队避免惊群、watch 通知替代轮询、CP 语义锁更可靠；代价是性能低（写走 Leader + 集群共识）
- Redis：性能高、实现简单，但过期时间/续约/主从丢锁等边界情况要自己兜
- 选型：低频高可靠（调度选举、Leader 选主）→ ZK/etcd；高频可容忍极小概率失败（业务幂等兜底）→ Redis

### Q6：续约（看门狗）有什么坑？

①**续约线程与业务线程的可见性**：业务卡死（死循环/GC 长停）时看门狗还在续约，锁永远不释放，其他节点永远等待——看门狗要在"业务心跳"上续约而不是无脑定时续；②续约失败的中断信号业务方根本收不到/不处理，组件形同虚设——所以组件设计要强制回调或抛出；③集群时间跳变影响 PX 判断。

### Q7：本地转交锁会不会有风险？（激进优化的追问）

有：①**转交期间实例崩溃**——被转交的线程没真正拿到 Redis 锁（锁还在原线程名下，虽有 UUID 归属问题）；实现上转交本质是"实例内复用同一把分布式锁"，实例崩溃 → 锁到期自然释放，影响可控；②转交链过长导致**锁实际持有时间远超预期**，续约压力增大；③饥饿：本地不断有新线程插入转交，其他实例长期抢不到 → 需要转交次数上限 + 公平性退避。

### Q8：Singleflight 优化和"一致性哈希去锁"矛盾吗？

不矛盾，是递进关系：同实例内先 Singleflight 收敛竞争（优化锁的使用）；再把同业务请求路由到同节点（一致性哈希），此时连分布式锁都可以退化为**本地锁**——因为同 key 的并发已被拓扑结构天然串行化。一个治标一个治本，一起讲体现方案演进能力。

## 五、专题深挖：从 SETNX 到 Redisson——分布式锁基础层完全拆解

### 1. SETNX 与原子互斥命令家族

**SETNX = SET if Not eXists**："key 不存在才设置，存在就什么都不做"。设置成功返回 1、已存在返回 0。Redis 最古老的互斥原语，分布式锁的奠基石。但裸 SETNX 没法同时设过期时间，Redis 2.6.12 起 `SET` 命令加了修饰参数，**现代标准写法**：

```bash
SET lock:order:1001 uuid-xxx NX PX 30000
# NX = 同 SETNX 语义    PX 30000 = 顺带 30 秒租约
# 一条命令原子完成"抢锁 + 设租约"
```

**原子互斥/条件命令家族**（面试能报出这串说明底子好）：

| 命令                           | 语义          | 锁/并发场景用途                  |
| ---------------------------- | ----------- | ------------------------- |
| `SETNX`                      | 不存在才设       | 抢锁（原始版）                   |
| `SET key val NX PX ms`       | 不存在才设 + 带过期 | **现代抢锁标准**                |
| `GETSET key val`             | 设新值返回旧值（原子） | 原子换值，旧锁检测                 |
| `SET key val XX`             | 存在才设（NX 反义） | 续约时的安全写                   |
| `INCR` / `DECR`              | 原子计数        | 计数信号量、限流                  |
| `EVAL lua`                   | 整段脚本原子执行    | 解锁（比对 token 再删）、续约、一切复合操作 |
| `HSET` + `PEXPIRE` + pub/sub | hash 结构存锁   | Redisson 可重入锁的实现基础        |

记忆点：**Redis 单线程执行命令 = 每条命令天然原子**。分布式锁的全部技巧，就是把"抢、续、放"三个动作各自压缩进一条原子命令（或一段 Lua），不留中间状态。

### 2. 展开"SETNX 成功 = 排他"（原文核心论证三层拆解）

原文："如果一个线程能够用 SETNX 成功地在 Redis 上设置好一个键值对，那么在它删除这个键值对之前，别的线程都没办法再设置同样的键值对。"

- **第一层：为什么"设置成功"= 拿到锁？** Redis 单线程处理命令：50 个实例同时发 `SET lock:k token NX`，命令在事件循环里排队挨个执行，第一个发现 key 不存在、设置成功返回 1，后面 49 个全部返回 0。**没有任何时序能让两个客户端同时成功——互斥性是单线程模型在数学上保证的，不是概率上的。**
- **第二层：为什么删之前别人没法再设置？** `NX` 语义"存在即失败"，key 活着期间任何 `SET NX` 都被拒。"key 的存在性"就是锁状态位：key 存在 ⇔ 锁被持有；key 消失 ⇔ 锁空闲；删 key = 释放锁。
- **第三层：为什么"分布式"？** 判定权在所有实例共享的第三方 Redis。JVM 锁只管本进程，而 50 台机器连同一个 Redis 抢同一个 key——**竞争被收敛到中立仲裁者手里**。

两个隐患（原文后续展开）：持锁者删 key 前宕机 → 死锁 → 必须 `PX` 租约兜底；租约到期业务没跑完 → 互斥破 → 需要续期（看门狗）。

### 3. 加锁失败如何等待（三种策略按档次排）

**① 朴素自旋（面试能写，生产慎用）**：

```java
public void lockWithSpin(String key, String token, long leaseMs, long timeoutMs) {
    long deadline = System.currentTimeMillis() + timeoutMs;
    long backoff = 10;  // 初始退避 10ms
    while (System.currentTimeMillis() < deadline) {
        Boolean ok = redis.set(key, token, SetParams.setParams().nx().px(leaseMs));
        if (Boolean.TRUE.equals(ok)) return;   // 抢到，返回
        try {
            Thread.sleep(backoff + ThreadLocalRandom.current().nextLong(10));
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new RuntimeException("等锁被中断", e);
        }
        backoff = Math.min(backoff * 2, 100);  // 指数退避，封顶 100ms
    }
    throw new RuntimeException("等锁超时");
}
```

三个细节都是考点：**总超时兜底**（不能无限等，联动 07 篇超时控制）、**指数退避**（别拿固定频率打 Redis）、**随机抖动**（防等待者同频重试 → 惊群，见追问 Q3）。

**② 发布订阅等待（Redisson 的做法，生产级）**：自旋的本质缺陷是锁释放瞬间等待者不知道，只能等下次轮询。Redisson 改成事件驱动：

```
1. 抢锁失败 → 订阅频道 redisson_lock__channel:{key}
2. 挂起自己（Semaphore.tryAcquire(等待超时)），不再轮询
3. 持锁者解锁时 PUBLISH "UNLOCK_MESSAGE" 到频道
4. 等待者被唤醒 → 立刻再抢 → 失败则重新订阅挂起
```

延迟从平均半个轮询周期降到毫秒级，且零无效请求。

**③ 直接失败（fail-fast）**：很多业务根本不该等——抢不到锁说明有并发重复操作（防重复提交、防重任务），直接报错让用户重试。**等不等取决于语义是"我要排队"还是"拒绝重入"。**

### 4. 锁如何续期（看门狗 watchdog）

问题：租约 30s 业务跑 40s——第 30s 锁过期，互斥破。思路：**业务活着，就定期给锁续命**。

```
持锁成功（租约 30s）
   └─ 后台定时任务：每 10s（租约的 1/3）检查
        ├─ 业务还在跑 → 重置过期时间为 30s（续约）
        └─ 业务结束/线程死了 → 不再续约 → 锁到期自然释放
```

关键设计点：

- **续约间隔 = 租约 / 3**：一次失败还有两次机会，不会一次抖动就丢锁
- **续约命令**：Lua 原子完成"GET 比对 token + PEXPIRE"（先确认锁是自己的）
- **续约前提是持锁线程活着**：线程死了续约线程也死，锁自然释放——**看门狗不会造成死锁**，这是它比"设超长过期时间"优雅的原因
- **坑**（见追问 Q6）：Full GC / 线程池打满导致续约线程被饿死 → 锁照样过期 → 互斥破。看门狗降低的是"过期误伤"的**概率**而非 100% 保证——回到 Martin Kleppmann 的批评：基于时间的锁永远敌不过停顿（GC pause，见 Q4）

**Redisson 默认行为**：`lock()` 不传超时 → 自动开看门狗（租约 30s、每 10s 续）；传了 `leaseTime` → 不续期，到期就释放。

### 5. Redisson 介绍

**Redisson = Redis + son**，不是简单的 Redis 客户端，而是 **Redis 上的分布式 Java 工具库**——把 Redis 包装成熟悉的 `java.util.concurrent`：

```java
RLock lock = redisson.getLock("order:1001");
lock.lock();                       // 抢锁 + 自动看门狗续期
try {
    // 临界区
} finally {
    lock.unlock();                 // token 校验 + Lua 原子释放
}
```

前面 2~4 节的脏活它全包了：

| 手写方案           | Redisson 对应物                                              |
| -------------- | --------------------------------------------------------- |
| SET NX PX 抢锁   | `lock()` 底层 Lua：hash 结构 `HSET key threadId 1` + `PEXPIRE` |
| 自旋等锁           | pub/sub 订阅 + Semaphore 挂起唤醒                               |
| 看门狗续期          | `lock()` 不传参自动开启；`lock(30, SECONDS)` 关闭                   |
| token + Lua 解锁 | `unlock()` 内置                                             |

能力全景：`RLock` 可重入锁、`RReadWriteLock` 读写锁、`RFairLock` 公平锁（按等待顺序）、`RedLock` 多实例红锁、`RSemaphore` 信号量、`RCountDownLatch` 倒数闩，以及 `RMap`/`RBucket`/`RAtomicLong` 等分布式数据结构。

**底层为什么用 hash 不用 string**：可重入要记录"谁、加了几次"——`HSET lockKey threadUUID:threadId 1`，重入 `HINCRBY` 加一，解锁减一，减到零才真删 key。面试常考的实现细节。

**使用注意（选型话术）**：Redisson 解决"锁的易用性和完备性"，**解决不了主从切换丢锁这个架构级问题**（见 Q6 Redlock）。普通业务 Redisson 单机/主从够用；金融级强互斥考虑 ZK/etcd（CP）或 Fencing token。

## 六、专题深挖：SETNX 设置的 key，为什么别人"删不了"？

**认知纠正：别人其实删得了。** `DEL` 命令不检查任何身份——任何客户端都能删任何 key，Redis 没有 key 的"所有者"权限概念。感觉"删不了"是因为正规用法里没人直接 DEL，释放锁的标准动作是带身份校验的 lua：

```lua
-- 释放锁：先验身份再删除
if redis.call("GET", KEYS[1]) == ARGV[1] then   -- value 是我的 UUID 吗？
    return redis.call("DEL", KEYS[1])            -- 是才删
else
    return 0                                     -- 不是我的锁，不动
end
```

**两层防线各防各的**：

| 威胁 | 防线 | 性质 |
|---|---|---|
| 别人抢走锁（覆盖我的 key） | SETNX——key 已存在则设置失败 | Redis 命令**强制** |
| 别人误删我的锁 | 释放前比对 UUID，不匹配不删 | 客户端**约定** |

**为什么需要第二层约定**——"别人删你的锁"不是恶意而是事故：

```
线程1: 持锁 → 卡顿/GC 太久 → 锁过期自动释放 → 线程2 抢到同一把锁
线程1: 缓过来，执行完直接 DEL → 把线程2的锁删了！
```

有了 UUID 比对：线程 1 的 lua GET 出来是线程 2 的 UUID，`return 0` 不动——线程 2 的锁保住。

**防追问两个边**：
- "有人不守约定直接 `DEL lock_key` 呢？" → 防不住。Redis 层面无权限隔离（顶多 ACL 限制危险命令）。所以"锁绝对可靠"只是工程前提不是铁律——34 篇强一致方案的前提之一正是它
- "比对+删除为什么必须 lua，两条命令不行？" → 有窗口：GET 确认是我的 → 此刻锁恰好过期被别人抢到 → 我执行 DEL 删了别人的锁。lua 在单线程里原子执行，把"检查+删除"焊成一步

**一句话总结**：SETNX 管"抢"，UUID+lua 管"删"；前者是 Redis 强制的，后者是共同遵守的协议——**分布式锁本质是建立在约定上的，而不是 Redis 提供的权限机制**。

## 七、命令拆解：`SET lock:order:1001 uuid-xxx NX PX 30000`

```
SET lock:order:1001 uuid-xxx NX PX 30000
 │         │            │       │   │   └── 30000 毫秒 = 30 秒
 │         │            │       │   └────── PX：过期时间单位是毫秒（EX 是秒）
 │         │            │       └────────── NX：key 不存在才设置（Not eXists），已存在则失败返回 nil
 │         │            └────────────────── value：UUID，锁持有者身份标识（解锁时凭它验身）
 │         └─────────────────────────────── key：锁的名字，lock:业务:业务ID 命名约定
 └────────────────────────────────────────── SET：设置键值对
```

**每个部分的角色**：

- **`lock:order:1001`**：锁的资源名。锁的粒度由 key 决定——这把锁只锁"1001 这个订单"，别的订单互不影响。粒度越细并发越高
- **`uuid-xxx`**：身份 token。谁加锁谁生成，解锁时 lua 比对它（见专题六）
- **`NX`**：互斥语义。已有别人持锁 → 返回 nil，抢锁失败；没有它，普通 SET 会覆盖别人的锁
- **`PX 30000`**：租约 30 秒。持锁者崩溃/断网，锁到期自动释放，防死锁。**必须和 SET 一条命令完成**——拆成 `SETNX` + `EXPIRE` 两条，第一条成功后客户端崩了，key 永远没有过期时间 → 死锁

**执行结果**：

- 成功：返回 `OK` → 持锁，30 秒内别人抢不走
- 失败：返回 `(nil)` → 锁被别人持有，进入等待策略（轮询重试 / 订阅删除通知）

这条命令 = "加锁 + 设租约"的原子版本，Redis 2.6.12 起支持，分布式锁现代标准写法。面试写 `SETNX` + `EXPIRE` 两步的，会被追问"中间崩了怎么办"。

## 八、专题深挖：Redisson 看门狗（watchdog）机制

**触发条件**：只有 `lock()` **不传租约时间**时启用；显式传 `lock(30, SECONDS)` 则 Redisson 认为你自己管理过期，看门狗不启动。

**核心参数**：`lockWatchdogTimeout = 30000ms`（默认可配），**续约周期 = watchdogTimeout / 3 = 10 秒**。

**运作流程**：

```
lock() 成功
  → 往 Netty 的 HashedWheelTimer 注册延时任务（10 秒后执行）
  → 10 秒后执行续约 lua：
      if hexists(lockKey, threadId) then     -- 锁还在我手里吗？
          pexpire(lockKey, 30000)            -- 在就把 TTL 重置为 30 秒
          → 续约成功 → 注册下一个 10 秒延时任务（循环）
      else
          → 锁已不在 → 停止续约
  → unlock() 时取消续约任务
```

关键点：**续约本质是"重置过期时间"而非延长**——每 10 秒把 TTL 拨回 30 秒，业务跑多久锁活多久。续约同样 lua 原子执行（`hexists` 验持有者 + `pexpire` 重置）。

**"如何判定业务线程还在正常进行"——答案是：它不判定。**

看门狗没有任何线程健康检查（不查线程状态、不查心跳、不感知业务进度）。它跑在 Netty 定时器线程里，唯一判断条件是 **Redis 里 hash field（threadId）还存在**——"只要 JVM 活着、锁在我名下，就默认业务还在跑，继续续约"。三种情况：

| 场景 | 看门狗行为 | 结果 |
|---|---|---|
| 业务正常执行 | 每 10s 续约 | 锁一直在 ✓ |
| **JVM 崩溃/被杀** | 看门狗线程同归于尽，续约停止 | 锁 30s 后自动过期，**不死锁** ✓ |
| **业务卡死但 JVM 活着**（Full GC 10 分钟、死循环、等下游超时） | **照常续约** | 锁一直不放，其他人进不来 ✗ |

第三行是看门狗的著名软肋（Martin Kleppmann 批评分布式锁的论据）：**"持锁者还活着" ≠ "持锁者还在正常干活"**。GC 长暂停期间锁一直被续，暂停结束后业务拿着可能已不安全的锁继续写——若期间发生过锁过期+别人抢锁，就是双持锁。

**工程正确姿势**：
- 普通业务：看门狗够用——JVM 崩溃自动放锁的收益远大于 GC 场景风险
- 关键写路径（钱、库存）：看门狗 + **Fencing token**（加锁拿递增序号，存储端拒绝序号小的写入）——安全性从"锁"转移到"数据层校验"
- 面试标准答案："它不知道业务活着没有，只确认锁还在我手里。JVM 活着就续约，JVM 死了续约线程跟着死、锁自然过期——**它防的是死锁，防不了 GC 长暂停下的双持锁，那要靠 fencing token**"
