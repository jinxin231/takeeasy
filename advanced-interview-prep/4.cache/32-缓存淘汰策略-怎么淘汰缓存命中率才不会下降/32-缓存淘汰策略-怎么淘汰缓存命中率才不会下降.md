## 一、文章总结

**为什么需要淘汰**：必须控制缓存内存开销（本地缓存塞太多 → 频繁 GC 甚至 Full GC）。内存到上限后最保守的做法是报错拒写，但多数业务认为"旧数据虽未过期但可能用不上了，不如淘汰腾给新数据"——**新数据比老数据更可能被访问**。

**两大经典算法**：

| 算法 | 原理 | 实现 | 变种 |
|---|---|---|---|
| LRU 最近最少使用 | 淘汰最长时间未被访问的 | 链表：访问挪队尾，队首淘汰；Java `LinkedHashMap` 一行实现 | 只在写时挪动（倾向保留写频繁数据） |
| LFU 最不经常使用 | 淘汰使用次数最低的 | 按频率排序，次数相同淘汰最先插入（或随机） | 只统计**一段时间**内次数（实现复杂度高） |

**LRU 的死穴**（面试加分）：
- **历史记录场景**：越久的数据越该留，LRU 反着来
- **遍历场景**：全表/全量遍历把缓存"洗"一遍——刚被遍历到的挪到队尾保留，而真正有用的全被淘汰，遍历完缓存命中率归零

**实践结论**：优先 LRU（时间局部性对大多数应用成立），特殊场景换 LFU 或定制。

**Redis 的淘汰控制**：
- `maxmemory`（实例总内存上限）+ `maxmemory-policy`（淘汰策略）
- **无法控制单业务的内存**——只能间接控制：限制业务的键值对数量 × 单键值对大小（1 万对 × 1KB = 10MB 上限）
- 实现思路：额外维护键值对计数（区分"新增 key" vs "已有 key 改值"）+ **监听删除事件**（过期/被淘汰也能收到通知）+ **lua 脚本**封装保证原子性

**补充：Redis 八种淘汰策略**（文章提了 volatile-lru，补全）：
- `noeviction`（默认）：不淘汰，写报错
- `allkeys-lru` / `volatile-lru`：所有 key / 仅设了过期时间的 key 中 LRU
- `allkeys-lfu` / `volatile-lfu`（4.0+）：同上按 LFU
- `allkeys-random` / `volatile-random`：随机
- `volatile-ttl`：淘汰剩余 TTL 最短的

**亮点方案：按优先级淘汰（业务定制）**——同一公司内业务重要性有差别，同一业务内用户重要性也有差别（VIP vs 普通）：
1. 用**有序集合（zset）按优先级 score 排序**，元素个数 = 键值对数量
2. 写操作走 **lua 脚本**：检查数量是否超上限 → 未超：写 key + 入 zset；超了：取 zset 第一个 key（优先级最低）连键值对一起删
3. **监听删除事件**，同步从 zset 移除（防计数漂移）
4. 优先级的不同算法衍生不同策略：
   - **大对象先淘汰**：一次腾出大量空间（本地缓存常用）；缺点是大对象重算代价可能高
   - **小对象先淘汰**（= **代价低先淘汰**）：小对象重算快，未命中波动小；缺点是新对象大时要连删好几个
   - **按冷热淘汰**：小博主数据先淘汰（大博主粉丝多，被访问概率高）——与"热点数据缓存更久"同思想

**案例**：本地缓存用 LRU 把大客户数据淘汰了，而大客户实时计算很慢 → 未命中 RT 暴增、客户抱怨"时快时慢"。改为**优先淘汰小客户数据**后，平均 RT 下降 40%（小客户计算快，影响小）。

**面试准备清单**：公司 Redis 淘汰策略及调整史；本地缓存怎么控内存/什么淘汰算法；缓存引发的故障案例；有空手写一个本地缓存（防追问细节）。

## 二、Q&A（问题 + 标准答案）

### Q1：为什么需要缓存淘汰？

控制内存开销是硬约束（本地缓存失控 → Full GC；Redis 失控 → OOM/丢数据）。内存满后新数据进不来，而"新数据大概率比老数据更有用"，所以淘汰旧数据腾空间。最理想的方案其实是加内存不触发淘汰——但现实资源有限，淘汰策略是必须面对的。

### Q2：LRU 和 LFU 的区别？怎么实现？

- LRU 按**时间**：最久未访问的淘汰。链表/LinkedHashMap，访问挪队尾队首淘汰
- LFU 按**频率**：使用次数最少的淘汰。计数排序，次数相同淘汰先插入的
- LRU 适合时间局部性（大多数场景）；LFU 适合"长期热门"数据，但老数据计数高有"缓存污染"问题（新来的热点挤不进去）——所以有了"只统计一段时间"的变种

### Q3：LRU 在什么场景失效？（深度题）

①历史记录类：越老越不该淘汰，LRU 正好相反；②**遍历/扫描场景**：一次全量遍历把所有真热数据挤出缓存（刚遍历的冷数据反而成了"最近使用"），遍历后命中率归零——所以用 Redis 要警惕定时全量扫描类任务。

### Q4：Redis 支持哪些淘汰策略？你们用的什么？

`maxmemory` 控总量，`maxmemory-policy` 定策略：noeviction（默认，写报错）、allkeys/volatile 的 lru、lfu、random、volatile-ttl。回答时**必须补上你们公司实际用的**（如 volatile-lru）及原因。

### Q4-1：淘汰策略什么时候被触发？（文章没讲，必补）

**写入类命令执行前，检查 `used_memory` 是否超过 `maxmemory`，超了就在主线程跑淘汰循环，删到水位线下才放行命令。** 两个前提缺一不可：

- `maxmemory` 必须显式设置：64 位默认 0 = 不限内存，永不触发淘汰，涨到被 OS OOM Killer 干掉——生产必配项
- `maxmemory-policy` 不能是默认的 `noeviction`：默认策略超了直接写报错（`OOM command not allowed`），读照常

源码层面在 `processCommand()` 处理每条命令前检查，三个推论：

1. **淘汰在主线程同步执行**——要删的 key 多或是大 key，命令延迟尖刺（联动 02 篇"响应变慢"排查）；生产配 `lazyfree-lazy-eviction yes` 异步释放内存
2. 一次写入可能连带删 N 个 key
3. **近似淘汰**：随机抽 `maxmemory-samples` 个（默认 5，建议 10）放进 16 槽淘汰池选最差的——调样本数换精度，再次印证"Redis 宁可近似也不要全局排序开销"（联动 31 篇）

`volatile-*` 系隐藏坑：只从带 TTL 的 key 里淘汰，没 TTL 可淘汰时**退化成 noeviction**，写照样报错。从库不自己淘汰，靠主库传播 DEL（同 31 篇"删除决策权归主库"）。`maxmemory` 统计不含复制输出缓冲——主库挂从库时缓冲撑爆内存不受保护，照样可能 OOM。

### Q4-2：大厂生产上一般选什么策略？

一句话：**绝大多数纯缓存用 `allkeys-lru`，但真正的共识是"淘汰策略只是保险丝，不是容量方案"**。

- **`allkeys-lru`（事实标准）**：纯缓存（数据可从 DB 重建）场景，所有 key 参与淘汰，时间局部性对多数业务成立
- **`allkeys-lfu`（进阶）**：热点稳定场景（榜单/商品详情）。LRU 怕新数据冲击，LFU 按频率识别真热点；要调 `lfu-decay-time` 否则老热点永远不下台
- **云厂商默认 `volatile-lru`**（ElastiCache/阿里云）：保守选择，只淘汰用户明确设了 TTL 的 key，避免误删当存储用的数据。**策略选择 = 对数据可丢弃性的认知**——云厂商不知道你数据能不能丢所以保守，自建集群定位明确就该 allkeys-lru
- **`noeviction` + 监控告警（反直觉但常见）**：①Redis 当存储用（主数据/会话/锁）——宁写报错不静默丢数据；②容量治理成熟的团队——`evicted_keys` 持续 > 0 说明容量规划失守，该扩容而非靠淘汰硬扛，noeviction 让问题立刻暴露

配套三条（大厂和"会用 Redis"的差距）：

1. **按业务重要性分集群**（联动 06 篇）：淘汰策略按集群配，混在一起怎么配都不对
2. **纯缓存集群 key 全部带 TTL**：淘汰是保险丝，TTL 是日常；没 TTL 内存只涨不跌，天天触发淘汰
3. **`maxmemory` 配实例内存 70~80%**：留余量给复制缓冲、AOF 缓冲、fork COW——写满才淘汰已经晚了

**30 秒话术**：
> "纯缓存集群统一 allkeys-lru，热点稳定的用 allkeys-lfu 调衰减；当存储用的配 noeviction 宁报错不丢数据，evicted_keys 接告警——持续大于零是容量问题该扩容。所有 key 强制带 TTL，maxmemory 留 20% 缓冲给复制和 fork。云厂商默认 volatile-lru 是对数据可丢弃性的保守，自建集群定位明确的话 allkeys-lru 更合适。"

### Q4-3：为什么说淘汰策略只是保险丝？高水平容量方案长什么样？

**保险丝类比**：电路里保险丝的作用是电流异常时烧断自己保护设备——但没有电气工程师把"保险丝天天烧"当供电方案。同构地：

| 保险丝 | Redis 淘汰 |
|---|---|
| 烧断是异常事件，触发即电路设计有问题 | `evicted_keys > 0` 是异常事件，容量规划已失守 |
| 烧断有代价：停电 | 淘汰有代价：命中率掉、回源 DB、主线程删 key 延迟尖刺 |
| 好设计 = 保险丝永远不烧 | 好方案 = 淘汰永不触发，但必须配着兜底 |
| 烧了要排查：为什么过载 | 淘汰了要复盘：哪个业务涨的、该不该扩容 |

普通团队"配了 allkeys-lru 就高枕无忧"= 把保险丝当稳压器；大厂认知：**淘汰策略的意义是兜底那个"万一"，容量方案才是日常**。

**业内高水平容量方案六环闭环**：

**① 接入评审（事前——容量从入口管起）**：接 Redis 先过评审工单——容量预估（key 数量级 × 平均 value 大小 × 增长率 × 留存周期 → 算 3 个月/半年后水位）；纯缓存集群无 TTL 直接打回；单 value 超阈值（如 100KB）要求拆分或走对象存储；QPS 预估决定单实例还是集群版。

**② 容量分配与配额（按业务切块）**：按业务重要性分集群/实例（联动 06 篇），各自独立配 maxmemory 和淘汰策略；业务配额制（Q5 的 zset+lua 是最小实现，成熟团队用 proxy 层统一配额统计）；maxmemory 配物理内存 70~80%，余量给复制缓冲、AOF 缓冲、fork COW。

**③ 监控指标体系（事中——水位可视化）**：

| 层 | 指标 | 告警意义 |
|---|---|---|
| 水位 | used_memory / maxmemory 占比 | 70% 关注、80% 预警、90% 紧急 |
| 淘汰 | evicted_keys（保险丝）、expired_keys | 持续 > 0 = 容量问题报警 |
| 质量 | 命中率、内存碎片率 | 命中率缓降 = 淘汰在偷偷发生；碎片率 > 1.5 考虑重启整理 |
| 结构 | bigkey 巡检、无 TTL key 占比 | 结构性风险提前暴露 |

**④ 定期治理（让内存回流）**：bigkey 巡检（`--bigkeys` / `MEMORY DOCTOR`）发现即治理；`OBJECT IDLETIME` 找僵尸 key push 业务方删除；无 TTL 审计超阈值告警纳入业务考核；容量周报盯增长率 Top N——**增长是可预测的，事故是懒得预测的结果**。

**⑤ 弹性扩容预案（事前练过，事中不慌）**：垂直扩（升配）vs 水平扩（集群加节点/扩 slot）的耗时与影响面提前演练；水位 80% 触发扩容工单流；缓存失守时业务降级直连 DB + DB 侧限流兜底（联动 05 篇）——缓存挂了不能把 DB 打死。

**⑥ 复盘与计费（组织保障）**：每次 evicted_keys > 0 都复盘（哪个业务涨的、预估偏差在哪、评审为什么没拦住）；成本按业务归账（chargeback）——技术问题用经济杠杆解决；预估 vs 实际偏差反哺下次评审。

**整体视角**：

```
接入评审 → 配额分配 → 监控告警 → 定期治理 → 弹性扩容 → 复盘计费
（事前）    （切块）    （事中）    （回流）    （预案）    （闭环）
                ↑                                    ↓
                └────────── 偏差反哺预估 ←────────────┘
淘汰策略（allkeys-lru 等）= 挂在电路末端的保险丝，正常永不触发
```

**45 秒话术**：
> "我们对缓存容量的态度是：淘汰策略只是保险丝，正常运营 evicted_keys 必须为零，触发即复盘。容量方案是六环闭环——入口有接入评审，强制 TTL 和 value 上限、预估三个月水位；按业务分集群配独立配额；监控看四层指标——水位、淘汰、命中率、bigkey；定期治理僵尸 key 和无 TTL key 让内存回流；扩容预案提前演练，缓存失守时业务降级配 DB 限流兜底；最后成本按业务归账，用经济杠杆推动治理。容量问题的本质不是技术问题，是'增长可预测但没人预测'的管理问题。"

### Q5：怎么控制某个业务在 Redis 上的内存占用？（文章方案）

Redis 只能控实例总量，不能按业务限额。间接控制：限制业务的**键值对数量 × 单键大小**。落地：zset 记录业务的 key（score 可用优先级），写时用 lua 脚本检查数量上限，超限先删优先级最低的；监听删除事件同步维护计数。注意区分"新增 key"和"已有 key 改值"。

### Q6：为什么要用 lua 脚本？有什么并发问题？（思考题 2）

"检查数量 → 写入 → 更新 zset"是多步操作，两个客户端并发执行会同时通过检查 → 数量超上限；或"读取计数"和"删除"之间状态被改。lua 脚本在 Redis 单线程模型下**原子执行**，把多步操作变成一个不可分割的整体，避免分布式锁的复杂度和开销。

### Q7：大对象先淘汰还是小对象先淘汰？

没有标准答案，看业务：
- 大先淘汰：一次腾空间大——适合大小不均、大对象重算便宜的场景
- 小先淘汰（代价低先淘汰）：小对象重算快，未命中代价小——适合计算成本差异大的场景（我们的大客户案例：大客户计算慢，淘汰小客户数据保大客户体验）
- 抽象：**按"重算代价"淘汰，而不是按对象大小**——代价是逻辑概念，任何关键资源消耗都可以量化成代价

### Q8：淘汰策略和命中率的关系？怎么验证策略好坏？

淘汰策略的直接目标就是**在有限内存下最大化命中率**（淘汰最不可能再被访问的）。验证方式：对比实验——换策略前后观测命中率、RT、miss 后回源耗时；本地缓存可打标后用 A/B 或灰度验证。文章案例：改策略后平均 RT 降 40%。

### 项目经历栏·案例：按业务优先级定制淘汰策略

**版本 A（简洁版，一行）**
- 优化缓存淘汰策略：定位到 LRU 会误淘汰重算成本高的大客户数据导致 RT 抖动，设计"zset 优先级排序 + lua 脚本原子控制"的定制淘汰机制，优先淘汰低优先级数据，平均响应时间下降 40%

**版本 B（详细版，供面试口述）**
> 我们一个本地缓存用 LRU，业务反馈几个大客户查询时快时慢——我一听"时快时慢"就怀疑是缓存问题。排查发现 LRU 会把大客户数据淘汰掉，而大客户数据实时计算很慢，一未命中 RT 就暴增。我做了两件事：一是扩缓存可用内存；二是设计按优先级的淘汰策略，优先淘汰小客户数据——小客户计算快，未命中也没什么波动。改造后平均响应时间下降 40%。后来我把这个思路推广到 Redis 上：用有序集合按优先级排序，写操作用 lua 脚本原子地检查上限、写入、淘汰，再监听删除事件维护计数。优先级算法可以按业务换：代价低先淘汰、按冷热淘汰都是同一框架。

### 项目经历栏·案例二：机票价格缓存淘汰策略选型与调优（真实业务场景）

**版本 A（简洁版，一行）**
- 负责 4G 机票价格缓存（爬虫 + 航司 API 双源各半）的淘汰策略选型：基线 allkeys-lru 上线，识别出爬虫批量回写刷新 LRU 时间戳造成"写污染"的风险，通过爬虫刷新时段命中率监控 + LRU/LFU 对比实验验证策略；按双源重建成本差异设计 TTL 分级（爬虫数据长 TTL、API 数据短 TTL），让低重建成本数据优先过期，缓存命中率稳定在 XX% 以上

**版本 B（详细版，供面试口述）**
> 我们的机票价格缓存 4G，数据一半来自爬虫爬航司官网、一半来自航司 API。淘汰策略我选的 allkeys-lru 做基线——查询侧时间局部性极强：干线航线、近 7 天出发日期的查询量是长尾的几个数量级，"最近被查的还会被反复查"。但选型时我识别出两个自家场景的特殊点：第一，爬虫是主动批量回写的，而 Redis 的 LRU 写入时也刷新时间戳——爬虫每刷一轮，那批无人查询的 key 全变成"最近使用"，真热 key 反而可能先被淘汰，这是遍历污染的变种。所以上线后我专门盯爬虫刷新时段前后的命中率，一旦出现规律性下跌就切 allkeys-lfu 做对比实验——LFU 计数器是对数概率递增，批量写入冲不动频率排序。第二，两个数据源的重建代价完全不同：API 毫秒级重查，爬虫慢且有反爬风控，淘汰了可能暂时拿不到报价。按"重算代价"原则，我给爬虫数据设长 TTL、API 数据设短 TTL，让便宜的先过期、贵的活久一点。另外这个场景 TTL 首先是业务正确性——缓存价和实际价不一致就是客诉，所以 TTL 按价格可接受陈旧度定，淘汰策略只做容量兜底，evicted_keys 持续大于零就该扩容而不是调策略。

**这个案例的面试价值**：把 32 篇三个最亮的点一次性落地——①LRU/LFU 选型不是背定义而是看访问模式；②遍历污染的变种识别（写入也会污染 LRU）；③Q7"按重算代价淘汰"的真实应用。

## 四、面试官连环追问清单（含参考答案）

### Q1：直接控制某个业务的内存使用量（而不是间接控制）怎么做？（思考题 1）

思路：给每个 key 记录大小（`MEMORY USAGE` 或写入时自算），维护业务的"已用内存计数"（lua 脚本里增减），写入前检查 `已用 + 新对象大小 > 上限` 则先淘汰。麻烦在于：①对象大小本身不好精确（编码、指针、分配器对齐）；②改值、删除、过期都要维护计数，一致性靠 lua + 删除事件兜底，工程复杂度高——所以实践中多用"数量 × 单键上限"的间接控制。

### Q2：Redis 的 LFU 是怎么实现的？为什么不用真计数？（补充深挖）

Redis 4.0 的 LFU 用 **8bit 对数计数器**（`lru` 字段复用，存 LFU 时是 16bit 衰减时间 + 8bit 计数）：访问时**按概率递增**（当前计数越大越难涨，对数增长），并按时间**周期性衰减**（`lfu-decay-time`）——变相实现了"只统计一段时间"的效果，防止老热点永远霸榜。面试能讲出"概率递增 + 时间衰减"就算到位。

### Q3：淘汰是全局扫描吗？会不会像全表扫描一样卡？

不是。Redis 淘汰是**采样**：每轮从候选集随机取 N 个（`maxmemory-samples`，默认 5），淘汰其中最符合策略的一个，不够再采。近似 LRU/LFU 而非精确——用精度换性能，样本数可调（越大越准越慢）。所以 Redis 的 LRU 是"近似 LRU"，与 LinkedHashMap 的精确 LRU 不同。

### Q4：淘汰触发时机是什么？被淘汰的数据去哪了？

每次**写命令执行前**检查 `used_memory > maxmemory` 则触发淘汰循环（不是后台异步）。被淘汰的 key 直接删除，若主从架构 DEL 同步到从库；若配了淘汰通知（`notify-keyspace-events` 的 evicted 事件），应用可监听——这正是文章"监听删除事件维护计数"的机制来源。

### Q5：本地缓存怎么选淘汰策略？Caffeine 为什么快又准？

- Guava：LRU 分段实现，并发分段锁
- Caffeine：**Window TinyLFU**——Count-Min Sketch 记频率（4bit 计数，概率性），准入窗口（1%）+ 主区域分段 LRU（SLRU），新对象进窗口区，淘汰时窗口区候选与主区域候选 PK 频率——同时利用了 LRU 的局部性和 LFU 的抗扫描性，遍历场景也不会崩命中率。面试答本地缓存淘汰，Caffeine 这个设计是最大的料

### Q6：你的业务适合 LRU 还是 LFU？（开放题）

判断依据是访问模式：时间局部性强（最近访问的还会再访问，如会话、热点新闻）→ LRU；长期频率稳定（长期热门商品）→ LFU；有明显业务分级（VIP/普通）→ 定制优先级淘汰；有周期性遍历 → 避开 LRU 或用带频率成分的（Caffeine TinyLFU）。能结合自己业务讲出"为什么"就是高分。

## 五、专题深挖（讨论补充）

### 专题 1：LRU 只算写，会把读频繁的 key 删掉吗？

**会。** 这是"只在写时挪动"变种的坑：LRU 的核心是"最近被**使用**过的留下"，如果只在 put 时挪队尾、get 不挪，那么一个被高频读取但从不修改的 key 会一直停在最初写入的位置，逐渐沉到队首被淘汰——哪怕它每秒被读一万次。

标准 LRU 里**读和写都算"使用"**：`LinkedHashMap` 的 `accessOrder=true` 模式 get 也会挪动；Redis 的近似 LRU 任何访问（含读）都会刷新 key 的 lru 时钟字段。纯写时挪动只适用于"写入热度 = 访问热度"的场景（如写后必读），通用缓存这么实现是错误的。

与 LRU 遍历死穴（全量扫描把冷数据刷成"最近使用"，挤出真热数据）本质相同：**"使用"的定义错了，淘汰的就错**。

### 专题 2：如何查看 Redis 的淘汰策略？

```bash
CONFIG GET maxmemory-policy     # 当前策略，如 allkeys-lru
CONFIG GET maxmemory            # 内存上限，0 表示不限制（64 位默认）
INFO memory                     # maxmemory_policy、used_memory、used_memory_rss
INFO stats                      # evicted_keys：累计被淘汰的 key 数
```

重点看 `evicted_keys`：持续增长说明内存长期不足，要扩容或治理大 key。云厂商控制台一般在实例详情页直接展示这两个配置。

设置：`CONFIG SET maxmemory-policy allkeys-lfu` 即时生效，但**必须写进 redis.conf 持久化**，否则重启丢失。

### 专题 3：自己实现本地缓存，要注意什么？

按重要性排序：

1. **容量上限 + 淘汰策略**：防 Full GC 的命根子，无上限的本地缓存 = 内存泄漏延时炸弹。LRU 起步（LinkedHashMap 十行），有遍历场景上 Caffeine
2. **过期机制**：惰性删除（get 时检查）+ 定期清理兜底——纯惰性会让过期 key 长期占内存。过期和淘汰是两回事，都要
3. **并发安全**：put/get/淘汰是多步复合操作（查满 → 淘汰 → 写入），分段锁或 CAS，不能裸 HashMap；ConcurrentHashMap + LinkedHashMap 混用注意原子性
4. **空值缓存（防穿透）**：查 DB 为 null 也要缓存（短 TTL），否则恶意 key 每次打穿到 DB（见 35）
5. **统计埋点**：命中率、淘汰次数、加载耗时必须暴露——没有命中率数据，调容量换策略都是拍脑袋
6. **回源加载并发控制**：热点 key 过期瞬间 N 线程同时回源（击穿，见 35）——加载加锁/singleflight，只放一个线程查 DB
7. **警惕大对象和引用泄漏**：缓存存的是引用，调用方改对象会污染缓存；对象太大加剧 GC

面试话术：先答 1~3（基本盘），主动补 4~6（工程经验），收尾一句"生产上直接用 Caffeine，它就是这些考虑的最佳实践集合"。
