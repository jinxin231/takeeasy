## 一、文章总结

**预备知识：double-check 模式**——"检查 → 加锁 → 再检查"，兼顾并发安全与性能（读写锁场景；分布式锁没读锁时第一次检查不加锁；可用原子操作替代读锁）。是后续所有方案的基础代码模式，也可单独作为并发优化亮点。

**核心分析框架：不一致的两个根源**（能讲到这层就是亮点）：

| 根源 | 本质 | 能否解决 |
|---|---|---|
| ① 操作部分失败 | "更新 DB + 更新缓存"要么都成功要么都失败 = **分布式事务问题**；缓存基本不支持 XA | ❌ 不可避免，只能**尽量缩短不一致窗口**（重试、自动校验修复） |
| ② 并发操作 | 多线程并发更新 DB 和缓存，时序交错 | ✅ 可解决：让**同一时刻只有一个线程在更新** |

**解决"并发更新"的四条路**：

| 方案 | 机制 | 一致性程度 |
|---|---|---|
| 缓存模式 | Write Back（Redis 且不丢数据时业务视角天然一致，见 33 笔记） | 缓解 |
| **分布式锁** | 更新和回源都串行化 | 接近强一致（见亮点方案） |
| **消息队列** | 同业务的更新请求排队，消费者串行执行；失败可重试 | 最终一致 |
| **版本号** | 低版本不能覆盖高版本；DB 加版本字段，Redis 用 lua 校验版本再更新（可用更新时间替代） | 解决并发覆盖，但版本号维护麻烦 |

**消息队列方案要点**：同一业务消息必须**有序**（否则更新出错）；消息只当**触发器**——消费者收到后**查 DB 最新数据**更新缓存（不能用消息体数据，先写 DB 的不一定先发消息）。但既然要先写 DB 再发消息，**不如直接用 Canal 监听 binlog（Refresh Ahead）**，效果更好。

**多级缓存更新顺序**（本地缓存 + Redis + DB）：**先 DB，再本地缓存，最后 Redis**。理由：①DB 是最准数据源；②本地缓存更新几乎不失败；③查询先查本地，先更新本地保证用户立即可见新值；④即便 Redis 更新失败，有本地缓存挡着也读不到 Redis 的旧值。

**亮点方案一：一致性哈希 + 缓存**（呼应微服务 02 讲）：
- 用户 ID 一致性哈希 → 同一 key 的请求只落一个节点 → 节点内配合 **Singleflight**（同 key 同节点最多一个线程在更新）
- 节点下线无影响（流量自然切到唯一新节点）；**节点上线（扩容）有短暂不一致**：新节点头 2 秒不读写缓存，等老节点在途请求自然返回——用 2 秒的 RT 劣化换零不一致
- 价值：把负载均衡、并发分析、一致性串成一个出人意料的组合方案

**亮点方案二：分布式锁两种思路**：

**思路一（常规）：先本地事务，后分布式锁**
```
本地事务提交 → 加分布式锁 → 删除缓存 → 释放锁
读：先读缓存（不加锁，高性能关键）→ 未命中 → 加分布式锁 → double-check 再读一次缓存 → 回源回写 → 释放锁
```
只解决并发更新，不解决部分失败。

**思路二（激进）：先删除缓存，再提交事务——无限接近强一致**
```
开启本地事务 → 加分布式锁 → 删除缓存 → 提交事务 → 释放锁
```
- **关键机制（理解的钥匙）**：读路径未命中时也必须抢同一把锁才能回源——"缓存已删、事务未提交"的窗口期读线程全卡在锁上，等能回源时事务已提交，必得新值
- 失败穷举（必考）：删缓存失败 → 事务不提交 → 两边都旧 = 一致；删成功但提交失败 → 缓存空 + DB 旧 = 一致（只是多删一次）——**任何失败形态都留不下"DB 新、缓存旧"**
- **达成强一致的两个前提**：①分布式锁绝对可靠（一人持锁他人绝无可能拿到）；②删除缓存超时重试直到确认成功
- **最大缺点：本地事务容易超时**（等锁、网络抖动删缓存都会拉长事务）。缓解：先加锁再开事务——代价是锁持有时间变长，且删除仍在事务内，超时风险仍在

**面试准备清单**：每个用缓存的地方怎么解决一致性的？没解决能容忍多久不一致？不一致多久能发现/修复？有没有自动发现修复机制？——强调"**我知道能有多不一致、多久能收敛**"。

## 二、Q&A（问题 + 标准答案）

### Q1：缓存不一致的根源是什么？

两个：①**操作部分失败**——更新 DB 和缓存无法保证原子性，这是分布式事务问题，缓存不支持 XA，不可避免，只能靠重试和自动校验修复缩短窗口；②**并发操作**——多线程并发更新时序交错，这个可解，核心是让同一时刻只有一个线程在更新（分布式锁/消息队列/版本号/缓存模式）。

### Q2：怎么用消息队列解决缓存一致性？

把同一业务的更新请求发到 MQ 且**保证有序**，消费者串行更新 DB 和缓存——天然实现"同数据单线程更新"。失败重试对业务无影响。只能做到最终一致。注意消息只当触发器，消费者要**回查 DB 最新值**再更新缓存（消息体数据可能已过时）。

### Q3：版本号方案怎么用？

每次更新版本号 +1，低版本数据不能覆盖高版本。落地：DB 加 version 字段；更新 Redis 时用 **lua 脚本先校验缓存里的版本号再写**。Cache Aside 的并发不一致场景都能被它化解。缺点：版本号维护麻烦；可用更新时间戳替代（要处理时钟回拨）。

### Q4：多级缓存（本地 + Redis + DB）按什么顺序更新？

DB → 本地缓存 → Redis。DB 最准所以最先；本地缓存更新几乎不失败且查询先经过它，先更新可立即见效；最后更新 Redis，即使失败也有本地缓存挡着，读不到旧值。硬要挑毛病仍有不一致场景，但这个顺序把窗口压到最小。

### Q5：一致性哈希负载均衡和缓存结合怎么用？扩容时怎么办？

同 key 请求固定落一个节点，节点内用 Singleflight 保证同 key 只有一个线程在更新 → 消除并发更新。节点下线无感（流量切走仍唯一）；**节点上线（扩容）**时短暂有两个节点服务同 key → 新节点头 2 秒不读写缓存，等老节点在途请求返回，用短暂 RT 劣化换零不一致。

### Q6：分布式锁方案怎么设计？（思路一）

写：本地事务提交 → 加分布式锁 → 删缓存 → 放锁。读：先读缓存**不加锁**（高性能关键）；未命中再加锁，**double-check** 再读一次缓存（可能别的线程已回写），还没有才回源回写。读路径只在未命中时抢锁，保证了读性能。

### Q7：怎么做到"无限接近强一致"？（思路二）

把**删除缓存放进本地事务**：开事务 → 加锁 → 删缓存 → 提交 → 放锁。失败分析：删失败则事务不提交（一致）；删成功但提交失败只是多删一次（一致）。两个前提：锁绝对可靠、删除必重试到成功。代价：**本地事务容易超时**（等锁/网络抖动），缓解办法是先加锁再开事务，但锁持有时间变长。

### Q8：思考题 1——先提交事务再释放锁，顺序能反过来吗（先放锁再提交）？

不能。先放锁再提交：放锁瞬间其他线程的读请求会回源——此时事务**还没提交**，读到的是旧值并回写缓存，而这个事务随后可能提交成功 → 缓存留下旧值且无人再删。所以**锁必须覆盖到事务提交**，提交完成前锁不能放。

### Q9：思考题 2——"先加锁 → 本地事务提交 → 最后删缓存"有什么缺点？

缓存在**整个事务期间**都是旧数据且可被读到：事务提交后到删缓存前有窗口，读到旧值并可能回写；且锁持有时间 = 整个事务 + 删除操作，并发度最差。不一致场景：事务已提交、删缓存失败 → 缓存旧值一直存活直到过期。

## 四、面试官连环追问清单（含参考答案）

### Q1：为什么不直接用分布式事务保证 DB 和缓存一致？

缓存中间件（Redis/Memcached）基本不支持 XA 这类强一致事务协议；就算硬套 TCC/Saga，两个资源一个内存一个磁盘，协调成本和性能损耗远超收益。而且缓存的定位就是"可容忍短暂不一致的加速层"——为最终一致性设计的基础设施，硬要强一致是拿错工具。

### Q2：消息队列方案里消费者更新缓存失败怎么办？

MQ 重试机制天然兜底：消费失败 → 不提交 offset → 消息重投 → 再次尝试。配合消费幂等（重复更新同值无副作用）即可。这也是 MQ 方案相比"业务代码里删缓存"的优势——**把"删除失败的重试"从业务代码移到了基础设施**。

### Q3：版本号方案里时钟回拨怎么办？

用时间戳当版本号时，时钟回拨会导致新数据版本号反而变小被拒。解法：①逻辑时钟（DB 自增 version 字段，最可靠）；②混合逻辑时钟（HLC）；③接受小概率问题，监控发现后人工修复。严肃场景用 DB 自增版本号。

### Q4：Canal 监听 binlog 刷新缓存，有哪些不一致窗口？

①binlog 产生 → Canal 消费 → 刷缓存的链路延迟（正常毫秒级，积压时秒级+）；②Canal 宕机期间缓存持续旧；③批量大事务产生大量 binlog 造成积压。对应：监控 Canal 位点延迟告警；读敏感业务关键操作可同步删缓存 + binlog 异步兜底（双保险）。

### Q5：思路二里"删除缓存"为什么在事务内？为什么它能"无限接近强一致"？

先明确前提（理解思路二的钥匙）：**读路径未命中时也必须抢同一把分布式锁**才能回源（同思路一的读路径）。所以"缓存已删、事务未提交"这个危险窗口虽然存在，但**窗口期任何读线程都卡在锁上，无人能回源**；等抢到锁时事务已提交，回源必得新值。

**穷举所有结局——脏数据不可能产生**：

| 结局 | DB | 缓存 | 一致？ |
|---|---|---|---|
| 全部成功 | 新（已提交） | 空 → 回源得新值 | ✓ |
| 删缓存失败 | 旧（事务不提交） | 旧（没删掉） | ✓ |
| 删成功但提交失败 | 旧 | 空 → 回源得旧值 | ✓（只是多一次 miss） |

每种失败形态留下的都是"两边都旧"或"两边都新"，**永远留不下"DB 新、缓存旧"这个致命形态**——对比思路一"提交后删缓存失败 → 脏数据活到过期"，这就是思路二叫"无限接近强一致"的原因。

放事务外（提交后再删）就退回思路一：提交到删除之间有窗口，期间读请求回源旧值并回写缓存，旧值要等下次写或过期才消失。

**为什么只是"接近"**：强一致建立在两个工程前提上——①分布式锁绝对可靠（Redis 主从切换丢锁则穷举失效，见 07）；②删除必须重试到确认成功。前提做不到 100%，所以不是强一致。

**代价**：事务寿命 = 等锁 + 删缓存网络耗时（含重试）+ 正常事务时间 → 长事务占 DB 连接、持行锁，高并发下易超时。缓解：抢锁挪到开事务之前（锁外等待），事务只做"删缓存+提交"变短；但锁持有更久，其他写线程排队更久——两头必牺牲一头。

### Q6：如果分布式锁用 Redis 实现，"锁绝对可靠"怎么保证？（引向 07 讲）

单机 Redis：SET NX PX + 唯一标识 + lua 释放，够用但主从切换时可能丢锁（主库挂了锁没同步到从库）→ Redlock 多多数派方案（争议大，Martin Kleppmann 质疑过时钟依赖）。工程实践： Fencing token（单调递增令牌）+ 存储端校验，或干脆用 ZK/etcd（CP）做锁。详见 07 分布式锁笔记。

## 五、专题深挖：分布式锁方案完全拆解（思路一 + 思路二）

> 原文"分布式锁方案"小节的完整推演。作者原话："很多人用，但是很少有人给你解释清楚里面的弯弯绕绕。"

### 0. 先立背景：分布式锁在这里治什么病

不一致的两个根源，分工必须记住：

| 根源 | 本质 | 可治吗 |
|---|---|---|
| **操作部分失败** | "更新 DB"和"删/更新缓存"无法同成功同失败 = 分布式事务问题，缓存不支持 XA | ❌ 不可根治，只能重试/校验修复缩短窗口 |
| **并发操作** | 读写线程交错，顺序乱了出脏数据 | ✅ 让同一时刻只有一个线程动同一个 key |

**分布式锁治的是并发，不是部分失败。思路一和思路二的全部区别，就在于对"部分失败"的消化程度不同。**

### 1. 思路一：先本地事务，后分布式锁（性能不错，一致性一般）

**路径设计**：

```
写路径：执行本地事务（改DB）→ 提交 → 加分布式锁 → 删除缓存 → 释放锁
读路径：读缓存 → 命中直接返回
              → 未命中 → 加分布式锁 → （double-check 再读一次缓存）→ 回查DB → 回写缓存 → 释放锁
```

**关键点 ①：读路径回查为什么要加锁？**

若不加锁，存在致命交错：

```
写线程：提交事务 → 加锁 → 删除缓存 → 释放锁
读线程：          缓存未命中 → 查DB(旧值) → ──时间流逝── → 回写缓存(旧值)
```

读线程查完 DB、还没回写的窗口里，写线程完成"提交新值 + 删缓存"。随后读线程把旧值回写——**这个旧值没有任何人再来清理**（删除动作已过去），脏数据常驻直到 TTL 兜底。给"回查+回写"加同一把锁后，两个**复合临界区**互斥，只剩两种合法交错：

1. 读线程先完成（旧值回写）→ 写线程后删 → 旧值被清掉 ✅
2. 写线程先完成（删缓存）→ 读线程后查 DB → 查到已提交的新值 ✅

**关键点 ②：锁保护的不是"写 Redis"，而是复合临界区**

检验理解的精准表述：如果只是两个 Redis 写操作，根本不需要锁——Redis 单线程天然保证单命令互斥。锁的必要性完全来自**读线程的临界区里夹着一个对 DB 的慢速读取**：

| 临界区 | 包含步骤 | 不互斥的后果 |
|---|---|---|
| 写线程 | 提交事务 → 删缓存 | 删完被旧值回填，无人擦屁股 |
| 读线程 | 查 DB → 回写缓存 | 基于过期快照回写 |

反问检验：读路径回查若改成"查 Redis 里另一个 key"（不碰 DB），还需要锁吗？——不需要，那就退化成原子读+原子写，Redis 自己保证顺序。**锁的存在是为了消灭"读线程临界区横跨写线程删除动作"这种交错。**

**关键点 ③：第一次读缓存为什么不加锁？**

这是**高性能的关键**：99.9% 的读请求缓存命中，若每次都先抢分布式锁，等于所有读流量过一遍 Redis 锁，性能直接崩。所以第一眼读缓存无锁——这正是 double-check 的变种"**第一次检查什么锁都不加，因为分布式锁没有读锁**"。拿到锁后再读一次缓存（第二次检查），可能别的线程已回写好，不必回源。

**关键点 ④：为什么一致性"比较差"？**

只解决了并发交错，没解决部分失败：删缓存那步失败（网络抖动、Redis 挂），没有事务保护——DB 新值、缓存旧值，只能等 TTL 兜底。作者评价：安全、性能不错，但一致性比较差。

### 2. 思路二：先删除缓存，再提交事务（无限接近强一致，隐患大）

思路一的天花板在"删缓存"位于事务**之外**，失败没人管。思路二的灵魂只有一步：**把删缓存挪进本地事务**。

**路径设计**：

```
写路径：开启本地事务 → 执行事务操作 → 加分布式锁 → 删除缓存 → 提交事务 → 释放锁
读路径：同思路一（第一次读无锁；回查持锁 + double-check）
```

**为什么近乎强一致？所有失败路径全枚举**：

| 场景 | 结果 | 一致吗 |
|---|---|---|
| 删缓存失败 | 事务回滚不提交 → DB 没动，缓存旧值还在 | ✅ DB 旧 = 缓存旧 |
| 删缓存成功、提交失败 | 事务回滚 → DB 没动，缓存多删一次 → 下次读回源拿 DB 旧值重建 | ✅ 一致（代价：多一次回源） |
| 删完缓存、提交前，读请求进来 | 缓存未命中 → 回查要抢分布式锁，**锁还在写线程手里** → 读线程等锁 → 写线程提交、放锁 → 读线程回查到**新值** | ✅ 一致 |

两种死法都恰好收敛到"**DB 和缓存一起回到旧状态**"——"删除前置 + 事务回滚"的化学反应：删除成了事务的一部分，失败自动回滚兜底。并发窗口又被"读路径持锁回查"堵死。两条路全封，所以**无限接近强一致**。

**强一致成立的两个工程前提（必背）**：
1. **分布式锁绝对可靠**——一个线程持锁，别的线程绝不可能拿到（互斥破了全盘皆输 → 37 篇主题）
2. **删缓存超时必须重试直到确认成功**——不能"删失败就算了"

**思考题 1：顺序能反吗（先释放锁再提交事务）？**
不能。释放锁的瞬间读请求就能回查 DB——此时事务**还没提交**，读到旧值回写缓存，随后事务才提交 → 缓存旧、DB 新，脏数据。**锁是保护"删缓存 → 提交完成"这段窗口的屏障，必须提交先于放锁。**

**缺点（作者说"很大"）：本地事务容易超时。** 事务开着去抢分布式锁——锁被占久一点，事务干等超时回滚；网络抖动删缓存慢，同样拖垮事务。缓解：把加锁提到事务开始前（先加锁 → 开事务 → 删缓存 → 提交 → 放锁），代价是**锁持有时间更长**、吞吐下降，且删除仍在事务内，超时风险只缓解不根除。

**思考题 2：先加锁 → 提交事务 → 最后删缓存，有什么缺点？**
缺点一：锁占满整个事务期，并发度差。缺点二：有明确不一致场景——事务提交成功、删缓存失败：DB 新、缓存旧，且删除在事务外，没有回滚兜底。

### 3. 一图收束

```
思路一：事务 → 提交 → [锁: 删缓存]        治并发 ✓  治部分失败 ✗  性能 ✓
思路二：事务 → [锁: 删缓存] → 提交 → 放锁  治并发 ✓  治部分失败 ✓  事务易超时 ✗
                          ↑ 灵魂：删除前置，让事务回滚替失败兜底
读路径两个思路相同：第一次读无锁（性能），回查持锁 + double-check（防脏数据回写）
```

**作者的实践忠告（评论区原话印证）**：这套方案是面试顶级亮点，但生产上 99% 的场景 Cache Aside 就够了——"延迟双删面试用得多，实践用得少；大部分时候 Cache Aside 打天下"。它的真正价值是展示你能把**并发时序和失败路径分析到骨头里**。
