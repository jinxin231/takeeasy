> 整理日期：2026-11-06

## 一、文章总结

**预备知识：double-check 模式**——"检查 → 加锁 → 再检查"，兼顾并发安全与性能（读写锁场景；分布式锁没读锁时第一次检查不加锁；可用原子操作替代读锁）。是后续所有方案的基础代码模式，也可单独作为并发优化亮点。

**核心分析框架：不一致的两个根源**（能讲到这层就是亮点）：

| 根源 | 本质 | 能否解决 |
|---|---|---|
| ① 操作部分失败 | "更新 DB + 更新缓存"要么都成功要么都失败 = **分布式事务问题**；缓存基本不支持 XA | ❌ 不可避免，只能**尽量缩短不一致窗口**（重试、自动校验修复） |
| ② 并发操作 | 多线程并发更新 DB 和缓存，时序交错 | ✅ 可解决：让**同一时刻只有一个线程在更新** |

**解决"并发更新"的四条路**：

| 方案 | 机制 | 一致性程度 |
|---|---|---|
| 缓存模式 | Write Back（Redis 且不丢数据时业务视角天然一致，见 33 笔记） | 缓解 |
| **分布式锁** | 更新和回源都串行化 | 接近强一致（见亮点方案） |
| **消息队列** | 同业务的更新请求排队，消费者串行执行；失败可重试 | 最终一致 |
| **版本号** | 低版本不能覆盖高版本；DB 加版本字段，Redis 用 lua 校验版本再更新（可用更新时间替代） | 解决并发覆盖，但版本号维护麻烦 |

**消息队列方案要点**：同一业务消息必须**有序**（否则更新出错）；消息只当**触发器**——消费者收到后**查 DB 最新数据**更新缓存（不能用消息体数据，先写 DB 的不一定先发消息）。但既然要先写 DB 再发消息，**不如直接用 Canal 监听 binlog（Refresh Ahead）**，效果更好。

**多级缓存更新顺序**（本地缓存 + Redis + DB）：**先 DB，再本地缓存，最后 Redis**。理由：①DB 是最准数据源；②本地缓存更新几乎不失败；③查询先查本地，先更新本地保证用户立即可见新值；④即便 Redis 更新失败，有本地缓存挡着也读不到 Redis 的旧值。

**亮点方案一：一致性哈希 + 缓存**（呼应微服务 02 讲）：
- 用户 ID 一致性哈希 → 同一 key 的请求只落一个节点 → 节点内配合 **Singleflight**（同 key 同节点最多一个线程在更新）
- 节点下线无影响（流量自然切到唯一新节点）；**节点上线（扩容）有短暂不一致**：新节点头 2 秒不读写缓存，等老节点在途请求自然返回——用 2 秒的 RT 劣化换零不一致
- 价值：把负载均衡、并发分析、一致性串成一个出人意料的组合方案

**亮点方案二：分布式锁两种思路**：

**思路一（常规）：先本地事务，后分布式锁**
```
本地事务提交 → 加分布式锁 → 删除缓存 → 释放锁
读：先读缓存（不加锁，高性能关键）→ 未命中 → 加分布式锁 → double-check 再读一次缓存 → 回源回写 → 释放锁
```
只解决并发更新，不解决部分失败。

**思路二（激进）：先删除缓存，再提交事务——无限接近强一致**
```
开启本地事务 → 加分布式锁 → 删除缓存 → 提交事务 → 释放锁
```
- 失败分析（必考）：删缓存失败 → 事务不提交 → 一致；删成功但提交失败 → 只是多删一次 → 仍一致
- **达成强一致的两个前提**：①分布式锁绝对可靠（一人持锁他人绝无可能拿到）；②删除缓存超时重试直到确认成功
- **最大缺点：本地事务容易超时**（等锁、网络抖动删缓存都会拉长事务）。缓解：先加锁再开事务——代价是锁持有时间变长，且删除仍在事务内，超时风险仍在

**面试准备清单**：每个用缓存的地方怎么解决一致性的？没解决能容忍多久不一致？不一致多久能发现/修复？有没有自动发现修复机制？——强调"**我知道能有多不一致、多久能收敛**"。

## 二、Q&A（问题 + 标准答案）

### Q1：缓存不一致的根源是什么？

两个：①**操作部分失败**——更新 DB 和缓存无法保证原子性，这是分布式事务问题，缓存不支持 XA，不可避免，只能靠重试和自动校验修复缩短窗口；②**并发操作**——多线程并发更新时序交错，这个可解，核心是让同一时刻只有一个线程在更新（分布式锁/消息队列/版本号/缓存模式）。

### Q2：怎么用消息队列解决缓存一致性？

把同一业务的更新请求发到 MQ 且**保证有序**，消费者串行更新 DB 和缓存——天然实现"同数据单线程更新"。失败重试对业务无影响。只能做到最终一致。注意消息只当触发器，消费者要**回查 DB 最新值**再更新缓存（消息体数据可能已过时）。

### Q3：版本号方案怎么用？

每次更新版本号 +1，低版本数据不能覆盖高版本。落地：DB 加 version 字段；更新 Redis 时用 **lua 脚本先校验缓存里的版本号再写**。Cache Aside 的并发不一致场景都能被它化解。缺点：版本号维护麻烦；可用更新时间戳替代（要处理时钟回拨）。

### Q4：多级缓存（本地 + Redis + DB）按什么顺序更新？

DB → 本地缓存 → Redis。DB 最准所以最先；本地缓存更新几乎不失败且查询先经过它，先更新可立即见效；最后更新 Redis，即使失败也有本地缓存挡着，读不到旧值。硬要挑毛病仍有不一致场景，但这个顺序把窗口压到最小。

### Q5：一致性哈希负载均衡和缓存结合怎么用？扩容时怎么办？

同 key 请求固定落一个节点，节点内用 Singleflight 保证同 key 只有一个线程在更新 → 消除并发更新。节点下线无感（流量切走仍唯一）；**节点上线（扩容）**时短暂有两个节点服务同 key → 新节点头 2 秒不读写缓存，等老节点在途请求返回，用短暂 RT 劣化换零不一致。

### Q6：分布式锁方案怎么设计？（思路一）

写：本地事务提交 → 加分布式锁 → 删缓存 → 放锁。读：先读缓存**不加锁**（高性能关键）；未命中再加锁，**double-check** 再读一次缓存（可能别的线程已回写），还没有才回源回写。读路径只在未命中时抢锁，保证了读性能。

### Q7：怎么做到"无限接近强一致"？（思路二）

把**删除缓存放进本地事务**：开事务 → 加锁 → 删缓存 → 提交 → 放锁。失败分析：删失败则事务不提交（一致）；删成功但提交失败只是多删一次（一致）。两个前提：锁绝对可靠、删除必重试到成功。代价：**本地事务容易超时**（等锁/网络抖动），缓解办法是先加锁再开事务，但锁持有时间变长。

### Q8：思考题 1——先提交事务再释放锁，顺序能反过来吗（先放锁再提交）？

不能。先放锁再提交：放锁瞬间其他线程的读请求会回源——此时事务**还没提交**，读到的是旧值并回写缓存，而这个事务随后可能提交成功 → 缓存留下旧值且无人再删。所以**锁必须覆盖到事务提交**，提交完成前锁不能放。

### Q9：思考题 2——"先加锁 → 本地事务提交 → 最后删缓存"有什么缺点？

缓存在**整个事务期间**都是旧数据且可被读到：事务提交后到删缓存前有窗口，读到旧值并可能回写；且锁持有时间 = 整个事务 + 删除操作，并发度最差。不一致场景：事务已提交、删缓存失败 → 缓存旧值一直存活直到过期。

- 治理核心数据缓存一致性：按"部分失败/并发更新"两根源分层施策——更新链路 MQ 有序串行化 + 回源 double-check 加锁防并发覆盖，缓存刷新监听 binlog（Canal），不一致窗口从分钟级收敛到秒级，并提供自动校验修复机制兜底

**版本 B（详细版，供面试口述）**
> 我先分析了我们不一致的两个根源：操作部分失败和并发更新。部分失败无法根治，只能缩短窗口——我们把更新请求按业务 ID 发到 MQ 保证有序，消费者串行更新 DB 和缓存，消息只当触发器、回查 DB 最新值；后来干脆演进成 Canal 监听 binlog 刷新缓存，业务代码零感知。并发更新层面，读路径缓存未命中时加分布式锁 + double-check，防止回源并发覆盖；写路径是"本地事务提交后加锁删缓存"。多级缓存的更新顺序定为 DB → 本地缓存 → Redis，因为本地几乎不失败且查询先经过它。最后我们还上了定期对账校验，发现不一致自动修复——我的原则是：不强求强一致，但必须说清"能有多不一致、多久收敛"。

## 四、面试官连环追问清单（含参考答案）

### Q1：为什么不直接用分布式事务保证 DB 和缓存一致？

缓存中间件（Redis/Memcached）基本不支持 XA 这类强一致事务协议；就算硬套 TCC/Saga，两个资源一个内存一个磁盘，协调成本和性能损耗远超收益。而且缓存的定位就是"可容忍短暂不一致的加速层"——为最终一致性设计的基础设施，硬要强一致是拿错工具。

### Q2：消息队列方案里消费者更新缓存失败怎么办？

MQ 重试机制天然兜底：消费失败 → 不提交 offset → 消息重投 → 再次尝试。配合消费幂等（重复更新同值无副作用）即可。这也是 MQ 方案相比"业务代码里删缓存"的优势——**把"删除失败的重试"从业务代码移到了基础设施**。

### Q3：版本号方案里时钟回拨怎么办？

用时间戳当版本号时，时钟回拨会导致新数据版本号反而变小被拒。解法：①逻辑时钟（DB 自增 version 字段，最可靠）；②混合逻辑时钟（HLC）；③接受小概率问题，监控发现后人工修复。严肃场景用 DB 自增版本号。

### Q4：Canal 监听 binlog 刷新缓存，有哪些不一致窗口？

①binlog 产生 → Canal 消费 → 刷缓存的链路延迟（正常毫秒级，积压时秒级+）；②Canal 宕机期间缓存持续旧；③批量大事务产生大量 binlog 造成积压。对应：监控 Canal 位点延迟告警；读敏感业务关键操作可同步删缓存 + binlog 异步兜底（双保险）。

### Q5：思路二里"删除缓存"为什么在事务内？放事务外不行吗？

放事务外（提交后再删）就退回思路一：提交到删除之间有窗口，期间读请求会回源旧值并回写缓存，这个旧值要等下次写或过期才消失。放事务内是先删后提交——任何读请求在提交前回源，读到的都是**已提交**的旧事务数据（新数据未提交不可见），而提交后缓存已被删、回源必得新值。精妙之处就在于**用事务的可见性边界卡住了回源读旧值的路径**。

### Q6：如果分布式锁用 Redis 实现，"锁绝对可靠"怎么保证？（引向 07 讲）

单机 Redis：SET NX PX + 唯一标识 + lua 释放，够用但主从切换时可能丢锁（主库挂了锁没同步到从库）→ Redlock 多多数派方案（争议大，Martin Kleppmann 质疑过时钟依赖）。工程实践： Fencing token（单调递增令牌）+ 存储端校验，或干脆用 ZK/etcd（CP）做锁。详见 07 分布式锁笔记。
