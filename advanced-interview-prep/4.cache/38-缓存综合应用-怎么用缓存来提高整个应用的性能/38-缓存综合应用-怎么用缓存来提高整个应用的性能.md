## 一、文章总结

**核心观点**：用 Redis 是入行三个月就会的技能，不能拉开差距——**缓存面试的胜负手是有业务特色的具体方案**，且每个方案要能讲清六问：为什么这么设计？命中率多少？一致性怎么解决？命中/未命中性能差多少？实施前后数据对比？和业界一般方案比独特在哪？

**方案总览**（按从前端到后端的层次记忆）：

| 方案 | 一句话 | 关键要点 |
|---|---|---|
| 一致性哈希 + 本地缓存 + Redis | 同业务请求固定落一个节点，本地缓存命中率飙升 | 适用性最广；要讲清新节点上线的一致性处理 |
| Redis 崩溃降级本地缓存 | 平时只用 Redis，崩溃才启用本地缓存容错 | **反范式**（正常是先本地后 Redis，这里反过来）；恢复时渐进切回 |
| 请求级别缓存 | 缓存与请求同生命周期，响应返回即失效 | 解决"一个请求内多模块重复查同一数据"；**零一致性负担** |
| 会话级别缓存 | 缓存与 Session 同生命周期 | 权限类高频少变数据的绝配；监听修改事件清空 |
| 客户端缓存 | 调用方缓存微服务返回结果 | 反范式；淘汰策略不受服务端影响（隐藏优点） |
| 业务相关预加载 | 调 A 接口时预加载 B 接口数据 | 利用业务关联性；TTL 设短兜底 |
| 缓存预热 | 启动全量预热 or 小流量慢热 | 预热防雪崩；慢热配权重负载均衡 |

**各方案要点**：

**① 一致性哈希 + 本地缓存 + Redis**（性能案例）：只用 Redis → 加本地缓存 → 为防本地命中率低和内存浪费，客户端加一致性哈希让同业务请求落同一节点 → 性能提升 40%。几乎任何"本地缓存 + Redis"的组合前面都能加这一层。讨论时主动补一致性（见 34 笔记：新节点上线头 2s 不读写缓存）。

**② Redis 崩溃降级本地缓存**：正常走"Redis → DB"；监控到 Redis 崩溃（大量超时）→ 切"本地缓存 → DB"。保住 DB 且 RT 还行，代价是本地缓存一致性更差——**再叠一致性哈希缓解**。Redis 恢复后**逐步切回**（刚恢复的 Redis 是冷的，立刻全量切回会打爆 DB）。和 35 笔记的集群互备是同源思想，但成本为零。

**③ 请求级别缓存**：模块各自恪守边界导致一个请求里重复查同一数据（订单模块、支付模块都拿 user_id 查用户）→ 请求内缓存，2 次 DB 查询变 1 次。落地：Java Request-Scope Bean / Go `context.Context`。**不用本地缓存的原因：请求结束即失效，一致性问题归零**。应用面窄，找到真实场景再用。

**④ 会话级别缓存**：Session 级别的缓存（Spring Session-Scope Bean）。绝配场景：**权限信息**——一致性要求高、使用极频繁、但会话期间基本不变；监听权限修改事件主动清空。

**⑤ 客户端缓存**：调用方缓存微服务结果（如用户信息，TTL 1 分钟），省一次 RPC 开销。**隐藏优点**：服务端的淘汰策略是按所有业务全局算的——别的业务更高频时你的数据总被淘汰（服务端整体命中率高、你的业务命中率低）；自己缓存，淘汰策略只服务自己。**反范式警告**：加剧不一致（服务端改了你不知道）。变种：服务端提供 Jar 包，由 Jar 包内置缓存逻辑（需要你就是服务端研发或有推动力）。

**⑥ 缓存预热两种思路**：
- 启动时全量/热点加载——**防雪崩**（TTL 加随机偏移，见 35 笔记）
- **小流量慢热**：新节点权重压低 → 负载均衡只给少量流量 → 跑着跑着缓存热了 → 权重恢复正常（与 Nginx slow_start、熔断逐步放量同源，可把话题引到负载均衡）

**面试前整理作业**（思考题 2）：设计一个**从前端到后端每层都用缓存**的方案——前端静态资源缓存/长过期 → BFF 层 Session 缓存 → 微服务调用客户端缓存 → 服务内一致性哈希 + 本地缓存 + Redis → DB 层 buffer pool 调优。

## 二、Q&A（问题 + 标准答案）

### Q1：怎么系统性回答"你们怎么用缓存提升性能"？

按**从前端到后端**的层次讲：前端（静态资源缓存、长过期）→ 接入/BFF 层（会话级缓存）→ 服务间调用（客户端缓存）→ 服务内（一致性哈希 + 本地缓存 + Redis 多级缓存）→ 中间件（MySQL buffer pool 调优）。每层一个案例，胜过罗列 Redis 八股。

### Q2：本地缓存 + Redis 已经很常见了，怎么讲出新意？

加**一致性哈希负载均衡**：同业务请求固定落同一节点，本地缓存命中率飙升、内存不重复浪费。案例：性能苛刻接口从只用 Redis → 加本地缓存 → 加一致性哈希，性能提升 40%。主动补充节点上下线的一致性处理，把负载均衡知识串进来。

### Q3：Redis 崩了怎么保 DB？（反范式降级）

平时只用 Redis（不走本地缓存）；监控到大量 Redis 超时判定崩溃 → 启用本地缓存，查询改走"本地缓存 → DB"。保住 DB、RT 可接受，代价是一致性变差——用一致性哈希缓解。Redis 恢复后**渐进切回**（冷缓存全量切回 = 人为雪崩）。对比 05 讲集群互备：这是零成本版。

### Q4：请求级别缓存是什么？为什么不用本地缓存？

缓存生命周期 = 请求生命周期，响应返回即失效。场景：一个请求内多个模块各自查同一数据（模块边界导致重复查询）。用 Request-Scope Bean / context 实现。不用本地缓存的原因：**它根本没有一致性问题**——请求结束缓存就没了，最多容忍"请求处理期间数据被改"这一丁点不一致。

### Q5：会话级别缓存适合什么数据？

**一致性要求高 + 使用极频繁 + 会话期间基本不变**的数据——典型是权限信息：每个请求都鉴权，但用户权限在会话内几乎不改。实现：Session-Scope Bean + 监听权限修改事件主动失效。

### Q6：客户端缓存有什么意想不到的优缺点？

优点：省一次 RPC；**隐藏优点——淘汰策略自主权**：服务端缓存面向所有业务，你的数据可能被高频业务挤掉（服务端整体命中率高、唯独你低）；自己缓存，淘汰只按自己业务的访问模式来。缺点：反范式、加剧不一致（服务端改数据客户端无感知）。变种：服务端出 Jar 包内置缓存逻辑（推拉结合，一致性可控）。

### Q7：缓存预热怎么做？有什么坑？

两种：①启动时全量/热点加载——坑是**雪崩**（批量加载相同 TTL，集体过期，见 35 笔记：TTL 加随机偏移）；②**小流量慢热**——新节点低权重接入负载均衡，少量流量边跑边热，权重逐步恢复正常。第二个方案能把话题引到负载均衡，是天然的话题钩子。

## 四、面试官连环追问清单（含参考答案）

### Q1：本地缓存和 Redis 缓存怎么分工？什么数据放本地？

- 放本地：**量小、超热、读多写少、可容忍秒级不一致**的数据（配置、字典、权限、榜单头部）——本地缓存价值是省网络 RTT（微秒 vs 毫秒）
- 放 Redis：共享数据、大对象、需要集中失效/控制的数据
- 判断口诀：**"读它的频率 × 一致性容忍度"高才放本地**；写频繁或强一致的只放 Redis 或只放 DB

### Q2：多级缓存下数据一致性怎么维护？（串联 34 笔记）

- 更新顺序：DB → 本地缓存 → Redis（本地几乎不失败，先更新保证读路径立即见效）
- 本地缓存跨节点同步：短 TTL 兜底 + 变更广播（MQ/配置中心）主动失效；一致性哈希减少副本数
- 核心原则：**接受最终一致，但必须量化"多不一致、多久收敛"**

### Q3：客户端缓存和服务端缓冲突了怎么办？

- 本质是**两个独立缓存层**，一致性各自为政：客户端缓存 TTL 要显著短于服务端更新频率，容忍"服务端已改、客户端未感知"的窗口
- 改进：服务端提供客户端 Jar（内嵌缓存逻辑 + 失效通知），把缓存失效的控制权收回服务端——Push 模型失效或短 TTL + 版本校验
- 严禁场景：写路径或强一致路径上的数据

### Q4：预加载（预热）怎么决定加载什么？加载错了浪费吗？

- 依据：**业务关联概率**（A 之后调 B 的概率，埋点统计说话，不是拍脑袋）；只预加载**头部候选**（列表前 N 条），不全量
- 浪费控制：**超短 TTL**（1 分钟级）——用户没点也只是一分钟内的小内存占用，自动过期；这正是 01 讲"预加载 + 超短过期时间"案例
- 收益验证：对比预加载前后详情接口的缓存命中率和 RT

### Q5：权限这种强一致数据，会话缓存里修改了怎么保证立即生效？

三层保障：①**主动失效**：权限变更时发事件清会话缓存（同步删，不等 TTL）；②**写后读不穿**：变更操作本身不使用会话缓存，直查 DB；③兜底：会话缓存 TTL 控制在小量级，且高危操作（支付、改密）强制实时校验。原则：**高频读走缓存，关键写和敏感校验走实时**。

### Q6：小流量慢热和熔断恢复、Nginx slow_start 是什么关系？

同一思想的三个化身——**"系统冷启动/恢复时，直接全量流量会出事，必须渐进放量"**：Nginx `slow_start` 是负载均衡层的权重爬坡；熔断恢复是故障场景的流量爬坡；缓存预热是缓存场景的流量爬坡。面试时把这三个串起来讲，说明你抓住了"渐进式流量调度"这个普适模式，而不是三个孤立知识点。
