## 二、Q&A（问题 + 标准答案）

### Q1：为什么 B+ 树适合 InnoDB 索引？

以页为单位组织数据，多路分支降低树高，减少查找需要访问的页；记录集中在叶子层，叶子页有序相连，适合连续扫描。非叶子页不携带完整行，能放更多导航项。

B 树也支持范围检索，但 B+ 树沿叶子层扫描更直接。不要将“其他结构不能做数据库索引”当成结论，存储介质与访问模式会改变取舍。

### Q2：聚簇索引、二级索引和回表是什么关系？

InnoDB 的聚簇索引叶子存储行记录，二级索引包含索引列和主键值。走二级索引后仍需其他列时，通常要继续访问聚簇索引，这就是回表。

**回表不等于必然读磁盘**：需要的页可能已在 Buffer Pool；额外访问仍有成本。索引也不保证全部驻留内存。

### Q3：覆盖索引是一种独立索引类型吗？

它描述某个索引是否覆盖某条查询需要的数据。相同索引对一个查询覆盖，对另一个查询可能不覆盖。减少无用返回列，往往比把所有字段塞进索引更合适。

例如二级索引 `(buyer_id, created_at)` 通常也携带主键 `id`，查询这三列可能无需额外取完整行。

### Q4：联合索引遇到范围条件，后面的列还有用吗？

要区分缩小扫描区间、索引内过滤和覆盖查询。后续列即使不能继续有效收缩区间，也可能参与过滤或覆盖；不能统一说“完全失效”。

[MySQL 索引条件下推说明](https://dev.mysql.com/doc/refman/8.4/en/index-condition-pushdown-optimization.html)展示了先在索引中检查条件，再决定是否读取完整行的过程。

### Q5：低区分度、OR、NULL 都不能走索引吗？

不是。要看选择性、数据倾斜、访问成本和其他可用索引。少数失败记录的查询，可能很适合状态索引；OR 可能用 Index Merge；NULL 也可被索引。最终看实际执行计划和测量结果。

### Q6：主键越长，有什么代价？

二级索引携带主键，长主键会扩大多个索引，降低页内记录密度并增加缓存压力。设计主键时需同时考虑唯一性、长度、写入局部性和业务暴露风险。

## 四、面试官连环追问清单（含参考答案）

### Q1：有索引就一定比全表扫描快吗？

不是。命中大量记录且需频繁回表时，顺序扫描可能更便宜。小表也可能不值得走二级索引，不能仅凭 `type=ALL` 就判定存在性能故障。

### Q2：为什么不把查询列全放入覆盖索引？

过宽索引增加空间、写放大和缓存成本。应优先服务高频高成本查询，并对比已有索引，防止重复建设。

### Q3：InnoDB 能不能用哈希？

用户定义的普通 InnoDB 索引不等于 MEMORY 的 HASH 索引。InnoDB 还有内部自适应哈希机制，应区分“用户建索引”与“引擎内部优化”，具体支持及开关看版本。

### Q4：唯一索引允许多个 NULL，怎么保证业务唯一性？

先定义未知值的业务语义。需要每行都有业务键时，应要求非空；允许未知值时，多个 NULL 可能正是期望行为。不能用空字符串替代 NULL 后就假定语义无变化。

## 五、专题深挖：联合索引的验证表

> 独立演练设计，未在本地数据库执行。

假设索引为 `(tenant_id, status, created_at)`：

| 查询形态 | 分析重点 |
|---|---|
| tenant、status 等值，按时间排序 | 等值前缀之后可利用时间顺序 |
| 只查 status | 不满足通常的左前缀定位，仍需考虑版本优化和全索引扫描 |
| tenant 等值，status 范围，过滤时间 | 区间定位与后续过滤分开判断 |
| 只返回索引列与主键 | 考虑覆盖收益 |
| 返回大字段且匹配大部分记录 | 回表成本可能改变优化器选择 |

记录 `key`、估计行数、实际行数、返回量和耗时；冷热缓存分别比较。不要为制造漂亮计划而强迫所有查询使用索引。
