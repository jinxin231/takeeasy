## 一、文章总结

**主线**：分片键服务主要访问路径，其他维度的查询需要额外支持。原文比较 ID 内嵌路由、中间映射表、冗余分片、搜索存储和广播，再讨论同步失败及双向修改冲突。

核心取舍是查询能力、存储成本和一致性成本。工程上应先明确权威数据源，再设计派生视图，而不是让所有副本都独立修改同一业务状态。

## 二、Q&A（问题 + 标准答案）

### Q1：为什么按卖家查询会跨分片？

订单按 buyer_id 路由，同一个卖家的订单可能来自许多买家并散落各分片。只有 seller_id 时，无法直接推出唯一目标。

先估计该查询的频率、延迟和过滤条件，决定是否值得维护专门读模型。

### Q2：几种方案怎么选择？

| 方案 | 适合 | 主要代价 |
|---|---|---|
| ID 内嵌逻辑路由 | 已知订单 ID 的点查 | 编码和路由升级复杂 |
| 映射表 | 用另一键找到主键与路由 | 多一次查询和同步 |
| 卖家维度读模型 | 高频卖家列表、统计 | 存储、写放大、同步延迟 |
| 搜索存储 | 多条件检索 | 索引一致性和重建 |
| 有界广播 | 低频、受控兜底 | 扇出和尾延迟 |

不能只因一个低频后台查询就复制整个订单域。

### Q3：中间表不能再分片吗？

可以。例如按 seller_id 分片，卖家查询就能定向访问。新表服务的是新访问维度，并非必然陷入递归。

但超级卖家可能形成热点，要考虑分桶、时间维度或专门路由；分片不等于消除所有倾斜。

### Q4：只复制部分字段有什么收益？

同步筛选、排序、展示与路由所需字段，减少存储和更新成本。若多数查询还需逐条回源，可能产生 N+1，应按分片批量回查，并明确回源失败时的返回语义。

### Q5：CDC 更新读模型要保证什么？

事件可恢复、不丢位点；同一业务键的新旧版本顺序正确；重复消费幂等；删除可传播；错误有重试、死信和重建流程。只说“Canal 同步”并未解释一致性保障。

### Q6：卖家改订单应写哪个库？

优先让卖家端通过领域接口修改权威订单库，再同步卖家读模型。修改时验证权限、原状态和版本，不能信任可能过时的列表展示状态。

### Q7：为什么两个库都能改状态很危险？

买家取消与卖家发货可能分别成功，随后异步事件交叉覆盖，造成两端相反结果。需要统一业务状态机和冲突决议；分布式锁也不能消除双写部分失败。

## 三、简历可用案例

> 使用真实查询量、延迟目标、同步积压和异常恢复数据。

**专业技能栏**：能够根据访问维度设计分片路由、派生读模型与可靠同步机制。

**版本 A**：为【卖家订单查询】建立【最小字段读模型】，减少【广播扇出】，将查询 P99 从【前值】改善到【后值】，同步延迟控制在【实测范围】。

**版本 B**：先分析卖家常用筛选和展示字段，决定同步【字段集合】，并保留主键和路由信息。读取按卖家定向，详情按分片批量回源，修改统一落到权威库。同步侧实现版本比较、删除事件和断点恢复，再通过【对账与重建】验证遗漏不会永久残留。

## 四、面试官连环追问清单（含参考答案）

### Q1：刚下单后读模型查不到，怎么处理？

根据产品要求选择读己之写回源、短时状态提示或等待同步位点。不能把派生模型的未命中直接解释为业务不存在。

### Q2：广播查不到一部分分片，能返回“完整结果”吗？

不能。需区分部分结果与完整结果，明确失败和重试策略。对账类场景往往必须失败重查，而非静默漏数据。

### Q3：重试怎样避免重启后丢失？

将任务和进度保存到可靠队列或存储；定义去重键、租约/领取机制、退避与死信。进程内定时器只能解决进程仍存活时的重试。

### Q4：搜索结果能直接用于扣款或发货吗？

不应。搜索结果可能延迟，应回权威库重新验证权限与业务条件，通过条件更新保证状态合法。

### Q5：扩容后映射的物理库表地址变了怎么办？

通过稳定逻辑分片加版本化路由降低耦合，或可靠更新映射。长期暴露物理地址会使迁移与回退更加复杂。

## 五、专题深挖：单一权威写入的查询链路

```text
创建/修改订单 → 权威订单库 → 可靠变更流 → 卖家读模型 / 搜索索引
                                ↓
                         积压、失败、对账与重建

卖家列表 → 卖家读模型
卖家详情 → 路由后批量回源
卖家操作 → 领域接口校验 → 权威订单库
```

**独立故障推演**：先到删除事件，后到旧更新事件。如果消费者只会 upsert，订单可能在读模型中复活。应保留版本化删除信息或依靠经过验证的有序协议，重放旧事件不能覆盖更高版本的删除。

**验收重点**：查询返回量、分片扇出、同步 P99、最老积压年龄、死信数量、重建耗时和越权访问测试。
