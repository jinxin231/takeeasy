## 二、Q&A（问题 + 标准答案）

### Q1：如何回答“你怎么保障数据库性能和可用性”？

先说明业务目标与当前瓶颈，再讲对应措施及验证。性能看延迟、吞吐、资源与等待；可用性看检测、切换、恢复和数据完整性。多项优化不能只汇总成一个没有口径的“提升百分比”。

### Q2：Buffer Pool 越大越好吗？

不是。它缓存数据和索引页，但数据库还有连接、排序、临时表、日志等内存需求，操作系统也需要余量。专用机经验比例不能直接套到容器或混部环境。

应观察实际内存上限、页读取、工作集、swap/OOM 和业务延迟，再分阶段调整。参考：[InnoDB 启动配置](https://dev.mysql.com/doc/refman/8.4/en/innodb-init-startup-configuration.html)。

### Q3：Buffer Pool 实例数直接设 4 或 8 可以吗？

不应作为通用答案。默认值与支持方式随版本变化，分实例收益还取决于争用和每个实例大小。先确认实际版本和指标，再验证变更，不能只因为一个值看起来小就认定错误。

### Q4：MySQL Query Cache 还能调吗？

传统 SQL 结果查询缓存已经在 MySQL 8.0 移除。`query_cache_min_res_unit` 等只适用于相应旧版本，不是 8.0/8.4 调优项。它与仍然存在的 InnoDB Buffer Pool 完全不同。

参考：[MySQL 8.0 变更说明](https://dev.mysql.com/doc/refman/8.0/en/mysql-nutshell.html)。

### Q5：读写分离必须处理什么一致性问题？

副本可能尚未回放刚提交的数据。写后立即读、事务内读取、权限与状态校验，应按需求回主库、等待所需复制位点或采用其他已验证机制，不能简单“所有 SELECT 都去从库”。

### Q6：主从切换有哪些必需步骤？

确认故障、选合适候选副本、隔离旧主、提升新主、调整流量、处理连接重建及未决请求，并监控旧主恢复后的状态。

Keepalived 可帮助地址切换，但不单独解决复制位点、数据损失和脑裂防护。具体切换能力由数据库拓扑与管理系统共同提供。

### Q7：复制能代替备份吗？

不能。误删与逻辑损坏可能被复制到副本。需要独立备份、连续日志、保留策略与实际恢复演练，同时明确 RPO（可接受数据损失）和 RTO（恢复时间）。

### Q8：什么时候进入分库分表阶段？

在确认单机/单表瓶颈且较简单手段不足后，再评估路由、主键、事务、分页、非分片键查询与迁移成本。分片是整体架构变化，不只是多建几张表。

## 四、面试官连环追问清单（含参考答案）

### Q1：慢查询告警没响，为什么接口还是慢？

可能在连接池排队、锁等待、网络传输、应用线程或下游调用。应做端到端分段，而不是只检查数据库执行时间。

### Q2：副本很多，主库为什么仍压力很大？

写入、事务内读取、强一致读和复制开销仍在主库。副本增加不能自动解决热点写、共享依赖或连接风暴。

### Q3：一次 failover 成功就证明高可用了吗？

不够。还要覆盖网络分区、旧主重新上线、副本落后、连接池缓存地址和客户端提交结果未知。每种场景可能暴露不同故障。

### Q4：调参数提升了性能，为什么还可能不能上线？

如果损失持久性、挤占内存或恶化长尾，不满足业务目标就不能称为成功。一次只改变可归因的变量，并准备回退。

### Q5：备份任务成功为什么仍要恢复演练？

备份文件存在不代表可用：密钥、版本、日志连续性、恢复脚本和操作权限都可能出错，实际恢复耗时也可能超过目标。

## 五、专题深挖：把第 10–20 篇连成一个诊断路径

| 观察到的问题 | 优先检查 | 对应讲次 |
|---|---|---|
| 单条 SQL 慢 | 索引、扫描量、排序、计划 | 10–11 |
| 并发下阻塞 | 等待链、事务时长、隔离语义 | 12–13 |
| 提交结果或数据丢失不明确 | 日志、复制确认、幂等 | 14 |
| 改布局需要搬数据 | 快照、增量、校验、切换 | 15 |
| 分片 ID 与路由困难 | 发号与版本化路由 | 16 |
| 列表越翻越慢 | OFFSET、总序、游标、归并 | 17 |
| 跨库更新部分成功 | 原子协议或业务补偿 | 18 |
| 次要维度查不到目标分片 | 读模型、映射、受控广播 | 19 |
| 容量接近极限 | 增长、热点、物理资源与扩容 | 20 |

**独立演练建议**：围绕一个真实订单系统，把一次查询、一次更新、一次提交超时和一次主库故障串起来讲。每个步骤回答“证据是什么、保证到哪一层、失败后谁负责恢复”，比堆叠组件名称更有说服力。
