## 一、文章总结

**主线**：先发现慢 SQL，再用执行计划形成假设，通过改写查询或调整索引验证效果。原文按覆盖查询、排序、计数、索引提示、过滤条件和深分页展示优化入口，同时提醒大表变更的实施成本。

面试应准备优化前后的证据，也要讲清上线方式。以下问答补充现代 InnoDB 的行为边界，避免把执行计划标签直接当作性能结论。

## 二、Q&A（问题 + 标准答案）

### Q1：怎么找出最值得优化的 SQL？

结合慢日志、按指纹聚合的执行统计和业务链路。优先考虑总耗时大、调用频繁、尾延迟严重或阻塞关键业务的语句。一个执行稍慢但每秒调用很多次的查询，可能比偶发慢查询更值得优化。

确认参数分布、实际表规模、锁等待及连接池等待，避免把应用排队全部归因于 SQL 执行。

### Q2：EXPLAIN 应该看什么？

关注实际索引、访问方式、估计扫描量、过滤比例、连接顺序、排序和临时表。普通 EXPLAIN 的 `rows` 是估计值，并非实际执行记录。

[官方输出说明](https://dev.mysql.com/doc/refman/8.4/en/explain-output.html)可用于核对字段。支持时用 `EXPLAIN ANALYZE` 比较实际耗时、循环次数和行数；它会执行查询，应先控制环境、数据量和负载。

### Q3：索引列顺序按区分度排就行吗？

不行。先考虑等值过滤、范围过滤、排序和关联方式，再看选择性及其他查询复用。区分度不是唯一规则，不能忽略必须匹配的左前缀。

### Q4：ORDER BY 慢怎么优化？

以 `WHERE buyer_id=? ORDER BY created_at,id LIMIT ?` 为例，可评估 `(buyer_id,created_at,id)`。固定买家后利用索引次序读取，并用唯一键稳定排序。

是否生效还取决于排序方向、字段表达式和查询计划。出现 filesort 不代表必然落盘，也不代表一定需要修复。

### Q5：COUNT 怎么优化？

先分清要精确值、近似值还是只判断有无下一页。精确计数需对应快照；近似统计可以用于可接受误差的产品展示；“是否还有下一页”可多取一条判断。

独立计数表、缓存计数会引入更新一致性和修复问题。不能把 EXPLAIN 的扫描行数直接当作所有复杂查询的精确结果数。

### Q6：深分页如何改造？

稳定顺序下使用上一页末尾的复合游标，查询其后的记录，避免随页码增长丢弃大量候选行。代价是不能天然支持任意跳页，且可变排序字段仍可能引起跨页变化。

### Q7：WHERE 能随便替换 HAVING 吗？

只能移动语义等价的条件。聚合前过滤与聚合后过滤不同；`SUM(amount)>100` 不能直接改成对单行金额的筛选。对改写要比对结果，而不只比较耗时。

## 四、面试官连环追问清单（含参考答案）

### Q1：用了 FORCE INDEX 就算解决了吗？

只能说明当时数据下某条路径更好。还应检查统计信息、参数倾斜和索引设计，记录提示的适用条件；数据演变后提示可能变成负担。

### Q2：线上加索引一定锁住整表直到结束吗？

不是。Online DDL 对不同操作有不同并发能力，但仍可能遇到元数据锁等待。应按版本与操作核对算法支持、磁盘需求和复制影响，不能把 INSTANT 泛化为所有索引变更。

参考：[Online DDL 操作支持](https://dev.mysql.com/doc/refman/8.4/en/innodb-online-ddl-operations.html)。

### Q3：为什么测试环境很快，线上却慢？

测试可能缺少真实数据量、倾斜、并发写、冷缓存及长事务。应复现真实参数和工作负载，比较执行计划，而不只复制 SQL 文本。

### Q4：优化必须删掉 JOIN 吗？

不是。合理索引下 JOIN 可以高效。拆成多次调用可能增加网络开销、N+1 查询和一致性问题，必须按实际成本决定。

## 五、专题深挖：一次 SQL 优化的证据清单

| 阶段 | 需要留下的证据 |
|---|---|
| 基线 | SQL 指纹、参数范围、表规模、索引、调用频率 |
| 定位 | 执行计划、等待事件、扫描与返回量 |
| 验证 | 结果等价、P50/P99、CPU/I/O、写入代价 |
| 发布 | DDL 算法、锁等待处理、空间余量、回退步骤 |
| 观察 | 新旧版本对比、复制延迟、错误率、计划漂移 |

**独立演练**：准备普通买家和超大买家两类数据，分别比较原查询与改造查询。若只改善普通买家，却让大买家超时，就不能宣布优化完成。
