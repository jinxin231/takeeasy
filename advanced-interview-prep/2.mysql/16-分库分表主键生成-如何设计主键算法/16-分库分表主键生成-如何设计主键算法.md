## 一、文章总结

**主线**：比较 UUID、数据库发号与雪花式 ID 的取舍，解释主键顺序性对索引局部性的影响。原文进一步讨论位段分配、序列耗尽、分片倾斜及在 ID 中嵌入路由信息。

主键设计需要分清全局唯一、趋势递增、严格递增和无空洞。发号性能不是唯一目标，故障恢复和跨进程重复也必须覆盖。

## 二、Q&A（问题 + 标准答案）

### Q1：设计 ID 前先问什么？

唯一性的范围、峰值发号速率、保存年限、排序要求、是否离线生成、是否泄露时间或业务信息，以及调用方的数据类型。不同要求决定不同方案。

### Q2：UUID 都是完全随机、完全无序吗？

不是，不同版本的布局不同。随机 UUID 与带时间顺序的 UUID 应分开讨论。较宽主键会扩大二级索引；随机插入还可能增加页访问与分裂开销，但不能断言顺序插入永不分裂。

### Q3：雪花式 ID 如何保证唯一？

时间段、生成器标识和同一时间粒度内的序列组合区分 ID。前提是生成器标识不重复、时间回退被正确处理、序列不会绕回重用。

“机器 ID”应对应活跃发号实例，而不只是物理机器。一台机器多个进程也可能需要不同标识。

### Q4：典型 41/10/12 位怎么估算？

41 位毫秒时间约覆盖 69.7 年；10 位最多表示 1024 个生成器编号；12 位每毫秒可表示 4096 个序列值。这是编码容量，不是系统已经压测通过的吞吐量。

分配更多序列位，会挤压时间跨度或实例规模，必须同步更新编码、解析和迁移规则。

### Q5：时钟回拨怎么处理？

检测回退后按幅度等待、拒绝发号或使用可靠逻辑时间方案。进程重启和编号回收还需要持久状态或租约隔离，避免旧进程继续生成与新进程重叠的 ID。

不能把随机后缀当成严格唯一保证；它只能降低碰撞概率。

### Q6：号段模式有什么特点？

数据库分配互不重叠的区间，应用本地消耗，减少远程调用。需原子分配、避免范围溢出并处理进程崩溃造成的未使用号码。双缓冲可提前取下一段，但不能回收并复用已对外发出的号码。

### Q7：在订单 ID 中嵌入路由键有什么价值？

只拿到订单 ID 时也能定位分片，减少额外映射查询。但它绑定了路由协议，需要版本位或稳定逻辑分片；扩容后不能简单按照旧物理库表编号解释所有 ID。

## 四、面试官连环追问清单（含参考答案）

### Q1：雪花 ID 是严格全局递增吗？

通常不是。不同机器的时间偏差和同一毫秒内的编号顺序都会影响全局先后。严格全局排序往往需要额外协调。

### Q2：低并发时按 ID 低位取模为何倾斜？

若低位序列经常从同一数值开始，取模可能集中到少数分片。可重新设计散列与路由位，验证真实发号分布；不要只凭“ID 看起来随机”判断均衡。

### Q3：主键冲突后重新发号就万事大吉吗？

还要区分业务重复请求与随机碰撞。前者应返回原业务结果，不能重发 ID 后创建第二笔业务。数据库唯一约束是最后防线，不能代替业务幂等。

### Q4：64 位 ID 传到浏览器有什么问题？

JavaScript Number 无法精确表示所有 64 位整数。接口可以使用十进制字符串，并统一客户端、日志和签名的表示方式，避免精度损失。

### Q5：自增 ID 为什么有洞？

回滚、失败、预分配等都会产生空洞，不能用 ID 差值计算业务条数。需要连续业务编号时，应另设计相应业务协议。

## 五、专题深挖：发号器的故障测试矩阵

| 场景 | 验证目标 |
|---|---|
| 多实例同毫秒高并发 | 序列耗尽不会重复或绕回 |
| 时间小幅/大幅回退 | 策略明确，不默默发冲突号 |
| 进程崩溃后重启 | 不复用已发出的时间与序列组合 |
| 旧实例失联、新实例接管编号 | 旧实例不能继续有效发号 |
| 路由规则升级 | 新旧 ID 都能正确定位 |
| 号段申请超时 | 结果未知时不重复分配同一区间 |

**独立演算**：若序列减少至 8 位，则单生成器每毫秒仅 256 个编码位置。排队上限与超时必须同时设计，不能让所有业务线程无限等待下一批 ID。
