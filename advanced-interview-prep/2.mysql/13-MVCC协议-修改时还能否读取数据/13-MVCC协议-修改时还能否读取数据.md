## 一、文章总结

**主线**：MVCC 通过历史版本与可见性判断减少普通读取和写入之间的阻塞。原文围绕版本链、Read View、RC/RR 的区别展开，并讨论调整隔离级别的业务影响。

**阅读边界**：普通一致性读与锁定读要分开；RR 不能笼统理解为事务中任何语句都永远看到同一状态。隔离级别调整也不能只以“性能更好”为理由。

## 二、Q&A（问题 + 标准答案）

### Q1：有人正在修改一行，另一个事务能读吗？

RC/RR 下的普通一致性读通常可以读取对自己可见的已提交历史版本，不必等对方提交；锁定读或写入可能需要等待。答案取决于隔离级别和语句类型。

### Q2：版本链由什么构成？

InnoDB 记录修改该行的事务信息，并通过回滚指针关联 undo 中的历史信息。读取时沿历史版本寻找满足可见性规则的值。

历史数据不是永远保留。没有活跃读视图需要它们后，后台清理可以回收相关历史；长事务会拖延清理。

### Q3：RC 和 RR 什么时候建立 Read View？

RC 下每次一致性读使用新的快照；RR 下通常在第一次一致性读时建立，并由后续一致性读复用。`START TRANSACTION WITH CONSISTENT SNAPSHOT` 则用于按相应隔离级别显式建立一致性快照。

因此，不能把普通 BEGIN 的时间直接当作所有 RR 快照的时间。参考 [官方一致性读说明](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)。

### Q4：怎么判断一个版本可见？

概念上依次判断：是不是自己写的；是否早于快照中最早活跃事务；是否晚于快照生成时的事务 ID 上界；落在中间时，是否属于快照里的活跃事务。

**事务 ID 大小不等于提交先后**，所以不能只选“比自己 ID 小的最大版本”。

### Q5：当前读与快照读混用有什么风险？

当前读关注可更新的当前状态，并进行必要加锁；快照读读取历史可见状态。两者混用可能看到不同结果，且事务会看到自己已经做出的修改。

不要凭普通 SELECT 的旧结果执行无条件更新。库存、余额和状态推进可使用带业务条件的原子 UPDATE，并检查结果。

### Q6：RR 如何处理幻读？

同一快照的一致性读不会因别的事务后来插入而改变结果；锁定读则依赖访问范围上的锁来约束并发插入。混合读取、自己的写入及不同访问路径需单独分析，不能回答“RR 在任何场景都绝无幻读现象”。

## 四、面试官连环追问清单（含参考答案）

### Q1：缓存第一次查询结果，可以完全替代 RR 吗？

不能。它只复用已读数据，不能自动建立跨多表、多条件的一致性视图，也无法替代写入约束和并发控制。

### Q2：长时间只读事务为什么有影响？

它可能保持旧视图，使清理无法回收仍可能被读取的历史版本。应观察事务存活时间、历史链增长和存储压力，避免把大批处理放进无边界长事务。

### Q3：RC 一定比 RR 快吗？

不保证。收益取决于锁冲突、查询模式和负载。先确定所需隔离语义，再用代表性工作负载验证，不能用孤立的平均延迟做决定。

### Q4：SERIALIZABLE 是所有事务单线程执行吗？

不是这个意思。它要求可串行化效果，InnoDB 会使用更强的读写约束；不冲突的操作仍可能并发。实现方式不能等同于一个全局串行队列。

## 五、专题深挖：用时间线讲清楚读视图

> 独立推演，假设只有两个业务事务，A 不修改该行，初始值为 10。

| 步骤 | 事务 A | 事务 B |
|---|---|---|
| 1 | BEGIN | |
| 2 | 普通 SELECT，读到 10 | |
| 3 | | 更新为 20 并提交 |
| 4 | 再次普通 SELECT | |
| 5 | 锁定读该行 | |

第 4 步：RC 读取 20；RR 复用已有视图，读取 10。第 5 步不能沿用“RR 所以仍为 10”的推论；在没有其他干扰时，锁定读面对当前已提交的 20。

若把 A 的第一次普通 SELECT 移到 B 提交之后，普通 RR 事务首次建立的快照就能看到 20。这个变化正好用于检查是否误把 BEGIN 等同于创建读视图。
