# 面经总结 27：重复消费——高并发场景下怎么保证消息不会重复消费？

> 来源：极客时间《后端工程师的高阶面经》邓明（消息队列模块 27 讲）
> 整理日期：2026-11-06

---

## 一、文章总结

**重复消费的两个来源**：①生产者重复发送（超时后重试，不确定上次是否成功）；②消费者重复消费（处理完未提交就宕机，恢复后重拉）。**统一解法：消费逻辑幂等**——同一消息消费多少次，系统状态都一样。重试的前提是幂等（呼应微服务）；主流 MQ 宣称的 exactly-once 本质也是**重试 + 幂等**达成的。

**前置知识：布隆过滤器与 bit array**：
- BF：元素经哈希映射到比特数组 N 个位置置 1；查询全 1 则"可能存在"（**假阳性**），任一 0 则"必然不存在"。**判断"必然不存在"最可靠**；不支持删除
- bit array（bitmap）：值本身即下标，**精确无假阳性**——key 是数字（如自增主键）时更省内存更快。技巧：主键起点是 N（非 0，如防爬业务量/分布式 ID），bit 第一位代表 N，省掉前段空间

**基础方案：唯一索引**：
- 有本地事务：业务操作 + 插唯一索引**同一个本地事务**。提交后即使提交消息失败，重复消费必撞唯一索引被拦——天然幂等
- 无本地事务（如分库分表）：三步走——①**先插唯一索引**（状态=初始，防重复的关键）；②执行业务操作；③标记完成。风险点在②成功③失败 → **异步检测系统**定时扫描：业务已成功则补标完成，业务失败则触发重试

**亮点方案：布隆过滤器 + Redis + 唯一索引（层层削流）**——目标：到达 DB 的流量最小化（唯一索引的性能取决于 DB，扛不住高并发写）：
```
请求 → BF 判断：说"没处理过"→ 必没处理过，直接处理（拦截绝大多数流量）
     ↓ BF 说"处理过"（可能假阳性）
     → Redis 查近期处理过的 key：有 → 真处理过，返回；无 → 下一步
     ↓
     → 唯一索引兜底（业务唯一索引，无需额外建）
```
- **更新顺序（必考）**：先 DB 唯一索引（DB 最准，和业务同一本地事务）→ 再更新 BF 和 Redis（先后/并发都行，失败无所谓——唯一索引兜底）
- **Redis key 过期时间**：确保重复请求到达时 key 未过期（重试 10 分钟内到达 → TTL 11 分钟，1 分钟余量——呼应缓存 01 讲"按重试时间定过期"）
- **简化方案**：重试间隔长（1 小时）或 Redis 资源紧张 → BF + 唯一索引；怕假阳性且 Redis 资源足 → Redis + 唯一索引。**起步建议 BF + 唯一索引，假阳性严重了再加 Redis**
- **本地布隆过滤器**（极致性能）：一致性哈希让同 key 请求落同一实例（MQ 场景：同业务消息发同一分区）→ 本地内存 BF。重启重建两思路：①不重建，处理新请求中逐步建立（适合时效强的请求）；②用最近 N 天历史数据预建。BF 不准没关系，唯一索引兜底
- **替代品 bit array**：key 是数字时切换，更省内存无假阳性

**思考题 2 提醒**：重复请求占比 <1% 时，BF 几乎拦不到流量，方案价值大减——方案是为"高重复率"场景设计的。

## 二、Q&A（问题 + 标准答案）

### Q1：重复消费的原因和解决思路？

原因二选一：生产者超时重试重复发、消费者处理后未提交宕机重复消费。解法一句话：**消费逻辑幂等**——同消息消费 N 次状态不变。业界 exactly-once 本质也是重试 + 幂等，没有魔法。

### Q2：用唯一索引怎么做幂等？

有本地事务：业务操作 + 插唯一索引同一事务，重复消费必撞索引被拦。无本地事务（分库分表）：先插唯一索引（初始态）→ 执行业务 → 标记完成；②成功③失败的窗口用**异步检测系统**兜底（业务成功补标、业务失败触发重试）。要点：**先插索引再执行业务**，顺序不能反。

### Q3：高并发下唯一索引扛不住怎么办？（亮点方案）

层层削流：布隆过滤器（说没有必没有，拦掉绝大部分）→ Redis 近期 key（吃掉假阳性和近期重复）→ 唯一索引兜底。更新顺序：先 DB 唯一索引（和业务同事务），再更新 BF/Redis（失败无碍，索引兜底）。Redis TTL 按重试窗口定（重试 10 分钟 → TTL 11 分钟）。

### Q4：布隆过滤器说"处理过"就真处理过吗？

不一定（假阳性）。所以 BF 说"没处理过"才直接放行（必真），说"处理过"要降级到 Redis/唯一索引确认。BF 的价值是**用极小内存拦掉绝大多数首次请求**，假阳性交给后层消化——这就是为什么它适合"必然不存在"判断。

### Q5：Redis 那层的 key 过期时间怎么定？

确保**重复请求到达时 key 还活着**：预期重试窗口 10 分钟 → TTL 设 11 分钟（含余量）。间隔太长的业务（1 小时级）不适合放 Redis（内存浪费）→ 退化为 BF + 唯一索引。

### Q6：怎么进一步压榨性能？（本地 BF / bit array）

①**本地布隆过滤器**：一致性哈希让同 key 请求落同实例（MQ：同业务发同分区），本地内存 BF 零网络开销；重启后逐步重建或用最近 N 天数据预建。②**bit array**：key 是数字（自增 ID）时按值索引，精确无假阳性；起点非 0 时首位映射起始 ID 省空间。

### Q7：思考题 2——重复请求占比不到 1%，这个方案效果如何？

大打折扣。BF 和 Redis 层存在的意义是**拦截重复流量**，重复率极低时 99% 请求穿透到唯一索引——三层架构的开销（维护 BF、Redis 内存）换来的拦截收益≈0。此时直接用唯一索引（或乐观锁状态机）即可。**方案选型看流量特征：重复率越高，层层削流越值。**

### Q8：思考题 1——唯一索引方案在 RR 隔离级别下的阻塞问题，换成 RC 会怎样？

RR 下重复插入会走**唯一键冲突检测的加锁**流程（插入意向锁与已有记录锁交互），并发重复请求被**串行阻塞**直到前一个事务提交/回滚——行为可预期但并发度低。RC 下间隙锁基本禁用，唯一键检查的加锁范围更小，冲突检测更快失败（直接报 duplicate key）——对幂等判断反而更利落。这也是为什么高并发幂等表场景**推荐 RC**（联动故障排查 01 笔记的死锁案例：RR 下唯一索引 + 插入意向锁正是死锁温床）。

### 项目经历栏·案例：高并发幂等方案

**版本 A（简洁版，一行）**

**版本 B（详细版，供面试口述）**
> 我们的消费端要扛高并发重试流量，最初用唯一索引做幂等，但 DB 写压力大。我设计了层层削流的三层方案：请求先过布隆过滤器——它说没处理过就一定没处理过，直接放行，绝大多数流量在这一层就返回了；说处理过的（可能假阳性）查 Redis 里近期处理的 key（TTL 按重试窗口定，重试 10 分钟内到达就设 11 分钟）；穿透到最后的由业务唯一索引兜底。更新顺序很关键：先把业务数据和唯一索引放同一个本地事务提交（DB 最准），再更新 BF 和 Redis——这两步失败了也无所谓，因为索引兜底。后来还做了两个优化：key 是自增 ID 的业务切到 bit array，精确又省内存；要求生产者按业务 ID 哈希发分区，消费者用上了本地布隆过滤器。整套方案让 DB 的幂等校验压力降了两个数量级。

## 四、面试官连环追问清单（含参考答案）

### Q1：为什么"先插唯一索引"顺序不能反？（无事务三步方案）

先执行业务再插索引：两个并发重复请求可能**同时通过**"索引不存在"的检查，双双执行业务 → 重复处理。先插索引：第二个请求在第一步就撞索引冲突被拦。**索引插入是"占位"，占位必须先于一切业务动作**——这和分布式锁 SETNX 先占位是同一思想。

### Q2：异步检测系统怎么判断"业务到底成功没有"？

扫唯一索引表里的"初始态"记录，回查业务表：业务数据在 → 业务已成功，补标"完成"；业务数据不在且超时 → 判定业务失败，触发重试（重投消息或重放任务）。要点：①判断依据是**业务表的真实状态**，不是猜；②超时阈值要大于业务 P99 耗时，避免误判处理中的请求；③检测系统本身要幂等（重复补标/重复触发重试无害）。

### Q3：布隆过滤器的容量怎么规划？假阳性率多少可接受？

按预期元素数 n 和目标假阳性率 p 反推：`m = -n·ln(p)/(ln2)²` bit，最优哈希函数数 k = (m/n)·ln2。例：1 亿元素、1% 假阳性 → 约 114MB 内存。假阳性率选型：BF 后面还有 Redis/唯一索引兜着，**1%~0.1%** 都够用——不必追求极低 p（内存翻几倍不划算），p 只影响后两层的流量大小，不影响正确性。

### Q4：MQ 宣称的 exactly-once 是怎么实现的？为什么还要幂等？

Kafka 的 exactly-once = **生产者幂等**（PID + 序列号去重重试消息）+ **事务**（跨分区原子写入 + 消费位点与结果同事务提交）。它解决的是"Kafka 内部不重复"，但**消费端业务处理与外部系统的交互不在其管辖内**——你的消费逻辑把消息写 DB 后崩溃，恢复后照样重复。所以"Kafka 已经 exactly-once 了，业务不用幂等"是典型误解：**端到端 exactly-once 不存在，最终都要业务幂等兜底**。

### Q5：本地布隆过滤器重启期间会不会漏判？

会：重启后 BF 是空的，重复请求会被当成"没处理过"放行——但它会穿透到 Redis/唯一索引被拦住，**正确性无损，只是短期削流效果下降**。这就是"唯一索引兜底"设计的美妙之处：上层每一层都可以失效，正确性锚点永远在最下面。工程上再叠加预热（加载最近 N 天 key）把空窗削流效果尽快恢复。

### Q6：高并发下唯一索引本身会不会成为瓶颈/死锁源？

会（呼应故障排查 01 笔记）：RR 隔离级别下，并发 INSERT 唯一索引冲突涉及**唯一键冲突检测加锁 + 插入意向锁**，是经典死锁场景（"先查后插"两个事务互相等待）。缓解：①隔离级别降 RC（Gap Lock 基本禁用，冲突检测更快失败）；②唯一索引表尽量窄（少二级索引）；③用 `INSERT ... ON DUPLICATE KEY UPDATE` 原子语义；④削流（BF/Redis）让真正到索引的并发可控。
