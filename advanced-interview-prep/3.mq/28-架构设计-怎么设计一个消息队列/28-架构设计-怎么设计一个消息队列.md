> 整理日期：2026-11-06

## 一、文章总结

**考察本质**：站在设计者角度解释 Kafka 为什么长这样。框架：**生产者、消费者、broker、topic 四个维度**。文章用"MySQL 封装 MQ"作为具象案例贯穿。

**topic 设计**：
- topic 代表业务，必须存在；topic 内必须再细分**分区**——否则所有生产者/消费者竞争同一把锁，性能差
- MySQL 映射：**一个 topic 一张逻辑表，一个分区一张物理表**（分库分表视角；自增主键 = offset）
- 为什么不让所有 topic 共用一张表（加 topic 列）？①**性能**：一张表扛不住大数据高并发，分库分表要分出几千张表犯不着；②**隔离**：topic 天然业务隔离，分表互不影响；③便于把不同 topic 安排到不同数据库实例

**broker 与消息存储**：同 topic 的分区**分散到不同 broker**（一个 broker 崩溃最多影响一个分区）——MySQL 版：分区的物理表**分库**，且分散到**不同主从集群**（一主两从 = 天然副本，还免了自己管理主从选举，没有 ISR 概念但效果类似）。

**发送消息**：
- **推模型**：生产者主动推（消息产生速率与 broker 无关，broker 拉取不好控制频率和数量）
- **批量发送**：凑批发送 + `linger.ms` 兜底（超时未凑满也发，防消息滞留内存丢失）
- 极致优化：**生产者直连数据库**（本地依赖按 topic/分区找数据源，INSERT 即发——省一次网络通信，相当于生产者和 broker 一体）

**消费消息**：
- 消费者组 = 一个业务方；组内多消费者；**一个分区对一个消费组只能有一个消费者**（保留 Kafka 约束）
- **拉模型**：消费者才知道自己的消费速率（每 1s 拉 50 条）
- **偏移量表**：一个 topic 一张 `<topic>_consumers` 表（消费者组、分区、已提交 offset 三列）；提交 = UPDATE 行锁（行数少、只动行锁，性能很好）；**指定偏移量消费 = UPDATE committed_offset**，重拉 = `SELECT * FROM create_order_2 WHERE id > 100 LIMIT 50`
- 改进：offset 高并发更新 → **Redis 记录 + 异步刷新 DB**；风险是 Redis 宕机丢最新 offset（950 vs 1000）→ 恢复后重复消费 → **消费者幂等**兜底
- 极致优化：消费者**直连数据库**拉消息

**延迟消息（MySQL 版天然好做）**：消息表加 `send_time` 列，消费者拉取：
```sql
SELECT * FROM some_topic WHERE send_time <= now() AND send_time > $last_batch_send_max_time
```
记录的是**时间戳**而非 offset。
- **同时发送问题（亮点坑）**：同一毫秒有 90 条消息，LIMIT 50 会截断——下次 `send_time > 第50条时间` 会把同毫秒的另外 40 条**跳过**；改成 `>=` 又会重复拉
- **解法：自己算批次边界**——读够 50 条后继续检查后续行，`send_time` 与第 50 条相同的**一并纳入本批**（假设同一毫秒消息不会太多）。所有"按时间分页"的场景都要考虑这个问题

**设计权衡自述**（防追问）：用 MySQL 当存储 = 避开自研文件 IO/零拷贝等硬骨头；可换 PostgreSQL/Oracle/TiDB（Oracle 连分库分表都省了）。**真实使用场景：ToB 私有化部署**（客户没能力维护 MQ，软件又需要 MQ——如私有化 IM）。

**面试准备**：了解内存 MQ（进程内事件/测试）、TCP 直连 MQ（无 broker）、本地文件 MQ 等轻量形态；公司没用 MQ 的系统怎么实现异步/解耦/削峰。

## 二、Q&A（问题 + 标准答案）

### Q1：设计一个消息队列要考虑哪些方面？

四个维度：①topic——代表业务，内部必须细分分区（否则全局竞争一把锁）；②broker/存储——分区分散到不同节点保可用性，副本机制（Kafka 是 ISR，MySQL 主从天然自带）；③生产者——推模型 + 批量发送（linger.ms 兜底）；④消费者——消费者组、拉模型、偏移量管理（每分区对组内唯一消费者）。

### Q2：Kafka 为什么引入分区？只有 topic 行不行？

不行——不细分则所有生产者竞争同一写入锁、所有消费者竞争同一读取锁，并发度为 1。分区把单个 topic 的写入/消费通道复制成 N 份，是水平扩展和有序性（分区内有序）的双重基石。（同 24 笔记：分区是有序 WAL 日志。）

### Q3：为什么分区要分散在不同 broker？

故障隔离：一个 broker 崩溃，topic 最多损失一个分区的可用性，其余分区照常服务；同时也分散了读写流量。MySQL 版对应：分区表分散到不同主从集群，主从复制天然提供副本。

### Q4：为什么生产者用推模型、消费者用拉模型？

生产者：消息产生速率由业务决定，broker 无法预判——推模型让速率控制自然落在生产侧。消费者：**只有消费者自己知道消费速率**（处理逻辑快慢、下游压力），拉模型让消费者按自身能力取餐，天然背压。这是"谁掌握速率信息，谁主动"的通用设计原则。

### Q5：偏移量怎么管理？Redis 记录 offset 有什么风险？

MySQL 版：每 topic 一张 offset 表（组、分区、committed_offset），提交即行级 UPDATE，行少性能高；指定偏移量重消费 = 直接 UPDATE。优化：Redis 记录 + 异步刷 DB——风险是 Redis 宕机丢最新 offset（DB 里 950、实际 1000），恢复后从 950 重复消费 → 幂等兜底。

### Q6：MySQL 版延迟消息怎么做？同时发送问题怎么解？

消息表加 `send_time` 列，消费按时间戳拉取（`send_time <= now() AND send_time > 上批最大时间`）。同时发送坑：同一毫秒 90 条，LIMIT 50 截断后，下次 `>` 会跳过同毫秒剩余 40 条，`>=` 又重复——**解法是自己算批次边界**：读满 50 条后继续看后续行，send_time 与第 50 条相同的一并纳入本批。

### Q7：思考题 1——新消费者组接入，偏移量怎么初始化？

两种策略（对应 Kafka 的 `auto.offset.reset`）：①**latest**——初始化为各分区当前最大 offset（历史消息不消费，适合只关心新数据的业务）；②**earliest**——初始化为 0/最早 offset（历史全量消费，适合需要补数据的业务）。初始化动作：offset 表插入该组 × 各分区的记录，要么按 topic 配置默认策略，要么接入时让业务方显式选择。

### Q8：思考题 2——用 Redis 实现 MQ 怎么做？

- **List 版**：`LPUSH` + `BRPOP`（阻塞拉取），简单但**无消费者组语义**（一条消息只被一个消费者拿到，无法多业务方订阅）、无 offset 管理、弹出即删除可靠性弱
- **Pub/Sub 版**：真订阅模式，但**不持久化**，订阅者不在线就丢
- **Stream 版（5.0+，正解）**：`XADD` 追加（ID = 时间戳 + 序号，天然 offset）、`XREADGROUP` 消费者组 + pending 列表（未 ack 消息追踪）、`XACK` 确认、`XCLAIM` 转移死信——功能上已接近精简版 MQ；短板是内存容量与持久化级别
- 结论：轻量场景 Stream 够用，严肃场景还是专业 MQ

### 项目经历栏·案例：私有化部署的轻量级 MQ

**版本 A（简洁版，一行）**
- 为私有化交付场景设计 MySQL 版轻量消息队列：topic 映射逻辑表、分区映射分库分表物理表、主从集群天然副本，消费者组拉模型 + 偏移量表，原生支持延迟消息（send_time 列 + 批次边界自计算），客户零额外中间件依赖

**版本 B（详细版，供面试口述）**
> 我们的软件要私有化交付给中小客户，需要 MQ 能力但客户没运维 Kafka 的技术力量。我设计了基于 MySQL 的轻量 MQ：一个 topic 一张逻辑表，分区按分库分表拆成物理表（自增主键就是 offset），不同分区分散到不同主从集群——副本和选举直接复用 MySQL 主从。生产者推模型 + 批量发送，高要求场景提供直连数据库的本地依赖省一跳网络。消费者组拉模型，每 topic 一张偏移量表（组、分区、offset 三列，行锁更新性能足够），支持 UPDATE offset 实现指定位置重消费。最有意思的是延迟消息：加 send_time 列按时间拉取，我专门处理了"同一毫秒消息被 LIMIT 截断"的边界——读满批次后把与最后一条同时间戳的消息一并纳入。整个方案让客户的部署依赖只剩 MySQL。

## 四、面试官连环追问清单（含参考答案）

### Q1：MySQL 版和 Kafka 版 MQ 的性能差距在哪？为什么 ToB 场景能接受？

差距核心在 **IO 模型**：Kafka 是顺序写日志 + page cache + 零拷贝（见 29 讲），单机十万级 QPS；MySQL 写走 B+ 树更新 + redo/binlog 双写，单机万级。但 ToB 私有化场景的消息量（企业 IM、内部通知）远低于互联网峰值，万级绰绰有余——**架构选型是需求匹配，不是性能攀比**。换来的是：部署零新增组件、客户 DBA 现成会运维、事务/备份/监控全套现成。

### Q2：MySQL 版消息积压了怎么办？

复用分库分表手段：①加分区 = 加物理表（新 topic 也行）；②消费端直连数据库本身就是低延迟路径；③冷热分离——`send_time` 或自增 ID 分区，历史分区直接归档/删除（MySQL 版消息即数据，**数据生命周期管理比 Kafka 更灵活**）；④瓶颈若在 offset 更新，上 Redis + 异步刷。

### Q3：MySQL 主从复制延迟会不会导致读从库拉到"未来"或"重复"的消息？

消费者应**只读主库**（消息系统对一致性要求高于普通读业务）；如果读从库：复制延迟 → 新消息延迟可见（只是消费慢一点），但 offset 表如果也读写分离会出现"消息已拉但 offset 未同步"的窗口 → 重复消费。原则：**消息表和 offset 表必须同一数据源、同一读写路径**。

### Q4：消费者组内 rebalance 在这个设计里怎么体现？

Kafka 靠 coordinator 感知组成员变化并重分配分区；MySQL 版要自己实现：①消费者**心跳表**（定期上报，超时判死）；②分配器（选主或独立组件）按"分区数 vs 消费者数"重算分配关系写入分配表；③消费者按分配表调整自己的拉取目标。复杂度不小——这正是 Kafka 把协调者内置的价值，MySQL 版的简化选择是**静态分配 + 人工扩容**（ToB 场景组内成员变化极少）。

### Q5："同时发送问题"还在哪些场景出现？（模式迁移）

所有**按非唯一字段分页**的场景：按时间翻页（feed 流）、按分数翻页（排行榜）、按 update_time 增量同步（数据迁移/CDC 拉数）。通用解法三选一：①边界值同值并入本批（文章方案）；②**复合游标**（send_time + id 双条件：`WHERE (send_time > t) OR (send_time = t AND id > last_id)`——最严谨）；③业务上接受极小概率重复，靠幂等消化。

### Q6：如果让你加"顺序消息"能力，这个设计怎么扩展？

MySQL 版的分区物理表天然就是 Kafka 分区：同业务消息按业务 ID 哈希插入固定物理表（自增 ID 保序），消费端每表单消费者串行拉取。扩表（加分区）时的失序问题和解法与 Kafka 版完全一致（新表消费者延迟启动，见 24 笔记）——**设计是相通的，介质换了，模式不换**。

### Q7：offset 表会不会成为瓶颈？怎么量化？

每消费者每分区一行，总行数 = 组数 × 分区数，通常几十到几百行；更新走**主键/唯一索引行锁**，TPS 可达数千——按"消费速率 ÷ 批量大小"估算提交频率（每 50 条提交一次、消费 1 万条/秒 = 200 次更新/秒），离瓶颈很远。真到极限：Redis 计数 + 异步批量刷 DB（带幂等兜底的丢 offset 风险）。
