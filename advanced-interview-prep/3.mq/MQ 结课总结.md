# MQ 结课总结

MQ 的核心不是“怎么调用 API 收发消息”，而是：

> **当生产、存储、复制、消费、业务写入跨越不同系统边界时，如何处理丢失、重复、顺序和一致性问题。**

整门课可以收敛成三个根。

------

## 一、三个根：大部分 MQ 知识都能从这里推导出来

### 根一：MQ 的本质是时间解耦

在生产者和消费者之间加入一个持久化缓冲，让双方不再共用同一个时钟：



```text
同步调用：生产者必须等消费者处理完消息队列：生产者写入缓冲后离开，消费者按自己的速度处理
```

因此自然产生三个收益：

- **削峰**：生产高峰被队列吸收，消费者匀速处理；
- **解耦**：生产者不必知道下游是谁，新增消费者不必修改生产者；
- **异步**：调用方不再等待完整业务链路。

代价是引入了新的问题：消息会不会丢、会不会重、顺序是否保持、业务何时才算完成。

**使用判据**：生产者快、消费者慢；或者下游不需要立即返回结果、下游可能暂时不可用，MQ 才有明显的解耦价值。必须当场知道结果的调用，例如扣款是否成功，不应简单改成异步。

------

### 根二：两个动作跨越系统边界，就会出现原子性缺口

发送方无法区分：

- 对方没有收到；
- 对方已经收到并处理，但响应丢失或延迟。

超时之后：

- 重发，可能重复；
- 不重发，可能丢失。

这不是某个 MQ 的缺陷，而是不可靠通信下的根本限制。



| 场景           | 两个无法天然原子的动作         | 工程回答                                       |
| :------------- | :----------------------------- | :--------------------------------------------- |
| 生产端         | 发送消息 ↔ 收到确认            | 至多一次或至少一次；重试、幂等生产者           |
| 消费端         | 处理业务 ↔ 提交 offset         | 先处理后提交，接受重复；先提交后处理，接受丢失 |
| broker 复制    | leader 本地写入 ↔ 副本复制完成 | `acks=all`、ISR、多数派约束                    |
| 本地事务与消息 | DB 提交 ↔ 消息可见             | half message + 回查，或本地消息表              |
| 普通 RPC       | 请求执行 ↔ 调用方收到响应      | 幂等键、服务端去重                             |

**原子性缺口不能靠调整操作顺序消灭。工程上只能选择缺口朝向，再用重试、幂等、事务或对账控制代价。**

------

### 根三：磁盘随机写慢，不等于顺序写慢

Kafka 的高吞吐不是“不使用磁盘”，而是改变磁盘的使用方式：

1. **append-only 日志**：消息只追加到文件末尾，把随机写变成顺序写；
2. **page cache**：应用的 `write()` 通常到内核页缓存就返回，内核异步刷盘；追尾消费也经常直接命中页缓存；
3. **零拷贝**：发送消息时减少用户态与内核态之间的数据复制；
4. **整段清理**：旧内容不能随意修改，所以过期数据按 segment 整段删除。

其中：

- **page cache 主要降低应用等待延迟**；
- **append-only 主要保证最终落盘仍然是顺序写**。

因为应用返回成功不等于数据已经物理刷盘，单机断电仍可能丢失页缓存中的数据，所以 Kafka 的持久性主要依赖**多机复制**，而不是单机强制刷盘。

------

## 二、投递语义：至多一次、至少一次、恰好一次

### 1. 生产端



| 语义     | 行为                 | 风险                         |
| :------- | :------------------- | :--------------------------- |
| 至多一次 | 发出后不等待、不重试 | 可能丢失                     |
| 至少一次 | 等待确认，超时重试   | 可能重复                     |
| 恰好一次 | 传输层无法独立保证   | 必须依靠去重、事务等额外机制 |

Kafka 对应配置：

- `acks=0`：发完就忘；
- `acks=1` / `acks=all` + `retries>0`：至少一次；
- 幂等 producer：用 `(PID, 分区, 序列号)` 识别生产重试造成的重复。

默认通常选择至少一次，因为**丢失往往难以补救，重复则可以在消费端消化**。

### 2. 消费端

消费一条消息包含两个动作：



```text
处理业务 + 提交 offset
```



| 顺序           | 中途宕机的后果                         |
| :------------- | :------------------------------------- |
| 先处理，后提交 | 业务已生效、进度未记录，恢复后重复消费 |
| 先提交，后处理 | 进度已记录、业务未执行，消息永久跳过   |

所以严肃业务通常采用：



```text
关闭自动提交→ 处理业务→ 手动提交 offset→ 用幂等消化不可避免的重复
```

自动提交记录的是“已拉取”的进度，不保证“已处理”，可能造成消息丢失。

### 3. 幂等消费

**幂等 = 执行一次和执行多次，最终效果相同。**

可靠程度较高的实现方式：

1. **唯一约束 + 同一数据库事务**：业务写入和去重记录一起提交；
2. **状态机**：只允许合法状态迁移，重复消息影响零行；
3. **天然幂等操作**：优先覆盖写，谨慎使用“读取—修改—累加”。

两个常见错误：

- 分布式锁只能控制并发，不能阻止第一次执行完后再次执行；
- “先查是否处理，再处理”存在并发窗口，查重与执行必须原子化。

------

## 三、exactly-once：能力、边界与流处理

### 1. Kafka 提供的是什么

Kafka 的 exactly-once 主要包括：

- **幂等 producer**：消除生产者重试在单分区、单会话内造成的重复写入；
- **事务**：在流处理场景中，把 Kafka 内的输出写入与输入 offset 提交原子化。

它不保证：

- 消息在网络上只传一次；
- 业务代码只被调用一次；
- 写 MySQL、调用外部接口等副作用恰好执行一次。

**完整业务恰好一次 = 系统边界内的机制 + 边界外的幂等或事务性输出。任何 MQ 都无法单方面替外部系统兜底。**

### 2. 为什么流处理特别需要它

流处理是对持续到达的数据持续计算，例如：



```text
订单流 → 按类目分组 → 累计成交额 → 输出统计结果
```

有状态聚合中：



```text
成交额 = 成交额 + 200
```

如果结果已经生效、offset 尚未提交时宕机，恢复后订单会被重新处理，成交额就会重复累加。

但要注意：

- **有状态不是唯一判断标准**；
- 真正的判据是：**重放一次，是否会重复改变结果或产生副作用**；
- 无状态计算重复计算的结果可能相同，但仍可能产生重复输出；
- 有状态业务也可以保存事件 ID，自行实现去重。

因此，exactly-once 不是业务无法实现的黑魔法。它的价值是让框架统一处理：

- 状态恢复；
- 消费进度；
- 输出生效；
- 并行任务故障与扩缩容。

RocketMQ 同样可以作为 Flink 等流处理框架的数据源。区别是框架、连接器和输出系统如何共同保证一致性，而不是“只有 Kafka 能做流处理”。

## 四、partition：并行单位，也是顺序边界

一条日志的吞吐受单机和单盘限制，所以 Kafka 把 topic 拆成多个 partition：

- 不同 partition 可以分布在不同机器上；
- 写入可以并行；
- 消费组内，一个 partition 同一时刻只分配给一个 consumer；
- 消费并行度上限等于 partition 数。

直接推论：

1. consumer 多于 partition，多出的 consumer 闲置；
2. partition 扩容能提升并行度，但可能改变 key 的路由，破坏键内顺序；
3. 顺序保证只存在于**单 partition 内**，跨 partition 没有天然全局顺序。

### 顺序性的工程答案

大多数业务需要的是“同一实体的事件有序”，而不是全局有序：



```text
同一订单 ID → 同一 partition → 单线程顺序处理
```

顺序必须贯穿：



```text
生产发送 → partition 存储 → consumer 拉取 → 业务处理
```

常见破坏点：

- consumer 拉取后丢进线程池并发处理；
- 扩容 partition 导致同一 key 改换分区；
- producer 并发发送和重试导致后发的消息先成功；
- 错误地把“单 partition 有序”理解成“topic 全局有序”。

## 五、Kafka 复制：已确认消息的可靠性边界

### `acks` 决定何时确认



| 配置       | 确认时机               | 风险                            |
| :--------- | :--------------------- | :------------------------------ |
| `acks=0`   | 不等待                 | 最容易丢                        |
| `acks=1`   | leader 本地写入        | leader 宕机时可能丢失已确认消息 |
| `acks=all` | ISR 中所有成员复制完成 | 更可靠，延迟更高                |

### ISR 的作用

ISR 是“目前跟得上 leader 的副本集合”，动态变化：

- 慢副本会被暂时踢出，避免拖死整个分区；
- `acks=all` 等待的是 ISR 中的全部成员，不是配置上的全部副本；
- `min.insync.replicas=2` 防止 ISR 只剩 leader 时静默降级；
- ISR 不足时，broker 拒绝写入，而不是偷偷降低可靠性。

默认只从 ISR 中选举新 leader，并关闭：



```properties
unclean.leader.election.enable=false
```

因此，“不丢消息”的准确表述是：

> **在正确配置和副本假设成立时，已经确认的消息不会因为正常的 leader 切换而丢失。**

## 六、全链路可靠性配置



| 链路     | 推荐措施                                                     |
| :------- | :----------------------------------------------------------- |
| producer | `acks=all`、重试、幂等 producer                              |
| broker   | `replication.factor≥3`、`min.insync.replicas=2`、关闭 unclean election |
| consumer | 关闭自动提交、先处理后提交                                   |
| 业务     | 幂等消费、监控消费 lag、失败重试与死信处理                   |
| 运维     | 监控 ISR 缩水、副本离线、生产失败、消费积压                  |

这套配置不是绝对“零丢失”，而是把可靠性边界明确画在**已确认消息**上，并用延迟和可用性换取可靠性。

## 七、消费模型：pull、rebalance 与堆积

### 为什么采用 pull

pull 让消费者自己控制消费节奏：

- 快消费者多拉；
- 慢消费者少拉；
- 天然形成背压；
- broker 不必为每个消费者维护复杂的推送状态。

它是“时间解耦”在投递环节的延续。

### rebalance

触发原因包括消费者增减、partition 变化和订阅变化。

主要代价：

- 消费暂停，造成延迟尖峰；
- partition 接管者从最后提交的 offset 重拉，可能产生重复消费。

### 消费堆积诊断



```text
生产速度持续 > 消费速度 → lag 增长
```

- **consumer CPU、IO 很忙**：产能不足，考虑扩 partition 和 consumer、批量消费、优化处理逻辑；
- **consumer 很闲但 lag 增长**：通常阻塞在下游 DB、RPC 等同步依赖上。下游耗时也是消费产能的一部分。

## 八、事务消息与本地消息表

### 要解决的问题



```text
本地 DB 提交订单 + 发消息通知下游
```

两种朴素顺序都存在缺口：

- 先 DB 后消息：DB 提交后宕机，留下“有订单、无通知”；
- 先消息后 DB：DB 回滚，留下“幻影通知”。

### RocketMQ 的解法



```text
发送 half 消息（已持久化，但 consumer 不可见）→ 执行本地事务→ 根据事务结果 commit / rollback→ 若结果通知缺失，broker 回查 producer
```

它保证：

- DB 提交，消息最终可见；
- DB 回滚，消息不会错误生效；
- 不保证消费端不重复。

完整一致性链路：



```text
事务消息解决生产端双写+ 至少一次投递+ 消费端幂等= 端到端最终一致
```

### 与本地消息表的关系

两者共同思想都是：

> **先持久化“我要做这件事”的意图，再异步对账收敛。**

区别是：

- 本地消息表把意图放在业务 DB 中，可以与业务写入使用同一个本地事务；
- half 消息把意图放在 broker 上，因此需要回查本地事务结果。

## 九、产品选型



| 产品     | 设计原点           | 优势                                        | 典型场景                                 |
| :------- | :----------------- | :------------------------------------------ | :--------------------------------------- |
| Kafka    | 高吞吐日志流       | 顺序日志、page cache、partition、流处理生态 | 日志采集、行为埋点、实时计算、大数据管道 |
| RocketMQ | 业务消息           | 事务消息、延时消息、顺序消息、消息轨迹      | 订单、支付、履约、延时关单               |
| RabbitMQ | 灵活路由与轻量集成 | exchange 路由、低延迟、使用简单             | 企业内部异步任务、中小规模业务解耦       |

选型顺序：

1. 消息量级和吞吐；
2. 是否需要事务、延时、顺序等业务特性；
3. 团队的运维能力和生态成本。

## 十、最终应形成的判断框架

遇到任何 MQ 问题，先问五件事：

1. **这里跨了几个系统边界？**
2. **哪两个动作无法原子完成？**
3. **故障时选择丢失还是重复？**
4. **重复是否有幂等或去重兜底？**
5. **保证的范围到哪里为止，边界之外由谁负责？**

最后压缩成一句话：

**MQ 的可靠性不是“开启某个参数”，而是生产确认、broker 复制、消费进度、业务幂等和故障对账共同组成的一条链；任何一环缺位，前面所有保证都可能失效。**

理论部分到这里已经形成完整结构。下一步最值得做的是跑通一次真实链路：生产消息、消费写库、手动提交 offset、幂等去重，然后在“处理完成但尚未提交”时主动杀死 consumer，亲眼验证重复消费及幂等是否真正生效。
