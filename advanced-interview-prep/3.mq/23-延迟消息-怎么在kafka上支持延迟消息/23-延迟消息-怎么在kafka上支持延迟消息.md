# 面经总结 23：延迟消息——怎么在 Kafka 上支持延迟消息？

> 来源：极客时间《后端工程师的高阶面经》邓明（消息队列模块 23 讲）
> 整理日期：2026-11-06

## 一、文章总结

**为什么这题热**：Kafka 不支持延迟消息人尽皆知，但 Kafka 用得多、延迟需求又普遍（订单超时取消等）——"怎么让 Kafka 支持延迟消息"就成了高频考题。

**前置概念**：延迟队列 = 拿到的永远是最先过期的元素（Java `DelayQueue`）；延迟消息 = 消息在服务器上存够时间后才可被消费。

**现成方案盘点**：

| 方案 | 原理 | 缺陷 |
|---|---|---|
| RabbitMQ 插件 `rabbitmq_delayed_message_exchange` | 消息暂存 exchange 的 **Mnesia**（基于文件的数据库），到点投递到真队列 | 未刷盘/节点不可用**会丢消息**；**不支持高并发大数据量** |
| RabbitMQ TTL + 死信队列 | delay_queue 设 TTL 无消费者 → 过期消息进死信队列（= 业务队列） | TTL 是**队列级**，一种延迟一个队列，不支持随机延迟 |
| RocketMQ | 原生支持 18 个固定延迟级别 | 级别固定，非随机（补充） |

**方案一：定时任务调度**（最简单）：延迟 30 分钟消费 = 30 分钟后**发送**——注册一个到点发送消息的定时任务即可。缺点：定时任务中间件**撑不住高并发大数据量**，只适合小规模。

**方案二：分区设置不同延迟时间**（简单好用，文章推荐的基础方案）：
```
delay_topic：N 个分区各管一种延迟（如 1min/3min/5min/10min/30min）
延迟消费组：每分区一个消费者，拉到消息 → 按剩余延迟睡眠 → 转发到 biz_topic
```
- 业务方只需按延迟时间选对分区；业务消费者对转发过程无感
- **亮点 1：rebalance 问题**——睡眠期间 Kafka 判定消费者崩溃触发 rebalance，醒来换分区就白睡了。解法：睡眠前 **pause()**、睡醒 **resume()**。注意 pause 不是不拉数据，是 **poll 但拉 0 条**，让 Kafka 认为消费者还活着
- **亮点 2：一致性问题（先转发后提交）**——先提交 offset 再转发：宕机丢消息，不可接受。**先转发 biz_topic 再提交**：宕机恢复后重复转发，靠**消费者幂等**兜底（发送方本身就可能重发，幂等是 MQ 消费者的通用义务）
- **缺点**：①延迟时间必须**预设**，不支持随机延迟（按业务数据算延迟的场景不行）；②**分区负载不均**（大家都用 3min，1min/10min 分区闲置）——缓解：热门延迟附近多设几个相近分区（2min30s、3min30s），常规积压治理手段在这里不好用

**亮点方案：基于 MySQL 支持随机延迟**（高级，融合分库分表）：
```
delay_topic → 延迟消费者 → 转储 MySQL → 延迟发送者轮询 → 到点转发 biz_topic → 更新状态为已发送
```
瓶颈在 MySQL（**写密集**场景），四个优化手段（层层递进）：

| 手段 | 做法 | 要点 |
|---|---|---|
| **分区表** | 按"发送时间"分区（低并发按周、高并发按天），历史分区直接清理 | 最简单 |
| **表交替** | tab_0/tab_1 按天交替读写，交替时 TRUNCATE 旧表 | TRUNCATE 极快；延迟不能超一个交替周期 |
| **分库分表** | 按 biz_topic 分库分表；并发不均（topic 间流量差异大）时用**轮询插入**——查询只按发送时间找，插哪张表无所谓 | 轮询牺牲有序性换均匀；**保有序**则同 biz_topic 落同一张表 + delay_topic 也按 biz_topic 分区 |
| **批量操作** | 延迟消费者批量插入、延迟发送者批量更新已发送 | 一致性窗口变大 → 消费者幂等兜底 |

**实践忠告**：真实业务**尽量用固定延迟级别**，让业务适配（随机延迟成本太高）；随机延迟方案主要价值在面试展示技术深度。

## 二、Q&A（问题 + 标准答案）

### Q1：Kafka 怎么支持延迟消息？

基础方案：**delay_topic 按分区预设不同延迟时间**，延迟消费组每分区一个消费者，拉到消息按剩余延迟睡眠后转发到业务 topic。两个关键坑：睡眠期间要用 pause/resume 防 rebalance（pause 是 poll 0 条不是不 poll）；转发要先发后提 offset，重复消费靠消费者幂等兜底。缺点是不支持随机延迟、分区负载不均。

### Q2：睡眠等待为什么会触发 rebalance？怎么解决？

Kafka 靠 poll 判断消费者存活（`max.poll.interval.ms`），长时间不 poll 判定崩溃 → 触发 rebalance → 分区重新分配 → 睡眠白等。解法：睡眠前 `pause()`（**poll 照常发起但拉 0 条**，保活），睡醒 `resume()` 并把 offset 重置回之前拉取的位置。

### Q3：转发到业务 topic 和提交 offset 的顺序？各有什么风险？

**先转发后提交**（正确姿势）：提交失败 → 恢复后重复转发 → 业务消费者收到重复消息 → **幂等兜底**。先提交后转发：转发前宕机 → **消息丢失**，不可接受。原则：宁可重复不可丢失；幂等是 MQ 消费者的通用义务（发送方重试也会产生重复）。

### Q4：怎么支持随机延迟时间？（亮点方案）

MySQL 中转：延迟消费者把 delay_topic 的消息转储 MySQL，延迟发送者轮询把到点的消息转发出去。写密集场景优化四板斧：**分区表**（按发送时间分区，历史直接清）、**表交替**（TRUNCATE 极快）、**分库分表**（按 biz_topic 分；不均则轮询插入——查询只按时间，与表无关）、**批量操作**（批量插入/更新）。保有序则同 biz_topic 落同表 + delay_topic 按 biz_topic 分区。

### Q5：RabbitMQ 的延迟消息方案有什么坑？

插件版：消息存 exchange 的 Mnesia，未刷盘或节点不可用会丢消息、不支持高并发——生产慎用。TTL + 死信队列版：没有丢消息问题，但 TTL 是队列级，**一种延迟一个队列**，不支持随机延迟，业务要维护一堆 delay_queue。

### Q6：定时任务方案和 MQ 方案怎么选？

定时任务（到点发送）：实现零成本，但调度中间件撑不住高并发大数据量——小规模、消息少可以用。MQ 方案（分区延迟/MySQL 中转）：扛得住高并发，但复杂度高。选型按"延迟消息 QPS × 数据量"判断。

## 四、面试官连环追问清单（含参考答案）

### Q1：思考题 1——不同分区改成不同 topic 行不行？topic 分区怎么设？消费者怎么办？

可以，且更灵活（topic 可独立配副本、保留期）。每个延迟 topic（如 delay_1min、delay_3min）**单分区即可**（延迟消费本就串行等待，多分区无意义，除非单延迟级别也要并发——那就要消费组内多实例 + 每实例处理一个分区）。延迟消费者：每 topic 一个独立消费组（或一个消费组订阅全部 topic，内部按 topic 分线程池处理）。代价：topic 数量膨胀，元数据管理成本上升——分区版适合延迟级别少，topic 版适合级别多且差异大。

### Q2：思考题 2——怎么改造其他方案满足消息有序？

全链路"同 key 同路径"：①分区延迟方案——业务发送时按 biz_topic（或业务 key）哈希到 delay_topic 的固定分区，同一分区串行睡眠串行转发，天然保序；②MySQL 方案——同 biz_topic 落同一张表 + 延迟发送者按表串行扫描发送 + delay_topic 侧也按 biz_topic 哈希分区。核心都是**保证同业务消息经过的每一条路径都是单通道串行**。

### Q3：pause 期间消息积压在分区里，醒来一下涌出，会不会把下游打崩？

会，这正是"热门延迟分区负载不均 + 积压"的放大版。缓解：①resume 后**限速转发**（令牌桶控制转发速率，宁可延迟略微超期也不冲垮下游）；②下游 biz_topic 的消费者本来就该有消费能力规划；③监控分区 lag，超阈值告警人工干预。要点：延迟方案里"准时"和"不压垮下游"冲突时，**保下游**。

### Q4：MySQL 方案的延迟发送者怎么做高可用？多个发送者会不会重复发？

- 单发送者是单点 → 多实例部署，但**同一张表的扫描发送必须互斥**：用 DB 行锁（`SELECT FOR UPDATE` 抢占）或分布式锁/主备选举
- 重复发送的兜底仍是**消费者幂等**——即使做了互斥，宕机切换窗口仍可能重发
- 批量更新"已发送"状态与发送动作的次序：先发后标（重复）vs 先标后发（丢失）——同 Kafka offset 问题，选先发后标 + 幂等

### Q5：为什么不用 Redis/ZSet 做延迟队列？（常见替代方案追问）

ZSet（score=到期时间戳）+ 轮询 range 取到期消息，实现简单，是中小规模常用方案。对比：①Redis 内存存储，**容量和成本**不如 MySQL/Kafka；②持久化级别弱（AOF 也有窗口）——对消息可靠性要求高的场景要慎重；③高并发下轮询 ZRANGEBYSCORE 是大 key 操作（呼应缓存模块 bigkey 问题）。结论：轻量场景 ZSet 够用，严肃生产用 Kafka/MySQL 方案。

### Q6：RocketMQ 的延迟级别是怎么实现的？（对比深挖）

RocketMQ 把延迟消息先写入内置 topic `SCHEDULE_TOPIC_XXXX`（18 个延迟级别对应 18 个队列），每个队列有定时任务扫描，到期后重新投递到真实 topic。和文章"分区预设延迟"方案**思想完全一致**——都是"按级别分通道 + 定时搬运"。面试时指出这一点，说明你理解方案本质而不是背实现：所有延迟消息方案都是"**暂存 + 到点搬运**"的变体，差异只在暂存介质（分区/Mnesia/MySQL/Redis）和搬运者（消费者/定时任务）。
