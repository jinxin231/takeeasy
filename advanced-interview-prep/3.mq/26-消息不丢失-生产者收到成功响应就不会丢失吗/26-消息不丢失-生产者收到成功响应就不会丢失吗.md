# 面经总结 26：消息不丢失——生产者收到写入成功响应后，消息就一定不会丢失吗？

> 整理日期：2026-11-06

## 一、文章总结

**主从与 ISR**（地基）：分区是主从结构（主分区 + 从分区），主分区分散在不同 broker。ISR（In-Sync Replicas）= 与主分区**保持同步**的从分区集合；掉队（网络问题等）的从分区被踢出 ISR，进入 OSR。`min.insync.replicas` 限制 ISR 下限——acks=all 时 ISR 成员不足则**生产失败**。

**写入语义 acks（生产者决定）**：
| acks | 语义 | 丢失风险 |
|---|---|---|
| 0 | fire and forget | broker 收没收到都不知道；客户端批量缓存未发出就崩溃也丢 |
| 1 | 主分区写入成功即返回 | 主写完后立刻崩溃，新选的主缺这条消息 |
| all | 同步给所有 ISR 成员 | 仅剩 unclean 选举和刷盘两个窗口 |

**逐个环节的丢失场景**（体系化分析，面试骨架）：
1. **生产者**：acks=0；批量缓存未发送进程崩溃
2. **主从同步**：acks=1 主写完即崩，新主缺数据；**unclean 选举**（ISR 全空时从 OSR 选主，解决可用性但丢数据）→ 关键业务**禁用 unclean 选举**
3. **刷盘**：acks=all 也可能只到 **page cache**。三个参数：`log.flush.interval.messages`（定量刷）、`log.flush.interval.ms`（定时刷）+ `log.flush.scheduler.interval.ms`（定时检测）——记忆法：**定量刷或定时刷**；Kafka 官方**不建议调**，主张靠副本冗余
4. **消费者提交**：异步消费"拉取即提交"，工作线程未处理就宕机 → 已提交未消费（详见 04 积压笔记的批量提交）

**方案一：本地消息表（发送方保证"一定发了"）**——把"业务操作 + 发消息"的分布式事务转成**本地事务 + 补偿**：
```
本地事务：业务操作 + 消息表插入待发消息（同事务）
尝试发送 → 成功则标记已发送
异步补发线程：SELECT * FROM msg_tab WHERE create_time < now()-3min AND status='未发送' → 补发
```
- 三个易错点全部靠**异步补发**兜底（提交后宕机 / 发送成功未更新状态 / 重试成功未更新状态——后两者会**重复发送**，消费者幂等兜底）
- 表设计：消息体列 + **重试机制列**（间隔、已重试次数、上限）；重试耗尽**告警人工介入**
- 升华：**分布式事务 → 本地事务 + 补偿机制**，通用范式

**方案二：消息队列侧**——关键业务 `acks=all` + **禁用 unclean 选举**；刷盘参数按公司实际（示例 10000/2000/3000）。残余风险：主从同步完成但**都没刷盘**同时崩溃——概率极低，真丢只能人工补发。

**消费者侧**：普通消费无需额外动作；异步消费用**批量消费 + 批量提交**（见 25 笔记）。

**亮点方案：Kafka 消息回查（事务消息）**——两阶段提交的应用：
```
① 发"准备消息"到 look_back_msg（含业务 topic、消息体、业务类型、业务 ID、回查接口）
② 回查中间件落库
③ 业务完成后发"提交消息"（失败则发回滚状态）
④ 中间件转发到业务 topic
```
- **回查机制**：长时间未收到提交消息 → 中间件**主动回查业务方**（HTTP URL 或 RPC 泛化调用），业务方返回"提交/回滚"。回查接口设计成**可扩展**（HTTP/RPC 双通道）——体现系统设计能力的关键点
- **数据存储**：复用延迟消息的手段——分区表 / 交替表 / 分库分表（按业务 topic 分）
- **有序性**：可能先收到提交消息！要求同业务的准备/提交消息有序 → 发送方按业务 ID 哈希指定分区（联动 03 笔记）
- RocketMQ **原生支持**事务消息回查；Kafka/RabbitMQ 不支持——选型论据

**金句**：凡提重试，必生重复，**消费者必须幂等**。

## 二、Q&A（问题 + 标准答案）

### Q1：消息在哪些环节可能丢失？

四段链路：①生产者——acks=0 或批量缓存未发出进程崩溃；②主从同步——acks=1 主写完即崩；unclean 选举从 OSR 选主丢数据；③刷盘——acks=all 也可能只到 page cache，三参数控制（定量刷/定时刷）；④消费者——异步消费已提交未消费。逐段设防：acks=all + 禁 unclean + 刷盘参数 + 批量提交。

### Q2：ISR 是什么？什么情况会被踢出 ISR？

ISR = 与主分区保持同步的从分区集合。从分区拉取落后主分区超过阈值（`replica.lag.time.max.ms`，如网络分区、broker 负载高、磁盘慢）即被踢出，进入 OSR。`min.insync.replicas` 限定 ISR 下限，acks=all 时不足则写入失败——**可用性换不丢消息**。

### Q3：acks=all 就万无一失了吗？

不是。还有两个窗口：①**unclean 选举**（ISR 全空时从 OSR 选主）→ 关键业务禁用；②**刷盘**——ISR 各副本可能都还在 page cache，同时断电崩溃则丢消息。官方主张靠副本冗余而非强制刷盘（性能权衡）。残余风险概率极低，兜底是人工补发。

### Q4：怎么保证"业务操作成功，消息一定发出去"？

**本地消息表**：业务操作和"插入待发消息"放同一个本地事务；发送成功标记已发送；异步补发线程扫描超时未发送的消息重发（带重试次数/间隔控制，耗尽告警）。本质：**分布式事务 → 本地事务 + 补偿机制**。重复发送靠消费者幂等兜底。

### Q5：Kafka 怎么支持消息回查（事务消息）？（亮点方案）

借鉴两阶段提交：先发准备消息到 look_back_msg（带业务信息和回查接口），中间件落库；业务完成后发提交消息，中间件转发到业务 topic。未收到提交消息时，中间件**回查业务方**（HTTP/RPC 接口，可扩展设计）决定提交还是回滚。三个关键点：回查接口可扩展、存储用分区表/分库分表、准备与提交消息按业务 ID 哈希分区保序。

### Q6：思考题 1——转发到业务 topic 成功，但标记"已发送"失败，会怎样？

中间件认为这条消息"未发送成功"，后续回查/重试机制会**再次转发**到业务 topic → 业务消费者收到重复消息 → 幂等兜底。和"先转发后提交 offset"是同一个模式：**宁可重复，不可丢失**。

### Q7：思考题 2——回查存储用 Redis 替代 MySQL 的优缺点？

优点：读写性能高、轮询扫描快、省去 SQL 层。缺点：①**可靠性降档**——内存存储 + 持久化有窗口（AOF 刷盘策略），丢消息风险与"不丢失"主题冲突；②容量受内存限，海量待发消息成本高；③大 key/扫描问题（呼应缓存模块）。结论：量小、容忍极小概率丢失可用 Redis；严肃场景还是 MySQL/分库分表。

### Q8：消费者怎么保证"肯定消费了"？

普通消费：处理完再提交 offset（关自动提交）即可。异步消费：批量消费 + 批量提交（全批处理完才提交），重复消费幂等兜底，部分失败重试/丢回队列（详见 25 笔记）。

## 四、面试官连环追问清单（含参考答案）

### Q1：为什么官方不建议调刷盘参数？

Kafka 的可靠性设计哲学是**靠副本冗余而非单机持久化**：只要 ISR 里有一个副本活着且刷盘，数据就不丢——副本分布在不同机器，同时断电的概率远低于单机。强制刷盘（如每条/每 100ms）会显著拉低吞吐（磁盘 IO 是 Kafka 顺序写优势的反面），收益却只覆盖"所有副本同时断电"这个极小窗口。所以默认依赖 OS 后台刷盘 + 副本，参数留给极端合规场景。

### Q2：本地消息表和 RocketMQ 事务消息怎么选？

本地消息表：不依赖 MQ 特性（Kafka 也能用）、业务侵入大（要建表、写补发任务）、**同步发消息**（业务操作后立刻尝试发，时效好）。事务消息（回查）：MQ/中间件承担回查调度，业务只需实现回查接口，侵入小，但**消息真正可见的时间晚**（等确认/回查周期）。选型：MQ 原生支持（RocketMQ）优先用事务消息；Kafka 环境则本地消息表或自建回查中间件。

### Q3：回查接口的幂等和并发怎么处理？

回查可能被并发触发（超时扫描 + 业务刚提交同时发生）：业务方回查接口必须**幂等**（同一 biz_id 多次查询返回一致状态——查的是本地事务状态，天然幂等）；并发冲突由中间件侧解决——转发前加分布式锁（按 biz_id）或数据库状态机 CAS（未发送→已发送），保证只有一方真正转发。

### Q4：禁用 unclean 选举的代价是什么？

ISR 全空的极端场景下（如机房断电、网络分区），分区**不可用**（不可读写），直到 ISR 成员恢复。即：禁用 unclean = **用可用性换不丢消息**（CP 取向）。所以要配套：副本数 ≥ 3、跨机架/跨可用区部署、min.insync.replicas=2——把"ISR 全空"的概率压到天文数字级。

### Q5：acks=all + min.insync.replicas 的常见搭配是什么？为什么？

`acks=all` + `replication.factor=3` + `min.insync.replicas=2`：容忍一个副本掉队仍正常写入，两个副本都持久化才算成功——数据安全性、可用性、性能的三方平衡。min.insync.replicas=1 退化成 acks=1 的语义；=3 则任何一台抖动就写失败，可用性差。

### Q6：消息链路都设防了，为什么还说"丢消息"在实践中最难定位？

因为丢失点可能在链路任何一环，而表象只在消费端（"怎么没收到"）。定位方法论：**沿链路反向取证**——消费端 offset 是否连续 → broker 分区日志里有没有（按时间/key 查）→ ISR 历史（那段时间是否发生 unclean 选举/副本不足）→ 生产者日志（acks、重试、批量缓存丢失）→ 发送方业务日志（本地消息表状态）。平时就要有全链路消息追踪（消息 ID 贯穿发送-broker-消费），出事才能分钟级定位。

### Q7：重复消息和丢失消息是什么关系？（哲学题）

**可靠传输的铁律：不丢和不重，最多完美一个，另一个靠幂等消化。** 原因：确认机制在分布式环境下存在"不知道对方收到没有"的盲区（两军问题），重试是唯一解，而重试必然引入重复。所以所有可靠性方案的终点都是"**至少一次投递 + 幂等消费**"——丢失治理收敛为重试，重复治理收敛为幂等（见 27 讲）。
