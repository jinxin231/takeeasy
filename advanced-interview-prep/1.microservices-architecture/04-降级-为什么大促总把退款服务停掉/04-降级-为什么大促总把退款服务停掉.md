## 一、文章总结

**降级的本质**："凑合过呗，还能离咋的"——**牺牲不重要的部分，保住重要的部分**。识别出"谁比谁重要"是一切降级方案的根源。

**降级 vs 熔断**（常一起考）：

| | 熔断 | 降级 |
|---|---|---|
| 服务状态 | 完全不提供 | 有损提供 |
| 适用 | 写服务、想快速降负载 | 读服务、能容忍有损 |
| 共同点 | 都要判定服务健康、都要考虑恢复时的**抖动** | 同左 |
| 选择原则 | 优先降级；降不了（写服务）或要快速卸负载才熔断 | 同左 |

**降级的两大类做法**：

1. **跨服务降级**（粗暴）：整个服务停掉（大促停退款）；停部分节点挪作他用；停止访问某些资源（不重要服务停止上传日志）
2. **本服务有损**：返回默认值；禁用/降采样可观测组件（埋点）；同步转异步；简化流程（非关键步骤不执行或异步执行，如新内容暂缓推送推荐系统）

**两个亮点方案**：

- **读写服务降级写服务**：B 端写（商家录入）+ C 端读（用户浏览）合并部署 → 读 RT 超阈值时停掉 B 端写服务，资源全给 C 端。附加论据：**一次写对 DB 的压力远大于一次读**。推广：内容平台停作者端；普通/VIP 用户只保 VIP。业务价值怎么定？问产品经理/看营收（关键词"赚钱"），**唯一例外是合规**（内容审核不赚钱也绝不敢降）
- **快慢路径降级慢路径**：缓存-DB 结构，触发降级后**只查缓存，未命中直接返回错误**，不回源 DB。逻辑：未命中回源的少数请求会占据大部分系统资源，砍掉慢路径后性能瓶颈只取决于 Redis，QPS 上限大幅提高。推广：慢路径=DB 查询/多服务调用+复杂计算；任何下游崩溃都自动切成"不再调用该下游"的有损模式

**跨节点亮点（刷框架理解深度）**：跨服务降级只能降同节点上的服务；跨节点（停 B 的部分节点、腾出来部署 A）理论上网关可以做，但**大部分网关和微服务框架都没实现**——说这句能显示你研究过框架的边界。

**评论区高价值补充（作者确认）**：
- 三者关系正解：**可用性是目的，限流是手段，被限流的请求可以被熔断或降级**（作者原话）
- 降级代码落在哪：中间件（middleware/filter）负责判断+**标记降级请求**，业务代码根据标记走降级分支；通用降级（返回默认值）可纯配置化——自研一套通用降级机制本身是亮点
- 降级恢复：经验值等待 + **试探恢复**（放一两个请求不走降级逻辑，正常则逐步放量，类似熔断半开）
- 写服务内部降级：写多数据源可降级为"只同步写最重要的，其余异步/事后数据修复工具补偿"；埋点类数据可直接弃写
- 同步转异步算降级（作者倾向）

## 二、Q&A（问题 + 标准答案）

### Q1：什么是降级？和熔断有什么区别和联系？

降级是提供有损服务，熔断是完全不提供服务。两者都要解决"如何判定不健康"和"如何恢复（防抖动）"。选择原则：**优先考虑降级**；写服务无法降级（降了等于丢数据），想让系统负载快速下降时熔断更干脆。举例：第三方短信平台挂了，短信服务可降级（返回明确错误码+引导）也可熔断；订单库挂了，订单服务**只能熔断**——写路径没有有损方案。

### Q2：跨服务降级有哪些手段？

整个服务停掉（大促停退款）；停掉部分节点挪作他用；停止访问某些资源（日志压力大时让不重要服务停止上传、只存本地）。要点：必须明确服务间的业务价值排序。

### Q3：本服务有损降级有哪些手段？

返回默认值；禁用或降采样埋点/指标采集；同步转异步（先回"已接收"，后台线程或定时任务再处理）；简化流程（非关键步骤砍掉或异步，如新内容暂缓推送推荐系统）。

### Q4：读写服务降级写服务，案例怎么讲？

骨架：服务合并部署两类接口（B 端商家录入 = 写，C 端用户浏览 = 读）；读 QPS 高、重要性强；当 C 端 RT 超阈值，自动停掉 B 端写接口，资源全给 C 端；C 端恢复后自动恢复 B 端。加分论据：写请求对 DB 压力远大于读（锁、redo/undo、binlog），停写能显著给 DB 减负。变种：作者端/C 端、普通用户/VIP。

### Q5：快慢路径降级，为什么"只查缓存"能救命？

缓存-DB 结构中，未命中回源的请求是慢路径：**极少数慢路径请求会占据大部分系统资源**（连接、线程被长时间占住），整体吞吐被拖垮（与 Redis 02 篇"偶发慢查询"同理）。触发降级后只走快路径（查缓存），未命中直接返回错误，性能瓶颈就只取决于 Redis 的 QPS 上限，高得多。代价：部分请求拿到失败响应——有损但保活。

### Q6：怎么判定一个服务的业务价值？

最简单：问产品经理；或按公司营收来源定——**越能赚钱越重要**。唯一例外是**合规类**（内容审核是纯成本也绝不敢降级，降了等着被请喝茶）。引申原则：B/C 合并部署降级 B 端；付费/非付费降级非付费；同节点服务分三六九等，降级从不重要的开始。

### Q7：降级在工程上怎么落地？

三层配合：
1. **判断层**：中间件（框架 middleware/filter）按规则（RT/错误率阈值，或开关）判断
2. **标记层**：把请求标记为"降级请求"向下传递
3. **执行层**：业务代码读标记走降级分支——正常逻辑和降级逻辑必然是你自己写的
通用的部分（如返回默认值）可以做成纯配置。降级开关放配置中心（Nacos/Apollo）统一推送；大促前把降级预案做成清单并演练。

### Q8：降级后怎么恢复？怎么防抖动？

与熔断恢复同源：先等一个经验时长，然后**试探恢复**——放少量请求不走降级逻辑，能正常响应就逐步放量，不行就继续等。试探可细化为"每秒放一个请求"。核心话术：**任何故障处理都要考虑恢复策略会不会引起抖动**。

### Q9：思考题——写服务内部能降级吗？写多个数据源能降级为只写一个吗？

可以，看业务容忍度：正常同步写全部数据源，降级后**只同步写最重要的**（如 MySQL），其余（如 ES）转异步写入，或干脆暂停、靠事后**数据修复工具**对账补齐。埋点/观测类数据可直接弃写。更细的玩法：写接口按重要度再分级——大促停掉商家大部分写接口，但**保留改价和商品下架**（出 BUG 价时商家能即时止损）。

### Q10：思考题——限流、熔断、降级三者什么关系？

作者钦定口径：**可用性是目的，限流是手段，被限流的请求可以被熔断或降级**。三兄弟常一起回答"如何提高可用性/负载很高怎么办/下游崩了怎么办"这三类问题。形象记忆（评论区饭馆比喻）：熔断=关门谢客，限流=排队等位，降级=热门菜卖完了给您上个平替。

## 三、简历可用案例

> ⚠️ 替换业务背景与数字；亮点方案的追问点（触发阈值、恢复策略、业务价值排序）要能自圆其说。

### 专业技能栏（可加 1 条）

- 具备高可用体系化治理能力，综合运用熔断、降级、隔离等手段：落地过 B/C 端合并部署下的写服务降级、缓存-DB 结构的快慢路径降级，熟悉降级开关、试探恢复与防抖动设计

### 项目经历栏·案例一：读写服务降级写服务

**版本 A（简洁版，一行）**
- 设计 B/C 端合并部署服务的降级方案：C 端读接口 RT 超阈值时自动降级 B 端商家写接口，资源倾斜读路径，数据库写压力同步释放；RT 恢复后试探性自动回切，大促期间核心读路径零故障

**版本 B（详细版，供面试口述）**
> 我维护的服务同时提供两类接口：B 端商家录入门店资料（写）和 C 端用户浏览门店首页（读），合并部署。C 端读 QPS 高出一个数量级且直接面向用户。我接入了跨服务降级：当 C 端接口响应时间超阈值，自动停掉 B 端写接口，把机器资源和数据库写能力全让给 C 端——一次写对 DB 的压力远大于一次读，停写后 DB 负载明显缓解。B 端商家这段时间不能改资料，业务上可以接受；C 端 RT 恢复正常后，按试探恢复策略逐步放流回切 B 端。这套方案本质是服务按业务价值分三六九等：B/C 合并部署降 B 端、付费非付费降非付费，唯一不敢碰的是合规类服务。

### 项目经历栏·案例二：快慢路径降级慢路径

**版本 A（简洁版，一行）**
- 落地缓存-DB 结构的降级保护：高并发或下游异常时触发降级，请求只查缓存不回源 DB，未命中快速失败，防止少数慢路径请求耗尽线程与连接资源拖垮全站，核心查询吞吐提升数倍

**版本 B（详细版，供面试口述）**
> 我们的查询链路是典型的缓存-DB 结构：先查 Redis，未命中回源 DB。高并发时我发现一个隐患：极少数缓存未命中的请求会占据大部分系统资源——它们长时间占着线程和 DB 连接，导致整体吞吐下降、RT 飙升。我设计了快慢路径降级：框架层检测到并发/RT 触发阈值后，把请求标记为降级请求，降级请求只走快路径（查缓存），未命中直接返回明确错误码，不再回源。这样性能瓶颈只取决于 Redis 的承载能力，核心查询在高并发下依然稳定。这个思路可以推广：任何服务能分出快路径（缓存）和慢路径（DB/多服务调用+复杂计算）的，降级时砍掉慢路径就能保住有损服务。后续所有关键服务我都配了类似的下游崩溃自动降级。

## 四、面试官连环追问清单（含参考答案）

### Q1：降级和熔断只能选一个时怎么选？

看两点：**能不能有损**（读服务可降级，写服务降不了只能熔断）、**要不要快速卸负载**（熔断立刻归零，降级仍消耗部分资源）。答题模板："原则上优先降级，因为还保持着有损服务；但写服务无法降级，且需要负载快速下降时熔断优于降级。"

### Q2：降级方案里"同步转异步"算降级还是熔断？

算降级（作者观点）：请求仍被接受并返回"已接收"，只是处理延后——提供了有损但确定的服务。熔断是当场拒绝。注意转异步要看业务：对实时性无要求的（通知、埋点）可以转；交易主链路慎用。

### Q3：降级的触发方式有哪些？

手动（大促预案，运维/值班推开关）；自动（RT/错误率/QPS 超阈值，框架或 Agent 触发）。工程上：开关放配置中心秒级推送；自动触发要配** hysteresis（迟滞）**，避免阈值线附近反复横跳——这也是抖动的一种。

### Q4：跨服务降级的粒度只能到"同节点"吗？跨节点怎么办？

文章观点：大部分网关/微服务框架只支持本服务降级，跨节点的"停 B 节点部署 A"需要手工。**云原生答案（补充加分）**：这本质上是资源调度问题——K8s 的 **Pod Priority & Preemption（优先级抢占）** 就是它的产品化：给核心服务 Pod 高优先级，资源不足时调度器驱逐低优先级 Pod（=降级 B），把节点腾给核心服务（=扩容 A）。能把文章的"理论设想"对接到 K8s 落地机制，是架构师级别的回答。

### Q5：为什么说"极少数慢路径请求会占据大部分资源"？

慢路径请求 RT 是快路径的 10~100 倍（缓存 1ms vs DB 回源+计算 100ms），在固定线程池/连接池模型下，**占用时长 = 资源占用**。假设 5% 请求走慢路径，它们占用的线程时间可能超过 50%——排队效应放大后就是全站变慢。这是排队论直觉，和 Redis 偶发慢查询、MySQL 慢 SQL 堆积是同一类病。

### Q6：降级方案和隔离是什么关系？（联动 06 讲和 02 讲负载均衡）

隔离是**事先分好**资源（VIP 独立集群、大客户专属节点、线程池隔离），降级是**事中做减法**（砍掉不重要的）。两者配合：隔离保证坏人影响不到好人，降级保证资源不够时先牺牲谁。答题时主动串联，体现体系化。

### Q7：降级恢复时发生抖动，实际长什么样？

症状：恢复信号发出 → 流量瞬间全量回切 → 刚恢复的服务/DB 还没暖（缓存冷、连接池未建立、JIT 未编译）→ 再次打挂 → 又降级 → 循环。对策：试探恢复 + **灰度放量**（1%→10%→50%→100%）+ 预热。这套话术同样适用于熔断恢复和发布后验证。

### Q8：哪些服务"给多少钱都不能降"？

合规类（内容审核、风控反欺诈——不赚钱但降了要出大事）；资损类（支付、清结算核心写路径——宁可熔断返回明确错误，不能有损写入）；数据一致性底线类（库存扣减——降级超卖比不可用更可怕）。分类逻辑：**降级的代价是否可逆、可补偿**。

## 五、专题深挖：降级预案体系（架构师视角的补全）

文章讲了单点方案，架构师面试更常被问"你们大促的降级体系怎么建的"。一张清单：

```
事前：
├── 服务分级：P0（交易主链路）/P1/P2/P3，明确每一级的降级顺序
├── 降级开关矩阵：每个开关 = 影响面 + 回滚方式 + 负责人，配置中心统一管理
├── 预案演练：大促前真实推开关验证（别让它成为从来没按过的按钮）
事中：
├── 自动触发：RT/错误率/水位阈值 + 迟滞区间防抖动
├── 手动兜底：值班室一键降级面板
└── 观察：降级率本身是核心监控指标（降级比例过高 = 容量规划失职）
事后：
└── 复盘：哪些降级被触发、是否有该降没降的、开关是否及时回切
```

**一句话收口**：单点降级方案是术，服务分级 + 预案体系是道；面试官问"大促怎么保障"时，先讲体系再讲两个亮点方案做实例，层次感就出来了。
