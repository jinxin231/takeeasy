## 一、文章总结

**核心框架**：服务注册与发现模型很简单，**三角形模型**——三个顶点（客户端、注册中心、服务端），三条边（客户端-注册中心、注册中心-服务端、客户端-服务端）。所有高可用方案无非是回答：**三角形的任何一个顶点或任何一条边出问题了，该怎么办？**

**基本流程（必须背熟）**：

- 上线（正向 6 步）：服务端向注册中心注册自身信息（主要是**定位信息**）→ 注册中心与服务端保持心跳 → 客户端首次调用前向注册中心拉取可用节点列表并**本地缓存** → 客户端与注册中心保持心跳和数据同步（服务端变动时注册中心通知客户端更新）→ 客户端发起请求 → 服务端返回响应
- 下线（反向 4 步）：服务端通知注册中心准备下线 → 注册中心通知客户端 → 客户端收到后不再向该节点发请求 → 服务端**等待一段时间后**才真正下线（等待时间 ≥ 通知传播延时）

**注册数据**：定位信息是必需的，其余数据取决于微服务框架功能。例：**分组功能**——服务端注册时带上分组信息（如"VIP 节点"），客户端收到 VIP 请求就只发给 VIP 节点。

**高可用三板斧**（本文亮点所在）：

| 角度 | 关键词 | 要点 |
|---|---|---|
| 服务端崩溃检测 | 心跳 | 心跳失败 ≠ 崩溃（可能只是网络抖动）：失败立刻通知客户端停用，但**继续发心跳**；恢复则再通知可用；持续失败一段时间才认定彻底崩溃（此时无需再通知） |
| 客户端容错 | 换节点（failover） | 崩溃到客户端感知有延时（≈ 心跳间隔），期间请求会失败 → 客户端调不通就换节点重试，并把该节点**暂时挪出可用列表** |
| 注册中心选型 | AP | 注册中心选 AP 不选 CP（Eureka、Nacos AP 模式），不一致由客户端容错兜底 |

**面试准备清单**（面试前要搞清楚的数据）：
1. 公司用的注册中心中间件 + 该中间件优缺点（应对"为什么用它"）
2. 注册中心集群规模、读写 QPS、机器性能（CPU/内存）
3. 准备一个**注册中心故障排查/优化案例**（聊注意事项和 Bug 时用）
4. 公司没用微服务的话，自学 ZooKeeper / Nacos / etcd 其一，面试时也能讲出深度

**补充知识（文章未提，面试加分）**：
- **Eureka 自我保护机制**：15 分钟内心跳续约成功率低于 85% 时进入保护模式，不再剔除任何实例——防止网络分区时大规模误杀，是 AP 思想的极致体现
- **Nacos 双模式**：临时实例走 AP（Distro 协议），持久实例走 CP（Raft），可按服务粒度选择
- **推拉模型差异**：Eureka 客户端定时拉取 + 服务端多级缓存（有延时）；Nacos 2.x gRPC 长连接推送；ZooKeeper watch 一次性通知（触发后需重新注册 watch）
- **ZooKeeper 做注册中心的硬伤**：master 选举期间集群不可用（CP 的代价）；watch 是 Pull 模式的推，事件不保证可达

**面试策略要点**：
1. 基本模型人人会背，**亮点在高可用三角度**——主动用"整个模型比较简单，不过实践中做到高可用很不容易"来钓面试官追问
2. 回答善用**关键词**串场：注册数据 → 分组 → 心跳 → 换节点 → 客户端容错 → 体量小
3. 话题引导：面试官问 ZK/etcd/Nacos 任一中间件，主动提到自己用它做注册中心；问微服务高可用，把注册与发现作为高可用的一个环节讲
4. 公司用 CP 注册中心（如 ZK）时的标准话术：**"体量小"**——集群规模不大时 CP 也够用，但自己在推动迁移 Nacos AP 模式

## 二、Q&A（问题 + 标准答案）

### Q1：讲讲服务注册与发现的基本模型？

**三角形模型**：客户端、注册中心、服务端三个顶点，三条边。
- 上线：服务端启动注册定位信息（IP+端口）→ 与注册中心保持心跳 → 客户端调用前先拉取可用节点列表并本地缓存 → 客户端与注册中心保持数据同步 → 发起调用
- 下线：服务端通知注册中心 → 注册中心通知客户端 → 客户端停止向该节点发请求 → 服务端等待一段时间（覆盖通知延时）后真正下线
- 收尾话术："模型比较简单，但实践中做到高可用很不容易"——钓面试官追问

### Q2：服务端突然宕机（来不及通知注册中心），会发生什么？怎么解决？

- 问题：宕机无法走正常下线流程，注册中心不知情，客户端继续把请求打到死节点上，全部失败
- 解决：**心跳检测**。注册中心与服务端保持心跳，心跳失败即怀疑崩溃
- 但心跳失败 ≠ 崩溃（网络抖动也会失败），两难困境：判快了误杀活节点，判慢了死节点继续吃请求
- 正确策略：心跳一失败**立刻通知客户端停用该节点**（宁可错杀，保护请求）；同时**继续发心跳**——恢复则通知客户端该节点可用；持续失败一段时间后才认定彻底崩溃（此时不用再通知，之前已通知过）

### Q3：心跳失败了要不要重试？立刻重试还是间隔重试？

- 不重试直接判崩溃 → 处理不了偶发性网络不通（误杀）
- 重试 N 次、每次间隔 10s → 判定时间太长（3 次 × 10s = 30s），期间成千上万请求打到死节点
- 不加间隔连续重试 → 避不开抖动（第一次失败时网络大概率还没恢复，立刻重试多半还是失败）
- **最佳实践：先立刻重试几次，都失败再间隔一段时间重试**。所有重试机制都要谨慎设计次数和间隔，确保在业务可接受范围内重试成功
- 升华：所有带心跳的分布式系统，判断节点崩溃都是这个棘手问题

### Q4：从服务端崩溃到客户端不再发请求，这段延时怎么算？

```
最坏延时 = 服务端↔注册中心心跳间隔 + 注册中心通知客户端的时间
```
注册中心通知客户端通常在毫秒级，所以**延时 ≈ 心跳间隔**。心跳间隔就是在"发现崩溃的速度"和"心跳开销"之间做权衡。这段延时内的失败，只能靠客户端容错来兜。

### Q5：客户端容错具体怎么做？被挪出列表的节点什么时候放回去？

- 做法：调用失败后**换节点重试**（failover）；服务发现组件/负载均衡器把失败节点**暂时挪出可用列表**，短期内不再使用
- 放回时机分两种情况：
  1. **注册中心通知该节点崩溃了** → 不用主动放回，等注册中心通知恢复后更新列表即可
  2. **只是客户端↔服务端之间网络不通**（服务端和注册中心都活着）→ 客户端要**主动对该节点发心跳探测**，成功则放回；连续几次失败则认定节点崩溃，不再放回

### Q6：注册中心自己崩溃了，系统会怎样？（文章思考题）

- 已有服务的调用**不受影响**：客户端用本地缓存的节点列表继续调（这是客户端本地缓存设计的价值）
- 受影响的是**变更能力**：新实例无法注册上线、下线/扩缩容无法感知、崩溃节点无法被剔除（只能靠客户端容错换节点）
- 如果客户端长期连不上注册中心，客户端本身应该考虑**整体退出**（它已无法保证拿到正确视图）
- 所以注册中心本身必须是集群部署、高可用的——它是微服务的"咽喉"

### Q7：注册中心选型，CAP 里选 CP 还是 AP？为什么？

- **标准答案：选 AP**。注册中心数据（节点列表）不一致的后果是客户端拿到错误节点 → 调用失败 → **客户端容错换节点重试即可兜住**，代价可接受
- 反过来选 CP 的代价：网络分区/主选举期间注册中心**不可用**——新实例无法注册、变更无法下发，整个微服务体系的伸缩能力停摆，这比"列表不准"严重得多
- 落地：Eureka、Nacos（临时实例/AP 模式）
- 公司用 CP（如 ZooKeeper）的话术："体量小、集群规模不大，CP 也够用；但我在推动迁往 Nacos AP 模式"

### Q8：注册数据除了 IP 端口还有什么？

定位信息是必需的，其余取决于框架功能设计。典型例子：**分组信息**——服务端注册时声明自己是 VIP 节点/灰度节点，客户端按请求属性路由到对应分组。还可以带：权重（负载均衡用）、元数据（版本、环境、机房，用于路由和就近访问）、健康检查路径等。

## 四、面试官连环追问清单（含参考答案）

### Q1：心跳间隔怎么定？太短太长各有什么问题？

- 太长：崩溃发现慢，延时 ≈ 心跳间隔，期间请求持续打到死节点
- 太短：心跳开销大（注册中心 QPS = 节点数 / 间隔），且更容易被网络抖动误判
- 经验值：10~30s 级别常见（Eureka 默认 30s 续约、90s 剔除；Nacos 临时实例默认 5s 心跳、15s 标记不健康、30s 剔除）。结合"立刻重试几次 + 间隔重试"策略在检测速度和误判率间取平衡

### Q2：Eureka 的自我保护机制了解吗？（补充亮点，文章未提）

- 机制：15 分钟内续约成功率 < 85% 时进入自我保护，**停止剔除任何实例**
- 设计意图：宁可保留可能已死的实例，也不在**网络分区**时大规模误杀健康实例——AP 思想的极致体现
- 代价：分区期间客户端可能拿到死节点 → 靠客户端容错（重试 + Ribbon 换节点）兜底，形成完整闭环
- 防坑：自我保护不是 Bug 是 feature，生产环境不建议关闭

### Q3：Nacos 的 AP 和 CP 是怎么共存的？

- **临时实例（默认）走 AP**：Distro 协议，节点间异步同步，可接受短暂不一致；靠客户端心跳（默认 5s）维持，超时剔除
- **持久实例走 CP**：基于 Raft，数据强一致，适合数据库等有状态服务的注册
- 按服务粒度选择（`ephemeral=true/false`），这是 Nacos 相比 Eureka（纯 AP）、ZK（纯 CP）的差异化优势

### Q4：ZooKeeper 做注册中心有什么坑？（应对"我司用的是 ZK"）

- **CP 硬伤**：Leader 选举期间（数十秒）集群不可读不可写——注册中心不可用意味着无法注册新实例、无法感知变更
- **watch 不可靠**：watch 是一次性的（触发后需重新注册），且事件不保证 100% 送达（会话超时边界），客户端必须配合定时全量拉取兜底
- **不适合超大规模**：写走 Leader、全量数据内存存储，节点数十几万级时压力明显
- 话术收尾：所以体量小可以用，体量大了应该换 AP 模型

### Q5：优雅下线为什么要"等待一段时间"？等多久合适？

- 链路：服务端通知注册中心下线 → 注册中心通知客户端 → 客户端更新本地列表。通知传播有延时，期间仍有客户端把请求打过来
- 等待时间 ≥ 传播延时（≈ 注册中心通知客户端的时间 + 客户端刷新周期，毫秒到秒级；拉模式注册中心如 Eureka 要按客户端拉取周期 30s 来算，所以 Eureka 体系优雅下线更难）
- 工程细节：下线前还要停掉新流量入口（如从网关/LB 摘流）、处理完在途请求（Spring Boot graceful shutdown / Dubbo 优雅停机）、关闭线程池
- 防坑：直接 kill -9 跳过整个流程，等于"崩溃"，只能靠崩溃检测 + 客户端容错兜底

### Q6：客户端缓存了节点列表，会不会用到过期的数据？怎么保证新鲜度？

- 会，这是 AP + 本地缓存的固有特性。保障机制是**推拉结合**：
  - 推：注册中心发现变更主动通知（ZK watch、Nacos gRPC 推送）
  - 拉：客户端定时全量/增量拉取兜底（Eureka 30s 拉取），防止推送丢失
- 兜底始终是客户端容错：拿到过期列表顶多调失败一次，换节点重试即可——再次回到"客户端容错是 AP 体系的最后防线"
