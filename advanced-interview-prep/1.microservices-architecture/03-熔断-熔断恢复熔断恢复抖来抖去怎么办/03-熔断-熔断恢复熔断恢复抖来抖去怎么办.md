# 面经总结 03：熔断——熔断-恢复-熔断-恢复，抖来抖去怎么办？

> 来源：极客时间《后端工程师的高阶面经》邓明
> 整理日期：2026-11-04

---

## 一、文章总结

**核心定义**：熔断 = 微服务出问题时**拒绝新请求，直到服务恢复**。为什么"拒绝请求"反而提高可用性？因为熔断**给服务端喘息和恢复的机会**——如 CPU 100% 时拒绝新请求，已接收的处理完，负载自然降下来。

**两个基本问题**（所有熔断方案的骨架）：

| 问题 | 要点 |
|---|---|
| 怎么判断服务出问题了？ | 选指标（响应时间/错误率）→ 定**阈值**（业务要求，或观测 99 线 + 余量）→ 要求**持续超过阈值一段时间**（防偶发、防抖动） |
| 怎么知道服务恢复了？ | 微服务框架普遍做得差：熔断后保持固定时间（如 1 分钟）就认为恢复、直接放全量流量 → **抖动的温床** |

**抖动问题**（本文题眼）：服务在正常-熔断两个状态间频繁切换。
- 成因：超阈值立刻熔断（太敏感）；恢复时直接放 100% 流量（高并发还在，马上又熔断）
- 解法（服务端侧）：恢复后**逐步放量**：10% → 20% → 30%……而不是立刻 100%
- 缺陷：服务端还是收到 100% 流量，只是部分被丢弃——于是引出亮点方案

**亮点方案：熔断 + 负载均衡（客户端控制流量）**：
1. 服务端触发熔断时**返回代表熔断的错误**
2. 客户端收到熔断错误 → 把该节点**暂时挪出可用节点列表**，新请求不再打过来
3. 等待一段时间 → 逐步放开流量（发少量请求试探）
4. 正常处理 → 加大流量；再次返回熔断 → 再次摘除，再等
5. 循环直到完全恢复

**微创新方案：缓存崩溃熔断**（关键词）：
- 高并发接口重度依赖缓存：Redis 崩溃 → 触发熔断，保护 MySQL 不被打垮
- 恢复探测：额外开线程持续 ping Redis，恢复则退出熔断
- 可迁移：Redis 可换成任何关键第三方依赖

**面试准备清单**：
1. 公司有没有用熔断？怎么判断故障（指标）？怎么判断恢复？有没有防抖动措施？
2. 最佳策略：熔断作为**高可用微服务架构的一环**来讲（限流、降级、隔离同理）
3. 话题引导：被问限流/降级/服务崩溃怎么办，都可以引到熔断

**补充知识（文章未提，面试加分）**：
- **熔断器三态模型**（Resilience4j/Sentinel/Hystrix 通用）：CLOSED（正常）→ OPEN（熔断，快速失败）→ **HALF_OPEN（半开，放少量试探请求）** → 成功回 CLOSED，失败回 OPEN。文章的"逐步放量"就是 HALF_OPEN 的工程化表达
- **慢调用比例熔断**（Sentinel）：比"绝对响应时间"更精细——RT 超过阈值且**比例**超标才熔断，避免个别慢请求误触发
- **错误率 vs 错误数**：低流量服务用错误数，高流量用比例，防止小流量抖动误触发
- 恢复探测的工业实现：Sentinel 半开自动试探；文章的"后台线程 ping Redis"本质是**主动健康探测**，比被动等试探请求更快更准

## 二、Q&A（问题 + 标准答案）

### Q1：什么是熔断？为什么返回错误还能提高可用性？

服务出问题时拒绝新请求，直到恢复。核心逻辑：给服务端**恢复的机会**——服务过载（如 CPU 100%）时，拒绝新请求后已接收的请求处理完，负载降下来，服务才能恢复。不放任请求堆积是把"慢性死亡"变成"快速失败 + 快速恢复"。

### Q2：怎么判断微服务出了问题？

三件事：
1. **选指标**：响应时间、错误率最常用（本质和负载均衡动态算法一样，选代表健康度的指标）
2. **定阈值**：业务有明确要求按业务（如要求 1s 内 → 阈值 1s 或稍高留余地）；没有要求按观测数据——99 线是 1s，阈值定 1.2s（**明显超过正常响应时间**）
3. **持续一段时间才触发**（如持续 30s）：防偶发性 RT 突增，防抖动。过短会频繁熔断-恢复循环，过长会迟迟不熔断——具体值靠经验，30s~1min 常见

### Q3：为什么阈值要比业务要求多加 0.2s 余量？

防偶发性响应时间变长（GC、网络抖动等瞬时因素）。阈值卡死业务线 = 把正常波动误判成故障，会频繁误熔断。原则：**阈值应明显超过正常响应时间**。

### Q4：熔断之后怎么判断服务恢复了？框架做得如何？

微服务框架普遍做得**比较差**：熔断后保持固定时间（如 1 分钟）就认为恢复，直接放全量流量。这种做法是抖动的主要来源——如果熔断是高并发引起的，1 分钟后高并发还在，流量瞬间打满，服务立刻再次熔断，进入熔断-恢复-熔断循环。

### Q5：什么是抖动？怎么解决？

抖动 = 服务在正常和熔断状态间频繁切换。解法：**恢复时逐步放量**（10%→20%→30%……）而不是直接 100%。但服务端侧放量有缺陷：服务端仍收到 100% 流量，只是部分被丢弃——更优解是让客户端控制流量（见亮点方案）。

> 逐步放量的四种实现机制（概率闸门/令牌桶预热/动态权重/半开试探）及 Sentinel、Dubbo 上的具体落地，见文末"五、专题深挖"。

### Q6：熔断 + 负载均衡的综合方案是什么？（核心亮点）

让客户端接管流量控制：
1. 服务端触发熔断 → 返回**熔断错误**
2. 客户端收到 → 负载均衡层面**把该节点暂时摘除**，请求全发其他节点
3. 等待一段时间 → 发少量请求试探
4. 成功 → 逐步加大流量（结合"按调用结果调权重"的负载均衡策略）；再次熔断 → 再次摘除、再等
5. 循环直至完全恢复

优势：熔断节点不再承受任何流量（服务端侧放量方案还扛着 100% 流量），恢复更快更稳。与负载均衡讲的"根据调用结果动态调权重"一脉相承。

### Q7：如果所有节点都触发熔断了怎么办？

**熔断和负载均衡都解决不了**——比如根因是数据库出问题，所有节点熔断后客户端无可用节点。此时只能兜底：监控告警 + 人工介入。面试时主动"自己杠自己"提这个边界，反而加分。

### Q8：缓存崩溃熔断方案怎么讲？（微创新）

> 我的一个接口并发很高、重度依赖缓存。熔断策略是：Redis 崩溃就触发熔断——不熔断的话请求全部穿透到 MySQL，会压垮数据库。触发熔断后，我额外开一个线程持续 ping Redis，Redis 恢复则退出熔断、接收新请求。

留好的话题钩子：缓存失效 → 引导到缓存穿透/击穿/雪崩；熔断保护 MySQL → 引导到限流保护 MySQL；退出熔断 → 被追问"一次性放全量吗"→ 讲抖动和逐步放量 → 引出亮点方案（负载均衡配合）。

**版本 A（简洁版，一行）**
- 为核心微服务建立熔断体系：按业务 SLA 与 99 线观测数据设定响应时间阈值（99 线 1s → 阈值 1.2s，持续 30s 触发），恢复期采用逐步放量防止抖动，上线后服务过载场景的平均恢复时间显著缩短，未再发生雪崩式故障

**版本 B（详细版，供面试口述）**
> 为了保障微服务可用性，我在核心服务里接入了熔断，针对不同服务设计了不同策略。以最常用的响应时间策略为例：阈值根据业务定——产品经理要求 1s 内响应，我把熔断阈值设在 1.2s，多留 0.2s 余量防偶发抖动；响应时间超过 1.2s 且持续 30 秒才触发熔断，防止瞬时波动误触发。触发后新请求被拒绝，已有请求继续处理，给服务恢复的机会。恢复时不一次性放全量流量，而是逐步放量，防止高并发场景下反复熔断的抖动问题。

### 项目经历栏·案例二：缓存依赖熔断 + 客户端流量控制

**版本 A（简洁版，一行）**
- 设计"缓存崩溃熔断"保护数据库：高并发接口在 Redis 不可用时触发熔断，后台线程持续探测 Redis 恢复后自动退出；进一步落地"熔断 + 负载均衡"方案——客户端识别熔断错误后将节点摘除并按调用结果逐步放量，避免服务端恢复期再被打垮

**版本 B（详细版，供面试口述）**
> 我有个高并发接口重度依赖缓存，如果 Redis 崩溃，所有请求会穿透到 MySQL，基本会压垮数据库。所以我设计了缓存崩溃熔断：Redis 不可用就触发熔断快速失败，同时开一个后台线程持续 ping Redis，恢复后退出熔断。但这还不够——恢复期直接放全量流量会引起抖动。所以我进一步把熔断和负载均衡结合：服务端触发熔断时返回特定错误码，客户端收到后把这个节点暂时挪出可用节点列表，等待一段时间后发少量请求试探，成功就加大流量，再次熔断就再次摘除，直到完全恢复。当然这个方案有边界：如果是数据库本身出问题导致所有节点熔断，就只能监控告警人工介入了。

## 四、面试官连环追问清单（含参考答案）

### Q1：熔断和降级有什么区别？（经典混淆题）

- **触发主体**：熔断是**被动**的——服务/依赖出问题自动触发；降级是**主动**的——人为或按计划牺牲非核心功能（如大促关掉退款、评论）
- **目的**：熔断保护被调用方（给它恢复机会）；降级保护系统整体资源（集中力量保核心链路）
- **联系**：熔断触发后通常配一个降级逻辑做兜底（返回默认值/缓存/友好提示），所以熔断器框架里两者常一起出现。一句话：**降级可以是熔断的 fallback，但降级不等于熔断**

### Q2：熔断和限流有什么区别？

- **触发条件**：限流是流量超过**预设容量阈值**（QPS/并发数），服务可能还很健康；熔断是服务**已经出了问题**（慢、错、依赖挂）
- **目的**：限流防止"被流量打死"（事前防御）；熔断防止"被故障拖死"（事中止损）
- **配合**：限流在前挡住超容量流量，熔断在后隔离故障节点，降级做兜底——高可用三件套

### Q3：工业界熔断器是怎么实现恢复的？（三态模型）

CLOSED →（指标超标）→ OPEN（快速失败）→（冷却时间到）→ **HALF_OPEN**（放 1~N 个试探请求）→ 成功回 CLOSED，失败回 OPEN 重新计时。文章的"逐步放量"就是 HALF_OPEN 思想的工程化；文章的亮点方案更进一步，把试探和放量决策从服务端挪到了**客户端负载均衡层**。常见实现：Resilience4j（轻量、函数式）、Sentinel（阿里，带控制台、规则热更新）、Hystrix（已停止维护，选型时别再用）。

### Q4：个别慢请求会不会误触发熔断？怎么防？

- 用**比例 + 最小请求数**双重条件：如"1 分钟内请求数 > 100 且慢调用比例 > 50%"才熔断（Sentinel 慢调用比例策略）——低流量时几个慢请求不会触发
- 阈值明显超过正常水位（99 线 + 余量），不用平均值（平均值会被长尾拉高/拉低，误判）
- 持续一段时间才触发，防瞬时尖刺

### Q5：客户端摘除节点，和注册中心摘除有什么区别？会冲突吗？

- 注册中心摘除是**全局视角**（控制面）：节点对所有客户端不可见，传播有延时（见 01 讲）
- 客户端摘除是**本地视角**（数据面）：只影响自己，立即生效——熔断场景下更快更准，因为"这个节点对我熔断了"可能只对我成立
- 不冲突，是两层防御：客户端先本地摘除止血；如果节点真的崩了，注册中心心跳检测后会全局摘除，客户端再同步列表（三角形模型的又一次闭环）

### Q6：熔断期间被拒绝的请求去哪了？

需要**兜底（fallback）策略**，按业务选：
- 返回默认值/静态数据（推荐、个性化场景）
- 返回本地缓存/快照数据（可容忍旧数据）
- 写 MQ 异步补处理（写场景）
- 直接快速失败返回友好错误（无兜底价值的场景）
面试防坑：只说"拒绝请求"不提兜底，会被认为方案不完整——熔断是止损，兜底是用户体验。

### Q7：恢复时一次性放开全部流量会怎样？

高并发引起的熔断，恢复瞬间高并发还在 → 全量流量立刻把服务再次打垮 → 熔断 → 恢复 → 再熔断，形成**抖动**。服务在反复切换中完全无法恢复，还浪费资源处理"注定被拒绝"的请求。所以必须逐步放量（服务端侧）或客户端试探放量（亮点方案）。

### Q8："后台线程 ping Redis"这种主动探测，和被动等试探请求比，优劣？

- 优势：**更快**——不依赖业务流量触发试探，依赖恢复的瞬间就能感知并退出熔断；**更准**——探测的是依赖本身，不受业务请求随机性影响
- 代价：额外线程/连接开销；探测协议要自己维护（ping 通 ≠ 依赖完全可用，可能网络通了但 Redis 还在加载数据）
- 工业界对应：Nacos 的主动健康检查、Envoy 的 outlier detection + active health check，思想一致

## 五、专题深挖：逐步放量怎么实现 + Sentinel/Dubbo 落地

> 文章只说"恢复后逐步放量 10%→20%→30%"，落地时分两层问题：**放量的机制**是什么，以及**在你们的技术栈（Sentinel + Dubbo）上怎么挂**。

### 1. 四种放量机制（从简到繁）

| 机制 | 原理 | 代表实现 |
|---|---|---|
| 概率闸门 | 每请求按当前比例随机放行，定时任务上调比例（大数定律保证整体流量=比例） | 自研最简单方案 |
| 令牌桶预热 | 速率上限从低水位线性爬升 | Guava `RateLimiter(warmUp)`、Sentinel **WarmUp** 规则 |
| 动态权重 | 恢复节点从小权重开始爬坡，加权负载均衡天然分配少量流量 | **Nginx `slow_start`**、Envoy slow start、Dubbo 动态权重 |
| 半开试探 | 只放 1~N 个试探请求，成功即全量（两档，最粗糙） | Sentinel / Resilience4j HALF_OPEN |

概率闸门示例代码（自研时参考）：

```java
public class GradualRecoveryGate {
    private final AtomicInteger ratio = new AtomicInteger(10); // 当前放行比例 %
    public void startRecovery() {
        ratio.set(10);
        scheduler.scheduleAtFixedRate(() -> {          // 每 10s 提一档至 100%
            int cur = ratio.get();
            if (cur < 100) ratio.set(Math.min(100, cur + 10));
        }, 10, 10, TimeUnit.SECONDS);
    }
    public boolean allow() {
        return ratio.get() >= 100
            || ThreadLocalRandom.current().nextInt(100) < ratio.get();
    }
}
```

### 2. Sentinel 现状：半开只有两档，没有多档爬坡

项目已用 Sentinel 时要清楚它的**真实恢复行为**（面试实证素材）：

```
DegradeRule 熔断触发 → timeWindow（如 60s）内全部快速失败
  → 时长结束进入 HALF_OPEN：放【1 个】试探请求
      → 成功 → CLOSED 直接全量恢复（没有 10%→20% 爬坡！）
      → 失败 → 重新 OPEN
```

典型配置：

```java
DegradeRule rule = new DegradeRule("resourceName")
    .setGrade(RuleConstant.DEGRADE_GRADE_RT)   // 慢调用比例
    .setCount(1200)                            // RT 阈值 1.2s = 99线1s + 0.2s 余量
    .setTimeWindow(60)                         // 熔断时长
    .setSlowRatioThreshold(0.5)                // 慢调用比例超 50% 才熔断
    .setMinRequestAmount(100);                 // 最小请求数，防低流量误触发
```

**补齐逐步放量的两条路**：
- **路线 A：FlowRule 配 WarmUp**（先试这个）——`setControlBehavior(CONTROL_BEHAVIOR_WARM_UP).setWarmUpPeriodSec(60)`，流量从 `QPS/coldFactor(默认3)` 线性爬升；本为冷启动设计，与熔断恢复同构
- **路线 B：DegradeRule + WarmUp 叠加在同一资源上**——熔断器管"好了没"（半开试探），WarmUp 管"好了之后慢慢放"，组合出"试探 + 爬坡"，不用自己写概率闸门

落地动作：grep 项目现有 `DegradeRule`/`FlowRule`/`@SentinelResource` 配置（面试清单第一项），测试环境加 WarmUp 压测观察 QPS/RT 曲线。

### 3. Dubbo 落地：不改框架源码，走 SPI 扩展点

"客户端收到熔断错误 → 摘除节点"在 Dubbo 上的正确姿势是**写两个扩展插件**，框架源码一行不动：

```
感知层：Filter 扩展      → 拦截响应，识别熔断错误，标记节点状态
决策层：LoadBalance 扩展 → 选节点时跳过熔断节点，恢复期权重爬坡
```

**Filter（消费端激活）**：

```java
@Activate(group = CommonConstants.CONSUMER)
public class CircuitBreakerFilter implements Filter {
    @Override
    public Result invoke(Invoker<?> invoker, Invocation invocation) throws RpcException {
        Result result = invoker.invoke(invocation);
        if (isCircuitBreakerError(result)) {            // 识别服务端熔断错误码/BlockException
            NodeStateManager.markBroken(invoker.getUrl());
        } else if (!result.hasException()) {
            NodeStateManager.reportSuccess(invoker.getUrl());  // 成功 → 权重爬坡（成加败减）
        }
        return result;
    }
}
```

**LoadBalance（摘除 + 权重爬坡）**：

```java
public class BreakerAwareLoadBalance extends AbstractLoadBalance {
    @Override
    protected <T> Invoker<T> doSelect(List<Invoker<T>> invokers, URL url, Invocation inv) {
        List<Invoker<T>> alive = invokers.stream()
                .filter(i -> !NodeStateManager.isBroken(i.getUrl()))
                .collect(Collectors.toList());
        if (alive.isEmpty()) {                          // 全灭兜底：告警 + 选最不坏的
            Metrics.alert("all nodes broken: " + url.getServiceKey());
            alive = invokers;
        }
        return weightedSelect(alive, inv);              // 恢复节点权重小 → 天然只分 ~10% 流量
    }
}
// 权重状态机：熔断=0（摘除）→ 等待期过=10（试探）→ 每次成功 +10 → 回到 100；再熔断归 0 重计时
```

**挂载方式（都是配置，不改源码）**：

```
META-INF/dubbo/org.apache.dubbo.rpc.Filter              内容：circuitBreaker=com.xxx.CircuitBreakerFilter
META-INF/dubbo/org.apache.dubbo.rpc.cluster.LoadBalance 内容：breakerAware=com.xxx.BreakerAwareLoadBalance
```

```yaml
dubbo:
  consumer:
    loadbalance: breakerAware
```

**动手前先查两个现成轮子**：
1. **Dubbo 3.2+ `AdaptiveLoadBalance`**：按 CPU/RT/成功率自动给慢节点降权——"根据调用结果调整节点优先级"的 80% 已内置，`dubbo.consumer.loadbalance: adaptive` 即可启用
2. **Sentinel Dubbo 适配器**（`sentinel-apache-dubbo3-adapter`）：以 Filter 形式接入，熔断抛 `BlockException`——感知层现成，只需补 LoadBalance 层

### 4. 面试话术（Dubbo + Sentinel 实战版）

> 我们用 Dubbo + Sentinel。Sentinel 的熔断恢复是半开放 1 个试探请求、成功就全量，高并发下有抖动风险。"客户端收到熔断错误摘除节点"的方案在 Dubbo 上不需要改框架源码——我写一个消费端 Filter 识别 BlockException 标记节点状态，再实现自定义 LoadBalance 过滤熔断节点、恢复期动态权重爬坡，走 Dubbo SPI 扩展点挂载。另外 Dubbo 3.2 自带的 AdaptiveLoadBalance 就是按 RT 和成功率自动降权，和我们这套是同一思路的工业化实现。

加分点：把熔断话题引到"我写过 Dubbo SPI 扩展"——SPI 机制本身是 Dubbo 面试高频题，一鱼两吃。

## 六、专题深挖：Sentinel 架构全景 + atlas-api 限流实战

> 由"熔断指标存在哪"引出的一串问题：Sentinel 怎么部署、怎么工作、Token Server 是什么、集群限流选 Redis 还是 Token Server、以及我们 atlas-api 的真实方案。

### 1. 熔断指标存在哪？（决策数据 vs 观测数据）

**决策数据在调用方进程本地内存的滑动窗口里**——熔断判定每次调用都要查、要纳秒级完成、决策只影响本进程，所以只能本地。

- Sentinel 核心结构 **LeapArray**（滑动时间窗 + 环形数组）：每个 bucket（如 500ms）记 passCount/completeCount/totalRT/exceptionCount/blockCount，调用结束按时间戳定位 bucket 用 **LongAdder 无锁累加**，判定时聚合窗口数据
- Resilience4j：时间分桶或最近 N 次环形位图；Hystrix：RollingNumber（1s 切 10 桶）；Dubbo AdaptiveLoadBalance：EWMA 指数加权移动平均（呼应 02 讲"近期请求权重高、随时间衰减"）
- **观测数据是另一条独立链路**：内存指标 → Prometheus 抓取 → TSDB → Grafana。它有时延（抓取间隔 15s），**不能做熔断判定依据**；熔断要实时性，监控要全局视角，两个需求决定两种存储

**重要推论：熔断判定是每个调用方独立进行的**。A 客户端看节点 X 错误率 60%（熔断）、B 客户端看 5%（正常）——各自统计各自内存的数据。这不是 bug 是设计：网络分区时 A→X 不通、B→X 通，本地视图恰好是对的。这也是熔断能和客户端负载均衡（本地摘除节点）天然结合的原因——**数据和决策本来就在同一个地方**。

### 2. Sentinel 怎么工作？支持哪些请求？

**核心就是 jar 包（library），嵌在业务进程里**，不需部署服务端。工作流程是"资源抽象 + ProcessorSlot 责任链插桩"：

```
Entry entry = SphU.entry("resource")     ← 插桩点
  → StatisticSlot（LeapArray 滑窗统计）
  → FlowSlot（流控判定）→ DegradeSlot（熔断判定）→ SystemSlot（系统保护）
  → 任一不过抛 BlockException 快速失败
业务执行 → entry.exit()（记录 RT/异常）
```

**协议无关**：Sentinel 是代码级组件，"支持什么请求"取决于适配器插在哪个拦截点：

| 接入方式 | 拦截点 | 效果 |
|---|---|---|
| sentinel-web-servlet | HTTP Filter | 每个 URL 成为资源 |
| Spring MVC/WebFlux/Gateway adapter | 拦截器/GatewayFilter | HTTP 接口保护 |
| sentinel-apache-dubbo3-adapter | Dubbo Filter（消费+提供端） | 每个 Dubbo 方法成为资源 |
| Feign/gRPC/RocketMQ adapter | 各自拦截点 | 对应调用保护 |
| 手写 SphU.entry() | 任意代码块 | 保护任何东西（DB 操作、Redis 调用） |

**部署形态四件套**：① sentinel-core（jar，核心）② dashboard（独立控制台，只管监控展示和规则下发，**挂了不影响运行时**）③ datasource（从 Nacos/Apollo 拉规则做持久化——默认规则只在内存，**重启就丢，生产必须接 DataSource**）④ Token Server（唯一的服务端组件，仅集群限流需要）。

### 3. Token Server 详解

**本质：一个纯内存的计数服务进程，全局滑动窗口计数器就在它内存里**——没有 DB、没有 Redis、没有持久化。

- 解决的问题：本地内存统计不了全局（"10 实例合计 QPS ≤ 1000"），集中计数必须有个"中央"
- **为什么敢用纯内存**：限流计数是瞬态数据，进程重启只是窗口重置、限流松一拍，几秒恢复，**没有正确性问题**——这个场景对持久化零需求，换来最低延迟
- 两种部署：**嵌入模式**（集群挑一台实例兼任 server，零新增组件）/ **独立模式**（专门进程，按命名空间分摊）
- 单点容错：Client 发现不可达时按配置 fail-open 或退化本地限流；对 HA 要求远低于普通服务，**用客户端降级兜底解决，而不是高可用存储**
- 对比记忆：**熔断不需要 Token Server**（调用方本地视角就是对的），只有全局配额需要它

### 4. 集群限流：Redis vs Token Server

误区纠正：Redis 分布式限流**并没有省掉网络调用**——两者都是每请求一次网络交互（Redis 走 Lua 脚本原子执行，Token Server 走 RPC 要令牌）。集中计数就意味着每次判定要问一次"中央"。

| 维度 | Redis 模式 | Token Server |
|---|---|---|
| 单次延迟 | ~0.5~1ms（网络+Redis+Lua） | 略低（纯内存、无通用协议开销） |
| 故障域隔离 | Redis 是共享设施，**缓存挂限流跟着挂** | 专用组件，挂了只影响限流，可 fail-open |
| 热点 key 风险 | 热门资源计数集中一个 key → 单 slot 热点 | 内存分散，无此问题 |
| 批量优化 | pipeline 语义受限 | Client 原生批量要令牌，交互降数量级 |
| 基础设施 | **Redis 现成，零新增组件** | 要额外部署/选主（嵌入模式可免） |

结论：性能 Token Server 略优，工程 Redis 胜在复用；成熟做法是两个后端都支持 + 本地兜底。**唯一反模式：为省网络调用退回单机限流**——多实例下总额失控。

### 5. atlas-api 真实案例：atlas-rate-limit 框架（简历级素材）

我们没用原生 Sentinel，而是自研了 `atlas-rate-limit`（atlas-common），把多种后端统一封装：

- **接入层**：`@AtlasRateLimit(group, resource)` 注解 + AOP 切面，方法级拦截、协议无关（HTTP 控制器/Dubbo 方法通用）
- **多后端可插拔**（RateLimitMode）：本地 Bucket4j 令牌桶（单机保护）/ **Redis ZSet 滑动窗口**（集群级总配额）/ Sentinel Token Server（集群限流）
- **动态规则**：Nacos 下发（`dataId=atlas-rate-limit-rules`）热更新，免改代码重启
- **兜底降级**：Redis 不可用 → `LocalFallbackRateLimiter` 退化本地限流 + 钉钉告警（10 分钟防轰炸去重）
- **监控**：ES 聚合日志
- **标准化拒绝**：HTTP 429 + `RateLimit-Limit/Reset/Retry-After` 头（RFC 风格，客户端可优雅退避）
- **多租户配额**：按 cid→clientCode 区分客户配额（B2B 刚需）
- **演进教训**：`getOfferPrice` 曾手写单机固定窗口限流器，被收编进框架——三个硬伤：单机控不住总额（QPM=配额×实例数）、固定窗口 2x 突刺、无动态配置

**面试话术**：

> 我们的 B2B 开放 API 有按客户配额的需求，我参与设计了注解式限流框架：AOP 拦截，后端可插拔——本地 Bucket4j 做单机保护，Redis 滑动窗口做集群配额，也封装过 Sentinel Token Server；规则 Nacos 热更新；Redis 故障退化本地限流并告警；被拒统一 429 + Retry-After。难点在分布式配额一致性和兜底降级。集群限流选型上，Redis 和 Token Server 都是每请求一次网络调用，差异在故障域隔离和热点 key，我们用本地兜底解决 Redis 故障的可用性。

被追问实现细节时，重点准备 `RedisZSetSlidingWindowRateLimiter`（ZSet 滑窗的 Lua 原子性、窗口边界处理）。
