# 面经总结：负载均衡——调用结果、缓存机制是怎么影响负载均衡的？

> 整理日期：2026-11-03
> 关键词（文章给出的记忆锚点）：**大请求、成加败减、上下限、可用性、应用发布**

## 一、文章总结

**核心框架**：负载均衡 = 回答"请求发给哪个节点"。算法分两类：

| 类别 | 算法 | 特点 |
|---|---|---|
| **静态**（统计学上的"最合适"） | 轮询/加权轮询、随机/加权随机、哈希/一致性哈希 | 不感知节点实时状态 |
| **动态**（实时检测） | 最少连接数、最少活跃请求数、最快响应时间 | 单指标代表负载，各有失真 |

**各算法要点与缺陷**：

| 算法 | 原理 | 缺陷/亮点 |
|---|---|---|
| 轮询/加权轮询 | 排排坐分果果；加权按权重比例 | 亮点：**平滑加权轮询**（源自 Nginx），避免高权重节点被连续命中 |
| 随机/加权随机 | 随机数选节点 | 统计上等效轮询，但可控性差（脸黑时连打同一节点） |
| 哈希 | 参数哈希值 % 节点数 | 哈希函数不均匀会倾斜；**扩缩容全部重新映射**（普通哈希的硬伤） |
| 一致性哈希 | 哈希环 + 顺时针找第一个节点 | 扩缩容只影响相邻区段；节点在环上可以不均匀；面试热点 |
| 最少连接数 | 选连接数最少的 | **连接复用时失真**——10 个请求可能复用 1 个连接 |
| 最少活跃请求数 | 选"已接收未返回"请求最少的 | 请求大小不同会失真（10 个大请求 vs 10 个小请求） |
| 最快响应时间 | 选响应时间最短的（综合性指标，最准） | 要注意**时效性**：近期请求权重高，采集值随时间衰减 |

**动态算法的共同死穴**：客户端各自采集数据，视角不全（客户端 1 不知道客户端 2 的 30 个连接）。解法：服务端随响应回传元数据，或从观测平台（Prometheus）查——但业界很少用，框架基本不支持服务端上报。

**两个亮点方案（拉开差距的关键）**：

1. **调用结果动态调权重（成加败减）**：
   - 调用成功→加权，失败→减权（"失败"指网络错误/超时等非业务失败）
   - 网络错误减多一点（问题严重），超时减少一点（容易恢复）
   - **必设上下限**：下限不为 0（永不被选中/除零），上限为初始权重 2~3 倍（防连续命中）；用 uint/int8 还要防溢出——很多公司在这里出过线上故障
   - 权重绝对值不重要（100:200 ≡ 1000:2000），但**调整步长要按比例**
   - 可引导话题到服务注册与发现（临时摘除节点本质相同，都是提高可用性）

2. **一致性哈希 + 本地缓存**：
   - 用用户 ID 做一致性哈希 → 同一用户的请求固定落到同一节点 → 本地缓存命中率高、内存不重复浪费、不一致性**缓解**
   - 注意话术：只能**缓解不能根治**——节点数量变化（最常见就是**应用发布**：先下线再上线）时，同一份数据会短暂缓存在多个节点上，可能读到旧值

**面试准备清单**：
- 搞清公司网关/Nginx、客户端负载均衡各用什么算法
- 准备一个负载均衡相关事故（没有就用文章的"大请求"案例改造）
- 有余力就用 gRPC 接入自己写的算法做实验，防现场手写

**补充（文章未提，面试加分）**：
- **一致性哈希需要虚拟节点**：文章只讲了哈希环，没提虚拟节点——物理节点少时环上分布不均会倾斜，工业实现（Memcached/Dubbo）都给每个物理节点生成 100~200 个虚拟节点再落环，详见专题深挖
- **各框架默认算法**（被问"你们用的什么"时对照）：Nginx 默认轮询（支持 ip_hash/least_conn/least_time）；Dubbo 默认**加权随机**（另有 leastactive/consistenthash）；Ribbon 默认轮询（有 WeightedResponseTimeRule）；gRPC 默认 pick_first，常用 round_robin
- 思考题评论区有价值答案，已收入 Q9/Q10

## 二、Q&A（问题 + 标准答案）

### Q1：常见的负载均衡算法有哪些？怎么分类？

静态：轮询、加权轮询（+平滑）、随机、加权随机、哈希、一致性哈希。动态：最少连接数、最少活跃请求数、最快响应时间。静态靠统计学均衡，动态靠实时指标。业界落地最多的反而是最简单的轮询/随机——花哨算法面试和晋升有用，落地不多。

### Q2：平滑加权轮询算法过程？

每个节点维护 `weight`（初始权重）和 `currentWeight`（当前权重），每轮：
1. 所有节点 `currentWeight += weight`
2. 选 `currentWeight` 最大的节点
3. 被选节点 `currentWeight -= sum(weight)`

例：A=5, B=1, C=1，一轮 7 次选择结果为 **A A B A C A A**——A 占 5/7 但被均匀摊开，不会连选 5 次。`currentWeight` 会出现负数，这是设计的一部分（为负则下轮必不被选中）。该算法最早出自 Nginx。

### Q3：一致性哈希的原理？解决了什么问题？

- 节点和请求都算哈希值落到哈希环上，请求从落点**顺时针**找第一个节点
- 解决普通哈希（hash % N）的硬伤：**N 变化时几乎全部 key 重新映射**；一致性哈希在节点增删时**只影响环上相邻区段**的 key
- 节点在环上不要求均匀分布，要求的是负载均衡——所以引出虚拟节点（见专题深挖）
- 记不住算法就用"约火锅"比喻：现在 3:45，下一个整点 4:00 集合——顺时针找下一个

### Q4：最少连接数/最少活跃数/最快响应时间，为什么都可能失真？

都用单一指标代表负载：
- 连接数 ≠ 负载：连接多路复用时 10 个请求可复用 1 个连接
- 活跃请求数 ≠ 负载：10 个大商家请求比 10 个长尾请求重得多
- 响应时间是综合性指标最准，但要注意时效性（近期权重高、随时间衰减）

更深一层的共同问题：**客户端视角不全**。各客户端只看到自己和服务端之间的数据。根治要服务端上报（响应带元数据 / 查询 Prometheus），但业界基本没落地。

### Q5：怎么根据调用结果动态调整权重？

口诀**成加败减**：
- 成功加权重、失败减权重；"失败"是非业务概念（网络错误、超时），拿到业务失败响应也算调用成功
- 区分错误严重度：网络错误多减，超时少减（容易恢复）
- 权重体现节点差异性，绝对值不重要，但调整步长要按初始权重等比例
- 本质与注册中心"摘除临时不可用节点"相同——都是提高可用性，可互相引导话题

### Q6：权重调整的上下限是什么坑？

- **下限不能为 0**：权重 0 的节点可能永不被选中，或除零导致负载均衡崩溃
- **上限**：一般不超过初始权重 2~3 倍，防止该节点被连续选中
- **溢出**：用 uint/int8 存权重时，频繁加减可能溢出——不少公司因此出过线上故障
- 这是"很多开发者意识不到"的点，面试主动讲是亮点

### Q7："大请求"导致负载不均衡的案例怎么讲？

话术骨架：
1. 问题：用轮询，整体响应时间均匀，但**不固定间隔**出现偶发慢请求，程度不一
2. 定位：大请求（大商家拉全量订单）落到某节点后占据大量 CPU/内存，后续打到该节点的请求全变慢
3. 本质：**所有负载均衡算法都不考虑请求本身的大小**——这是根治不了的，只能规避
4. 解法二选一：
   - 业务拆分：批量请求限制每批最多 100 条
   - 隔离（更高级）：每天计算大客户名单，负载均衡器全量加载名单，大客户请求路由到专属节点——大客户照样慢，但不影响别人；还能顺势引到服务治理的隔离话题

### Q8：一致性哈希怎么和本地缓存结合？为什么不能彻底解决一致性？

- 结合：按用户 ID 一致性哈希路由 → 同一用户请求固定落同一节点 → 该节点的本地缓存必命中、数据不重复存、不一致窗口小
- 不能根治的原因（关键词**应用发布**）：节点数变化时 key 的归属节点变化。例子：请求 1 在老节点查 user 1 的昵称（未缓存）；此时扩容/发布；请求 2 被导到新节点把昵称改成"小刚"；请求 1 从老节点本地缓存读到的还是旧值。应用发布 = 先下线再上线，是节点变化最常见的原因

### Q9：思考题——随机和轮询统计效果差不多，为什么实践中轮询用得多？

轮询**可控、确定、平滑**：严格轮流，不存在"脸黑连续命中同一节点"。随机在统计学上等效，但小样本下可能连续打同一节点，极端时诱发雪崩。工程上确定性优于统计学等效。（反向知识点：Dubbo 默认其实是加权随机——说明两者确实可互换，面试可提这句显得有实操。）

### Q10：思考题——最少连接数在客户端负载均衡会失真，为什么用在网关上就没问题？

网关是**所有流量进入服务端的唯一入口**，网关上统计的连接数就是服务端的真实全量连接数；而客户端只能统计自己与服务端之间的连接，看不到其他客户端。同一个算法，数据源是否全量决定了它是否有效。

### 项目经历栏·案例一：大请求隔离路由

**版本 A（简洁版，一行）**
- 治理负载不均导致的偶发慢请求：定位为批量类大请求（大客户拉全量数据）随机落节点后占满资源，拖累同节点其他请求；通过"离线计算大客户名单 + 定制负载均衡路由规则"将大请求导流至专属节点组实现隔离，普通请求 P99 显著下降

**版本 B（详细版，供面试口述）**
> 我们线上用的是轮询负载均衡。监控上整体 RT 很均匀，但会不定期出现一批特别慢的请求，间隔和程度都不固定。排查后发现根因是大请求：大商家拉当日全量订单这类批量请求，落到哪个节点就占住该节点大量 CPU 和内存，同期打到该节点的请求全部变慢。这本质上是所有负载均衡算法的通病——它们都不感知请求本身的大小。我的解决方案是隔离：每天离线计算一批大客户名单，负载均衡器加载名单后，识别到大客户请求就路由到专门的几台节点。大客户的请求依旧慢，但普通客户不再受影响。这个方案还能和服务治理的隔离机制（如 VIP 用户独立集群）打通。

### 项目经历栏·案例二：一致性哈希提升本地缓存命中率

**版本 A（简洁版，一行）**
- 优化本地缓存体系：针对轮询路由下同 key 请求散落各节点导致的缓存命中率低、内存重复浪费问题，引入一致性哈希负载均衡（按用户 ID 路由），同一用户请求固定落同一节点，缓存命中率大幅提升、总体内存占用下降，并明确评估了发布窗口内的短暂不一致残留

**版本 B（详细版，供面试口述）**
> 我们有个性能苛刻的场景用了本地缓存，但轮询负载均衡导致同一个用户的请求会打到不同节点：每个节点都要缓存同一份数据，内存浪费严重，命中率低，数据不一致问题也突出。我把负载均衡改造成一致性哈希，按用户 ID 计算哈希路由，保证同一用户的请求固定落在同一节点，本地缓存命中率和内存利用率都明显改善。当然它没有彻底解决一致性——应用发布导致节点数变化时，同一份数据会短暂缓存在新旧两个节点上，存在读到旧值的窗口，我们通过发布时主动清缓存/短 TTL 兜底。

## 四、面试官连环追问清单（含参考答案）

### Q1：手写平滑加权轮询？（高频现场编程）

要点：两个权重数组；每轮 `currentWeight += weight` → 选最大 → 选中者 `currentWeight -= totalWeight`。能说出"选择结果序列平滑（A=5,B=1,C=1 → AABACAA）"和"currentWeight 允许为负"两个细节即过关。建议面试前用 gRPC 自定义 LoadBalancer 真写一遍。

### Q2：一致性哈希为什么要虚拟节点？（文章没讲，必考追问）

物理节点少（如 3 台）时，哈希环上节点位置随机，各节点负责的弧长差异巨大 → 负载倾斜。解法：每个物理节点生成 100~200 个**虚拟节点**（如 `node1#1`、`node1#2`...）散落到环上，请求先命中虚拟节点再映射回物理节点。虚拟节点数越多，分布越均匀；同时扩缩容时迁移的流量被摊得更碎更平。

### Q3：一致性哈希和 Redis Cluster 的 16384 槽是什么关系？

殊途同归：**槽就是"固定数量的虚拟节点"**。Redis 把哈希空间预先切成 16384 个槽，key 经 CRC16 落槽，槽再映射到节点——扩缩容只迁移槽而非逐个 key，和一致性哈希"只影响相邻区段"的目标一致，但管理更工程化（槽是显式一等公民，可查询可迁移）。对比着讲体现知识体系互通。

### Q4：动态调权和熔断是什么关系？

- 动态调权是**软处理**：节点变差就少发流量，仍保留部分请求探测恢复
- 熔断是**硬处理**：达到阈值直接摘除/拒绝，恢复要靠半开试探
- 二者可组合：超时→权重微降；连续失败触发熔断→权重骤降到下限（评论区作者提到的"SAO 操作"：超时降一点，熔断限流唰一下降到底）

### Q5：最快响应时间算法为什么要"时间衰减"？

节点状态是时变的：10 分钟前的快不代表现在快。只用近期样本（滑动窗口），且越近的响应时间权重越高，才能让算法对节点状态变化敏感。否则一个刚劣化的节点会因为历史好成绩继续被选中。这个"指标效用随时间衰减"的思想在服务治理（熔断恢复、限流窗口）里反复出现。

### Q6：如果让你设计一个自定义负载均衡算法，思路是什么？

文章给的范式：选**能代表你业务瓶颈的单一指标**。CPU 密集型应用就选 CPU 负载最低的节点；IO 密集型选磁盘/网络最闲的。难点不在算法而在**指标采集**：客户端采集视角不全，要服务端上报（响应带元数据）或从 Prometheus 查。能说到"采集比算法难"这层就很内行。

### Q7：网关、Nginx、微服务网关是什么关系？（评论区高频疑问）

Nginx 是最外层 Web 网关（必有）；微服务/API 网关（APISIX、ShenYu、Spring Cloud Gateway）管业务路由、鉴权、限流。大公司多层并存不冲突，各自承担不同职责。负载均衡在每一层都可能存在：Nginx → 网关集群 → 服务节点。

### Q8：全球化部署的负载均衡怎么考虑？（评论区进阶点）

先**地域亲和**：同大区 > 同机房 > 跨机房，再在局部范围内用轮询等基础算法。本质是分层路由 + 局部均衡。作者原话：大多数面试官也没落地过，简历没写不用深聊；写了就要准备专线延迟、数据同步、就近接入的完整故事。

## 五、专题深挖：一致性哈希的两个细节（文章没展开的部分）

### 1. 为什么普通哈希"扩缩容即灾难"

`hash(key) % N`：N 从 3 变 4，几乎所有 key 的余数都变 → 缓存场景等于全量失效（缓存雪崩的另一种形态）。一致性哈希把 N 从公式里拿掉：key 的位置与节点数无关，只按环上顺时针归属 → 增删节点只迁移该节点在环上负责的那一段弧。评论区指出文章没强调这点，**这是"为什么用一致性哈希"的第一答案**，哈希环只是实现。

### 2. 虚拟节点的量化直觉

- 3 个物理节点直接落环：弧长比例可能是 50%/30%/20% 这种歪斜
- 每节点 150 个虚拟节点（Dubbo 默认 160）：负载偏差可压到 5~10% 以内
- 虚拟节点的代价：路由表变大、实现变复杂——但都是客户端内存里的事，远小于倾斜的代价

### 3. 迁移成本对比

| 方案 | 节点增减时的迁移量 | 均衡性 |
|---|---|---|
| hash % N | 几乎全部 key | 好 |
| 一致性哈希（无虚拟节点） | 约 1/N | 差（节点少时） |
| 一致性哈希 + 虚拟节点 | 约 1/N，且摊碎 | 好 |
| Redis Cluster 槽（16384） | 按槽迁移，约 1/N | 好（槽数多且均匀） |
