## 一、文章总结

**核心框架**：限流回答三个问题——**用什么算法、对什么限流（对象）、限流之后怎么办**；真正的拉分题是**阈值怎么算**。

**算法分类**（与负载均衡算法同构：静态 vs 动态）：

| 类别 | 算法 | 一句话 | 关键点 |
|---|---|---|---|
| 静态 | 令牌桶 | 恒定速率产令牌，拿到令牌才执行 | 桶有容量 → **能积攒令牌，容忍小规模突发**；容量不能太大（攒多了限流失效） |
| 静态 | 漏桶 | 固定速率转交业务逻辑 | 令牌桶容量=0 的特例；**绝对均匀**，不容忍任何突发 |
| 静态 | 固定窗口 | 固定时间段内固定数量 | 窗口边界有 2x 突刺；窗口内可能有**毛刺**（1 分钟 1000 个，可能第 1 秒全来） |
| 静态 | 滑动窗口 | 窗口平滑挪动（t1-1min ~ t1） | 缓解边界突刺，但**毛刺问题依旧** → 窗口不能太长（秒级合适，分钟级不合适） |
| 动态 | BBR 类（自适应） | 用指标动态判定收/放流量 | 借鉴 TCP 拥塞控制；B 站 Kratos 有实现；原理难，不作硬性要求 |

**限流对象**：单机 vs **集群**（需 Redis 等中间件记录流量；网关做集群限流可摆脱 Redis）；业务维度：VIP 不限/普通限、按 IP（登录/秒杀，如 1s 50 次，考虑公共 IP）、按业务 ID。

**限流后的做法**（被限流的请求去哪）：
1. **同步阻塞等待**（偶发限流等下一秒就能处理；必须控制超时，不能无限等）
2. **同步转异步**（存起来低峰再处理，本质接近降级）
3. **调整负载均衡**：被限流 = 告诉 LB 少发请求给这个节点——**降低权重**（与熔断的区别：熔断是不再发，限流是少发）

**两个深度亮点**：
- **突发流量**：漏桶做不到（10ms 一个绝不超标）；令牌桶靠积攒令牌容忍（速率 100/s + 容量 20 = 每秒最多 120 个）
- **请求大小**：限流只管个数不管资源消耗——同样 100 QPS，一台全小请求没事，一台全大请求可能崩。动态限流能缓解不能根治（请求执行前不知道大小）

**阈值计算四思路**（本文核心，按推荐度排序）：

| 思路 | 做法 | 缺陷 |
|---|---|---|
| 看观测数据 | 高峰期集群 QPS 1000 → 阈值定 1200 留余量 | 要求已上线；业务巅峰 ≠ 性能瓶颈，阈值可能显著偏低 |
| **压测（最正）** | 全链路压测测出瓶颈 | 难、贵，很多服务测不了 |
| 借鉴 | 相关服务/转化关系（下单 100 → 支付转化率 90% → 90） | 全新业务没得借 |
| 手动计算 | 统计链路耗时：1 次回表查询 10ms + CPU 10ms = RT 20ms；4 核 → `1000ms÷20ms×4=200` | 准确度差；GC 语言还要打折 |

**压测 ABC 三点**（口诀：性能 A、并发 B、吞吐量 C）：
- A：性能最好的点（RT 稳定、利用率还在升）→ 性能苛刻服务选它
- B：系统快崩的临界点（RT 已长但还撑得住）→ 追求最高并发选它
- C：吞吐量最高的点（B、C 可能重合）→ 追求吞吐选它

**升华**：阈值做成**可动态调整**——上线先设小，观测健康再逐步上调。

**面试准备清单**：
1. 四个静态算法能手写/写清思路（现场手写题高发区）
2. 搞清公司每个限流的：阈值多少、为什么是这个值、被限流后怎么处理
3. 没上限流的核心接口 → 自己加上（压测定阈值，这本身就是亮点）
4. 有余力：给开源框架（如 gRPC）写限流插件开源——目标不是让人用，是证明你懂限流 + 熟悉 gRPC + 喜欢开源

**补充知识（文章未提，面试加分）**：
- **集群限流实现选型**：Redis 滑动窗口 vs Sentinel Token Server vs 网关——每请求一次网络交互省不掉，差异在故障域隔离、热点 key、批量优化（详见 03 熔断笔记·专题六）
- **取真实 IP**：过网关后 `request.getRemoteAddr()` 拿到的是网关 IP，要用 `X-Forwarded-For` 第一个 IP，并防伪造（思考题 1）
- **Sentinel 匀速排队**（CONTROL_BEHAVIOR_RATE_LIMITER）：漏桶思想的工业化实现
- **BBR 一句话原理**：以"瓶颈带宽 × 传播时延"（BDP）为控制目标，同时测量带宽和 RTT，追求"跑满管道但不在瓶颈处排队"

## 二、Q&A（问题 + 标准答案）

### Q1：限流算法有哪些？最重要的区别是什么？

静态：令牌桶、漏桶、固定窗口、滑动窗口；动态（自适应）：BBR 类（借鉴 TCP 拥塞控制，Kratos 有实现）。**最重要的区别是能否处理小规模突发流量**——漏桶绝对均匀做不到，令牌桶靠积攒令牌可以。

### Q2：令牌桶和漏桶的区别？

令牌桶：恒定速率产令牌入桶，请求拿令牌执行，**桶有容量可积攒** → 偶发突发流量也能处理（速率 100/s + 容量 20 → 每秒最多 120）。漏桶 = 容量为 0 的令牌桶特例：令牌产生即取走、不积攒，**绝对均匀**（100/s 就是 10ms 一个，多一个不行）。注意：令牌桶容量不能设太大，否则积攒过多限流失效。

### Q3：固定窗口和滑动窗口的区别？共同缺陷？

固定窗口：固定时间段（如 1s）内固定数量，窗口**突然**挪动——窗口边界有 2 倍突刺（第 1 秒末 + 第 2 秒初各 100 = 瞬间 200）。滑动窗口：窗口**平滑**挪动（起始位置随时间后移），缓解边界突刺。**共同缺陷是毛刺**：窗口内的请求分布不可控（1 分钟 1000 个可能第 1 秒全来），所以窗口不能太长——秒级合适，分钟级不合适。

### Q4：限流对象有哪些维度？

- 范围：单机限流 vs 集群限流（集群要 Redis 等中间件记流量；网关实现可摆脱 Redis）
- 业务维度：按 IP（登录/秒杀防攻击，1s 50 次——考虑公共 IP，正常人手速到不了）、按用户/业务 ID、VIP 不限普通限（增值服务）

### Q5：被限流的请求怎么处理？

1. **同步阻塞等待**：偶发限流等下一窗口就能处理（101 个请求里多出的 1 个等 1s）；**必须控制超时**
2. **同步转异步**：存起来低峰期再处理（接近降级）
3. **调整负载均衡权重**：降低转发概率——与熔断的区别：熔断是不再发，限流是少发

> 这三种处理在 Sentinel 里分别怎么落地（匀速排队/blockHandler/429+Retry-After），以及为什么不能把限流理解成"直接拒绝"，见专题五第 6、7 小节。

### Q6：限流阈值怎么确定？（核心题）

四个思路，按推荐度：**压测 > 观测数据 > 借鉴 > 手动计算**。
- 观测数据：高峰期集群 QPS 1000 → 定 1200 留余量；缺陷是要求已上线，且业务巅峰 ≠ 性能瓶颈（集群能吃 3000 但只有 1000 流量时，估出的阈值显著偏低）
- 压测：最好是**线上全链路压测**（限流针对线上环境，模拟越真越准）
- 借鉴：相关服务直接借用；有转化关系的按比例（下单 100 × 支付转化 90% = 支付 90）
- 手动计算：统计全链路耗时估算（见 Q9）

### Q7：压测结果怎么用？ABC 三个点怎么选？

压测曲线（QPS-RT-吞吐量）上三个候选点，口诀**性能 A、并发 B、吞吐量 C**：
- A 点：性能最好（RT 稳定不变、利用率在升）——性能苛刻的服务选 A
- B 点：快崩的临界点（RT 已长但撑得住）——追求最高并发选 B
- C 点：吞吐量最高（有时与 B 重合）——追求吞吐选 C

### Q8：面试官杠"压测很难/测不了"怎么办？

先表态度（委婉但坚决）：**压测是基操**——没有压测数据，性能优化和可用性改进无从下手，迟早要建。然后给退路：借鉴相关服务阈值；全新业务就手动计算。

### Q9：手动计算阈值怎么算？准吗？

沿调用链统计所有耗时点：DB 查询次数、微服务调用、中间件访问。例：1 次回表查询 10ms + CPU 计算 10ms = RT 20ms；4 核实例 → `1000ms ÷ 20ms × 4 = 200 QPS`。**准确度差**：GC 语言要刨除垃圾回收开销（200 再打折，折扣取决于 GC 频率和消耗）；只能当上线前的初始值，上线后靠观测修正。

### Q10：用了限流系统为什么还会崩？（请求大小亮点）

限流只管**请求个数**，不管请求的**资源消耗**。两台实例都限 100 QPS，一台全是小请求没事，一台全是大请求可能崩。动态限流算法能缓解不能根治——**请求只有被执行时才知道它多大**。和负载均衡不考虑请求资源消耗是同一类问题。

**版本 B（详细版，供面试口述）**

## 四、面试官连环追问清单（含参考答案）

### Q1：经过网关后怎么拿到用户真实 IP？怎么防伪造？（思考题 1）

- 直连场景：`request.getRemoteAddr()`
- 过网关/反向代理后：getRemoteAddr 拿到的是**网关 IP**，要读 `X-Forwarded-For` 头的**第一个 IP**（客户端原始 IP）
- 防伪造：XFF 是客户端可伪造的——只信任**你自己的网关追加的那一跳**（如 Nginx 配置 `proxy_set_header X-Real-IP $remote_addr`，后端只认网关设置的 X-Real-IP）；直接暴露的服务不接受客户端自带的 XFF
- 防坑：层层代理下 XFF 是逗号分隔链，取错位置（取最后一个）会拿到代理 IP

### Q2：令牌桶的容量怎么定？

容量 = 容忍突发的幅度。权衡：太大 → 积攒令牌多，突发时可能瞬间打满（容量 1000 + 真来 1000 个 = 限流失效）；太小 → 退化成漏桶失去突发容忍。经验：容量设为**秒级速率的 10%~20%**，即容忍 100~200ms 的突发；对毛刺敏感的服务直接上漏桶/匀速排队。

### Q3：滑动窗口怎么实现？精度和成本怎么平衡？

- 单机实现：环形数组分桶（如 1s 切 10 个 100ms 桶），当前窗口 = 最近 10 桶求和——**分桶越细越平滑越准，内存和计算越贵**
- 集群实现：Redis ZSet（member=请求 ID，score=时间戳；Lua 原子执行 ZREMRANGEBYSCORE 清窗口外 + ZCARD 计数 + ZADD）——我们 atlas-rate-limit 的 `RedisZSetSlidingWindowRateLimiter` 就是这个
- 防坑：ZSet 方案每请求都写 Redis，注意热点 key；精度和成本平衡的另一种思路是"固定窗口计数 + 前一窗口加权"（Sentinel 的思路）

### Q4：BBR 动态限流的基本原理？（了解即可）

传统拥塞控制（如 TCP Reno）把"丢包"当拥塞信号，为时已晚。BBR 换思路：**测量瓶颈带宽和传播时延，以 BDP（带宽时延积）为控制目标**——跑满管道但不在瓶颈处排队。映射到微服务限流：用 RT、CPU、负载等指标动态收放流量，而不是固定阈值。业界落地少（大多数框架没有 BBR 限流器），B 站 Kratos 有实现。面试不要求会写，能讲清思想即可。

### Q5：单机限流和集群限流怎么选？实现上差在哪？

- 单机：本地内存计数（Bucket4j/Guava RateLimiter），零外部依赖、零网络开销；但**多实例下总额 = 阈值 × 实例数**，控不住总量
- 集群：计数集中到 Redis（Lua 滑窗）或 Token Server，**每请求一次网络调用省不掉**；网关层做集群限流可摆脱 Redis
- 选型：防攻击/兜底 → 单机够用；对外开放 API 配额/保护下游 DB → 必须集群。详细对比见 03 熔断笔记·专题六

### Q6：阈值上线后发现不合适怎么办？

这正是"阈值要可动态调整"的落点：
1. 规则放配置中心（Nacos）热更新，改阈值不用发版——我们 atlas-rate-limit 就是这么做的
2. 上线策略：**先设小**（宁可误杀），观测健康后逐步上调——比"设大了被打崩再降"安全
3. 长期：配合容量规划，大促前按预估流量重新压测标定

### Q7：网关限流和服务内限流是什么关系？重复吗？

不重复，是两层防御：
- **网关层**：粗粒度、全局视角（总入口 QPS、IP 黑名单、路由级配额），第一道闸
- **服务内**：细粒度、业务视角（按客户/接口/依赖资源），第二道闸
网关漏过来的（或内部服务间调用不经过网关的），服务内限流兜底。类比：大厦门禁 + 楼层门禁。

## 五、专题深挖：四大限流算法 Java 手写实现

> 现场手写题高发区。统一接口语义：`tryAcquire()` 返回 true = 放行，false = 被限流。均为线程安全（synchronized 足够面试；生产用 LongAdder/CAS 优化）。

### 1. 固定窗口

```java
public class FixedWindowRateLimiter {
    private final int limit;          // 每窗口允许请求数
    private final long windowMillis;  // 窗口长度
    private long windowStart;         // 当前窗口起始时间
    private int count;                // 当前窗口已计数

    public FixedWindowRateLimiter(int limit, long windowMillis) {
        this.limit = limit;
        this.windowMillis = windowMillis;
        this.windowStart = System.currentTimeMillis();
    }

    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();
        if (now - windowStart >= windowMillis) {  // 窗口过期 → 整体重置（这就是"突然挪动"）
            windowStart = now;
            count = 0;
        }
        if (count < limit) {
            count++;
            return true;
        }
        return false;
    }
}
```

**缺陷演示**：limit=100/秒，第 1 秒末打满 100，第 2 秒初又打满 100 → 边界瞬间 200 个请求，这就是 2x 突刺。

### 2. 滑动窗口（日志版，最好写）

```java
public class SlidingWindowLogRateLimiter {
    private final int limit;
    private final long windowMillis;
    private final Deque<Long> log = new ArrayDeque<>();  // 窗口内每个请求的时间戳

    public SlidingWindowLogRateLimiter(int limit, long windowMillis) {
        this.limit = limit;
        this.windowMillis = windowMillis;
    }

    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();
        while (!log.isEmpty() && now - log.peekFirst() >= windowMillis) {
            log.pollFirst();              // 剔除滑出窗口的旧记录 → 窗口"平滑挪动"
        }
        if (log.size() < limit) {
            log.addLast(now);
            return true;
        }
        return false;
    }
}
```

**权衡**：精确平滑，但内存 O(limit)。生产优化成分桶环形数组（1s 切 10 个 100ms 桶求和），内存 O(1)、精度换成本——分桶越细越准越贵。集群版即 Redis ZSet（score=时间戳，Lua 原子执行 ZREMRANGEBYSCORE + ZCARD + ZADD），我们 `RedisZSetSlidingWindowRateLimiter` 就是这个。

**核心判断逐行拆解**（`while (!log.isEmpty() && now - log.peekFirst() >= windowMillis)`）：

| 部分 | 作用 |
|---|---|
| `!log.isEmpty()` | 防御：空队列时 `peekFirst()` 返回 null，后续运算会 NPE |
| `log.peekFirst()` | 取队头 = 窗口内**最旧**的时间戳（deque 按时间有序，队首最老） |
| `now - 最旧时间戳 >= windowMillis` | 最旧记录距今超一个窗口长度 → 已滑出窗口，必须删除 |

用 `while` 是因为可能有多条同时过期（系统空闲很久，攒下的记录全过期），要循环清到"队首仍在窗口内"或"队空"为止。

**时间轴实例**（window=1000ms，limit=3）：

```
时刻 0ms:    请求A → 队列空，直接放行    log=[0]
时刻 200ms:  请求B → 队首0未过期，放行   log=[0, 200]
时刻 500ms:  请求C → 放行               log=[0, 200, 500]
时刻 800ms:  请求D → size=3 已满，拒绝   log=[0, 200, 500]
时刻 1001ms: 请求E → 清理：1001-0=1001 ≥ 1000，A出队
                     log=[200, 500]，size=2 < 3，放行
                     log=[200, 500, 1001]
```

800ms 时 D 被拒：窗口内实打实已有 3 个请求——滑动窗口日志**完全没有**固定窗口的边界突刺，这是它"最精确"的原因。

**四个边界追问点**：
1. **为什么 `>=` 而非 `>`**：时间戳恰满一个窗口宽度即视为滑出，`>=` 保证"窗口内最多 limit 个请求"任何瞬间严格成立
2. **为什么清理后才能判断 size**：不清理，过期记录一直占名额，限流器"假满"——空闲很久后第一个请求反而被拒
3. **为什么用 deque**：队首出队 O(1)、队尾入队 O(1)，天然按时间有序，只需查队首
4. **`synchronized` 的代价**：单机加锁即可，但意味着这是单机限流；集群限流要把 log 挪到 Redis ZSet

### 3. 令牌桶

```java
public class TokenBucketRateLimiter {
    private final double rate;      // 每秒产令牌数
    private final double capacity;  // 桶容量（可积攒上限 → 容忍突发）
    private double tokens;          // 当前令牌数
    private long lastRefillTime;

    public TokenBucketRateLimiter(double rate, double capacity) {
        this.rate = rate;
        this.capacity = capacity;
        this.tokens = capacity;                 // 初始满桶
        this.lastRefillTime = System.currentTimeMillis();
    }

    public synchronized boolean tryAcquire() {
        refill();
        if (tokens >= 1) {
            tokens -= 1;
            return true;
        }
        return false;
    }

    private void refill() {                     // 惰性补充：访问时才结算，不开后台线程
        long now = System.currentTimeMillis();
        tokens = Math.min(capacity, tokens + (now - lastRefillTime) / 1000.0 * rate);
        lastRefillTime = now;
    }
}
```

**两个讲点**：① 不用后台线程定时产令牌，而是每次访问时按时间差惰性结算（惰性求值，工程标配）；② capacity 就是"突发容忍度"——rate=100/s、capacity=20 时每秒最多放 120 个。

### 4. 漏桶（水位线版）

```java
public class LeakyBucketRateLimiter {
    private final long intervalMillis;  // 出水间隔 = 1000/rate，保证绝对均匀
    private final int capacity;         // 桶容量（最多允许排队的请求数）
    private long nextFreeTime;          // 水位线：下一个可出水时间点

    public LeakyBucketRateLimiter(int rate, int capacity) {
        this.intervalMillis = 1000 / rate;
        this.capacity = capacity;
        this.nextFreeTime = System.currentTimeMillis();
    }

    public synchronized boolean tryAcquire() {
        long now = System.currentTimeMillis();
        long myTurn = Math.max(now, nextFreeTime);            // 本请求轮到的出水时间
        if (myTurn - now > (long) capacity * intervalMillis) {
            return false;         // 要等的时间超过桶容量 → 溢出，限流
        }
        nextFreeTime = myTurn + intervalMillis;               // 水位上涨一格
        return true;
    }
}
```

**讲点**：不真的维护队列，用"水位线"（下次出水时间戳）等价表达——排队位置 = (myTurn - now) / interval。这个是非阻塞版（拒绝即失败）；阻塞等待版（`myTurn - now` 在容量内则 sleep 等待）就是 Sentinel **匀速排队**（`CONTROL_BEHAVIOR_RATE_LIMITER`）的思想。

### 四算法速查

| 算法 | 一句话核心 | 突发容忍 | 手写要点 |
|---|---|---|---|
| 固定窗口 | 窗口到点整体清零 | 边界 2x 突刺 | 判窗口过期重置 |
| 滑动窗口 | 窗口随时间平滑挪动 | 缓解突刺，毛刺依旧 | 队首过期剔除 |
| 令牌桶 | 攒令牌，拿了才执行 | ✅（容量内） | 惰性结算，min(capacity) |
| 漏桶 | 固定速率出水 | ❌ 绝对均匀 | 水位线 = 下次出水时间 |

### 5. Sentinel 匀速排队（CONTROL_BEHAVIOR_RATE_LIMITER）详解

**定位**：Sentinel 流控的三种控制行为之一——

| 行为 | 超阈值时的动作 | 语义 |
|---|---|---|
| `CONTROL_BEHAVIOR_DEFAULT`（默认） | 立即抛 BlockException | 快速失败 |
| `CONTROL_BEHAVIOR_WARM_UP` | 阈值从 count/coldFactor 爬升 | 预热 |
| `CONTROL_BEHAVIOR_RATE_LIMITER` | **不拒绝，排队等到轮到自己** | 匀速通过（漏桶思想） |

```java
FlowRule rule = new FlowRule("myResource")
    .setCount(100)                                   // QPS 阈值 100
    .setControlBehavior(RuleConstant.CONTROL_BEHAVIOR_RATE_LIMITER)
    .setMaxQueueingTimeMs(500);                      // 最多排队 500ms
```

**核心机制：虚拟排队，没有真队列**。内部只维护 `latestPassedTime`（最近放行时刻），每个请求算自己"轮到的时间"：

```
costTime = 1000ms / QPS阈值              ← 理论间隔（QPS=100 → 10ms）
expectedTime = latestPassedTime + costTime
if expectedTime <= now: 直接放行（队列为空）
else:
    waitTime = expectedTime - now
    if waitTime > maxQueueingTimeMs: 才拒绝
    else: CAS 推进 latestPassedTime（预约占坑）→ sleep(waitTime) → 放行
```

两个实现细节：
1. **CAS 预约代替真队列**：并发线程各自 CAS 把 latestPassedTime 推进一个 costTime，拿到互不重叠的时间槽再各自 sleep——保证严格匀速出水，无锁、O(1) 内存
2. **拒绝只发生在"队太长"时**：QPS=100、超时 500ms → 最多 50 个在排队，第 51 个并发请求才被拒。匀速排队不是永不拒绝，而是**把瞬时毛刺摊平到时间轴，用延迟换通过率**

**最大的坑**：`sleep(waitTime)` 睡的是**业务工作线程**（Tomcat/Dubbo worker）——高峰时大量线程被"睡觉"的请求占住 → 线程池耗尽 → 不相干接口也 hang 死。所以在线低延迟接口主流仍是快速失败，匀速排队只给"**可以慢不能丢**"的场景（定时任务削峰、写 DB、调第三方、消息消费限速）。一句话：**匀速排队把"拒绝"换成"占着线程等待"——保护下游，但消耗自己的线程资源**。

**对照表**：

| 实现 | 机制 | 差异点 |
|---|---|---|
| Sentinel 匀速排队 | 预约时间戳 + sleep + 超时上限 | 队太长会拒绝 |
| Guava RateLimiter.acquire() | 预约制（nextFreeTicketMicros） | 无限等待不拒绝 |
| 漏桶真队列版 | 请求入队，worker 定速消费 | 占内存队列，有背压 |

### 6. 限流后的处理在 Sentinel 里怎么落地

Sentinel 的职责止于**发信号**（抛 BlockException / FlowException），之后怎么处理是业务选择。完整图景：

```
请求超阈值
  ├─ 默认行为：抛 BlockException → 快速失败（就是"直接拒绝"）
  ├─ 匀速排队规则：sleep 等待轮到自己（"同步阻塞等待"的框架内建版）
  └─ BlockException 被业务捕获后的自定义处理：
       ├─ blockHandler / BlockExceptionHandler → 返回降级数据（兜底）
       ├─ catch 后投 MQ 存起来 → 低峰再处理（"同步转异步"）
       └─ 返回 429 + Retry-After → 让客户端等一等再来（atlas-api 的做法）
```

挂载点：
- `@SentinelResource(blockHandler = "...")` / 全局 `BlockExceptionHandler`：自定义兜底（返回降级数据/默认值）
- 匀速排队规则：把"同步阻塞等待"做成框架内建行为（见第 5 小节）
- "同步转异步""调整负载均衡"不在 Sentinel 内，需业务自己实现（catch BlockException 后投 MQ；或结合 Dubbo 自定义 LoadBalance——见 03 熔断笔记专题五）
- 我们 atlas-rate-limit 的做法：统一返回 **HTTP 429 + Retry-After**——本质是把"阻塞等待"的决策权交给客户端（告诉它多久后重试），服务端不占用线程

### 7. 为什么"限流后的做法"要单独讲（破"限流=拒绝"的误区）

"限流就是直接拒绝"是没做完的思考，三层原因：

1. **被限流 ≠ 请求该死**：偶发超一个请求（阈值 100 来了 101 个），直接拒绝第 101 个是矫枉过正——它等 1 秒就能被正常处理。拒绝是最省事但最粗糙的处理，成熟方案要问"这个请求能不能被挽救"
2. **可用性与用户体验的分界线**：纯拒绝视角下限流只是保住了系统，但请求失败对用户就是损失。阻塞等待、转异步、引导重试都是在"系统不崩"的前提下**尽量少牺牲请求**——和熔断必须有 fallback 同理：止损只是上半场，兜住体验才是全场
3. **面试区分度**：人人会背四个算法，"被限流的请求去哪了"能答出阻塞等待/转异步/调整负载均衡/429+Retry-After 的人很少。算法是 70 分答案，剩下 30 分在阈值计算和限流后处理

一句话：**拒绝是限流的下限而不是全部**——匀速排队把等待做进框架，转异步和 429 重试引导是业务层标准动作，合起来才是完整的限流方案。

## 六、atlas-api 限流算法现状（实查结论）

框架算法**按规则可选、非写死**，mode 在 Nacos（`dataId=atlas-rate-limit-rules`，group=`SENTINEL_GROUP`）按规则配置：

| Mode | 算法 | 实现类 |
|---|---|---|
| `BUCKET4J_REDIS`（线上标准用法） | **集群令牌桶** | `redis/Bucket4jRedisRateLimiter` |
| `BUCKET4J_LOCAL`（兜底默认值） | 单机令牌桶 | `local/Bucket4jLocalRateLimiter` |
| `REDIS_ZSET_SLIDING_WINDOW` | Redis 滑动窗口 | `redis/RedisZSetSlidingWindowRateLimiter` |
| `REDIS_FIXED_WINDOW` | Redis 固定窗口 | `redis/RedisFixedWindowRateLimiter` |
| `SENTINEL_TOKEN_SERVER` | Sentinel 集群流控 | `sentinel/SentinelTokenServerRateLimiter` |
| `DISABLED`（规则缺省值） | 不限流 | — |

一句话：**集群令牌桶为主，滑动窗口/固定窗口/Token Server 可按规则切换，Redis 故障降级单机令牌桶**。每个接口具体用哪个以 Nacos 实际规则为准。
