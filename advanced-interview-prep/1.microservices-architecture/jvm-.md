# JVM 全景课程 · 结课总结

## 一、课程主线：一张生成式结构

整门课从两条根公理生长出来，所有知识点都是它们的推论：

- **公理一**：JVM 逐条执行字节码，解释器的成本 = dispatch 开销 + 内存往返 → 一切性能机制（JIT、分层编译、推测优化）都是为绕过这个成本而生；
- **公理二**：回收安全的唯一判据是**不可达**（不是引用计数）→ GC Roots、分代、写屏障、收集器演化、泄漏分析全部由它推导。



```
执行模型 ──┬── 运行时数据区 ── OOM 分类学          ├── 类加载(常量池/符号引用)── 初始化时机/异常家族          ├── JIT(计数器→分层编译→推测优化)── 逆优化/预热          ├── JMM(as-if-serial→happens-before)── volatile/Mark Word/锁升级          └── GC 公理 ── 分代 ── 写屏障 ── G1/ZGC ── 故障链 ── 调优实战                └── 泄漏模式 ── MAT ── 排障方法论(终点)
```

## 二、各章核心结论

### 1. 执行模型

- JVM 是**栈式虚拟机**：操作数在操作数栈上，指令简洁但条数多；
- 解释器慢的三个根因：dispatch 分支开销、操作数内存往返、断流水线——不是"逐条翻译"本身慢；
- JIT 的存在理由：把热点代码一次性翻译成寄存器机器码，消除上述全部三项。

### 2. 运行时数据区

- 判别式：**逃出方法/线程的对象必须上堆**；数组永远是对象（纠正过你的"基本类型数组可上栈"误解）;
- 区域总账：PC 寄存器、Java 栈（`-Xss`)、本地方法栈、堆、Metaspace、直接内存——各自有独立的 OOM 报文。

### 3. OOM 分类学（六种报文）



| 报文                                     | 区域           | 要点                                       |
| :--------------------------------------- | :------------- | :----------------------------------------- |
| `Java heap space`                        | 堆             | 泄漏 or 堆太小，MAT 排查                   |
| `GC overhead limit exceeded`             | 堆             | 98% 时间 GC 回收不到 2%——濒死挣扎信号      |
| `unable to create new native thread`     | 栈（容量维度） | 线程数爆炸，不是单栈深度问题               |
| `StackOverflowError`                     | 栈（深度维度） | 无限递归                                   |
| `Metaspace` / `Compressed class space`   | 元空间         | 两个子限制，别混（你的探测错题）           |
| `OutOfMemoryError: Direct buffer memory` | 堆外           | 配合 `-XX:+DisableExplicitGC` 是经典组合坑 |

### 4. GC 公理与泄漏

- 可达性分析是**保守**的：宁可留垃圾，不可杀活对象；
- 泄漏的精确定义：**对象已无用，但仍存在从 GC Root 到它的强引用路径**;
- 引用分级：强 → 软（内存敏感缓存）→ 弱（ThreadLocal key)→ 虚（堆外内存回收钩子）。

### 5. 分代与写屏障

- 弱分代假说：绝大多数对象朝生夕死 → 复制式 Eden/Survivor 经济学；
- 卡表/RSet 管**空间**（谁引用了这个 Region),SATB 管**时间**（并发标记期间的对象图快照）——你亲口问过"是不是同一个东西"，答案：不是，一空间一时间；
- 并发标记的漏洞：黑→白引用 + 白被摘钩，SATB 用"删除时记录旧值"堵上。

### 6. G1 → ZGC

- G1：Region 化 + 停顿预测模型，按回收性价比选 CSet,`-XX:MaxGCPauseMillis` 是软目标；
- ZGC：染色指针 + 读屏障，并发转移，STW 亚毫秒；转发表的地址映射存在 native 内存（ZForwarding)——回答过你"新地址存哪";
- 你们生产栈：JDK21 + Generational ZGC，日志里的 `Using 1 Workers` 是 ZGC 动态调整，不是异常。

### 7. Full GC 诱因链（故障清单）

统一根因：**老年代/元空间装不下该装的东西**。五条链：晋升失败、分配速率过高、Humongous 对象、并发标记启动太晚、`MetaspaceSize` 触发线（JDK8 调大它）、`System.gc()`。

### 8. 调优实战（你的生产环境）

- 火焰图两座塔：**塔一 89%** = 价格计算链 BigDecimal 运算风暴（`divide(new BigDecimal(100))` 每调用新建对象，改 `movePointLeft(2)` + 常量化 + 汇率 memoize);**塔二 10%** = fastjson 缓存反序列化，应缓存解析后对象；
- 容器纪律：JDK11+ 自动识别 cgroup，但 JDK8 老版本要自己算 `-Xmx`；堆建议 `-Xms=-Xmx`;
- 因果链闭环：分配速率下降 → Minor GC 变稀 → CPU 跟着降。

### 9. 类加载

- class 文件 = 常量池（符号表）+ 结构描述 + 字节码；指令存**索引**，索引指向**符号引用**，运行时才解析——编译期与运行期是**两个世界**;
- 由此推出 jar hell 家族：`NoSuchMethodError` / `NoSuchFieldError` / `NoClassDefFoundError`(Maven 仲裁只留一个版本时）;
- 初始化时机："**谁定义，谁初始化**"；被动引用（经子类访问父类字段）不初始化子类——javac 编译期就把 `B.x` 改写为 `A.x`;`static final` 编译期常量直接内联进调用方（改常量库必须全量重编依赖方）;
- `Class.forName` 触发初始化，`ClassLoader.loadClass` 只加载——你探测时的疑问在此解决。

### 10. JIT

- 双计数器：调用计数器管方法，回边计数器管循环（OSR 运行中换帧——你的两道错题都在这，后来立住了）;
- 分层编译：Level 0 解释（收集 profiling)→ Level 3 C1 → Level 4 C2;
- 推测式优化三段式：情报（profiling)→ 赌博（内联/剪枝）→ 安全网（逆优化）;
- 逃逸分析三件套：**标量替换**（对象直接消失）、**锁消除**（局部 StringBuffer 的 synchronized 白加）、栈上分配（HotSpot 主要靠标量替换间接实现）;
- 故障场景：逆优化风暴、Code Cache 满导致 JIT 停摆、启动毛刺要预热。

### 11. JMM 与锁

- as-if-serial 只保证**单线程**；多线程正确性 = 手工建立 happens-before 边（程序次序/锁/volatile/线程生命周期 + 传递性）;
- volatile 双重语义：可见性 + **禁重排**;DCL 需要的是后者——`new` 三步中"构造初始化"与"引用赋值"无依赖可重排，volatile 写是单向门（你的旧模型"volatile=可见性"已修复）;
- 锁成本阶梯：锁消除（0)→ 轻量级 CAS（纳秒）→ 自旋（赌局）→ 重量级 park（微秒+上下文切换）；偏向锁已被 JDK 移除——为单线程假设优化的时代负债；
- Mark Word 是复用字段：锁状态位决定它存 hash/age 还是锁指针。

### 12. 排障方法论（终点决策树）



```
CPU 高吗?├─ 高 → top -Hp → 线程名三分流:业务/GC/JIT└─ 低而卡 → 线程状态分布:     ├─ BLOCKED:同一 monitor→锁热点;成环+jstack 报告→死锁     ├─ WAITING 在池 borrow → 资源耗尽(假性死锁,jstack 不报)     └─ TIMED_WAITING 下游 → 下游慢,不是 JVM 的病
```

死锁 vs 锁热点的三判别式：monitor 地址数量、BLOCKED 线程是否持有锁、jstack 是否报告。死锁根治 = 全局统一加锁顺序。
