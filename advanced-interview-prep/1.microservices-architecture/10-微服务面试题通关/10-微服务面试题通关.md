## 二、整体性问题

**Q：什么是微服务架构？**
单体应用按业务能力拆分为一组小型服务，每个服务独立开发、部署、扩缩容，拥有独立数据存储，服务间用轻量协议（HTTP/RPC）通信，去中心化治理。代价是引入分布式系统的复杂度：网络不可靠、数据一致性、服务治理。

**Q：怎么保证微服务架构的高可用？**
四大支柱：容错（Design for Failure）、隔离限制故障范围、监控告警 + 自动故障处理实现快速发现修复、规范变更流程（review + 回退）。详见 09。

**Q：怎么判定服务是否健康？**
分层判定：①进程级：K8s liveness 探针；②服务级：readiness 探针 / 注册中心心跳；③业务级：/health 接口检查关键依赖（DB、Redis）连通性。注意区分"进程活着"和"能正常服务"。

**Q：服务不健康该怎么办？**
调用方：熔断 + 负载均衡摘除该节点 + 重试其他节点；注册中心：心跳超期剔除；严重时降级返回兜底数据；同时告警通知值班。

**Q：怎么判定服务已从不健康恢复？**
被动：健康检查恢复 → 重新注册上线；主动：熔断器半开状态放少量探测流量，连续成功 + 观察窗口内错误率/RT 回落后逐步放量，防恢复抖动（见 03）。

**Q：Redis 崩溃了会怎样？**
短期：缓存失效，流量打到 DB——必须立刻限流保护 DB + 降级（返回默认值/本地缓存兜底）。长期靠 Redis 自身高可用（哨兵/Cluster）把不可用窗口压缩到秒级（见 09 专题 2、cache 模块）。

**Q：Kafka 崩溃了怎么办？**
发送端：写本地消息表/磁盘文件暂存，恢复后定时补偿重发；消费端：消费暂停表现为消息积压，恢复后追数即可（注意积压告警）；Kafka 自身靠多副本 ISR 防单点。关键同步链路要有"MQ 不可用也能走通"的降级路径。

**Q：设计一个开放平台要考虑什么？**
①认证鉴权（AK/SK、OAuth2）；②限流配额（按租户分级）；③签名防篡改防重放；④接口幂等（唯一请求 ID）；⑤回调机制 + 重试补偿；⑥文档 + mock 联调环境；⑦监控计量（调用量计费）；⑧版本管理与废弃策略。

## 三、01 服务注册与发现

**什么是注册中心？**
服务实例地址的目录服务：提供者注册地址、消费者订阅拉取、变更主动推送，配合健康检查剔除故障实例。

**基本模型？**
提供者启动注册 → 注册中心存储 → 消费者订阅并缓存到本地 → 消费者基于本地列表负载均衡直连提供者 → 变更时注册中心推送通知。

**服务上线/下线的步骤？**
上线：启动 → 注册 → 预热/就绪检查 → 接流量。下线：先从注册中心注销（摘流）→ 等待变更传播到所有消费者 → 处理完存量请求 → 关闭进程。

**选型考虑哪些因素？**
CAP 取舍、变更推送时延、性能与规模、健康检查机制、生态（配置管理一体化）、运维成本。

**为什么用 Zookeeper/Nacos/etcd？**
ZK：CP、成熟、watch 机制完善，但注册场景可用性不足；Nacos：AP/CP 可切换 + 配置管理一体，国内微服务主流；etcd：Raft 强一致 + watch，K8s 生态标配。

**什么是 CAP？**
一致性、可用性、分区容忍性不可兼得；网络分区（P）必然发生，实际只能在 C 和 A 之间取舍。

**注册发现选 AP 还是 CP？**
**AP**。注册信息短暂不一致可接受（客户端本地缓存兜底、重试其他节点），但注册中心不可用会导致全站无法寻址——可用性优先。

**注册中心高可用？**
多节点集群 + 客户端本地快照缓存 + 跨机房部署；极端情况静态节点列表人肉兜底。

**服务崩溃如何检测？**
租约/心跳机制：提供者定期续约，超期未续约（如 30s）判定死亡并剔除；长连接断开可加速发现。

**客户端容错措施？**
本地缓存节点列表、调用失败重试其他节点、熔断、注册中心全挂时用缓存/静态列表继续调用。

**注册中心崩溃了怎么办？**
客户端凭本地缓存正常调用已有服务；新实例无法注册/变更无法推送——需尽快恢复；兜底是静态配置节点列表 + 异构备份注册中心。

**注册中心怎么判断服务端崩溃？**
被动等待租约过期是主要手段；主动探测（TCP 探活）做补充。注意"崩溃检测有延迟"，这段时间客户端可能还往死节点发请求——靠客户端重试其他节点消化。

## 四、02 负载均衡

**了解哪些算法？**
静态：轮询、加权轮询、随机、加权随机、一致性哈希；动态：最少连接、最快响应、按调用结果动态调权。

**静态和动态的核心区别？**
静态不看节点实时状态，按预设规则分配；动态采集节点负载/RT/错误率实时调整分配比例。静态简单无开销，动态更均衡但有统计和通信成本。

**轮询和随机的区别？**
轮询严格均匀但有状态（要维护游标），并发下需要原子操作；随机无状态、实现简单，请求量足够大时趋近均匀，小样本下不均衡。

**平滑加权轮询？**
每轮：各节点当前权重 += 静态权重 → 选当前权重最大的 → 选中者当前权重 -= 总权重。效果：权重大的节点分散命中，避免普通加权轮询的"连击"。

**如何根据调用结果调整负载均衡？**
统计各节点的错误率、RT，动态降低表现差节点的权重；恢复后逐步升回。

**为什么要动态调权重？权重代表什么？**
同配置节点实际性能有差异（宿主机混部、邻居噪声、硬件代差）。权重 = 该节点分到流量的相对比例。

**你们公司调过权重吗？为什么？**
（结合真实经历答：如混部节点宿主机负载高导致 RT 长尾 → 引入按 RT 动态降权。）

**最快响应时间算法的缺点？**
①快节点被持续打满直到变慢，流量集中；②RT 统计窗口抖动导致权重震荡；③可能引发"全部涌向当前最快节点 → 打挂 → 涌向下一个"的迁移式雪崩。

**内存/CPU 敏感应用的负载均衡设计？**
节点定期上报宿主机 CPU/内存使用率，客户端选择资源余量最大的节点（最少负载算法），并配权重平滑防抖动。

**静态算法为什么仍出现偶发流量不均衡？怎么解决？**
算法只保证请求数均匀，不感知请求成本差异（复杂请求集中落到某节点）和节点实时状态。解决：动态负载均衡 + 熔断摘除异常节点 + 限流兜底。

## 五、03 熔断

**为什么熔断能提高可用性？**
下游故障时快速失败，不再等待超时：释放线程/连接资源，防止故障沿调用链向上扩散（雪崩）。

**判断节点健康看哪些指标？**
错误率、慢调用比例（RT 超阈值占比）、异常总数、连续失败次数；配合最小请求量防小样本误判。

**触发熔断后该熔断多久？**
无固定值，常用**指数退避**：5s → 10s → 30s 逐次拉长，半开探测成功后立即恢复。

**响应时间超过多少触发熔断？**
按该接口 P99 基线的 2~3 倍设慢调用阈值，再结合业务 SLA 校准。

**超阈值就一定要熔断吗？**
不是。要同时满足：统计窗口内**最小请求量**达标 + 慢调用**比例**超阈值。单次慢请求可能是 GC/网络抖动。

**怎么避免偶发超阈值？**
滑动时间窗口统计 + 比例阈值而非绝对次数 + 最小样本量门槛。

**熔断后如何恢复？**
进入半开状态放行少量探测请求：成功则关闭熔断器（逐步放量），失败则继续熔断并延长退避时长。

**抖动的原因和解决？**
原因：阈值设置在临界区 + 恢复策略太激进（一恢复就全量）。解决：熔断-恢复阈值分离（滞回）、恢复后逐步放量、延长统计窗口平滑毛刺。

## 六、04 降级

**什么时候用降级？举例。**
大促保核心链路（停退款、积分、推荐）；下游服务不可用；系统整体过载丢卒保车。

**降级的好处？**
把有限资源集中到核心链路，用非核心功能的可用性换核心功能的可用性。

**跨服务降级的常见做法？**
调用方侧：配置中心下发降级开关，关闭对非核心服务的调用或返回兜底数据；服务端侧：主动返回降级响应。

**怎么评估服务重要性？**
按业务价值（是否影响营收/核心交易链路必经）+ 影响用户面，与产品/运营共同定级（P0~P3），形成书面的服务分级清单——**这清单是事先定的，不是出事再分的**。

**服务内部常见降级思路？**
功能降级（关推荐/评论）、数据降级（返回缓存/默认值）、页面降级（静态页/简化页）、同步转异步、降低精度或采样率。

**怎么判断哪些服务需要降级？**
按分级清单 + 调用链依赖梳理：核心链路上的非必需环节优先降级。

**降级状态保持多久？**
不看固定时长，看指标：系统负载、错误率回落到安全水位并稳定一个观察期后，再考虑恢复。

**恢复怎么防抖动？**
分批恢复、逐步放量（10% → 30% → 100%），每步观察核心指标。

**公司首页怎么保证高可用？**
页面静态化 + CDN、多级缓存（本地 + Redis）、非核心模块降级开关、入口限流、多机房容灾。

## 七、05 限流

**限流的目的？**
保护系统不被超出容量的流量打垮；公平分配资源；防恶意刷接口。

**限流算法有哪些？**
固定窗口计数器、滑动窗口计数器、漏桶、令牌桶。

**不同算法怎么选？**
要严格匀速输出（保护下游）用漏桶；要允许合理突发用令牌桶；简单粗暴用计数器，滑动窗口比固定窗口平滑（解决临界突刺）。

**限流对象怎么选？**
多维度组合：接口、用户、IP、租户/应用；网关层 + 服务层双层布防。

**阈值怎么确定？**
首选压测得出极限容量，取 70~80% 留安全余量；没条件压测就沿调用链估算（如单查询 10ms + 10ms CPU，4 核单机 ≈ 1000/20×4 = 200 QPS）。

**怎么应对突发流量？**
令牌桶允许桶内突发；Sentinel 匀速排队模式把突发摊平；入口接 MQ 削峰填谷。

**被限流的请求怎么处理？**
直接快速失败（默认）；偶发限流可短排队等待（注意超时）；同步转异步低峰补偿；负载均衡降权重少发——与熔断的区别：**熔断是不发，限流是少发**。

**用了限流为什么系统还会崩？**
阈值设置不合理；只限 QPS 没限并发数/连接数；下游变慢导致请求堆积击穿资源；突发流量在限流生效前已到（如连接建立阶段）。

**普通用户 10 次/分、1000 次/天，VIP 不限，怎么实现？**
按用户身份路由不同限流规则：Sentinel 热点参数限流（按用户维度），或自定义规则引擎先解析身份再匹配对应阈值规则，VIP 走白名单跳过。

## 八、06 隔离

**什么是隔离？解决什么问题？**
把资源（线程、连接、机器、集群）按业务/用户群体分割，让局部故障被限制在局部，不横向扩散。

**了解哪些隔离策略？**
线程池隔离、信号量隔离、进程/容器/物理机/集群/机房级部署隔离、连接池按业务拆分、快慢线程池分离、VIP 独立集群。

**某个服务崩溃时怎么保证其它服务不受影响？**
独立部署 + 熔断 + 资源隔离三件套：部署上分开，调用上熔断，资源上池子分开。

**线程池/连接池怎么避免业务互相影响？**
舱壁模式（Bulkhead）：按业务拆独立线程池和连接池，互不共享；快慢任务双池分离，慢任务探测后转交慢池；池大小按业务容量评估，设队列上限防堆积。

## 九、07 超时控制

**为什么要做超时控制？**
没有超时，下游一慢请求就堆积，线程/连接耗尽，自身被拖垮——超时是快速失败的前提。

**缺乏超时为什么会连接泄露、线程泄露？**
线程阻塞在等待响应上不释放，占住连接池连接和线程池线程；新请求持续到达持续占用，最终耗尽——不是真泄露，是"占着不放"的行为等同泄露。

**什么是链路超时控制？**
整条调用链共享一个总截止时间，每跳把剩余时间传给下一跳，任何一跳发现时间不够就直接快速失败。

**如何确定超时时间？**
压测得各接口 P99，超时 = P99 ×（2~3）或 P99 + 固定余量；链路总预算按用户可接受时间倒推分段分配。

**怎么在链路中传递超时？**
RPC 框架的上下文/附件（如 Dubbo attachment、gRPC deadline）或 HTTP 自定义头携带。

**传递的是什么？**
两种选择：绝对截止时间戳 或 剩余毫秒数。

**怎么计算网络传输时间？**
精确测不了。工程做法：预留固定网络余量（如 50ms），或干脆传绝对 deadline 让传输损耗自然体现在剩余时间里。

**什么是时钟同步问题？**
传绝对 deadline 依赖收发两端时钟一致；时钟有偏移会导致提前/延后超时。靠 NTP 校时缓解，或改用传剩余时间规避。

**客户端和服务端谁来监听超时？**
双端都要：客户端超时触发快速失败和熔断统计；服务端超时中断处理释放资源——只设一端都浪费。

**超时后能不能中断业务？怎么中断？**
Java 不能安全强杀线程。手段：协作式中断（interrupt + 检查点）；IO 类等待靠 socket/statement/HTTP client 各自的 timeout 参数真正生效；已提交 DB 的事务靠 DB 侧超时（如 innodb_lock_wait_timeout）。

## 十、08 调用第三方

**怎么保证调用第三方接口的可用性？**
四件套：一致性抽象（多供应商统一接口）+ 客户端治理（限流/熔断/超时/重试）+ 可观测性（监控告警，给维护者和业务方两类）+ 测试支持（mock 服务）；有多家可替换时自动切换供应商。

**所有第三方切换一遍后全崩了怎么办？**
认怂 + 告警：多家同时崩是小概率，尽人事听天命；能异步的先存起来等恢复后补偿。

**调用第三方出错怎么重试？次数和间隔怎么定？**
次数 ≤ 3；间隔指数退避（如 1s/2s/4s）加随机抖动防重试风暴；前提接口幂等；按错误类型区分：超时/5xx 可重试，业务错误（4xx）不重试。

**怎么判定第三方已非常不可用要切换？**
同熔断标准：错误率/超时率在滑动窗口内超阈值且达到最小样本量，判定后自动切换备用供应商，并持续探测原供应商以便切回。

**时效性要求不高的接口怎么优化架构？**
同步转异步 + MQ 彻底解耦：业务方丢消息进 MQ，消费端调第三方，结果经 MQ 回调通知——第三方抖动完全不影响主链路。

**压测依赖第三方接口怎么解决？**
mock 服务三要素：模拟响应时间（平均 RT + 随机偏移）、能模拟超时/失败以验证容错触发、压测流量按标记分流到 mock 而真实流量走真实调用。

**业务依赖一个非常关键的第三方，怎么保证不出错？**
多供应商 + 自动切换兜底；客户端治理全套；调用链路对账（成功数核对）+ 自动补偿；商务层面签 SLA 约束。
