## 一、文章总结

**核心结论**：热点问题分两种，面试基本只考第二种。

| 类型 | 表现 | 解法 |
|---|---|---|
| 节点级热点 | 一组高 QPS 的 key 恰好落在同一节点 | 重设计 key 结构 / 调整槽映射，散开即可 |
| **key 级热点** | 单个 key 的 QPS 就极高（百万级） | 三大方案：本地缓存、缓存多份、**拆分 key（治本）** |

**三大方案对比**：

| 方案 | 本质 | 适用 | 代价/风险 | 定位 |
|---|---|---|---|---|
| 本地缓存 | QPS 大部分命中应用内存，不到 Redis | 读多写少、容忍不一致 | 数据一致性加剧 | 治标 |
| 缓存多份 | test_key0~N 存副本，轮询/随机读 | 读多写少 | 写要同步全部副本，部分失败 | 治标 |
| **拆分 key** | my_biz → my_biz_0~9，QPS 分摊 | 读写都有效 | 全局查询需特殊处理 | **治本、刷亮点** |

**分 key 四要点（面试话术骨架）**：
1. **分 key 策略**：按哈希（id%10）、按值范围（日期）、按业务（User 基本信息/登录信息拆两个 key）、按 QPS（保证各 key QPS 接近而非平均分）
2. **特殊场景处理**：全局 TopN 查询 → 各 key 取 TopN 归并；实时性要求低 → 定时任务算好全局 TopN 推本地缓存/多份 key
3. **均匀分散**：手动算 CRC16 → 槽 → 节点，发现聚集就换 key 结构；key 不必有规律，应用维护映射数组即可
4. **冗余**：多拆一些 key，应对数据与 QPS 增长

**判定原则**：拆分后是否还存在热点；数据倾斜场景则看数据量是否均匀。

**补充/修正（文章未提或不精确，面试加分）**：
- ⚠️ 文章说"用 CLUSTER INFO 获得槽映射关系"——**不准确**。`CLUSTER INFO` 只给集群概要（状态、已分配槽数），拿槽→节点映射要用 **`CLUSTER SLOTS`**（或 `CLUSTER NODES`）。面试说错会被抓住
- 文章通篇没讲**热点怎么发现**（只讲解决）——见 Q8，这是你补上去就拉开差距的点
- 全局 TopN 除了"归并+定时任务"，还有实时方案 **`ZUNIONSTORE`**（见追问 Q3）
- 分 key 场景下 **hash tag `{my_biz}` 是反模式**——它强制多个 key 落同一槽，与分散目标相反（与 02 篇"多 key 原子操作需要 hash tag"恰好是一对矛盾，能讲清这个 trade-off 很加分）
- 本地缓存方案可以提 **Redis 6.0 client-side caching**（RESP3 tracking 协议，服务端主动推送失效），是"本地缓存一致性"的现代答案

**面试策略要点**：
1. 中小公司没遇到过也要准备热点案例（不局限于 Redis）
2. 简历 Redis 技能栏加"擅长解决热点问题/数据倾斜"
3. 主动把话题延伸到其他中间件（Kafka/ES/MySQL 分库分表），岗位要什么就对比什么，还能引导话题

## 二、Q&A（问题 + 标准答案）

### Q1：什么是 Redis 热点问题？分哪几类？

某个节点或单个 key 的 QPS 过高形成性能瓶颈。分**节点级**（一组热 key 落在同一节点，重设计 key 散开即可）和 **key 级**（单 key QPS 极高，与集群规模无关——上百节点的集群也救不了一个 key）。面试考的基本是后者。典型场景：秒杀库存扣减、热点话题点赞、排行榜、热文缓存。

### Q2：key 级热点的三个解决方案是什么？怎么选？

- **本地缓存**：请求先查应用内存（Caffeine 等），命中则不打 Redis。适合读多写少；代价是一致性
- **缓存多份**：同一内容写 test_key0~N，业务随机/轮询读其一，QPS 摊到副本上。适合读多写少；代价是写放大与部分失败，且**必须保证副本落在不同节点**，否则白搭
- **拆分 key（治本）**：按策略把单 key 拆成 N 个子 key，读写 QPS 都分摊。代价是全局视图查询要特殊设计
- 选择思路：读热点先本地缓存/多份；写热点或要治本必须分 key；三者可叠加（分 key + 全局结果再做多份/本地缓存）

### Q3：本地缓存方案的细节和坑？

- 结构：本地缓存（Caffeine/Guava）在前，Redis 在后， miss 才回源
- 坑一：**一致性**——写频繁或一致性要求高的场景不能用；被追问一致性要能答（见追问 Q1）
- 坑二：本地缓存本身也有热点（单实例内存有限、重启冷启动雪崩），TTL 要短且加抖动
- 加分：提 Redis 6.0 client-side caching（服务端 tracking 主动失效推送）

### Q4：缓存多份方案的细节和坑？

- 写：同时写 test_key0~N（N 份副本）
- 读：应用维护 key 列表，随机或轮询取一个读
- 坑一：写部分失败导致副本不一致 → 需要重试/定时对账/全量重建
- 坑二：**副本必须分散在不同节点**，否则制造新的节点级热点（设计 key 时算 CRC16 验证，同 Q7）

### Q5：分 key 怎么分？判定标准是什么？

四种策略：
1. **按哈希**：my_biz_%d，id%10 取后缀——最通用
2. **按值范围**：如按日期拆——注意时间型拆分本身容易制造热点（都查当天）
3. **按业务**：User 大 hash 拆成基本信息、登录信息两个 key
4. **按 QPS**：10w 元素的 list 拆 10 个 key，保证各 key QPS 接近，而不是平均分元素

判定标准：**拆分后是否仍有热点**（数据倾斜场景看数据量均匀性）。实践上要留冗余多拆几个，应对增长。

### Q6：分 key 之后，全局 TopN 这类查询怎么办？

以榜单为例（10 个 zset 子 key）：
- **离线方案（推荐，文章方案）**：定时任务从每个子 key 取 Top 100 → 归并排序得全局 Top 100 → 推送到各应用节点本地缓存（或多份 key）。业务查询直接命中本地缓存
- **实时方案一**：查询时从 10 个 key 各取 Top 100 归并——读 QPS 没分散，仅适合低频管理端
- **实时方案二（补充）**：`ZUNIONSTORE` 聚合 10 个子 zset 再 ZREVRANGE，逻辑最简但 O(N) 代价高，只适合中小数据量或离线计算

正确性：全局 Top 100 的任何成员必然在其所在子 key 的 Top 100 内，所以每片取 100 归并不漏（K 路归并的经典结论）。

### Q7：怎么保证拆分后的 key 落到不同节点？

1. `CLUSTER SLOTS` 拿到集群槽→节点映射（⚠️ 不是文章说的 CLUSTER INFO）
2. 手算每个 key 的槽：`slot = CRC16(key) mod 16384`（有 hash tag 时只算 `{}` 内部分）
3. 对照映射推得目标节点；发现多个 key 聚集同节点 → 换 key 结构重算
4. 重复直到全部散开
5. key 不必有规律：my_biz_0 / my_biz_abc / my_biz_b10 都行，应用维护映射数组 `[my_biz_0, my_biz_abc, ...]`，用 id%N 作下标取 key

### Q8：热点 key 怎么发现？（文章没讲，必备补充）

- **redis-cli --hotkeys**：基于 LFU 采样扫热 key（要求 maxmemory-policy 为 LFU 类：allkeys-lfu/volatile-lfu）
- **监控**：集群各节点 `instantaneous_ops_per_sec` 对比——某节点 QPS 显著高于均值就是节点级热点；配合 bigkey 巡检
- **代理层统计**：用了 Codis/云厂商代理层的话，代理一般自带 key 级别 QPS 统计（最精确）
- **客户端埋点**：lettuce/Caffeine 埋点统计 key 访问频率
- **业务预判**：秒杀商品、热榜这类天然热点，上线前就该按热点方案设计，而不是等出事

### Q9：热点问题和数据倾斜是什么关系？

一对双生子：数据倾斜（数据集中在一个节点/key）很可能造成热点，热点往往也意味着倾斜。治本都是分 key，区别只在**评判标准**：热点看拆分后 QPS 是否均匀，倾斜看数据量是否均匀。

### Q10：怎么把热点话题延伸到其他中间件？

| 中间件 | 热点/倾斜形态 | 对应解法 |
|---|---|---|
| MySQL 分库分表 | 按月分表，当月表 QPS 爆表（时间型热点） | 改按周分表；热商户单独拆（见追问 Q8） |
| Kafka | 某 partition 消息量/GC 远超其他（key 设计不当） | 重选 partition key、热点 key 加随机后缀打散 |
| Elasticsearch | 某 shard 过大/查询集中（routing 倾斜） | 调整 routing、拆索引（按时间/业务） |
| 共性 | 单点承载不了被哈希到一起的负载 | **分而治之 + 均匀散列**，思想完全通用 |

面试时按目标岗位选例子：岗位要求 ES 就用 ES 举例，顺便引导话题到你的强项。

## 四、面试官连环追问清单（含参考答案）

### Q1：引入本地缓存后，数据一致性怎么保证？

- 弱一致场景：短 TTL（秒级）+ 过期自然收敛，最简单
- 变更感知：写 Redis 后发失效广播（Redis pub/sub、MQ 消息），各节点收到后清本地缓存——注意 pub/sub 不保证送达，要有 TTL 兜底
- 现代方案：Redis 6.0 **client-side caching**（RESP3 tracking），服务端主动推送失效通知给客户端
- 强一致场景：直接不要用本地缓存（本地缓存的前提就是容忍短暂不一致）

### Q2：缓存多份方案写入时部分副本失败怎么办？

- 写入路径：同步写全部副本 + 失败重试；重试仍失败记入异常队列/告警
- 兜底：定时任务用源数据全量重建所有副本（副本是冗余，可重建）
- 读路径容忍：读到略旧副本可接受（该方案本来就只用于读多写少、弱一致场景）
- 本质上这是用**可用性换一致性**，面试主动点破这个 trade-off

### Q3：分 key 后实时查全局 TopN，除了归并还有什么方案？各有什么代价？

- **K 路归并**（每子 key 取 TopN 再合并）：正确性依据——全局 TopN 的任一成员必在其所在子 key 的 TopN 内；代价是每次查询 N 次 ZREVRANGE + 归并，读 QPS 没被分散
- **ZUNIONSTORE**：`ZUNIONSTORE tmp 10 my_biz_0 ... my_biz_9` 再 ZREVRANGE tmp，一条链路完成；代价 O(N) 与数据量成正比，大集合慎用，适合离线/低频
- **定时预计算 + 本地缓存/多份 key**（生产推荐）：读零成本，代价是秒~分钟级延迟和一份定时任务
- 选型口径：实时性要求高的管理后台用归并，C 端高 QPS 一律预计算

### Q4：为什么分 key 场景下 hash tag 是反模式？什么情况下又必须用？

- hash tag（`{my_biz}:0`）强制多个 key 只按 `{}` 内内容算槽 → **全部落同一节点**，与"分散热点"目标背道而驰
- 但多 key 原子操作（Lua 脚本、事务、MSET 等）在集群模式下要求 key 同槽，这时**必须**用 hash tag——例如 02 篇拆 key 后又要跨 key 原子操作的场景
- 结论：hash tag 是"聚"的手段，分 key 是"散"的手段；同一组 key 要不要同槽，取决于你要原子性还是要分散性，两者不可兼得——能讲清这对矛盾是高分点

### Q5：CRC16 槽是怎么算的？为什么是 16384 个槽？

- `slot = CRC16(key) mod 16384`；key 含 `{...}` 时只对第一个非空 `{}` 内子串计算
- 为什么 16384（2^14）：作者 Antirez 的设计权衡——槽要足够多以支持细粒度迁移均衡，又控制集群心跳 gossip 消息体积（每个节点用 bitmap 通报自己负责的槽，16384 bit = 2KB，65536 则要 8KB）；且官方认为集群很难超过 1000 节点，16384 槽足够摊匀

### Q6：写热点怎么办？以秒杀库存扣减为例

本地缓存和缓存多份都救不了写（多份还放大写）。写热点只有两条路：
1. **分桶扣减**：stock 拆成 stock_0~9 各存 1/10 库存，请求随机/轮询落到某个桶，用 Lua 保证"查库存+扣减"原子；任一桶有货即可成交，汇总得总库存。难点：桶间库存不均时的兜底（桶空但别桶有货 → 重试其他桶或定时再均衡）
2. **MQ 削峰**：扣减请求进 MQ，消费者匀速处理，把瞬时写热点摊平到时间轴——代价是异步，需要前端轮询/推送结果
- 面试话术：先说分桶（Redis 内解决），再补 MQ（架构层解决），体现分层思维

### Q7：hotkey 和 bigkey 叠在一个 key 上怎么办？

- 02 篇说过"bigkey 常同时是 hotkey，两个绝症叠加"——这种 key 的治疗顺序：**先拆 key**（分 key 同时把数据和 QPS 都拆小，一石二鸟），拆不动再考虑本地缓存兜底读
- 注意分 key 后的大 key 迁移：集群扩缩容 MIGRATE 同步阻塞，热 key 迁移要在低峰做
- 预防：上线前评估 key 的"预期 QPS × 预期大小"，超过阈值直接按分 key 设计，别等事故

### Q8：分库分表后热点商户导致数据倾斜，怎么分 key？（评论区真题）

场景：按商户 ID 分库分表，少数高频交易商户数据量/QPS 远超均值。
- **热点商户单独拆**：识别 Top N 大商户，其数据按"商户 ID + 子序号"二次散列到多个库表（如 merchantId_hash 再 %4），路由层维护"大商户名单"
- **虚拟桶**：一致性哈希/虚拟桶方案，大商户映射到多个桶
- 通用启示：**倾斜治理的第一步是识别热点实体**（大商户、大 V 用户、爆款商品），对热点实体单独设计路由规则，而不是全局换哈希函数——这个思路对 Redis hotkey、Kafka 热 partition 都成立

## 五、专题速查：热点治理决策树

```
发现节点 QPS 异常（监控 instantaneous_ops_per_sec）
├── 是多个 key 共同造成？→ 节点级热点 → 重设计 key/槽映射散开
└── 单 key 造成？→ key 级热点
    ├── 读为主？
    │   ├── 容忍短暂不一致 → 本地缓存（+失效广播/client-side caching）
    │   └── 一致性要求高 → 缓存多份（副本分散到不同节点）
    ├── 写为主？→ 分 key / 分桶（库存类）+ MQ 削峰兜底
    └── 需要全局视图？→ 预计算归并 TopN 推本地缓存
分 key 必做三件事：定策略 → 算 CRC16 槽验证均匀 → 留冗余
```

## 六、专题深挖：节点级热点、CRC16 与 hash tag、改名重哈希

### 1. 先懂地基：CRC16 与槽路由（面试不用深究，理解即可）

- **CRC16 = 循环冗余校验**，本是通信领域的检错算法。在 Redis Cluster 里被纯粹当作**哈希函数**用：`任意 key 字符串 → 0~65535 的整数`，具备确定性（同 key 结果恒定）和均匀性（差一个字符结果迥异）
- **槽公式**：`slot = CRC16(key) mod 16384`。key → 槽 → 节点，全程纯数学，**没有任何负载感知和动态调度**
- **为什么选 CRC16**：计算极快（查表法位运算，每个命令都要算，必须便宜）；16 位输出刚好覆盖 16384 槽；不防碰撞——路由场景也不需要
- **类比**：CRC16 之于 Redis Cluster，就像 `hashCode()` 之于 HashMap——把 key 翻译成数字，数字决定住哪个桶
- **hash tag 规则**：key 含 `{...}` 时，**只对第一个非空 `{}` 内的子串**算 CRC16。实测示例：

```
{shop:1001}:stock  → 参与哈希的是 "shop:1001"     → CRC16=40909 → 槽 8141
{shop:1001}:sales  → 参与哈希的是 "shop:1001"     → CRC16=40909 → 槽 8141（同上，同节点）
shop:stock:1001    → 参与哈希的是整个 key          → CRC16=34036 → 槽 1268
shop:sales:1001    → 参与哈希的是整个 key          → CRC16=56912 → 槽 7760
```

### 2. hash tag：为什么故意让多个 key 住一起

`{shop:1001}:stock`、`{shop:1001}:sales` 是**多个独立 key，共享同一个路由标记**（`{}` 只影响槽计算，不影响存取）。好处三件套：

1. **多 key 原子操作**：集群模式下 Lua 脚本、事务要求所有 key 同槽（脚本在单节点执行，跨节点即分布式事务，Redis 明确不做）。不同槽直接报错 `CROSSSLOT Keys in request don't hash to the same slot`
2. **批量查询一次往返**：`MGET` 同槽 key 合法且一次 RTT；跨槽报错，只能拆成多个独立 GET
3. **数据局部性**：同一商户全部数据聚在一个节点，单连接处理、迁移分析都方便

**代价（交易的另一面）**：该商户的所有 QPS 压在一个节点上。普通商户无所谓，一旦长成头部爆款 → 节点级热点。设计口径：**hash tag 是用单节点压力换多 key 原子性**；对可能长成热点的实体（大商户/大 V/爆款商品），要么预留拆分方案，要么放弃原子性改用补偿逻辑。

### 3. 节点级热点的解法：改名重哈希

**原理**：既然槽由 key 名纯数学决定，改 key 名就改了槽——节点级热点本质是"key 命名事故"，不需要分 key 那套重方案。

**⚠️ 防坑**：集群模式 `RENAME` 要求新旧 key 同槽，跨槽报 `CROSSSLOT`——"改名"本质是**数据跨节点搬家**，不是一条改名命令。

**标准流程（双写过渡法）**：
1. **设计新 key 并验证**：脚本预计算所有新名字的槽，对照 `CLUSTER SLOTS` 确认散开
2. **应用发版**：写=双写新旧 key；读=先读新 key，miss 回读旧 key 并顺手回填（read-through 自愈）
3. **离线回填存量**：低峰期 `redis-cli -c --scan --pattern '旧前缀:*'`（**禁用 KEYS \***），逐 key 用 `DUMP` + `PTTL` + `RESTORE <ttl>` 搬运（保住类型和 TTL）
4. **校验 → 切流 → 清理**：抽查一致 → 停双写 → 观察 1~2 周 → `UNLINK` 删旧 key

### 4. 代价评估（决策口径）

| 成本项 | 大小 | 说明 |
|---|---|---|
| Redis 侧操作 | 小 | SCAN + DUMP/RESTORE，脚本半天搞定 |
| 应用发版 | 中 | key 逻辑收敛在 KeyBuilder 就好改；散落 N 个服务则痛苦 |
| 双跑期一致性 | 中 | 2~4 周双写 + 校验手段 |
| **原子性丢失** | **可能很大** | key 若靠 hash tag 聚一起跑 Lua，改名即 Lua 报废，要重设计补偿逻辑 |

**决策流程**：先查这组 key 有没有被 Lua/事务/MGET 捆绑。
- 没有 → 纯命名事故，成本=一次发版+一个迁移脚本，放心做
- 有 → 改名=拆当初的架构决策，要掂量；可能忍著或用分 key 思路整体重构更划算

**一句话**：改名重哈希在 Redis 层面是小事，在业务逻辑层面可能是大事——成本取决于当初为什么把它们凑在一起。

### 5. 节点级 vs key 级热点（对比收口）

| | 节点级热点 | key 级热点 |
|---|---|---|
| 成因 | 一组热 key 哈希后恰好挤在同一节点（命名事故） | 单个 key 的 QPS 就超限，数学上无法再摊薄 |
| 与集群规模 | 有关——挪走就解决 | **无关**——百节点集群也救不了一个 key |
| 解法 | 改名重哈希（去 hash tag 或换结构），成本低 | 本地缓存 / 缓存多份 / 分 key，成本高 |
| 判断方法 | 节点间 `instantaneous_ops_per_sec` 对比 + key 槽分布分析 | 单 key QPS 统计（--hotkeys / 代理层 / 埋点） |
